The **PR babysitter** drives the loop that takes the landing PR from committed work to every check green on every PR, then merged and released. It runs in one of two modes (section *Modes*):

- **Delegated** (`/pr-babysit bg`): a team lead spawned it in the background with a **briefing file**, which it reads first, in full. Its **principal is the lead**, and its channel to the lead is **SendMessage**: every tier-3 escalation and every report (round milestones, the green report, the final report) goes there as a message. The round log stays its deep-state artifact; the message is the interrupt that tells the lead to look.
- **Inline** (the default for `/pr-babysit`): the main session itself is the babysitter, and its **principal is the operator**.

"Principal" below means whoever rules on tier-3 escalations. The **wave header** (the top section of the round log inline, or the briefing file in delegated mode) is **immutable and authoritative** for everything wave-specific: intent, deliberate renames, sanctioned reds, frozen surfaces. This file is authoritative for standing mechanics, and `CLAUDE.md` for the repo's CI fix cycle, watchdog semantics, BLOCKER convention and quick-fixes. Where they conflict: wave header > this file > CLAUDE.md defaults.

The finish line is loop step 8; the merge after it is loop step 9. Nothing stops at "probably green": the principal verifies the final claim independently, so reports carry run URLs and exit codes, never summaries.

## Modes

- **Inline is the default** (operator directive, 2026-08-05). Delegation was tried as the default on the 0804-1 wave and the wave did not finish: CI reached green at 05:35Z and the babysitter never saw it, because its wake-up watches died four times across the night and the last one took the terminal verdict with it. The PR sat in DRAFT hours later with every check green. A delegated loop's failure mode is that nobody watches the watcher; in-session, the loop rides the same wake-ups as the rest of the session, where a stall shows at once.
- **Inline deltas.** The wave header goes at the top of the round log; there is no separate briefing file. After a compaction or a restart the session re-reads this file, the wave header and the STATUS block before touching anything. Tier-3 calls are autonomous (section *The tier system*). Residue in the tree is drained by path and by epic (section *Tree ownership*); new uncommitted paths that are plainly part of the same wave are committed rather than stepped around, the opposite of the delegated never-absorb-by-inference rule, because inline the principal is the person editing the tree. Inline, the session merges itself at loop step 9; nobody needs to ask for the merge (operator ruling 2026-10-02).
- **When `bg` is still right.** A genuinely multi-day wave: the 0707 in-session babysitter died of context exhaustion mid-campaign. The lead then watches the round log itself, because nothing else does.

## Preflight (both modes)

- **One babysit at a time.** The task board is checked for a live babysit task, and inline, for an existing background babysitter, because a second pusher triggers the cancel-old-ci race and the shared-tree hazard. When one is live, the loop stops and says so.
- **Resume detection.** When PRs already exist for the branch (the launcher's state block), the loop resumes at CI and reviews and re-creates nothing; the wave header records it. The console PR's review state is read too: whether it is still a draft, and `python3 .claude/hooks/stop/wl_review.py --check` (loop step 7). That decides whether the loop resumes pre-ready (driving CI green) or post-ready (settling review findings and threads).
- **Cold start.** When the session lacks the context to fill the wave header's first four slots (intent, deliberate renames, sanctioned reds, frozen surfaces), it surveys the diff, fills what it can, and asks the principal the unfillable questions before round 1: two questions up front beat a wrong first round.
- <!-- scope: pr.sibling-repos -->**Sibling repos under `private/` that are not submodules.** Some checkouts hold independent, gitignored git repos under `private/`, invisible to `git status`, to `git submodule status` and to every submodule-shaped instruction; agents have repeatedly taken everything under `private/` for a submodule and walked past uncommitted or unmerged work there. They are discovered every run, never hardcoded: `for d in private/*/; do d="${d%/}"; [ -e "$d/.git" ] || continue; git config -f .gitmodules --get-regexp path 2>/dev/null | awk '{print $2}' | grep -qx "$d" || echo "NON-SUBMODULE: $d"; done`. For each one found:
  - It is not part of the console PR: never `git add` it, never bump a pointer for it, never sweep it into the snapshot.
  - It is checked for uncommitted changes and unmerged branches, and the finding is reported; nothing is committed, merged or deleted there without an explicit request.
  - Its remote may not be GitHub: `git -C <dir> remote get-url origin` comes before any `gh` call, since PR tooling that assumes GitHub fails silently elsewhere.
  - `git rev-list --left-right --count origin/main...HEAD` prints `<on main only> <on branch only>`; the second number is the branch's own unmerged commits, and misreading it as "behind" has written weeks of unmerged work off as a stale checkout.<!-- /scope -->

## Rule 1 - TEST ANY CHECKABLE RULING OR DIAGNOSIS BEFORE EXECUTING IT

A ruling issued from an artifact (a briefing, a diff, a config file, a chat log) is a **hypothesis**, whoever issued it: the principal, a reviewer, or the babysitter. **The babysitter holds the running system.** When a ruling is checkable, it is checked, then executed. That is the job, explicitly authorized, not insubordination.

A principal once ruled a gate vacuous ("populate it or delete it") because its config file was an empty `{"entries": []}` and it printed `✓ valid` after checking nothing. A second reviewer agreed. **Both had read the file; neither had run the gate.** The babysitter ran it, planted a dead command in the page it guards, and watched it go **red**. The empty config was the list of items *excused* from checking, so empty excused **nothing** and the gate was the strictest in the suite. **Populating it would have weakened it; deleting it would have destroyed the gate that had caught the very bug cited as proof it was broken.** Its one real defect was a success message that understated its work.

So:
- **Ask the thing that decides.** Run the gate rather than reading its config; build the binary rather than reading the build script.
- A ruling that deletes, weakens or suppresses a check is **the ruling most worth testing**: the cost of being wrong is asymmetric and permanent.
- A refutation is reported with the evidence, and **says plainly that the ruling was wrong.** A principal who is only ever obeyed is a single point of failure.
- The same holds for a handed-over diagnosis and for the babysitter's own: verified before it is committed. In one wave the lead's own "proof" of a CI fix was itself broken (the cold-build gotcha below) and nearly discarded a correct fix.

## Rule 2 - FIX IT. Filing it is not finishing it, and "not my change" is not an exit

**A red blocks the finish line regardless of who wrote it.** Whether it came from the diff, from `main`, from a submodule, or from shared infrastructure broken an hour ago is diagnostic information: where to look and how carefully to verify. It is never a reason to stand down. Provenance goes in the round log, never in a decision to stop.

- **A GitHub issue for a red is not an outcome.** It is the loop declining to run. The loop investigates, fixes, commits, pushes and goes round again; an issue already filed and then fixed is closed with a comment describing the fix. (Real case: a babysitter met a broken review pipeline, wrote an excellent evidence-backed issue, and stopped, converting a night of autonomous work into a ticket. The operator's reply was "STOP opening new issues.")
- **"Pre-existing", "environmental" and "flaky" are claims, not verdicts.** Each is proved (clean-room repro; the did-this-job-pass-on-the-PR test), and once proved it is still repaired or routed around. Proving a red is somebody else's does not make the PR green.
- **Shared CI infrastructure is in scope when it blocks the finish line**: gates, workflows, the review pipeline, the release path. Blast radius raises the bar for evidence and verification, not for acting. The smallest correct fix, verified by asking the thing that decides (run the gate, run `actionlint`, read the script the gate actually uses), logged as a DECISION for post-hoc veto.
- **The bar for "this cannot be fixed" is high**: the defect is stated precisely, the fix was tried, and it needs a product or intent decision only the principal can make. Even then, inline, the loop decides and logs rather than stops (Rule 1's tie-breakers apply).
- **A fix that trades a loud failure for a silent one is no fix.** The tempting minimal patch is often "turn off the thing that is erroring"; what that thing was for comes first. In one case `track_progress: true` looked cosmetic and was the only channel posting the review report two downstream steps parsed; disabling it would have made the job green and the review nonexistent.

## The sole reader of CI state

Nobody polls CI behind the babysitter, reads job logs behind it, or diagnoses reds behind it; nobody is double-checking the run, which is exactly why the loop is the babysitter's. A red is found, owned and fixed, not waited on.

So **its reports are the principal's only window.** In delegated mode they travel as SendMessage to the lead; an idle notification is not a report. A report carries deltas only: the round, what changed since the last report, and the decision needed, if any. Live state is in the round log's STATUS block (section *Round log*), and the reasoning in the round log, never in the message: essays in chat bury the one line that needed a decision and, inline, burn the context the loop needs to survive. Escalation is for a real tier-3; otherwise fix, push, log, continue.

**Overnight and unattended runs are the normal case.** Nobody answers until morning, in either mode. Rounds are budgeted for that, the round log stays current enough for a cold reader to take over, and the night never ends on "waiting for a ruling": the loop decides (or, delegated, sends the escalation and keeps draining tier-1/2), logs, and stays alive.

### No turn ends with a run in flight and no armed wake-up

**A background task that exits on the run's terminal state IS the loop.** Nothing else wakes the babysitter. After every push, and before any report, one is armed: `.ci/scripts/ci/ci-trace.py --wait` with `run_in_background: true`. No hand-written loop: ad-hoc watch commands are refused by the pre-bash guard, and a hand-rolled watch left running blocks the Stop hook. The script survives a watchdog re-run by construction and reports every job that is neither `success` nor `skipped`, with the failing STEP and its log command; the process exit re-invokes the session with that in hand.

**The mechanics live in the `ci-watch` skill (`.claude/skills/ci-watch/SKILL.md`), read before the first watch:** the wake-up contract, cancelled versus superseded, and the compound-watch bug. What follows is specific to this loop.

- **One wait per background command.** A watch notifies on process EXIT, not on output. Observed 2026-08-24: a watch printed `failed: ["Quality / Static"]` at 23:55:13, then moved into a second loop waiting for a review marker a red run never posts; the failure sat unread for ninety minutes. A second condition gets a second watch, armed after the first fires. A watch whose output file is non-empty while still running has already answered.
- **Not `gh run watch`.** It dropped four times out of four in one campaign, and it sometimes exits 1 while the run is still `in_progress`: `.ci/scripts/ci/ci-trace.py --run <id> --jobs` confirms, and the watch is re-armed.
- **A turn that ends without one simply stops**, and the run is watched by nobody. A CI round is 15-30 minutes, so the session ends turns across it, and a dead loop goes unnoticed for an hour. A report to the principal is not the end of a turn; the loop is. A run that has just started is a reason to arm the watch, not to stop.
- **The watch itself can drop silently.** A watch that never fires is indistinguishable from a run that never finished. On any re-invocation the head is re-checked (`.ci/scripts/ci/ci-trace.py`) rather than trusting the watch; re-arming costs nothing.
- **A 1-hour heartbeat backs the watch**, armed at the start of the wave and torn down at the finish line (`CronCreate`, or the `loop` skill; the watchdog tick in delegated mode). Each tick re-checks the head, re-arms if the run is in flight, and doubles as the stuck-detector: a STATUS timestamp that has not moved across a tick in which the run changed state means the loop is wedged, so it warm-starts from the round log. The final report says the heartbeat was torn down.
- The one legitimate stop with a run in flight is a **tier-3 the loop cannot proceed without**, and even then the watch stays armed and the report says so.

## Tree ownership and the snapshot boundary

- **Two trees, one session each, and the tree is the job.** The landing tree (`./run.sh worktree landing`, path and branch in `rediacc-landing.json`) belongs to the babysitter: it babysits the one landing PR, fixes its CI, merges, watches the release and carries a main-only hotfix (loop steps 1-9). The development tree (the main checkout) always builds: loop step 0 and the writers run there, it commits, runs local `ci:quick` and `vm:check`, pushes only as a backup, opens no PR, and never waits on landing. Its branch is stacked on the landing branch and takes landing's fixes one way through `git rebase <landing branch>`. In a repo with no landing record the single checkout plays both roles. Other agents work in leases (`./run.sh worktree lease`): they commit on a detached HEAD, never push, and their commits land through the lines `./run.sh worktree land <id>` prints.
- **The landing tree takes fix work only while its PR is open** (`.claude/rediacc_hooks/pr_freeze.py`, keyed on the tree role): a commit there is a `fix`, `style` or `test`, a record or review commit, the merge pointer bump, or one carrying `focus-fix:#<id>` for an open item that carries `pr:<n>`. Feature work belongs in the development tree.
- **The first commits drain the residue.** CLAUDE.md rule 1 commits verified work as it lands, so the tree holds little when the loop starts. Whatever is there is committed by path, one epic per commit with its `PR-TASK:` trailer (`git commit -F <msg> -- <paths>`), taking all of it, staged and unstaged. The **snapshot**, one `git add -A -- .` per repo into a single commit, is the fallback for residue that cannot be split by epic. Unstage and gitignore only clear accidental artifacts (binaries over 5 MB, build output, tsc-emit `.js` shadowing `.ts`), flagged; work is never deleted. `.claude/settings.local.json` stays uncommitted when it is local-permission noise, and a non-submodule repo under `private/` is never added.
- **All means all, and an ownership note does not carve files out of it.** Inline, every uncommitted change in the tree is the principal's, including work from earlier sessions and from before a compaction. A `RULES.md` "these files belong to session X" note is a hygiene convention for live parallel editing, not a licence to leave work behind at drain time. (Real case, 2026-08-15: a babysitter excluded five finished CI-gate hardenings on the strength of such a note; the operator's correction was that every change in the tree belonged to the babysitter.) A claimed file that genuinely looks like a live half-finished edit gets one question to the principal naming the paths; the default is INCLUDE, in its own labelled commit.
- The blanket-`git add` pre-bash hook refuses a bare `git add -A`: the guard asks for a look at what is taken, not a veto. `git add -A -- .` or named pathspecs pass. `git restore --staged` and `git reset` are blocked for un-staging too, so the file list is built up front rather than staged wholesale and subtracted.
- **After the drain, `git add -A` is banned.** Every fix commit is staged by name and diffed against the round log's "files touched this round" list; anything staged that was not touched this round is another party's work leaking in, unstaged and flagged. (A round-7 `git add -A` once swept an npm-pruned lockfile into a fix commit.)
- New work absorbed mid-run arrives as an explicit message naming the paths. Nothing is absorbed by inference.

## The per-PR loop: one plan, one PR, one live branch per tree

Operator rulings 2026-10-02 (agent/plans/PLAN-plan-per-pr-loop.md) and 2026-11-21 (agent/plans/PLAN-simple-two-tree-loop.md). The numbered loop below is the CI half of this cycle:

- <!-- scope: pr.one-plan-per-pr -->**One plan per PR, and a plan rides exactly one PR.** The development branch builds the plans the hook names, and the landing PR carries them. <!-- scope: pr.queued-plan-start -->A queued plan starts only when the hook names it. <!-- scope: pr.plan-set -->The plan set is the body's `Plan:` plans (the operator-added ones carried by an `Operational-Reason:` included) plus their unfinished prerequisites (`Depends-On:`), prerequisites first, and the Stop hook blocks only on that set, its CI and reviews, its epic's items and the loop's own duties; everything else is one queued line.<!-- /scope -->
- **Each plan gets its epic when it starts.** <!-- scope: pr.epic-carries-plan -->`worklist.py --epic <me> new --plan <rel> <title>` (or `--epic <me> plan <epic-id> <rel>` for an existing epic), and every item of the plan's work is attached with `--epic <me> add`, since an item outside the PR plan's epic is queued, not blocking.<!-- /scope -->
- **Boxes are built by writers in the development tree.** Each open box goes to a writer (CLAUDE.md rule 4) or is done inline when small; the plan's `Owns:` and `Concurrency:` lines bound what its writers touch, and `block_plan_concurrency` refuses a spawn that would overlap another live writer's plan. A unit is committed the moment its acceptance check reads rc 0, and its box is ticked with that sha: `.claude/hooks/stop/worklist.py --plan-tick <me> <plan> <box> commit:<sha> --write`.
- **Handover happens when every plan on the development branch is code-complete.** Live-run boxes (bench, hostinger, VM) are finished by the landing tree before the merge, and the merge requires every box ticked.
- **Push on a `ci:quick` receipt, one per push, built when a push is due** (a red's fix, an epic milestone, a stop with unpushed commits), not per commit: a unit's acceptance is a named test or `npm run ci -- --narrow`. `npm run ci:quick` runs in a kept clean clone at HEAD (`block_unverified_push` compares its tree with the pushed `HEAD^{tree}`), and a schema 2 receipt carries every gate whose input hash is unchanged. A `FALLBACK` line says it ran in the checkout instead; the receipt's `droppedTouched` then names each dropped slow gate with its `--only` rerun line, and `block_unverified_push` refuses until each passed at the pushed tree (`npx tsx scripts/ci-runner/run.ts --only a,b,c`). No push lands in a running PR run that is not red; a red's fix pushes at once (agent/plans/PLAN-fast-loop.md).
- **A red is fixed against the narrow set.** `npm run ci -- --narrow` reruns the last receipt's non-carried fails, their learned clusters and the gates the fix touched, and writes no receipt (`--narrow --print` lists the set). `TRIAGE=1` on the pre-push wrapper stops at the first stage red with exit 3. A final `ci-trace.py` verdict folds the run's outcomes into the gate ledger (agent/plans/PLAN-gate-scheduling-learned.md).
- **The CI watch arms itself.** After a push of the live branch with an open PR (or the `gh pr create` that opens it), the post-bash hook `arm_ci_watch.py` starts `ci-trace.py --wait --until-final` in the background, one watcher per head, and records the verdict on the session's CI item. A hand-armed watch is the fallback when the hook reports it armed nothing.
- **Merge at the finish condition, and only then:** <!-- scope: pr.merge-condition -->every box of every plan in the set ticked, prerequisites included (a ticked own plan with an open prerequisite does not merge; the hook names the prerequisite's first open box instead), `CI Complete` SUCCESS on the PR head (`ci-trace.py`), `python3 .claude/hooks/stop/wl_review.py --check` at exit 0, and `Review Complete` green on the head with `python3 .claude/hooks/stop/wl_prreview.py --check` at exit 0. `Review Complete` is a required check (operator ruling 2026-10-03): only its `outage` token (the LLM was unavailable) is excused, and a timeout never lets the PR merge. The merge is `/pr-merge`, invoked by this loop without asking (loop step 9); it prints the evidence first and merges with `gh pr merge --rebase --auto`. An `Operational-Reason:` line in the PR body admits the merge with boxes still open (`plan_gate.plan_merge_refusal`).
- **Then the release, then the next PR.** The landing tree watches Console CI on main and the edge release at the merged sha, carries a main-only hotfix, and on a fully green release notifies the development session (`cd-done`). The development session promotes at a commit boundary (`./run.sh worktree landing --promote`): the development branch becomes the next landing PR, and the landing tree goes back to step 1.

## The loop

**Spawned as a sub-agent (`/pr-babysit bg`), this loop does not commit.** `block_commit_on_main` refuses every sub-agent's `git commit` (operator ruling 2026-10-04, no exemption): the babysitter leaves each verified change in the tree, lists its paths in its report, and the lead commits and pushes. Inline, the loop commits as written below.

0. **Preflight the plan (development tree), before any writer.** A plan was written against an older tree, so it is revalidated first (agent/plans/PLAN-plan-preflight.md): `.claude/hooks/stop/worklist.py --plan-preflight <me> <plan>` prints the open boxes, the citations, the main commits that touched the cited paths, and the dependencies. Then:
   - **Survey fan-out.** The open boxes go in batches of at most 8 to `Agent(subagent_type=Explore, model=haiku)` with their signatures, the overlap list and the plan's "Current state" section; each surveyor answers one line per box, `<sig> <present|absent|partial> <kind>:<tok> <kind>:<tok> -- <note>`, plus the premise claims the tree contradicts.
   - **Recording.** `worklist.py --plan-investigate <me> <plan> <sig> <verdict> <kind>:<tok> <kind>:<tok> -- <note> --write` per box, then `worklist.py --plan-tick <me> <plan> <sig> '<evidence>' --write` for every `present` box. Each contradicted "Current state" claim is rewritten in the plan, and a drifted citation with nowhere to relocate is re-cited by hand.
   - **Stamp and commit.** `worklist.py --plan-preflight <me> <plan> --write` sets `Revalidated:`, relocates the movable citations and refreshes `agent/INDEX.md` and `agent/plans/QUEUE.md`; the plan, `agent/ledgers/plan-investigation.jsonl`, `.ci/config/plan-boxes.json` and the two renders land as one `chore(plan): preflight <slug> @ <B12>` commit.
   - **After a stale rebase.** A `--plan-tick` that prints the stale-plan WARNING sends the loop back to this step before the next box.
1. **Survey and resume detection.** When PRs already exist for the branch, the loop resumes at CI and reviews and re-creates nothing.
2. **The one branch.** <!-- scope: pr.one-branch-one-pr -->Each repo holds one live `MMDD-N` branch per tree (the PR branch in the landing tree via `./run.sh worktree landing`, the development branch in the main checkout), and there is no stacking of PRs: `block_second_branch` and `block_second_open_pr` refuse a third branch, a branch in the wrong tree or a second PR, which only the operator's own `!` command can create.<!-- /scope -->
   A live branch carries the wave. The next landing branch normally arrives by promotion; a branch is cut only when no live branch exists in either tree (a cold start).
   <!-- scope: pr.consumed-names -->The next `MMDD-N` is MAX+1 over the names already consumed by PR heads, the same N across all repos, after `git fetch origin --prune` in each repo: `d=$(date +%m%d); gh pr list --state all --limit 100 --json headRefName --jq '.[].headRefName' | grep "^${d}-"`. Never over `git branch -r`: `delete_branch_on_merge` is true on all five repos, so a merged PR's branch is gone while its name is still spent, which is how `0826-1` was taken twice on 2026-08-26, hours after PR #576 merged it.
   The name takes no suffix (`block-nonstandard-branch-name.sh`), and `block_second_branch` admits only the computed name.<!-- /scope -->
   Conflicts on a rebase: lockfiles are never resolved wholesale (targeted resolution, then the npm gotcha below); search indexes (`cd packages/www && node scripts/generate-search-index.js --write-public`) and generated types and docs are regenerated through their generators, never hand-merged.
3. **Submodules first, every cycle**: commit, push to **origin** (GitHub: console CI submodule-inits from GitHub, so a GitLab-only push is invisible to it) and open a PR for each dirty submodule, then re-point the parent's pointer, then commit and push the parent. Conventional-Commit titles. **The console PR opens with `gh pr create --draft`; submodule PRs open plain** (renet, account and elite are private repos on the GitHub free plan, which has no drafts). The `block-nondraft-pr-create` hook enforces both directions. Before the parent commit, `git ls-files -s private/renet private/account` shows the pointers staged at the new submodule commits.
   <!-- scope: pr.submodule-branch-name -->**A submodule PR's branch is named exactly like the console branch.** The `Submodule Branches` gate and `/pr-merge` both match submodule PRs by that name, so a submodule change riding an older branch (a `0914-1` PR under a `0923-1` console branch) passes neither. Each submodule PR opens on the console branch name from the start.
   One already open on another name gets the same head pushed to a branch named like the console branch, a NEW PR from it linking the old one, and the old PR closed with a pointer. GitHub's branch-rename API is not the tool: it retargets PRs that use the branch as their BASE and CLOSES the PR whose HEAD it is (measured 2026-09-24: renaming account and renet `0914-1` to `0923-1` closed #87 and #111, `head_ref_deleted`; operator ruling the same day, after PR #590's gate refused both).<!-- /scope -->
   **Every submodule pointer rides at its latest, touched or not**, `private/homebrew-tap` included: a PR that omits a pointer bump ships whatever the parent last recorded. The test is which commit is newer, never whose work it is: `cd <submodule> && git fetch origin && git log --oneline -1 origin/main` against `git ls-tree HEAD <submodule>`. A dirty pointer can mean the worktree is AHEAD (included) or BEHIND (stale checkout: `git submodule update`, nothing committed); `private/homebrew-tap` once showed dirty at `1.2.3` while the parent recorded `1.2.5`, and committing it would have rolled the tap back two releases. The console PR body links the submodule PRs (the `Submodule Branches` gate reads them there) and spells out any user-facing surface change against what is provably unchanged.
4. **Local gates before trusting CI**: the `npm run ci` sub-checks, in parallel with the slow ones backgrounded (`check:types`, `lint:unused`, `check:lint`, `check:ci-renet`, `check:ci-account-server`, `check:test-cli`), and the www and CLI builds (`./rdc.sh --version`). Known environmental local reds: `validate:tutorial-audio` (no local R2 media), `check:actions` (not a CI gate).
5. **Watch CI** with the terminal-state watch above (`.ci/scripts/ci/ci-trace.py --wait --until-final`, backgrounded). On a red, `.ci/scripts/ci/ci-trace.py --why` comes first (a red `--wait` exit prints it already), then `--job <id> --errors` for the failing step and `--job <id> --log` for the COMPLETE log before any diagnosis. The branch's own commits are suspected first; nothing is called transient before a clean-room repro.
6. **Fix per the tier system**, delegating implementation to workers where the class fits, commit submodule-first, refresh the console PR body (it must actually change: identical text does not bump `updatedAt`), push. Fixes are **batched** into one push, since each push restarts the pipeline.
7. **Every commit is reviewed when it is made, never at the PR.** The post-bash hook starts a haiku reviewer per commit: a clean verdict with full coverage is one line of `agent/reviews/<branch>/clean.jsonl`, every other verdict an `agent/reviews/<branch>/<sha>.md`. The precondition for ready and merge: every commit since the base has a review record in `agent/reviews/<branch>/` with no open finding at or above `block_at` and no deferred finding, and every record is committed (`python3 .claude/hooks/stop/wl_review.py --check`; `npm run check:ci-review-resolutions` is the CI side). An open finding is settled with `.claude/hooks/stop/worklist.py --review-mark <me> <finding-id> fixed|not-a-bug|waived <arg...>` (`waived` only for an OPERATOR-ONLY triage, with `ASKED:<YYYY-MM-DDTHH:MM>Z`), finished reviews are committed with `worklist.py --review-commit <me>`, and `block_push_with_unrecorded_reviews` refuses a push until both hold. Human review threads: `gh api repos/<owner>/<repo>/pulls/<n>/comments`, the real ones fixed (tiered like everything else), every thread replied to substantively and resolved through GraphQL `resolveReviewThread`. Unresolved threads fail `Quality / Review Gate` (console) and `Quality / Submodule Branches` (submodule PRs) on the next run and block the merge through a hook.
8. **Loop until all green, then the finish sequence; green is not the stop.** Every job is green first: the run has 100+ steps, deploy-preview among the last.
   <!-- scope: pr.finish-sequence -->The finish sequence, in order: (a) `gh pr ready` on the console PR (`block-premature-ready` admits it only when `CI Complete` is SUCCESS on the current head, so a block means the head is not green); (b) `python3 .claude/hooks/stop/wl_review.py --check` and every line it prints settled (loop step 7); (c) the PR review waited on and answered with `wl_prreview.py` until `Review Complete` is green and `python3 .claude/hooks/stop/wl_prreview.py --check` exits 0; (d) every human review thread resolved or replied to substantively (a fix push may go red and restarts CI).
   The finish line is green, ready, per-commit reviews clean, `Review Complete` green with `wl_prreview.py --check` at exit 0, and every thread settled; inline, the loop then goes to step 9, and delegated, the babysitter final-reports and stops.<!-- /scope -->
   <!-- scope: pr.review-answer -->The PR-review wait, its exit codes and the one excused case are in `.claude/commands/pr-merge.md` step 3.<!-- /scope -->
9. **Merge, release, hand over** (inline; delegated, the finish condition goes to the lead and the babysitter stops). `/pr-merge` prints the finish evidence, merges with `gh pr merge --rebase --auto` (or the fast-forward fallback when GitHub cannot rebase), watches the release, carries a main-only hotfix, and notifies the development session on a fully green release. The landing tree waits on `origin/main` until promotion brings the next PR, then the loop starts again at step 1.

**Three pre-command hooks enforce this flow; a hook block is the flow speaking, not an obstacle.** `block-nondraft-pr-create` (console PRs `--draft`, submodule PRs plain), `block-premature-ready` (`gh pr ready` only once `CI Complete` is green; `--undo` always allowed), and `block-admin-merge` (`gh pr merge --admin` banned outright; the sanctioned merge is `gh pr merge --rebase --auto`, run by `/pr-merge`). A block means the command is wrong for the current state: the state is fixed, the hook never worked around.

## The tier system - decide by decision type, not check name

The test for every failure: **"Could this fix be wrong in a way that changes product behavior?"**

**Tier 1 - fix silently, log it.** The answer is derivable from the repo: lint, biome, shfmt; i18n hash, search-index and generated-docs regeneration (generated files are never hand-edited; the generator reruns); deps freshness (respecting `.syncpackrc.json` pins and `.deps-upgrade-blocklist`); lockfile reconciliation; PR-body refresh; submodule re-point; gofmt and golangci mechanics; transient infra per the classifier (docker hub, apt mirrors, installer outages).

**Tier 2 - fix, and record the reasoning in the round log for post-hoc veto.** Test or CI-only code that does not touch product behavior: a racing assertion to `expect.poll`, a CI-load timeout widened, a skip-if-submodule-absent guard. A sanctioned i18n-string class in the wave header (internal error wraps, say) is baselined as tier 2 **with every string enumerated in the log**.

**Tier 3 - STOP and escalate to the principal. No guessing.**
- Any **product-code** change.
- A test asserting the **old contract** on behavior the wave changed: which side is right needs the intent.
- A bot review comment challenging a **design decision** (mechanical nits are tier 1; rebuttals need the principal's rationale).
- Anything touching a **frozen surface**, a hand-maintained list keyed by command names, or a locale file's translated values.
- **Suspecting the gate itself is the bug.** Concluding the check is wrong is allowed, even encouraged, rather than contorting code to satisfy it; *editing* a gate is always tier 3.
- Any suppression: BLOCKER entries, allowlists, blocklists, `test.fixme`.
- A count or baseline that moved and cannot be reconciled **with a mechanism**. A moved count is a question, not a chore, and one that *improved* is as suspicious as one that got worse.

**A tier-3 by mode:**

- **Delegated (`bg`)**: one SendMessage to the lead with the failing gate, the complete log excerpt, 2-3 candidate fixes with blast radius, and a recommendation. While waiting, tier-1/2 keeps draining but **nothing is pushed**.
- **Inline: AUTONOMOUS, the operator is never asked.** The loop takes the safest reversible option and logs the call under **DECISIONS (post-hoc review)** in the round log, with the rejected alternative and why, so the operator can veto after the fact. Tie-breakers, in order: (1) never destroy data or weaken a check; (2) complete an already-ruled intent rather than re-litigate it; (3) the smallest change that makes the gate honest; (4) genuinely 50/50: pick one, log it, move on. The merge happens only through `/pr-merge` at the finish condition, and a direct push to `main` only as its fast-forward fallback. A manual release re-dispatch and deleting remote data are forbidden, not escalated.

## Workers - delegate the typing, keep the loop

Handing fix *implementation* to worker sub-agents is allowed, and expected for bulky work. **The babysitter keeps the loop**: sole reader of CI state, sole diagnoser, sole committer, sole pusher. A worker gets a completed diagnosis, an explicit file scope, and the acceptance check (the exact local gate command that must pass). That keeps a long inline campaign affordable: a 27-round wave must not burn the main context on lockfile reconciliation or 12-locale sweeps.

- **Model per fix class**: translation, i18n, naturalization, mechanical sweeps and doc churn go to a **Sonnet** worker; standard code fixes to **Opus**; genuinely cross-cutting fixes take the session model. **Sonnet is as cheap as a worker goes**: operator ruling `D-M1` (2026-09-23) takes Haiku off write dispatch entirely.
- **Worker contract**: a worker edits only its named file scope in the primary tree, never commits, pushes or touches git state, and reports the exact files it touched. The fix is a worklist item of this session carrying the PR token (`--add <me> "<what> pr:<n>/fix"`), named `focus-fix:#<id>` in the spawn so the commit that lands it passes the landing freeze. The babysitter verifies by running the acceptance gate itself, then stages by name per the snapshot-boundary rule.
- **Parallel workers only on disjoint file scopes.** The historical translators-racing-the-tree failure was *uncoordinated* parallel editing; orchestrated disjoint scopes are fine.
- **Tier-3 items are never delegated before the ruling.**

## Round log - durable state, liveness artifact, and the principal's status channel

The round log is `<projects-dir>/reports/pr-babysit-<branch>.md`, where `<projects-dir>` is what `wl_core.projects_dir` returns for the checkout (`python3 -c 'import sys, pathlib; sys.path.insert(0, ".claude/hooks/stop"); import wl_core; print(wl_core.projects_dir(pathlib.Path.cwd()))'` prints it), never a path typed from memory. **It is how the principal knows what is happening**: an unwritten round is an invisible round. It is updated every round, before the push. Inline, it is also what survives compaction: the round log is the loop's real memory and the chat is scratch.

Three parts, in order:

**1. Wave header** (written once, before the snapshot; **immutable**, superseded by a dated addendum, never rewritten): intent (a paragraph); deliberate renames and removals (a failing test or doc naming an old name is read against this map, not "fixed" backwards); sanctioned reds, each with its reason; frozen surfaces; known-good baseline numbers **with the command that measures each** (two parties measuring differently manufactures drift); decision-boundary additions (wave-specific tier adjustments); memory pointers (at minimum the previous `pr-babysit-*` memory, `feedback_ci_gate_chain_pr501`, `feedback_ci_review_gates_flow`, `feedback_ci_watch_pattern`). In delegated mode it may cite the briefing file path, branch and PR links instead.

**2. STATUS block**, directly under the wave header, **overwritten in place every round**:

```
## STATUS (round N, <utc time>)
run:      <id> <url>          heads: console <sha> | renet <sha> | account <sha>
result:   <X> green / <Y> red / <Z> cancelled
red:      <job name> — <one line root cause>   [tier N]
doing:    <what is being fixed right now>
blocked:  <the ruling needed, or "nothing">
```

**It is refreshed with the verb, never by hand:** `.claude/hooks/stop/worklist.py --roundlog <branch>` with the BODY on stdin. "Overwritten in place" invites the splice `text[:i] + new`, which replaces from the STATUS heading to END OF FILE and takes the whole history appendix with it; that happened on 2026-08-19, during a heartbeat tick, to a file with no backup. The verb replaces only the block, prints the bytes it kept above and below, and stamps the time itself, because a hand-typed stamp can be copied forward and this stamp is what a watchdog reads. Two hooks enforce it (`pre-edit/block-roundlog-write.sh`, `pre-bash/block-roundlog-truncate.sh`); targeted `Edit`s and `>>` appends stay allowed.

The block has two consumers, which is why it must not rot: (a) **warm-start**: on resume, replacement or post-compaction, the wave header and STATUS are read first and the history is appendix; (b) **liveness**: in delegated mode the lead's watchdog judges the babysitter alive by this block's timestamp.

**3. Append-only per-round detail** below: run id and URL, each failed job, root cause, tier, fix, commit shas per repo, files touched (and which worker touched them), and **every escalation and the ruling it got**, including rulings tested and refuted, with the evidence. A replacement agent warm-starts from it, and it seeds the memory write-back at the end.

**State ownership.** Live loop state (run, heads, result, red, doing, blocked) is written in the STATUS block and nowhere else. STATE.md during a wave carries `## Next action` plus one line `Round log: <path>`; run ids, green counts and red names are not copied there. The worklist carries per-item progress through `--update`, with the PR token on fix items. Chat and SendMessage carry deltas only.

**Claim before touching.** When the principal says it is looking at a specific red, or hands over paths, the claim goes in the log and the red is not re-diagnosed in parallel. Duplicate diagnosis is the standing failure mode of any pairing.

## Delegate mode: the lead's side

This section is the lead's half of `/pr-babysit bg`; everything above is the babysitter's. The lead does the four things only it can do: compose the briefing, hand over the tree, rule on escalations, verify the end. Its real work while the babysitter runs is the remaining task list; a lead with nothing to do but watch CI mis-scoped the wave.

1. **Briefing.** Written to `<projects-dir>/reports/pr-babysit-<branch>-briefing.md` (`<projects-dir>` as in *Round log*): the wave-header slots of the round-log spec, plus two delegate-only slots, **escalation routing** (domain to who answers; default the lead) and **anything time-critical**. **Immutable once the babysitter runs**: superseded by a new file, never rewritten. Briefing and round log stay two artifacts on purpose: the briefing is the lead's immutable handoff, the round log the babysitter's mutable state.
2. **Hand over the tree, register, spawn.** The landing tree goes to the babysitter (section *Tree ownership*). A fix only the lead can make goes to the babysitter as exact paths marked as the lead's, so it stages them by name and does not treat them as a leak. `TaskCreate` registers a babysit task so the board and the watchdog cover it. The spawn is backgrounded with a **name** (`babysit-<branch>`) so SendMessage routes both ways: `subagent_type: pr-babysitter` when registered, else general-purpose told to read this file as its role. The initial prompt is the briefing path, branch, PR links, anything time-critical, and the statement that the lead is its principal and its SendMessage target for every tier-3 and every report. The delegated babysitter does not commit (section *The loop*): the lead commits and pushes the paths each report lists.
3. **Messaging.** Tier-3 escalations and reports arrive as SendMessage; rulings, absorb-these-paths instructions and supersede-briefing pointers go back the same way, to the babysitter's name. An idle notification without a report is not a report: STATUS fresh means the armed-watch design (left alone); STATUS stale across an observed state change means a dead driver (one ping, then a replacement).
4. **The lead does not read CI.** From spawn to the green report the lead runs no `gh run watch/view/list`, fetches no job log, and diagnoses no red. The failure mode is **shadowing**: two agents burning full context for one answer. (Real case: lead and babysitter independently root-caused the same compile break and the same crashing gate, and fell into the same stale-`tsbuildinfo` trap.) **Two agents agreeing is not verification; it is the same answer, paid for twice.** The lead's status channel is the babysitter's messages and the STATUS block; a gap there is a question to the babysitter, not a look at CI.
5. **Rulings.** Each escalation arrives structured: gate, log, candidate fixes, recommendation. A load-bearing claim is verified **in the code**, not by re-running CI, and the ruling answers the question asked without adopting the red. **Rulings may be overruled, and that is safe**: the babysitter tests them first (Rule 1); one wave overturned the lead four times, once on an order to delete the strictest gate in the suite. A ruling issued from an artifact is a hypothesis, and says so. Learned rules: rule on the class, not the site (one commit per ruling); never diagnose from a truncated read (`grep | head` has hidden the decisive hit); no parallel editors against the babysitter's tree; baseline counts are agreed **with the command that measures them**; a suspiciously quiet gate may be short-circuiting upstream (one emitted 30 rounds of false comfort).
6. **Watchdog.** Liveness is the freshness of the STATUS block, judged from the artifact. An idle notification is the normal state of a healthy babysitter with an armed watch: idle, fresh STATUS and a run in flight is working as intended (one lead took three idle notifications in four minutes for a dying agent while the round log was 90 seconds old). The dead-driver signature is stale STATUS across a period in which the run demonstrably changed state: one ping, then a replacement brief that holds for the lead's GO (warm-start from the round log). The gates and generated artifacts the babysitter depends on are not edited while it runs.
7. **Verify once, then close.** On the green report the lead verifies independently, ONCE: every PR's checks through `gh`, run URLs required, and a spot-run of the local battery; this is the only GitHub API read of the babysit. Debugging aids are confirmed off (a `no-auto-retry` label, a loosened gate) and files the babysitter was told to leave alone are confirmed outside its commits. The round log is distilled into a `pr-babysit-<branch>` memory file. Then the lead runs `/pr-merge` (loop step 9); the babysitter never merges in delegated mode.

## Standing gotchas (each has burned a real run)

- **The git pre-commit refuses a commit that leaves a generated doc region stale** (`.claude/rediacc_hooks/git/pre-commit`, gen-docs `--affected`). `npx tsx scripts/gen/gen-docs.ts --write` runs as its own call and the regenerated files ride the commit with the input. When another writer has uncommitted provider inputs in the tree, regeneration happens in the push clone at the branch tip plus only this commit's files, and the docs are copied back (2026-10-06, 62794367e).
- **The local post-push hook (`cancel-old-ci.sh`) can kill the run its own push created** (race): run `cancelled`, only the Initialize job, ZERO failed jobs, no newer commit. That is not "superseded"; it is re-run.
- `cancelled` with a failed job is the watchdog killing it for that failure (real). `cancelled` with zero failed jobs is not automatically superseded: run 36953549081 (2026-10-02) was cancelled by the watchdog's job budget. `.ci/scripts/ci/ci-trace.py --run <id> --why` names the cause (`watchdog-budget`, `watchdog-failure`, `superseded`, `timeout-kill`, `runner-not-acquired`, `manual`, `unknown`). **Cancelled is never green.**
- **Watchdog verdicts live in the separate `Watchdog Monitor` runs**, whose run-name carries the target run id; the in-run `CI Watchdog` job only bootstraps. `.ci/scripts/ci/ci-trace.py --watchdog [<run>]` prints the classifier verdict, the cancellation roster and a pending auto-retry; `--job <id> --log` reads one generation's log.
- Empty retrigger commits are hook-blocked. Live-state gates (PR Description, Submodule Branches, Review Gate) rerun with `gh run rerun <id> --failed`. Commit-meta lines (Co-Authored-By, "Generated with") are hook-blocked in this repo.
- **After ANY renet edit, the full `check:ci-renet` runs**, not just build, test and gofmt: its i18n extractor gate has caught stragglers twice.
- **npm at the exact `NPM_VERSION` pin is the only npm.** Before every commit in `private/account`, `git status` is checked for `package-lock.json`, rewritten with `npx -y npm@<NPM_VERSION> install --package-lock-only --ignore-scripts`, and `npm run check:ci-lockfile` read green; a lockfile change is validated with a REAL cold-cache `npm ci --ignore-scripts` in a clean-room copy (`--dry-run` does not run the reify peer check).
- During a watchdog attempt-2, attempt-1 jobs are listed by `.ci/scripts/ci/ci-trace.py --run <id> --jobs --attempt 1`.
- **`Review Gate` force-cancels the run instantly**, without the drain other no-retry lanes get, so it shows as `cancelled` siblings plus one failed job. It is not a code failure: review feedback is outstanding. The thread is replied to and resolved, then `gh run rerun <id> --failed` (no commit needed).
- **A RESOLVED THREAD AND A REPLIED COMMENT ARE DIFFERENT FACTS.** `Review Gate` runs two independent checks: GraphQL `reviewThreads.isResolved`, and `check-review-comments.sh`, which demands a reply to every top-level comment. Observed: all 10 threads resolved while 3 bot comments with `line: null` (outdated positions) sat unreplied and never appeared as threads. **The gate's own script is the oracle to satisfy**, not the API reached for first.
- Expect the **serial gate chain**: each run reveals ONE real failure. A large wave has taken 27 rounds.
- **The PR-Description gate reads `lastEditedAt`, not `updatedAt`.** A push bumps `updatedAt`, so right after a push the body looks freshly edited while untouched. Verification: `gh api graphql -f query='{repository(owner:"rediacc",name:"console"){pullRequest(number:N){lastEditedAt updatedAt}}}'`. Identical text moves neither.
- **The watchdog silences the SLOWEST job, so breakage accumulates where nobody looks.** A ~15-min cross-compile job (the only darwin and windows build) was cancelled for 30+ rounds and never reported; two real compile breaks lived behind that silence. **A cancelled job and a passing job look identical in a run summary: a gate that never finished did not pass.** The `no-auto-cancel` PR label holds a failing run open so every job reaches its own verdict (a budget overrun still cancels; `docs/agent-reference/ci-gates.md` *Labels*); it costs a full-length round. Without it, the cancellation annotation on the `Watchdog Monitor` run names every job that had failed by then: that roster is read, not the first red. A long job that keeps getting cancelled is run locally (`npx tsx scripts/ci-runner/run.ts --only '<gate-id>'`, ids from `npm run ci:list`).
- **Errors STACK.** Fixing the first error promotes the second: a darwin break stood in front of a windows break for a whole campaign. After a build fix, the blocked thing is re-run before calling it progress.
- **A gate can CRASH rather than fail, and a crash names only itself.** A validator importing the live CLI died with `ERR_MODULE_NOT_FOUND` because its CI job never built the workspace package (invisible locally, where `dist/` is warm), standing in front of a real product-visible bug. A gate that dies before a verdict has no result, not a red one.
- **Deleting the output is not a cold build.** With `composite: true`, a stale `*.tsbuildinfo` makes `tsc` exit 0 while emitting nothing. A true cold repro removes `dist` **and** `*.tsbuildinfo`. **A check is checked for whether it could have failed**, recursively.
- **A parity check is blind to a defect that is uniformly wrong.** A dead flag in an English string sits identically in all 13 locale catalogues, in perfect parity; only an absolute check against the live CLI sees it.
- Every Bash call uses absolute paths; `cd` persists between calls.

## Guardrails (never violate)

- **Never** `git restore` / `git reset` / `git checkout` a tracked path, **never** stash: the tree is other people's uncommitted work until the snapshot. A revert from memory is not a revert; damage is stopped and reported.
- **Never** push `main` outside `/pr-merge`'s fast-forward fallback, **never** merge outside `/pr-merge` at the finish condition, **never** force-push except `--force-with-lease` to the live `MMDD-N` branch (`block_git_force_push`), **never** amend pushed commits.
- Outcomes are reported with evidence (exit codes, run URLs, shas). A green from before the last edit is not evidence about the last edit; gates re-run after the final change.
