## Design

D1. **What the server can read (resolved with plan 3).** F10 puts a detector on ingest that must survive a compromised host, so it scores the batch contents on the server. Forensics batches are therefore signed by the machine and chained (F5) but not sealed under the config CEK: destination address, port, bytes, process name and hash, DNS name and sensitive file path are readable by the account Worker, encrypted at rest only by R2. Zero knowledge is rejected for this data because a sealed batch would blind the server detector, which is the one detector a compromised machine cannot silence.
What stays unreadable: file contents and command output are never captured (F2), and run tails stay sealed (PLAN-console-run-index.md D3), so the timeline shows a run's tail only in an unlocked browser. This matches PLAN-forensics-detection.md D6 and D7, whose server detector scores the shipped batches in the account server every 5 minutes; plan 7 states it in the DPA.

D2. **One read service, one merge.** `forensics-read.service.ts` answers `timeline(org, scope, from, to, cursor)` with rows of one union (`packages/shared/src/incident/timeline.ts`): `audit` (day files and per-event objects of audit-r2), `run` (run-index rows), `flow` and `open` (the forensics store of plan 2), `anomaly` (plan 3's `forensics_findings`, machine and server sources), `gap` (missing heartbeats past two intervals) and `incident` (declare, contain, close). Rows sort by time and carry `source` and `observed | inferred`. Aggregates come from the same pass: bytes out per minute and the top 20 destinations by bytes with plan 3's ASN and country when present. A machine scope covers every repo on it plus the machine-level audit.

D3. **Access (F18).** Opening an investigation requires an owner or admin of a paid org (audit-r2's paid predicate), a step-up meeting the org minimum of PLAN-console-confirm-stepup.md D5, and writes `forensics_investigations(id, org, user, scope, expires_at)` valid 60 minutes, so a long investigation does not re-prompt every 10 minutes (Context 3). Every read carries the investigation id and writes one `console.forensics.view` event (scope, window, row kinds, never row contents).
Support reads only through `forensics_support_grants(id, org, scope, issued_by, expires_at, revoked_at)`: issued by an owner or admin after step-up, at most 7 days, revocable, read from the admin panel under root elevation, and each support view lands in the customer's audit with `actor.kind: 'support'`.

D4. **Declare incident (F19): evidence first, machine steps after.** The account side runs first and atomically: a `forensics_incidents` row (`id, org_id, scope_kind, scope_ref, window_from, window_to, status` of `declared | contained | closed`, `declared_by, declared_at, aware_at, notified_at, contained_at, closed_at, closed_by, fork_ref, steps`), an eviction hold over the window that plan 2's FIFO skips, and an R2 bucket lock rule per affected machine prefix and day (per month past 400 rules), written by `forensics-lock.service.ts` through the Cloudflare API with one serialized read-modify-write of the bucket's rule set.
Then the machine steps run through existing paths: `rdc repo fork <ref> --tag incident-<id>` and plan 1's level switch to Full; each step's outcome lands in `steps`, and a failed step leaves the hold in place and shows as a retry action. `aware_at` defaults to `declared_at` and may be set earlier, never later. Clocks: early warning at `aware_at + 24 h`, notification at `aware_at + 72 h`, final report one calendar month after `notified_at` (NIS2 Art. 23(4)(d) counts from the notification; before it is set, from `aware_at + 72 h`). Close releases the hold and the lock rules after 30 days, never at once.

D5. **Verify in the browser (F17).** `packages/shared/src/forensics/verify.ts` (WebCrypto, Node and browser) recomputes audit-r2 day-file hashes against each next header and plan 2's batch chain (hash links and Ed25519 batch signatures), and reports `{window, heads, gaps, edits, verifiedAt, verifier, toolVersion}`. The route serves raw day files and batch files for the window; above 2 GiB the page says so and offers `rdc forensics verify`, which runs the same module. Every export carries the stamp.

D6. **Changes since the last snapshot.** The panel runs `repo diff <ref> --stat --base <fork>` through the console executor, the base being the newest fork of the repo created before the window start, or the incident fork once one exists. A repo with no fork shows "no snapshot to compare" rather than a chunk-store browse (Context 5).

D7. **Verbs (F20).** Reads (`incident status`, `incident export`, `repo flows <ref> --since --until`, `repo opens <ref> --since --until`, `forensics verify`) call the account read API with the new privileged `forensics:read` scope; `incident declare|close` take `incident:manage`; `forensics level` calls a new renet function `forensics_level` over the existing SSH executor path, which wraps plan 1's `renet forensics level` verb (PLAN-forensics-capture.md D8, FC7); plan 1 hands the registration to this plan. Both scopes go only to owners and admins and only from a CLI login approved in an elevated browser session.
Severity per agent/plans/PLAN-console-contract-semantics.md D2: `incident declare`, `incident close` and `forensics level` are `caution`, the reads `none`. MCP: the reads opt in through the rmcp registry; `declare`, `close` and `level` carry `mcpExcludeReason` until the rmcp program rules otherwise.

D8. **Ask AI.** "Ask about this incident" opens plan 9's chat through the ai-in-pages bar with an `incident` template whose `readCommands` are the D7 reads. The asking owner's open investigation mints a single-use ticket bound to (user, org, scope, window, 15 minutes); the executor hands it to the dispatched read verb, so the AI reads exactly what the human may and its views are audited with `actor.kind: 'agent'`. The model is the customer's provider (F12); the timeline rows it reads leave to that provider, stated beside the bar.

D9. **UI.** `Investigate.tsx` under `/console/investigate/:kind/:ref`: scrubber over the window, merged rows with kind filters, an SVG bytes-out chart (no new dependency, Context 8), top destinations, the diff panel, Verify, Export, Declare (amber `caution` dialog of confirm-stepup D6) and the three clocks. Keyboard: the scrubber moves by arrow keys and Page keys, rows are a list with roving focus, every action has a visible focus ring. English keys in a `forensics` namespace; FI12 translates.

## Risks

- **Lock rules at scale.** One rule per machine and day, folded to months past 400, keeps an incident under the bucket's rule cap; the serialized write prevents two declares losing each other's rules.
- **A Worker that can lift locks.** The Cloudflare token can edit lock rules, so a compromised Worker could remove them; the eviction hold in D1 and the 30-day release delay are the second line, and the token lives only in the account Worker's secrets.
- **Server-readable flow metadata.** D1 makes it readable by design; D3 limits staff access to customer-issued grants and records each view where the customer sees it.
- **Unknown plan 2 module names.** FI3 and FI4 re-point their globs in the commit that edits them.
