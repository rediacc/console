## Why

The per-repository Docker API gate refuses every way a container can reach a GPU. `DeviceRequests` are refused whenever present (private/renet/pkg/dockerpolicy/policy.go:374), which covers `--gpus`, compose `deploy.resources.reservations.devices`, and CDI names such as `nvidia.com/gpu=all`, since Docker 25+ sends `--device <cdi-name>` as a DeviceRequest with driver `cdi`. Raw `Devices` are refused except `/dev/net/tun` (private/renet/pkg/dockerpolicy/policy.go:64, private/renet/pkg/dockerpolicy/policy.go:67, private/renet/pkg/dockerpolicy/policy.go:459), binds under `/dev` are refused (private/renet/pkg/dockerpolicy/policy.go:573), `DeviceCgroupRules` are refused (private/renet/pkg/dockerpolicy/policy.go:370), any runtime but runc is refused (private/renet/pkg/dockerpolicy/policy.go:92, private/renet/pkg/dockerpolicy/policy.go:400), and a security option beyond `apparmor=unconfined` and the no-new-privileges forms is refused (private/renet/pkg/dockerpolicy/policy.go:74, private/renet/pkg/dockerpolicy/policy.go:77). `SYS_PTRACE` is already an allowed capability (private/renet/pkg/dockerpolicy/policy.go:61), and `GroupAdd` is not read by the gate at all. The compose validator builds a HostConfig of only privileged and the pid/ipc/uts modes (private/renet/pkg/compose/validate.go:168), so `devices`, `deploy`, `cap_add`, `security_opt` and `runtime` pass it unread; PLAN-converge-preflight-and-repo-recovery adds that parity, and this plan extends the same table to GPU spellings.

The machine side has nothing to hand a grant to. The per-repository daemon.json (private/renet/pkg/daemon/systemd.go:573) names no runtimes and no `cdi-spec-dirs`, and it is rewritten on every start (private/renet/pkg/daemon/start_foreground.go:688). The containerd sandbox binds `/dev` recursively (private/renet/cmd/renet/daemon_containerd_exec.go:247) and `/usr` and `/etc` read-only (private/renet/cmd/renet/daemon_containerd_exec.go:281, private/renet/cmd/renet/daemon_containerd_exec.go:282), with `MS_REC` (private/renet/pkg/daemon/mount_sandbox_linux.go:246), but deliberately not host `/run` (private/renet/cmd/renet/daemon_containerd_exec.go:255) and not `/var/lib` (private/renet/cmd/renet/daemon_containerd_exec.go:270), so neither `/var/run/cdi` nor `/run/nvidia-persistenced/socket` is visible to a repository's dockerd. `renet setup` installs GPU drivers only (private/renet/cmd/renet/setup_command.go:116, private/renet/cmd/renet/setup_command.go:117; AMD is parity-only, no ROCm, per decision D3 at private/renet/cmd/renet/gpu_drivers.go:22) and `renet system check-drivers` probes them through lspci and nvidia-smi (private/renet/cmd/renet/system_commands.go:391, private/renet/cmd/renet/system_commands.go:422). Nothing installs nvidia-container-toolkit, runs `nvidia-ctk`, writes a CDI spec, or knows `/dev/dri` or `/dev/kfd`, and the CLI has no GPU surface.

Grants already exist for bind roots and delegated networks: `Delegations` (private/renet/pkg/dockerpolicy/delegation.go:38), the grant file and its store (private/renet/pkg/dockergrant/grant.go:71, private/renet/pkg/dockergrant/grant.go:245) under `/etc/rediacc/grants`, re-read by the gate on each request through `dockergrant.Source`'s mtime cache (private/renet/pkg/dockergrant/grant.go:418, wired at private/renet/cmd/renet/daemon_dockerproxy_exec.go:114), and edited by the hidden `renet daemon grant` (private/renet/cmd/renet/daemon_grant.go:42). A device grant is one more kind in that same file, so it takes effect on the next request with no daemon restart.

## Decisions (taken by the lead under the operator's design ruling; recorded for veto)

1. CDI is the only admitted form. The gate is evaluate-only (`Evaluate` at private/renet/pkg/dockerpolicy/policy.go:310 returns a Decision and never rewrites a body), and teaching the proxy to rewrite request bodies is a new capability with its own attack surface. So a legacy `--gpus` request, `{Driver: "nvidia"}` or an empty driver with capability `gpu`, is refused with a message that names the granted CDI form (`use --device nvidia.com/gpu=all`, or compose `devices: [nvidia.com/gpu=all]`) instead of being mapped. The compose validator gives the same message.
2. Specs live only under `/etc/cdi`, which the sandbox already sees through its `/etc` bind. `/var/run/cdi` is not bound into the sandbox. nvidia-container-toolkit's own docs generate to `/var/run/cdi/nvidia.yaml` and, from v1.18.0, its `nvidia-cdi-refresh` service regenerates that file on install, driver change and boot (https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html); renet writes a systemd drop-in for that service setting `NVIDIA_CTK_CDI_OUTPUT_FILE_PATH=/etc/cdi/nvidia.yaml` (the environment variable of `--output`, https://github.com/NVIDIA/nvidia-container-toolkit/blob/main/cmd/nvidia-ctk/cdi/generate/generate.go) and removes a stale `/var/run/cdi/nvidia.yaml`, so the host's system Docker and every repository daemon read one spec.
3. The persistenced socket is bound read-only into the sandbox only when the inventory records `/run/nvidia-persistenced/socket`. A spec generated in nvml mode mounts it into containers when it exists, and runc inside the sandbox fails the container if the source is missing. The bind is one file, not host `/run`, so the T1 isolation of PLAN-renet-run-docker-sock-isolation is unchanged.
4. Grant names are exact CDI names. Granting `nvidia.com/gpu=all` admits exactly `nvidia.com/gpu=all`, not `nvidia.com/gpu=0`; an operator who wants one card grants that card's name. A grant is validated at write time against the specs present under `/etc/cdi`, so a typo is refused rather than recorded.
5. Exclusivity is enforced at grant time, under a store-wide lock over `/etc/rediacc/grants`: an exclusive grant of a name refuses when any other network holds that name, and any grant of a name refuses while another network holds it exclusively. The gate does not scan other networks' files per request.
6. A fork gets a new network id and so starts with no device grant (default deny); the grant file is bound to the repository mount (`RepoMountPath`, private/renet/pkg/dockergrant/grant.go:71), so it never follows a fork.
7. Raw `Devices`, `DeviceCgroupRules`, `/dev` binds, a non-runc runtime and seccomp or AppArmor relaxations stay hard denials, granted or not. A CDI grant is the only door.
8. Changing daemon.json's shape bumps `RuntimeEpoch` from 2 to 3 (private/renet/pkg/daemon/runtime_epoch.go:39), as the G1 fingerprint rule requires (`TestRuntimeLayoutFingerprint`, private/renet/pkg/daemon/runtime_epoch_fingerprint_test.go:51, hashes daemon.json per flavor at private/renet/pkg/daemon/runtime_epoch_fingerprint_test.go:172). The next `rdc machine setup` on each machine then converges every running repository once.

## Design

- D1. Inventory. New package `pkg/gpu` detects, without lspci being required: NVIDIA through `nvidia-smi --query-gpu=index,uuid,name,driver_version,memory.total --format=csv,noheader` (on WSL, `/usr/lib/wsl/lib/nvidia-smi`); render nodes through `/sys/class/drm/renderD*` with each node's PCI vendor from `/sys/class/drm/renderD*/device/vendor`; AMD compute through `/dev/kfd`; WSL through `/dev/dxg` plus `/usr/lib/wsl/lib`. It writes `/etc/rediacc/gpu/inventory.json` = `{version, generated_at, platform: native|wsl, gpus[], render_nodes[], kfd, dxg, toolkit_version, specs[{path, kind, devices[]}], persistenced_socket}`. A machine with nothing writes the file with empty lists, which is what `rdc machine gpu list` reports as none.
- D2. NVIDIA specs. When the inventory has an NVIDIA GPU, `renet setup` (flag `--install-nvidia-toolkit auto|true|false`, default auto) installs `nvidia-container-toolkit` from NVIDIA's libnvidia-container repository (apt list `https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list`, rpm repo `https://nvidia.github.io/libnvidia-container/stable/rpm/nvidia-container-toolkit.repo`, key `https://nvidia.github.io/libnvidia-container/gpgkey`, per https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html), with that key embedded and pinned the way gpu_drivers.go pins the CUDA keys, then runs `nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`, adding `--mode=wsl` on WSL (`wsl` is one of the modes in https://github.com/NVIDIA/nvidia-container-toolkit/blob/main/pkg/nvcdi/mode.go; auto would also resolve it, the explicit flag makes the spec reproducible). The toolkit's runtime is NOT configured into any daemon (`nvidia-ctk runtime configure` is never run), since Decision 7 refuses a non-runc runtime.
- D3. renet's own specs. `/etc/cdi/rediacc-dri.yaml` (kind `rediacc.io/dri`, one device per render node, named `renderD128` and so on, each a `deviceNodes` entry for `/dev/dri/renderD<N>`) and, when `/dev/kfd` exists, `/etc/cdi/rediacc-amd.yaml` (kind `rediacc.io/amd`, device `gpu<N>` = `/dev/kfd` plus that card's render node, and `all`). These need no ROCm userspace; they map device nodes only, which keeps D3 of the driver plan intact. Specs are rewritten each setup and their names recorded in the inventory.
- D4. Daemon. daemon.json gains `"cdi-spec-dirs": ["/etc/cdi"]`; `RuntimeEpoch` becomes 3 with its doc paragraph and the fingerprint golden re-recorded through `RuntimeFingerprintUpdateCommand` (private/renet/pkg/daemon/runtime_epoch.go:392). The sandbox adds the persistenced-socket file bind of Decision 3 and nothing else; the comment beside the host `/run` exclusion names this one exception and why.
- D5. Grant model. `dockergrant.Grant` gains `Devices []DeviceGrant{Name, Exclusive, GrantedBy, GrantedAt}`; `Empty` and `Policy` (private/renet/pkg/dockergrant/grant.go:88, private/renet/pkg/dockergrant/grant.go:93) carry them; `dockerpolicy.Delegations` gains `Devices []DelegatedDevice` and `Empty` (private/renet/pkg/dockerpolicy/delegation.go:44) counts them. `renet daemon grant` gains `--device <cdi-name>[:exclusive]` and `--revoke-device <cdi-name>` (repeatable), validated against `/etc/cdi` and the exclusivity rule of Decision 5.
- D6. Gate. `evalCapsDevicesSecurity` (private/renet/pkg/dockerpolicy/policy.go:355) admits a `DeviceRequests` entry only when its driver is `cdi`, it carries no count, capabilities or options, and every DeviceID is a granted name; anything else is a hard denial, with Decision 1's message for the legacy nvidia forms and `device %q is not granted to this repository; grant it with rdc repo gpu grant` for an ungranted CDI name. `GroupAdd` stays unchecked (a group without the node grants nothing); the allow/deny table pins that.
- D7. Compose parity. On top of the preflight plan's devices/deploy/runtime parity, the validator maps compose's GPU spellings onto the same HostConfig fields (service `devices:` entries that parse as CDI names become DeviceRequests with driver `cdi`; `deploy.resources.reservations.devices` and `gpus:` become the legacy driver form), so `renet compose` and the gate give one verdict and one message.
- D8. Bridge and CLI. Bridge functions `machine_gpu_list` (reads the inventory) and `repository_gpu_grant` / `repository_gpu_revoke` (network id, device, exclusive; provision access), with tiermap entries and i18n strings. CLI: `rdc machine gpu list <machine>` (table and `--json`), `rdc repo gpu grant <repo-ref> --device <cdi-name> [--exclusive]`, `rdc repo gpu revoke <repo-ref> --device <cdi-name>`, the granted names mirrored into the repository's `state.repos` entry (machine-derived facts already live there), and a GPU column in the repository list reading that mirror.
- D9. Preflight. The converge preflight of PLAN-converge-preflight-and-repo-recovery classifies a GPU request whose CDI names are all granted as allowed, and an ungranted or legacy one as refused with D6's message.

## Risks

- The epoch bump restarts every running repository on every machine at its next setup, hostinger's 11 included. It rides the existing converge machinery (PLAN-renet-runtime-converge), so it is ordered, health-checked and resumable, but it is a real bounce; H1 runs it deliberately rather than leaving it to the next routine upgrade.
- A spec generated before a driver upgrade goes stale (library paths move). The `nvidia-cdi-refresh` drop-in regenerates `/etc/cdi/nvidia.yaml` on driver change and boot; on WSL, where the driver lives on the Windows side, `rdc machine setup` regenerates it, and the inventory records `generated_at` so `rdc machine gpu list` can show the age.
- CDI hooks in the NVIDIA spec (`nvidia-cdi-hook create-symlinks`, `update-ldcache`) run as runc hooks inside the sandbox, from `/usr/bin` (visible read-only). If a hook needs a path the sandbox hides, the first live run (W1, then a native-NVIDIA machine when one exists) shows it; the fix is a narrow bind with evidence, never host `/run` or `/var/lib`.
- The `state.repos` mirror can drift from the machine's grant file if a grant is edited with `renet daemon grant` on the machine directly. The machine file is the enforcement point and the mirror is display only; `rdc machine gpu list` reads grants live from the machine, so the drift is visible.
- An exclusive grant is a reservation, not a scheduler: two containers of the one granted repository still share the card. The docs page says so.
- No native-NVIDIA or AMD machine is available for acceptance; W1 covers WSL and T1 covers the grant mechanics with a fake node. Native NVIDIA (nvml mode, persistenced socket) and AMD (kfd) are covered by unit fixtures only until such a machine is added.
