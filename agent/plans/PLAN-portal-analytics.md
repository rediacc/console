## Ask

Items 5, 6 and 8 of console#519. The marketing site measures clicks up to the region picker and then goes blind: the account portal loads no analytics at all, so signups, trial starts and purchases are not counted, and the `purchase` event the site defines fires on a page Stripe never returns to. The UTM parameters the site now forwards across the region-picker hop arrive at the portal and are thrown away. After a checkout that started on the site there is no way back to it.

This plan loads the same analytics the site uses, on the three public regional portals only, keeps the first-touch attribution, emits `signup`, `trial_start` and `purchase` where they really happen, and adds an optional "back to rediacc.com" link after checkout. It also removes the portal's one unused signup client. The www half (CTA truthfulness, the dead www page, the www denominator) is PLAN-www-funnel-truthfulness.md. No existing plan covers portal analytics (grep for plausible, trial_start and funnel over agent/plans and agent/plans/_done on 2026-11-16).

## Design

- **One analytics module.** `web/src/lib/analytics.ts` owns everything: `isAnalyticsHost(hostname)` (true only for a `BAKED_IN_REGIONS` domain), the script loader and queue stub (same script URL and `plausible.init` options as BaseLayout), `captureAttribution(location)` and `track(event, props)`. `track` is a no-op off an analytics host, so tests, bench, Enterprise and on-prem send nothing.
- **Same Plausible site as www.** Plausible counts a visitor as a hash of the site, IP and user agent per day, so reusing the www site id is what joins a www pageview and a portal trial into one funnel. A second site would split them. The script id is a constant beside the loader; it duplicates the BaseLayout literal by necessity (the account repo builds without packages/www), and a comment at both sites names the other.
- **Attribution survives the hop.** `main.tsx` calls `captureAttribution` before React mounts, so `IndexGate`'s rewrite can no longer lose it. First touch wins: `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content` and the validated `returnUrl` go to `localStorage` (`rediacc.attribution`, 24 h expiry; localStorage because the magic link opens a new tab). Every `signup`, `trial_start` and `purchase` event carries the UTM fields as props.
- **Events where they happen.** `success_url` gains `&plan=<code>&trial=<1|0>` from the values the server already has. `Subscription.tsx` fires `trial_start` (trial=1) or `purchase` (trial=0) with `{ plan, ...utm }` once, then replaces the URL without `plan` and `trial` so a reload cannot fire it again. `magic-link/verify` returns `firstSignIn: true` when the user had no refresh token before this sign-in, and `MagicLinkVerify.tsx` fires `signup`. Revenue amounts are not sent (no amount reaches the client without another Stripe read).
- **CSP.** `script-src` and `connect-src` in the Worker's table add `https://plausible.rediacc.com`. Nothing else widens.
- **Back to site.** The success banner shows "Back to rediacc.com" linking the stored `returnUrl` when one exists and its origin is exactly `WK_SITE_ORIGIN`; otherwise no link. The server is not involved.
- **Register client.** Delete `authApi.register` and its response type if nothing else uses it. The endpoint stays.
- **Out of scope.** Plausible goals, funnels and segments are dashboard settings (PLAN-www-funnel-truthfulness.md O1). Server-side Stripe webhook events to Plausible are not built: a client event under-counts ad-blocked visitors, and that is accepted for a funnel ratio.

## Risks

- Ad blockers drop client events; the funnel ratio is biased low for the portal steps. Accepted (Design, out of scope).
- The script id lives in two repos. If the www site is ever recreated, both literals change; the cross-reference comments are the only guard.
- `firstSignIn` reads refresh-token history; a future cleanup job that prunes old refresh tokens would make a returning user look new. A5's test documents the rule so such a job has to face it.
- The account surface needs a VERIFIED `npm run vm:check -- --changed` on the head tree before the live recorder runs (docs/agent-reference/plan-records.md, "The ladder").
