## Ask

Operator, 2026-11-22T04:23Z, answering how `rdc` should work against a PR preview address: "Per-preview signer, as a plan". <!-- style-ok -->

Operator rulings ASKED:2026-11-22T05:06Z, asked in plain English and recorded here in the third person. The goal is a PREVIEW CHANNEL, not only a signer.

1. Use case: the operator works with a customer directly on an edge case and asks the customer to use a preview address to see whether a PR solves the problem, so a customer tests a PR on the customer's own real machines. Bench is shared and any developer may overwrite it, so previews must be fully isolated.
2. Licences signed for a preview are real but tightly limited: 7 days, renewable while the preview lives, scoped to the preview's own subscription.
3. Only the operator and agents open PRs (no outside contributors); a fork preview still never gets a signer.
4. The customer uses a fresh preview account (signed up on the preview or created for the customer) with a temporary preview subscription; no real account data is copied.
5. One switch command that remembers the way back, for example `rdc preview use <name>` and `rdc preview leave`: the customer's existing config keeps its real server and returns to it exactly.
6. When switched, rdc on the customer's computer AND renet on the customer's machines move to the builds of that PR, so the account service, CLI and renet match the PR exactly; leaving reinstalls the published versions the customer had.
7. Preview addresses use random words per PR instead of the guessable `pr-<number>` (the console repository may become private, and untested preview code must not be easy to find), with a stable PR-to-words mapping stored where deploy, cleanup and the switch command can read it.
8. Customers must be told what happens if they forget to leave: what renet does with an expired preview licence (running apps keep running? creation and changes refused?) is verified on a test machine, and the message is designed from that result.

Operator answers ASKED:2026-11-22T05:23Z, asked in plain English and recorded here in the third person:

1. Repos created during a preview stay in the same config file, with no separate list and no sync. On `rdc preview leave` they are re-licensed from the real account (eu, us or an Enterprise server), counting against the real plan's limits; when the plan is full, the customer is told which repos could not be licensed. There is no deletion path.
2. No up-front step switches all machines. Every server that rdc or renet touches while the preview is active gets the preview renet (as rdc already installs its own embedded renet on contact) and joins a touched-server list in the preview overlay state; on leave, the list is shown and, after confirmation, exactly those servers go back to the pre-preview renet.
3. Only the operator creates a customer's preview account (the `preview_account` command plus a one-time sign-in link); self sign-up on a preview and its email-verification dependency are dropped.
4. A PR that changes an on-disk format may still be a preview, but `rdc preview use` warns explicitly that switching back may not read data the PR writes, and requires confirmation; the PR marks itself so the warning appears.
5. Defaults accepted: three words from a 2048-word list for names, and GHCR pull-request image tags keep the PR number.

## Design

### D1. Where the per-preview signer lives (kept from the signer design)

- Option A (recommended): a second Worker `<name>-signer`, built from `workers/signer` with a preview template, deployed by `deploy-preview` right before the preview Worker. No route, no workers.dev host, reached only by the preview's `LICENSE_SIGNER` binding. It binds the preview D1 as `SHARED`, and `SHARED_HOSTS` is the one preview host. Deploying it also drops `SIGNERLESS_PREVIEW` from the preview render.
- Option B: a `LicenseSigner` entrypoint inside the preview Worker. One Worker less, but the delegated key sits in the isolate that answers every public request.
- Option C: keep `signer-bench-eu` and teach it preview hosts and databases. Rejected: the production key signs for PR code again (the reason the binding was removed, Context 1).

### D2. Which key it signs with (kept)

- Option A (recommended): a fresh Ed25519 key pair per deploy, the private half pushed only as a `wrangler secret bulk` secret of `<name>-signer`, and a delegation cert for the public half from the central signer. `signer-bench-eu` gets a caller tier `{tier: "preview", name, host, region}` that admits only `signDelegationCert`, and the cert's fields come from the central signer's own rules (D3), never from the request. `<name>-signer` fetches its certs on demand and caches them in the preview D1.
- Option B: a renet that trusts a preview key. Rejected: the customer would run a second renet, which is not what ships (Context 7).
- Option C: the production key as a secret of a PR-deployed Worker. Refused outright.

A malicious PR can read its own preview's delegated key and sign licences only for subscriptions in its own preview namespace, under the cert limits, until `validUntil` (Context 6); it cannot mint a cert for a subscription outside that namespace. The residual risk is Context 12.

### D3. The fresh preview account and its subscription (ruling 4)

Renet binds a delegated licence to the cert's subscription id (Context 6), and each fresh account owns its own organisation and subscription, so one cert per preview cannot serve several customers.

- Option A: one reserved subscription per preview, every customer account a member of one preview organisation. One cert, but customers on the same preview share an organisation and see each other's machines.
- Option B (recommended): one cert per preview subscription, in a namespace the central signer enforces. On a preview (`ENVIRONMENT = "preview"`), every new organisation gets a temporary preview subscription whose id is `pv-<name>-<8 hex>`, on a fixed preview plan, ending 7 days after creation and extended while the preview lives (D4). The preview tier of the central signer admits a cert request only when the subscription id matches `^pv-<name>-[0-9a-f]{8}$` for the caller's own `name`, fixes plan, size and issuance limits itself, caps validity at 7 days, and caps certs per preview (for example 20 per 7 days, counted in its control store). The `pv-` prefix cannot collide with a production subscription id, so a leaked preview key never signs for a real customer.
- Option C: no account on the preview; the customer's real account is proxied. Rejected by ruling 4 (no real data copied).

Account creation (answer 3): only the operator creates a customer's preview account, with `python3 -m rediacc_ci.deploy.preview_account --pr <n> --email <addr>`, which writes the account and its organisation into the preview D1 and prints a one-time sign-in link. Sign-up on a preview host is refused (`ENVIRONMENT = "preview"` answers the sign-up route 403 `PREVIEW_SIGNUP_CLOSED`), so no preview needs email verification or outbound mail. Nothing from a real account is read.

### D4. Licence lifetime and renewal (ruling 2)

A preview licence is valid 7 days with its `renewalUrl` on the preview host. Renet's periodic `license renew` (Context 10) renews it through the preview signer while the preview lives; the preview signer refreshes its cert when fewer than 5 days remain, so a live preview never lets the cert lapse, and each redeploy's fresh key re-signs on the next renewal. Once the preview is gone, the host answers nothing and the cert expires within 7 days, so renewal fails and growth stops (D11). Expiry is the revocation; renet has no revocation list.

### D5. Random-word names and the PR-to-name lookup (ruling 7)

- Option A (recommended): derived, not stored. `name = "pv-" + three words` chosen by HMAC-SHA256(`PREVIEW_NAME_KEY`, PR number) from a fixed 2048-word list (`.ci/config/preview-words.txt`), 33 bits per name. `rediacc_ci.deploy.preview_name --pr <n>` is the one implementation; deploy, cleanup, the R2 channel and the sweep call it, and the operator runs it to look up a PR's address. The key is a Bitwarden secret, so the mapping is stable across runs, needs no store that can drift, and is unrecoverable without the key. The switch command needs no lookup: the customer receives the name, and the name is both the host `https://<name>.rediacc.workers.dev` and the channel `cli/<name>/`.
- Option B: random words minted on first deploy and stored in a private R2 object `previews/pr-<n>.json` plus a reverse index. Survives a key rotation, but every reader needs bucket credentials, and a lost object strands a live preview.
- Option C: the name in a PR label or body. Rejected: readable to anyone who can read the repository, which ruling 7 rules out once it is public.

The public faces move to the name: the Worker (and so the host), the signer Worker, and the R2 channel. Internal names (`account-pr-<n>` D1, the `ci-pr-<n>` concurrency group) stay, because no customer and no outsider sees them. The sweep recognises `^pv-[a-z]+-[a-z]+-[a-z]+(-signer)?$` and deletes one whose name no open PR derives. `pr-<n>.rediacc.workers.dev` and `cli/pr-<n>/` stop being published.

### D6. Publishing the PR builds to the preview channel, with integrity (ruling 6)

The PR run already stages every platform's CLI to R2 (Context 22); only the channel name changes (D5). Integrity today is one sha256 from the same origin as the binary (Context 14).

- Option A: unchanged, sha256 from the manifest only.
- Option B (recommended): a second origin. The deploy writes the channel manifest's version and per-platform sha256 into the preview Worker (a `PREVIEW_BUILD` var), server-info returns them as `previewBuild`, and `rdc preview use` refuses a binary whose hash differs between the R2 manifest and the preview server. A tampered bucket object or a stale channel is caught before anything runs.
- Option C: a GPG-signed `SHA256SUMS` per preview, as the local release writes. Strongest, but it puts the release signing key in a PR job, which D2's reasoning refuses.

Renet needs no separate publishing: it rides inside the verified CLI (Context 18).

### D7. A preview build's version identity

A PR build carries the next release's plain version (Context 21), which collides with that release's renet slot and makes the way back a refused downgrade.

- Option A (recommended): PR builds stamp `X.Y.Z-preview.<sha7>` into the CLI and renet. It sorts below `X.Y.Z` by semver, gets its own slot, shows in `rdc version` and `renet version`, and lets the provisioner recognise a preview renet by its suffix. `isDevVersion` and `bareVersion` must classify the suffix deliberately (box B1 states how).
- Option B: keep the version and key slots by version plus hash. Smaller change, but a preview renet stays indistinguishable from the release in every log and support report.

### D8. `rdc preview use` / `leave` / `status`: state and rollback (ruling 5)

- Option A (recommended): an overlay. The config keeps its `account` section byte-identical; `rdc preview use <name>` adds a `preview` block `{name, host, enteredAt, channel, formatChange, previous: {cliVersion, cliSha256, updateChannel}, touched: {<machine>: {slot, version, sha256, touchedAt}}}` and `readAccountPointer` answers the overlay's host and token while the block exists. The preview token lives in its own `api-token-<config>.preview-<name>.json`, so the real token is never touched. `leave` deletes the block and the preview token, and the real server, key and token are in force again by construction.
- Option B: copy the account fields into `previous` and overwrite them. Restoring depends on the copy being complete; a field added later is lost.
- Option C: a separate named config. Rejected: the customer's machines and repos live in the existing config, and ruling 5 keeps that config.

The CLI binary: `use` runs in the customer's current binary, which copies itself to `~/.local/share/rediacc/preview/rdc.pre-preview` (with its sha256 in the state), then installs the preview channel's binary with D6's check. `leave` reinstalls the latest build of the recorded previous channel (forced, since the version may be lower) and falls back to the kept copy when that channel is unreachable. Because `leave` normally runs inside the PR's own binary, the kept copy is the emergency exit: `use` prints the exact command `~/.local/share/rediacc/preview/rdc.pre-preview preview leave`, and `leave` is written so a pre-preview binary that carries this plan can complete it. Every command in preview prints a one-line banner naming the preview, its licence end date, and `rdc preview leave`.

### D9. Switching renet on the machines and back (ruling 6, answer 2)

There is no up-front switch of every machine. While the overlay exists, the preview CLI's embedded renet goes to a server the first time rdc touches it, through the provisioner path rdc already runs on contact (Context 18-19). Before the first replacement on a server, the provisioner records that server's current slot, version and hash under `preview.touched` and writes a pin marker into that slot, which the slot prune skips while the marker exists (otherwise two preview redeploys would prune the way back, Context 19). A server rdc never touches keeps its renet and never enters the list.

`leave` prints the touched-server list with each server's recorded and current renet version, asks for confirmation, and switches exactly those servers back: it repoints `current` to the pinned slot when its hash still matches the record, restarts renet's daemons, and removes the pin; only when the slot is gone does it re-provision from the restored CLI. A server that cannot be reached stays in the list with its record, `leave` reports it, and `rdc preview leave --machine <m>` finishes it later; the overlay is removed only once the list is empty. The downgrade guard admits replacing a `-preview.` renet without `REDIACC_ALLOW_DOWNGRADE` (D7); every other refusal stays.

Rejected: switching every machine in the config at `use` (answer 2), which changes servers the customer never meant to test on.

Backup and autostart units whose `ExecStart` names a versioned path are reconciled on both switches (`REMOTE_INSTALL_PATH`, packages/cli/src/services/renet/renet-provisioner.ts:71).

### D10. Licences on the machine across the switch (answer 1)

Context 9 makes this safe by structure. Repos created during the preview are ordinary entries of the same config file; nothing keeps a separate list and nothing syncs. In preview, the CLI requests a preview licence only for a repo that holds no master-key licence on its server; existing repos keep their real master-signed licences, which renet keeps preferring and keeps renewing through the real server.

On `leave`, for each touched server, the CLI finds every repo whose only licence files are preview-key ones (read from the server's licence store, Context 9), deletes every preview-key licence file, and re-licenses those repos from the real account the config names (eu, us or an Enterprise server) through the normal activation path, counting against the real plan's limits. When the plan is full, `leave` names each repo that could not be licensed and the limit that refused it; those repos keep running and can be stopped and started (operate tier) and refuse growth until the plan admits them. There is no deletion path.

### D11. Expiry and the message to the customer (ruling 8)

By reading (Context 10), when a customer forgets to leave and the preview licence or cert expires: running apps keep running, `repo up`, autostart after a reboot and `exec` keep working, `down` and `delete` work, and create, fork, resize, expand and backups are refused with `LICENSE_REQUIRED`. Box E1 measures every one of these on a fleet VM before the message is written; a measured difference changes the message, not the measurement.

The message, shown at `use`, in the banner when fewer than 2 days remain, and as the guidance for an `expired` or `cert_expired` refusal whose licence carries a preview key (replacing the on-prem text of Context 11 for that case):

> This machine is on preview `<name>`, a test build of a fix. Its licences end on `<date>` and renew only while the preview exists. After that, running apps keep running and can be stopped and started, but new repositories, forks, resizes and backups are refused. Run `rdc preview leave` to return to `<real server>` and the published rdc and renet; repositories created on the preview are then licensed from the real account, within its plan.

### D12. A PR that changes an on-disk format (answer 4)

Renet has no state-version guard (Context 20), so a PR that writes a newer vault, chunkstore manifest, journal or autostart unit format can leave data the pre-preview renet refuses after `leave`. Such a PR may still be a preview; it marks itself, and `use` warns.

- Option A (recommended): a committed marker file `.ci/config/preview-format-change.json` on the PR, `{"formats": ["<format>", ...], "reason": "<one line>"}`. It is reviewed with the code it describes and disappears with the PR. `deploy_www.py` reads it into `PREVIEW_BUILD.formatChange`, server-info returns it, and `rdc preview use` prints the formats and the reason, states that switching back may not read data the PR writes, and requires typed confirmation (`--accept-format-change` for a scripted run). `rdc preview status` repeats the warning.
- Option B: a PR label. Rejected: the deploy job would need a GitHub API read, and a label is not reviewed with the diff.
- Option C: detect a format change from the diff (`schema.go` constants, `ManifestVersion`). Kept as a backstop only: D1 fails the deploy when the diff touches a known format-version constant and no marker exists, so a forgotten marker cannot reach a customer silently.

### D13. Lifecycle and cleanup

Created by `deploy-preview` on each push: name derived (D5), signer Worker and key rotated (D1, D2), channel staged under the name (D6). Destroyed on PR close by `ops-cleanup-preview.yml` (Worker, signer Worker, D1) and `ops-cleanup-r2-staging.yml` (the channel), and by the housekeeping sweep for anything a failed close left behind. A customer still switched when the preview dies is covered by D8 (`leave` works with the host and the channel gone) and D11.

### D14. Fork safety (ruling 3)

A fork preview never gets a signer. `deploy-preview` gains `github.event.pull_request.head.repo.full_name == github.repository` in its `if:`, the condition `.github/workflows/ops-cleanup-preview.yml:33` already carries, so a fork run skips instead of failing at the Bitwarden step; `preview_signer.py` also refuses when `GITHUB_EVENT_PATH` names a fork head.

## Risks

- Unpublished PR code runs on a customer's real machines. The way back is the product: D8 keeps the real config untouched and a pre-preview binary that can finish `leave`, D9 pins the pre-preview renet slot, LP4 and LP5 prove both, including with the preview gone. A PR whose `leave` is broken is caught by the kept binary, which is why that binary's command is printed at `use`.
- A renet that cannot go back cleanly: renet has no state-version guard (Context 20), so a PR that writes a newer on-disk format can leave data an older renet refuses. Such a PR is still offered (answer 4); D12's marker makes `use` warn and require confirmation, and the deploy backstop refuses a format-constant change that carries no marker. A daemon restart on switch may interrupt work in flight; LP2 and LP4 measure whether running apps keep serving.
- A touched server that cannot be reached at `leave` keeps the preview renet; D9 keeps it listed and keeps the overlay until it is switched back, so it is never forgotten silently.
- A licence left behind: a customer who never leaves keeps running apps without growth (D11), and the message says so. A leaked delegated key signs only inside its own `pv-<name>` namespace for at most 7 days (D3, D4).
- A1 may show an artifact that needs the master key, or E1 may show expiry stopping something; each exists to find that before code, and D3 or D11 changes rather than the measurement.
- The name key is one secret: its loss renames every live preview on the next push and strands switched customers on a dead host; `leave` still works (D8), and the key is rotated only between customer sessions.
- GHCR pull-request images keep the PR number in their tags by answer 5 (Context 22); no customer path pulls them.
- Four live plans share files (Concurrency); block_plan_concurrency serialises their writers, and S1, S2, D1 and N3 rebase onto whatever lands first.
