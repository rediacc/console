## Design

**Z1 No pins (Q1).** The reap protects a lineage while it is in use, not a list of hashes. `reapLineage` keeps its due-page loop and, before each page's R2 delete, runs one query: "an unexpired lease or an unexpired backup session exists for this lineage in this store", that is `backup_upload_leases` by `(subscription_id, lineage_guid, store_id, expires_at > now)` OR `backup_sessions` by `(subscription_id, grand_guid = lineage, intent = 'backup', store_id, expires_at > now)`. If either exists, the lineage is skipped for this run: the remaining pages are not deleted and nothing is counted as freed. The check runs again on every page, so a session minted in the middle of the reap stops the next page. The one window left is a session minted between the last check and that page's R2 delete. Pins had the same window, and the commit-time HEAD, the sweep and repair cover it. The doc comment is rewritten to say this. `existsBatch` writes nothing and answers `{ existing }`. `pinExpiresAt` leaves the DTO, since renet never reads it. The replicator's `pin()` goes, and its lease is the protection. A migration adds the session index. A later release drops `backup_exists_pins` along with its schema entry, the scope-registry entry, the lineage and tenant purge entries and `sweptPins` in the maintenance report.

Two resume paths keep the invariant "every exists answer the commit relies on was given inside the live lease or session":
- renet (R1). A resume re-asks the run's whole original question inside the new session, not just the pending set. With no base that is `NonZeroHashes()` (`full`). With a base matching `u.BaseSnapshotID` it is the hashes the base does not name (`changedAndSample`'s `changed`, `delta`). The base's manifest row protects the rest, as on a first attempt. If the base is missing or different, the resume asks the full set. Anything answered missing joins the pending set and is uploaded. This needs a renet release, and P1's deploy waits on it (LR1).
- Replicator (P2). The cursor gains `leaseExpiresAt`, the lease expiry the batch wrote. A resumed cursor with that time missing or in the past is discarded, so the batch restarts at `hashIndex` 0 with zeroed counters: the existing lost-cursor path, with a listing re-bill at commit.

**Z2 Expiry sweep (Q3).** src/services/retention-sweep.service.ts exports `sweepExpiredAuthRows(db, now)`. For each of the nine tables it runs `DELETE FROM t WHERE id IN (SELECT id FROM t WHERE expires_at < ? LIMIT 5000)` in a loop until a page comes back short. That is one bound parameter per statement, the event-log purge's form, and every statement stays under D1's 100-parameter limit however many rows have expired. It returns per-table counts and logs one `retention_sweep` system event. W1 adds it to `runRetentionSweeps` as a fourth `allSettled` member.

**Z3 Telemetry to Analytics Engine (Q2).** `TELEMETRY_TYPES` holds `cli.*` (prefix), `config.pull` and `config.version.read`, and lives in event-log.service.ts as a single list. src/services/telemetry-sink.service.ts holds `writeTelemetry(ae, entry)`. It maps an entry to one AE data point, with `indexes: [subscriptionId]`, blobs `type, source, userId, orgId, teamId, actorTokenId, idempotencyKey, JSON data truncated to the AE blob limit`, and doubles `[1]`. It also holds `queryTelemetry(sql-api client, filter)` for the portal, reading through the AE SQL API with a read token secret. AE keeps 3 months, which sets the portal's telemetry horizon. The idempotency dedup that the D1 unique index gives the CLI ingest does not exist in AE. The ingest still answers `accepted` by the AE write count, and a replayed batch can double-count telemetry, which is acceptable for counters and is stated in the code. Rollout as ruled: (A1) dual-write, D1 unchanged plus AE; (A2) portal and config history read telemetry types from AE and the rest from D1; (A3) the D1 write stops for telemetry types; the purge then drains the old rows. Retention after A3: `DEFAULT_AUDIT_RETENTION_DAYS = 90`, with one exemption list, `RETAINED_STATE_TYPES` (`repo_license_issued`, `repo_license_renewed`, `repo_license_retired`), kept at 400 days because billing.service.ts derives state from them. A test fails when a type read by `latestPerRepository` or `listBySubscriptionAndType` in a state-deriving caller is missing from that list.

**Z4 Config envelopes in R2 (Q4).** A new nullable column `config_versions.envelope_key` is the pointer. The envelope object is written at `configBlobKey(store, team, config, 'e/<version>-<uuid>.json')`, a sibling prefix of the `v/` blobs, so the sweep can list envelopes alone. Archive: put the envelope object, then insert the row with `envelope_key` and no `envelope_json`. A crash in between leaves an object the orphan sweep removes. Read: use `envelope_key` if set, else fall back to `envelope_json` until C2. Retention: a version row is deleted only when it is outside the newest 100 of its config AND older than 9 months (`created_at`). Deletion runs blob, envelope, then row, the existing blob-first order. `BlobStorageService` gains `list(prefix, cursor)` in the R2, S3 and memory implementations, with prefixes scoped by `assertScopedPrefix`. Orphan sweep (nightly, bounded per run): list `e/` objects page by page, and delete one when no row names its key and it is older than 24 h, a grace that covers a push in flight. Backfill (nightly, bounded per run until drained): for rows with `envelope_json` set and `envelope_key` null, put the object, then set `envelope_key` and null `envelope_json` in one statement guarded by `envelope_key IS NULL`. C2 drops the column and the fallback once LC1 has read zero such rows in every region.

**Z5 Waiting-chunk compaction (Q5).** `backup_waiting_chunks` is rebuilt so `hash` is a 32-byte BLOB instead of 64-char hex text, the surrogate UUID `id` goes, and the primary key becomes the existing scope `(subscription_id, lineage_guid, store_id, hash)`. The rebuild migration converts in SQL. Every reader and writer in backup-gc.service.ts converts at the boundary (hex in TypeScript, BLOB in SQL). `inJson` membership tests compare against BLOBs. The writer must confirm that D1's SQLite has `unhex()`; if it does not, it binds `Uint8Array` pages of at most 90 values (the existing `slice(i, i + 90)` form at private/account/src/services/backup-gc.service.ts:5261).

**Z6 Per-tenant write caps (Q6).** src/middleware/tenant-write-cap.ts takes a rate-limit binding per class and keys it `<subscriptionId>:<class>`. Classes: `audit` (CLI audit ingest, routes/license.ts), `config` (authenticated config requests and pushes, routes/configs.ts). Exists asks are left out: after Z1 they write nothing to D1. Over the limit, the answer is 429 with `{ error, code: 'TENANT_WRITE_RATE_LIMITED', class, retryAfterSeconds }` and a `Retry-After` header. No binding (Node entries, tests) means no cap. Limits live in workers/account/wrangler.<r>.toml as Workers rate-limit bindings, with the periods the binding allows (10 or 60 s). The starting values come from the review's budget (heavy tenant at 5,000 writes a day): `audit` 120 per 60 s, `config` 60 per 60 s. The binding is approximate per location, so a false refusal costs a retry and loses no data.

**Z7 Size report (Q7).** .ci/rediacc_ci/ops/d1_size_report.py, for every region in regions.json, reads through the D1 query API used in the review: table list, row counts, value bytes per table as `sum(length(col))` per column (D1 has no `dbstat`, so index bytes are an estimate with the review's 1.6 factor), the database file size, and the tenant count (`count(*)` of subscriptions). Alerts: tenants ≥ 25,000, or file size ≥ 5 GB (half the 10 GB limit), or an alerting bytes-per-tenant trend. The output is JSON plus a Markdown summary, and the exit code is 3 when any alert fires. A scheduled workflow runs it daily and opens or updates an issue on an alert. Names are only regions.json's, so the enterprise leak gate's masking rule holds.

**Z8 Sharding, built now, cut over later (Q8).** Each region has a directory D1 (the existing regional database) and N tenant shards. Global, staying in the directory: users, `email_hash`, organizations, memberships, teams, invitations, subscriptions, invoices, `invoice_*`, `webhook_processed`, refunds, `version_policy`, catalogue and partner tables. Tenant-scoped, moving to the shard: everything src/db/scope-registry.ts classifies by subscription (backup_*, config_*, event_log, api_tokens, issuance_ledger, repo_license_issuance_slots, signed_blobs, subscription_activations, delegation_certs). The writer re-reads the registry and lists the final split in the box. Assignment: a directory table `subscription_shards (subscription_id primary key, shard text, moved_at)`. A new subscription takes `shard = hash(subscription_id) mod N`. An existing one keeps its row, so changing N moves rows rather than rehashing them. With no row, the subscription is on shard 0, the directory itself, so with N = 1 today everything is the identity. The directory row is inserted in the same transaction that creates the subscription, at every code path that inserts into `subscriptions` (checked 2026-11-09 under private/account/src/services/): `SubscriptionService.create` (private/account/src/services/subscription.service.ts:216), `AuthService.register` (private/account/src/services/auth.service.ts:139), the magic-link signup in `AuthService.sendMagicLink` (private/account/src/services/auth.service.ts:366), `OrgService.createOwnedOrg` (private/account/src/services/org.service.ts:243), and `OnPremiseSubscriptionService.adopt` (private/account/src/services/onprem-subscription.service.ts:159), so a new subscription always has one; a subscription with no row (only those created before H1) is on shard 0 by that rule, and the move tooling writes a row before it moves anything. src/db/shard-router.ts exports `dbFor(subscriptionId)` and `forEachShard(fn)` for cross-shard admin. Login by email reads the directory's users and `email_hash`. Billing webhooks resolve customer to subscription in the directory, then use `dbFor`. Admin lists (root.ts, root-stripe.ts) fan out through `forEachShard` and merge by timestamp. Move tooling (d1_shard_move.py): export one subscription's tenant rows by registry scope, import them into the target, compare per-table counts and hashes, flip the directory row, then delete the source rows. Dry run is the default, and the tool refuses while the subscription holds a live lease or session. The cutover (H5) waits on a size-report alert.

**Guardrail doc.** private/account/CLAUDE.md, schema section: the per-tenant budget (typical 100 KB and 500 writes a day, heavy 1 MB and 5,000), and the review rule that a per-tenant table needs a predicate sweep and a test deleting more than 100 rows in one run.

**Out of scope:** review item 12, the backup maintenance fan-out through a Queue. No ruling covers it, and it stays in the review's list.
