2. The CLI sends every account call through the sealed tunnel. `accountServerFetch` (packages/cli/src/services/account/account-client.ts:343) puts the bearer inside the envelope (`innerHeaders`, account-client.ts:405-416) and posts the sealed request to `${serverUrl}/account/api/v1/tunnel` (account-client.ts:440-441). The three callers that fail: `activate-repo` (packages/cli/src/services/account/license.ts:158), `activate-repo-batch` (packages/cli/src/services/account/license-batch.ts:503) and `repos/:guid/retire` (packages/cli/src/services/account/license-retire.ts:27-28, reached from `settleDeletedRepoLicense`).
3. Inside the executor the bearer is a placeholder. `rdc serve --mode container` reads `REDIACC_TOKEN` (packages/cli/src/commands/serve.ts:75), which the container boots with as `EXECUTOR_TOKEN_PLACEHOLDER` (workers/proxy/src/egress.ts:27). The egress swaps that placeholder for the issued token only on an exact `Authorization` header of an allow-listed `METHOD path` (`BEARER_ROUTES`, egress.ts:32-39; `routeOf`, egress.ts:89-107). A sealed bearer is out of its reach, the tunnel's inner route is invisible to it, and admitting the tunnel would let it re-dispatch to any route, voiding the allow-list.
4. The egress comment on the tunnel (egress.ts:14) is stale: it says the one container caller seen is the core audit flush. The licence activation and retire paths are container callers too, and they are fatal to `repo create` and `repo fork`.
5. The three account routes demand scope `license:activate` (private/account/src/routes/license.ts:238, :260, :286) and scope by the caller's own token: `apiTokenSubscriptionId`, `apiTokenTeamId` and `resolveAttribution` over `apiTokenId` (license.ts:101-125, :244-246, :266-268, :291-296). Retire with a team set refuses a repository another team issued (private/account/src/services/repo-license-retire.service.ts:63-66).
6. The token the egress swaps in cannot pass them. `issue(orgId)` mints exactly `['proxy:exec','audit:write']` (private/account/src/services/executor-issuer.service.ts:38) with no creator and no team (`apiTokenService.create(..., null, expiresAt, null, 'service-binding', issuerKey)`, executor-issuer.service.ts:412-421). Granting it `license:activate` would let every executor activate under the org with no team and no person behind it.
7. Precedent for acting on behalf of a principal: `POST /licenses/audit-events` takes `onBehalfOfTokenId` per event, refuses an issued executor token that omits it (`ON_BEHALF_REQUIRED`), and refuses a named token outside the caller's org with one answer for unknown and foreign alike (`ON_BEHALF_TOKEN_FORBIDDEN`), license.ts:415-494. `POST /configs/executor-grant` holds the fuller liveness rule for a principal token: live and unrevoked, same org, a recorded creator who still holds an org role, carrying `proxy:exec`, team not archived, and not the executor's own token or a sibling (private/account/src/routes/configs.ts:1186-1213).
8. The principal's token holds `proxy:exec`, not `license:activate`. Both mints a proxied caller can hold produce exactly `['proxy:exec']`: `/proxy/session-token` (private/account/src/routes/proxy.ts:215-222) and `/proxy/cli-token` (proxy.ts:303-310). So the brief's "the named token holds license:activate" check would refuse every real caller; Design 2 checks `proxy:exec` plus a live creator membership instead, the rule executor-grant already applies.
9. The container knows the principal's token id. Introspect answers `tokenId` (proxy.ts:156), the serve layer keeps it on the session principal (packages/cli/src/services/serve/auth.ts:327-328, sessions.ts:47), and the executor audit already sends it as `onBehalfOfTokenId` (packages/cli/src/services/serve/audit.ts:102, run-index.ts:287). Commands run in-process (packages/cli/src/services/serve/command-dispatch.ts:1-31), and the dispatch already scopes a per-request value with an AsyncLocalStorage wrap (`withForensicsTicket`, packages/cli/src/services/forensics/client.ts:187-192, applied at command-dispatch.ts:469).
10. `repositoryGuid` is a UUID on the account side (`issueRepoLicenseSchema`, private/account/src/types/subscription.ts:134), so the egress can hold the retire path to a strict UUID pattern without refusing a real call.
11. 44 non-test files under packages/cli/src call `accountServerFetch`; the core audit flush (packages/cli/src/services/core/audit.ts:165) is the other one seen in the bench tail, non-fatal and already covered by the container's own audit (egress.ts:14).

## Design

1. **New executor routes, not widened ones.** Three routes under `/account/api/v1/proxy/licenses/`: `POST activate-repo`, `POST activate-repo-batch`, `POST repos/:guid/retire`, in a new `private/account/src/routes/proxy-licenses.ts` mounted with one line in routes/index.ts. Widening the existing three was weighed and refused: it puts two authentication models (`license:activate` from a CLI token, `proxy:exec` plus a delegated principal) into one handler, so a missed branch would let a CLI token name someone else's token, and the egress would admit paths that ordinary CLI tokens also use. Separate paths keep the CLI routes byte-identical, give the egress a set of pairs only the executor uses, and keep each auth rule testable on its own. Both sets call the same service methods (`issueRepoLicense`, `issueRepoLicenseBatch`, `repoLicenseRetireService.retire`), so no licence logic is duplicated.
2. **Who may call, and on whose behalf.** Each route takes `apiTokenAuth('proxy:exec')`, then requires the caller to be an issued executor token (`issuerKey` set, the shape audit-events already singles out) and a body field `onBehalfOfTokenId`. The named token must be: found and neither revoked nor expired; in the same org as the caller (through its subscription's customer); carrying `proxy:exec`; created by a user who still holds an org role; on a team that is not archived when it has one; and not the caller itself or a token of the same executor principal. Every failure answers one 403, `ON_BEHALF_TOKEN_FORBIDDEN`, so the route is no token-existence oracle. The principal check is one shared function beside the routes, written once, read by all three.
3. **Scoping and attribution come from the principal.** The handler takes the named token's `subscriptionId` and `teamId` where the CLI routes take the caller's, and attribution runs `resolveAttribution` over the named token's id and subscription (license.ts exports it with those two inputs). The retire's `actorTokenId` is the named token. So a team-scoped principal activates under its own team and retires only what its team issued (repo-license-retire.service.ts:63-66), and the event log names the person, never the executor fleet.
4. **Request schemas.** `issueRepoLicenseSchema` and `issueRepoLicenseBatchSchema` gain executor twins that add `onBehalfOfTokenId` (string, 1-100), in private/account/src/types/subscription.ts; the retire body is `{ onBehalfOfTokenId }` alone. The response DTOs are the existing ones.
5. **The CLI in container mode.** A new module `packages/cli/src/services/account/executor-principal.ts` holds an AsyncLocalStorage of `{ tokenId }`, set by command-dispatch.ts around the dispatch only when serve runs with `--mode container` and the principal has a token id. license.ts, license-batch.ts and license-retire.ts ask it first: inside a container dispatch they send the call plain (no tunnel) to the executor route at the config's account URL (`http://account.internal`), with `Authorization: Bearer <REDIACC_TOKEN>` (the placeholder) and `onBehalfOfTokenId` in the body; outside one they call `accountServerFetch` exactly as today. A container dispatch with no principal token id fails the activation with a named error rather than falling back to the tunnel. The daemon (`--mode daemon`) keeps the tunnel path; it talks to the account server directly, not through the egress.
6. **The egress admits exactly three pairs.** `BEARER_ROUTES` gains `POST /account/api/v1/proxy/licenses/activate-repo` and `POST /account/api/v1/proxy/licenses/activate-repo-batch`; `routeOf` gains a `PROXY_LICENSE_RETIRE_RE` of `^/account/api/v1/proxy/licenses/repos/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/retire$` for `POST`, classed `bearer` with query `none`, so any query is refused (`query-not-allowed`). The tunnel stays refused. The egress.ts:14 paragraph is rewritten to say the licence activation and retire calls of a container dispatch travel on these three bearer pairs, that the core audit flush is skipped in a container, and that the tunnel stays refused for the reasons already given.
7. **The other tunnel caller.** The core audit flush (core/audit.ts) does nothing inside a container dispatch, since the executor audit records the same command server-verified; the bench tail then shows no tunnel refusal at all for a proxied `repo up`. Any further `accountServerFetch` caller reachable from a served command is found by PL4's inventory and given a decision there.

## Risks

- A principal token is short-lived (five minutes for a console session token, proxy.ts:327). A long `repo create` that activates late could name a token that expired mid-command; PL1's expired-token refusal is deliberate, and PL-L1 records whether the bench run sees it.
- The new routes widen what an issued executor token can cause: licence activations for a principal who already passed introspect and executor policy for the command. No activation happens without a live, same-org, `proxy:exec` principal, so the executor cannot activate on its own account.
- egress.ts and command-dispatch.ts are shared with PLAN-rmcp-writeback; a writer of each in parallel meets as a cherry-pick conflict at landing.
