## Ask

`rediacc/console` is public. On a `pull_request` event GitHub runs the workflow files, the local reusable workflows and every script under `.ci/` from the PR's merge commit, with repository secrets available. Several jobs on that path still receive production credentials. The fix is the one the repo already uses for Turnstile: mint a throwaway credential per PR (or per preview) and never hand a production one to PR-controlled code.

This plan file is public, so it names credential CLASSES and the files that change, not which production secret is reachable from which step. The detailed exposure map lives in rediacc/account#65.

## Context (checked 2026-11-16 against the tree)

1. Every credential now flows through Bitwarden Secrets Manager. The repository holds exactly one secret, `BWS_ACCESS_TOKEN` (`gh api repos/rediacc/console/actions/secrets` lists only it), and every job fetches what it needs through `.github/actions/bws-secrets`. One machine-account token can therefore read every entry of the one store project (`.ci/config/bws-secret-map.json:14` names a single `project`).
2. The stage-artifacts caller in `.github/workflows/ci.yml:1196-1228` runs on pull requests (`upload_pages: ${{ github.event_name == 'pull_request' }}`), passes `BWS_ACCESS_TOKEN` and grants `id-token: write` and `attestations: write` (`:1207-1211`). Both attestation steps in `.github/workflows/cd-stage.yml:410-425` are `if: github.event_name == 'push'`, so the OIDC grant is unused on a PR and only widens what PR code can mint.
3. `cd-stage.yml` fetches the release package-signing key step-scoped (`:156-164`, scrubbed after) and runs `rediacc_ci.build.build_linux_packages` with it and `RELEASE_SIGNING_REQUIRED: '1'` (`:165-175`). Step scoping (PLAN-scope-bws-signing-key-to-consuming-step.md S4) narrows WHICH steps see the key, not WHETHER a PR run sees it: the consuming step executes PR-controlled build code.
4. The package build already supports a non-default public key: `.ci/rediacc_ci/build/build_pkg_repo.py:569-591` reads `RELEASE_GPG_PUBLIC_KEY_FILE` (default `.ci/keys/gpg-public.asc`), refuses a signing key whose fingerprint differs from it, and copies that file into the repo as `apt/gpg.key` and `rpm/gpg.key` (`:593-595`).
5. Install validation trusts the channel under test, not a pinned key: `.ci/rediacc_ci/testrun/install_scripts.py:48` fetches `@RELEASES@/apt@SUFFIX@/gpg.key`, and the dnf path reads the channel's own `rediacc.repo` (`:88`). A throwaway keypair per PR channel therefore keeps apt and dnf validation passing unchanged. (Corrects the issue's citation of the retired bash install-methods test, which the Python port replaced.)
6. The preview Worker no longer holds the licence private key: `.github/workflows/ci.yml:1724-1727` and `.ci/rediacc_ci/deploy/deploy_www.py:198-205` bind `LICENSE_SIGNER` to `signer-bench-eu`. That signer signs with the production licence key (`.ci/rediacc_ci/deploy/deploy_signer.py:10`, `:51-52`, and the comment at `.github/workflows/ci.yml:1726`), so a licence a preview issues verifies under every production renet.
7. The preview Worker's other server secrets (tunnel key, session secret, server API key, outbound mail credentials) are still the production values, set by the "Set preview worker secrets" step of the deploy-preview job (`.github/workflows/ci.yml:1728-1760`). The preview serves on a public `*.workers.dev` hostname.
8. One broad Cloudflare API token name (`CLOUDFLARE_API_TOKEN`, 147 references across `.github` and `.ci/config`) serves deploys, D1, cache and Turnstile alike. The session can mint scoped tokens itself: `.ci/rediacc_ci/ops/cf_auth.py` `resolve_scoped` mints a token carrying named permission groups from the Global API Key profile, and `rediacc_ci.core.bws_env store-from-env --create` writes a value into the store from the environment (`.ci/rediacc_ci/core/bws_env.py:309`, `:1246`).
9. The per-PR Turnstile widget is the model to copy: created in the deploy-preview job (`.github/workflows/ci.yml:1659-1668`, `scripts/preview-turnstile.ts create`) and torn down by `.github/workflows/ops-cleanup-preview.yml`.
10. Repository Actions settings, read 2026-11-16: `allowed_actions: selected`, `sha_pinning_required: false`. The committed mirror `.ci/config/actions-allowlist.json:38` still lists `anthropics/*`, and that pattern is in use: `.github/workflows/ops-claude-review.yml:250` runs `anthropics/claude-code-action`, which produces the required Review Complete check.
11. `.ci/rediacc_ci/deploy/clone_d1.py:47-56` records that `--sanitize` cannot work (its SQL file was deleted in 57b61098c3) and that the only caller passing it was removed. The migration test clones without it.

## Design

**Decided, not boxes.** (a) The unsanitized D1 clone stays as it is: the issue records the decision to keep it, and the sanitizer SQL no longer exists (Context 11). (b) `anthropics/*` stays in the allowed-actions list: the issue proposed dropping it after `claude.yml` was deleted, but the PR review workflow uses it now (Context 10). (c) The orphaned `CLAUDE_CODE_OAUTH_TOKEN` repository secret is already gone (Context 1).

**D1. Signing: a throwaway key on PR runs.** `cd-stage.yml` gains an input `signing: release|ephemeral`; the ci.yml caller passes `ephemeral` on `pull_request` and `release` otherwise. Under `ephemeral`, a new module `rediacc_ci.build.ephemeral_signing_key` generates an unprotected RSA signing key in `$RUNNER_TEMP`, exports its public half, and sets `RELEASE_GPG_PRIVATE_KEY`, `RELEASE_GPG_PASSPHRASE` (empty) and `RELEASE_GPG_PUBLIC_KEY_FILE` for the build step; the step-scoped release-key fetch carries `if: inputs.signing == 'release'`. The fingerprint check in `build_pkg_repo.py` stays and now compares the throwaway pair, so a mixed-up key still refuses. The PR channel publishes the throwaway `gpg.key`, which install validation fetches (Context 5). `RELEASE_SIGNING_REQUIRED` stays `1` on both paths: an unsigned package is still a failure.

**D2. OIDC: no `id-token` on PR runs.** Split the caller into `stage-artifacts` (`if:` push or dispatch, keeps `id-token: write` and `attestations: write`) and `stage-artifacts-pr` (`if:` pull_request, `contents: read` and `packages: write` only), both calling `cd-stage.yml`. Reusable-workflow permissions are static per caller job, so the split is the only way to drop the grant by event.

**D3. Preview server secrets are generated per preview.** A new module `rediacc_ci.deploy.preview_keys` generates, in the deploy-preview job, a fresh X25519 pair, session secret and server API key, writes them through `wrangler secret bulk` stdin (the deploy_signer pattern, Context 6), and exports only the public halves as job outputs for the smoke test. Nothing in that set is fetched from the store any more. Outbound mail: the preview gets no production mail identity. If the account Worker starts without mail credentials (W1 measures this), the preview runs with mail disabled; otherwise it gets a sandbox identity created under OP1.

**D4. Preview licences come from a non-production signer.** `deploy_signer.py` gains a `preview` target, `signer-preview`, with the same Worker and bindings shape as `signer-bench-eu` and its own Ed25519 pair stored under preview names (`ACCOUNT_PREVIEW_ED25519_PRIVATE_KEY`, `ACCOUNT_PREVIEW_ED25519_PUBLIC_KEY`), minted once by the session with `store-from-env --create`. `deploy_www.PREVIEW_TOML` binds `signer-preview`. Bench keeps the production key: tutorials and live proofs rely on bench licences verifying under the released renet (PLAN-tutorial-recorder-licence.md), so changing bench's key is out of scope.

**D5. Scoped Cloudflare tokens for PR jobs.** The PR-reachable jobs get `CLOUDFLARE_API_TOKEN_PREVIEW`, minted through `cf_auth.resolve_scoped` with only the groups the preview deploy and its D1 and Turnstile steps use (W5 inventories them from the API calls each step makes), and stored with `store-from-env --create`. Cloudflare cannot scope Workers or D1 permissions to a name prefix, so the gain is dropping production zone, cache and DNS permissions from PR runs, not isolating `pr-*` objects from production ones; the residual is named in Risks.

**D6. The PR path cannot read release credentials at all.** Step scoping and per-PR credentials shrink exposure; the durable boundary is two Bitwarden machine accounts. The repository secret `BWS_ACCESS_TOKEN` becomes a PR-safe token that can read only a new store project holding the PR-safe entries. The release token becomes `BWS_RELEASE_ACCESS_TOKEN`, an environment secret on a `release` environment whose deployment policy admits only `main`, and only the push and dispatch release jobs name that environment. Creating machine accounts and projects is a Bitwarden web-vault action (OP2); setting the environment secret is `gh secret set --env release` (session).

**D7. A gate keeps it that way.** a new gate, `ci-bws-pr-path`, to be written and registered as a `check:` script (logic `.ci/rediacc_ci/quality/bws_pr_path.py`, reusing `check_bws_map.parse_requests`) reads `.ci/config/bws-pr-path.json`, which classes every store name `pr-safe` or `release-only` with a `BLOCKER:`-style reason for each `release-only` entry, and refuses: (i) a `release-only` name requested by any step of a job reachable on `pull_request`, following ci.yml callers into reusable workflows and honouring `if:` guards on `github.event_name` and on the new `signing` input; (ii) a store name missing from the class file; (iii) `id-token: write` on a job reachable on `pull_request`. It joins `quality-security`.

**Out of scope.** Step-scoping the rest of the secret class (GITHUB_APP_PRIVATE_KEY and others) stays with PLAN-scope-bws-signing-key-to-consuming-step.md S8's follow-up item #a3910bfd.

## Risks

- A throwaway signing key on PR runs means a PR channel's packages are signed by a key nobody else trusts. That is the point, but anything that pins the production fingerprint against a PR channel would break; Context 5 shows install validation does not. W3's pytest pins the refusal of a mixed pair so the fingerprint check cannot be weakened to make it pass.
- D5's residual: account-level Workers and D1 write cannot be prefix-scoped by Cloudflare, so a PR job can still touch production Workers until D6 removes the broad token from the PR path entirely. W2's gate makes that residual visible as long as it exists.
- D6 moves release jobs into an environment. `.github/workflows/ci.yml:1529-1540` records why the preview job carries no `environment:` (it creates deployment objects); the `release` environment is one fixed object, not one per PR, so that cost does not recur, but every release job's needs graph changes in one commit.
- Splitting `stage-artifacts` (D2) touches every job that `needs:` it; a missed consumer would skip silently. W4's acceptance includes the workflow invariants gate for that reason.
