## Rulings (operator, ASKED:2026-11-16T08:44Z, verbatim)
> 1. Keep the post-login Terms gate (TermsGate / requireCurrentTerms); no signup-form checkbox.
> 2. Split the consent notice into DEFAULT and US variants. DEFAULT checkbox label: "I agree to the Terms of Service and have read the Privacy Policy." US: the same checkbox plus a separate notice line directly below it, always visible (not collapsed, not a tooltip), readable size and contrast, linked to the checkbox with aria-describedby: "For users in the United States: disputes are resolved through individual binding arbitration instead of court, and class actions are waived. See Section 26 of the Terms for details{{OPT_OUT_SENTENCE}}." with an optional opt-out sentence controlled by config (Terms 26.6 has a 30-day opt-out). These strings are legal placeholders in the existing legal i18n pipeline (legal.consent.* in packages/www/src/i18n/translations/en.json ~10539, compiled by scripts/gen/gen-legal.ts into packages/shared/src/legal/consent.generated.ts, hand-translated per docs/i18n/CONVENTIONS.md, guarded by check:ci-terms-version); no new legal wording beyond these.
> 3. The US decision comes from the account Worker reading request.cf.country (Cloudflare) on GET /portal/terms and at POST /portal/terms/accept; unknown/missing/XX/T1 counts as US (fail-safe). The server re-resolves the variant at accept time and never trusts a client-sent variant. Expose the resolved variant in the GET /portal/terms status payload.
> 4. The acceptance record (terms_acceptances, private/account/drizzle/0083_terms_acceptances.sql) adds: displayed variant (DEFAULT|US), resolved country, and its source (geo|fallback; keep user_selected out since there is no selector), and the Privacy Policy version shown (already versioned in .ci/config/legal-documents.json / packages/shared/src/legal/documents.generated.ts). New migration after 0088.

## Design 1: the strings (ruling 2)
- `legal.consent.webCheckbox` becomes the DEFAULT label, the ruled sentence with the two document names as links in the catalog's existing HTML form: `I agree to the <a href="{{termsUrl}}">Terms of Service</a> and have read the <a href="{{privacyUrl}}">Privacy Policy</a>.` `{{legalName}}` and the arbitration sentence leave this key.
- A new key `legal.consent.webUsNotice` holds the ruled US line, with "Section 26 of the Terms" linked to `{{termsUrl}}#us-arbitration` and the `{{OPT_OUT_SENTENCE}}` token kept where the ruling puts it, before the final period.
- `cliPrompt`, `cliRefusal` and `stripeCheckout` are unchanged (Design 4 says why).
- **The opt-out sentence is config, read at build time.** `.ci/config/legal-documents.json` gains `consent: {usOptOut: false}`. gen-legal substitutes `{{OPT_OUT_SENTENCE}}` with the empty string while it is false, and with a leading separator plus `legal.consent.usOptOutSentence` while it is true. The setting is build-time because the stored notice text and its sha256 come from the generated module; a runtime switch would record a text no gate has seen. No wording for `usOptOutSentence` exists in the rulings, so the key is absent and `usOptOut` stays false until the operator supplies it (O1).
- **Canonical text.** The stored and hashed notice is the `toText` render of the catalog string (links as `text <url>`), the form the archived documents already use, so the row keeps the exact URLs shown. The US web notice stored is the label render, a newline, then the US line render.
- The 12 other locales are hand-naturalized (docs/i18n/CONVENTIONS.md section 2, as PLAN-terms-acceptance L3a-L3c did), with the same tokens and the same link targets as English.

## Design 2: the pipeline and the gate
- `CONSENT_KEYS` stays the per-method map; a second map names the variant-only key (`webUsNotice`). `consent.generated.ts` gains, per locale: `CONSENT_WEB_US_NOTICE` (the canonical US line), and `CONSENT_MARKUP` (the label and the US line with their `<a>` tags kept, for the portal), plus the sha256 of the stored US web text.
- `packages/shared/src/legal/types.ts` adds `CONSENT_VARIANTS = ['DEFAULT', 'US']` and `ConsentVariant`. `index.ts` adds `consentNoticeFor(method, locale, variant) -> {text, sha256}`: for `web-checkbox` and `US` it is the joined text of Design 1; for every other pair it is today's `consentNotice`. `privacyVersionAt(now)` returns `termsAt(now, documentVersions('privacy-policy')).current.version`.
- `check:ci-terms-version` grows four findings, each with a selftest control that turns it red:
  1. a locale lacks `webUsNotice`, or carries a token set or an `<a href>` target set different from English;
  2. `usOptOut` is true while any locale lacks a non-empty `usOptOutSentence`;
  3. the English title of `pages.termsOfService.sections.usArbitration` does not begin with `26.`, or its id is not `us-arbitration` (the notice names the section by number and anchor);
  4. the generated module's US entries differ from their render (the existing check 3 extended).

## Design 3: resolving the variant (ruling 3)
- **One resolver**, `private/account/src/utils/consent-region.ts`: `resolveConsentRegion(c) -> {variant, country, source}`.
  - `country` is `c.req.raw.cf?.country` when it is a two-letter upper-case string, else null.
  - `US` with source `geo` when the country is `US`; `DEFAULT` with source `geo` for any other real country; `US` with source `fallback` when the value is missing, malformed, `XX` or `T1`. The `XX` and `T1` values are kept in `country` as the evidence of why the fallback ran.
  - US territories that Cloudflare reports under their own codes (PR, GU, VI, AS, MP, UM) count as `US`, source `geo` (O2).
  - **Test seam:** only when `envConfig.testMode` is true, the header `x-rediacc-test-country` replaces `cf.country` (the value `none` simulates a missing one). Deployed Workers pin TEST_MODE false (Context 9), so the header is inert there, and a Node runtime without TEST_MODE resolves every request to `US`/`fallback`.
  - A request over the service binding has no `cf`, so it resolves to `US`/`fallback`; that is the fail-safe direction and needs no special case.
- **Payload.** `toStatusBody` adds `consentVariant: 'DEFAULT' | 'US'` from the resolver, so `GET /portal/terms` exposes it, and `GET /terms/status` carries it too because both share the function. `termsStatusResponse` and the portal's `TermsStatus` (private/account/web/src/api/endpoints.ts:116-125) gain the field. Country and source are not sent to the client.
- **Accept.** `POST /portal/terms/accept` resolves again and passes the result into `prepare`. The body never names a variant; a `variant` key is stripped by the schema and ignored, and a test proves that a US request sending `variant: 'DEFAULT'` stores `US`.
- **A changed resolution between GET and POST** (a VPN switched in between) would record a notice the user did not see. For `web-checkbox` the body therefore carries `shownNoticeSha256`, the generated sha256 of the notice the card rendered. When it differs from the sha256 of the server-resolved notice, the server answers 409 `TERMS_NOTICE_CHANGED` and stores nothing; the card reloads the status and shows the right variant. The hash is a check on the display, never an input to the variant: the server still records only what it resolved.

## Design 4: the record (ruling 4) and the other consent paths
- **Migration 0089** (`0089_terms_consent_variant.sql`) adds four nullable columns: `consent_variant` (`DEFAULT` | `US`), `resolved_country`, `country_source` (`geo` | `fallback`) and `privacy_version`. Rows written before 0089 keep NULL; the table is append-only (0083 header), so they are not rewritten. Every row written after it carries `consent_variant` and `privacy_version`, which the service sets and a test asserts.
- **`prepare`** takes the resolved region and returns the variant, the canonical text for `(method, locale, variant)` from `consentNoticeFor`, and `privacyVersionAt(now)`. **`row`** writes the four columns. **`insertIfStatement`** lists them in its positional `SELECT` (Context 5).
- **Account rows** (`web-checkbox`, `stripe-checkout`) store all four.
- **Free-machine rows** store `consent_variant` and `privacy_version`, with `resolved_country` and `country_source` NULL: PLAN-free-license R7 and the published privacy text promise no network data for a Free License (Context 11). The variant is still resolved from the CLI's request (O3).
- **CLI.** `cliPrompt` and `cliRefusal` already state the US arbitration and class waiver to every reader (Context 2), so the CLI shows one notice whatever the variant, and `packages/cli` does not change. `POST /licenses/free` resolves the region from the CLI's own request, so the row says which regime the server judged to apply; the stored text is the single CLI notice. An on-premise server relays FREE upstream, so the upstream sees the relay's geography; the gate is off on-premise (PLAN-terms-acceptance O7), and the relay row is still fail-safe at worst.
- **Stripe.** `stripeCheckout` carries the US sentence for every reader, so Stripe's message is unchanged. The region is resolved when the portal creates the Checkout Session (the user's request), and written into the session metadata as `termsVariant`, `termsCountry` and `termsCountrySource`, beside the `userId` the server already writes there. `recordCheckoutTermsConsent` reads them back; a session without them (created before this lands) records `US`/`fallback`. The webhook's own `cf` (Stripe's) is never read.

## Design 5: the consent card (ruling 2)
- The label renders `CONSENT_MARKUP[locale].webCheckbox`: the `<a>` tags become links (underlined, link colour, new tab), everything else is text. Only `href` values equal to the locale's terms or privacy URL (with the `#us-arbitration` anchor) are honoured; any other tag renders as its text.
- With `status.consentVariant === 'US'` a paragraph with id `terms-consent-us-notice` sits directly under the checkbox row, always rendered (no disclosure widget, no tooltip), at `text-sm` in the foreground colour rather than the muted one, and the checkbox carries `aria-describedby="terms-consent-us-notice"`. With `DEFAULT` neither the paragraph nor the attribute exists.
- On a narrow screen the notice wraps under the label at full card width, with no truncation and no horizontal scroll; the checkbox keeps its `shrink-0` column (private/account/web/src/components/legal/TermsConsent.tsx:87).
- Accept sends `{version, sha256, locale, method: 'web-checkbox', shownNoticeSha256}`; a 409 `TERMS_NOTICE_CHANGED` reloads the status.
