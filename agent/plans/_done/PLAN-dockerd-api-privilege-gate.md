## The finding

Verified live, ops-worker, 2026-10-23 (renet 0c3a88a plus the uncommitted `/etc` mask of c7dd6c1). Repo A's per-repo dockerd accepted a container-create request carrying `Privileged:true` and `PidMode:"host"` through `${DOCKER_SOCKET}` (`runpaths.DockerSocket(N)`, private/renet/pkg/runpaths/runpaths.go:61). A privileged container runs in the host user namespace with `CAP_SYS_ADMIN`, so `/proc/1/root` is the host root; from there it reached repo B's daemon socket at `/proc/1/root/run/rediacc/net-8576/docker-8576.sock` and listed `/proc/1/root/etc/rediacc`.

Two gaps make this one class of hole, not two:

1. **The compose validator is the only gate, and it only sees compose files.** `collectServiceErrors` refuses `privileged` (private/renet/pkg/compose/validate.go:160-165), `pid: host` (:170-173) and `ipc: host` (:176-181); `validateHostRuntimeBinds` refuses cross-repo and host-runtime binds (:331-357). None of it is in the Docker API path. A container that holds `${DOCKER_SOCKET}` (the supported Traefik/certs-dumper/nextcloud-aio bind, packages/json/templates/platforms/nextcloud-aio/docker-compose.yaml:11) speaks the raw API and never meets `ValidateComposeData` (private/renet/pkg/compose/validate.go:406).
2. **Privileged turns the D2 narrowing into a formality.** Once a container is privileged, `/proc/1/root` is the host mount namespace, so the per-network directory split (D2) and every bind refusal are bypassed. This is exactly the escape path `private/renet/docs/DOCKERD_SANDBOX.md` known limitation 1 (:188-218) names for a compromised root daemon, reached here by a legitimate repo on request rather than by a CVE.

## Design

### D1. Option comparison, with evidence

**Option A — a Docker authorization (authz) plugin.** `private/renet/docs/DOCKERD_SANDBOX.md:43-45` rejects authz plugins because "they only protect dockerd's HTTP API. They can be bypassed by going directly to containerd's socket or by invoking runc directly."
D2 of the dependency plan *partly* changes the first half: after D2 the sandbox binds only `runpaths.NetDir(N)` (private/renet/cmd/renet/daemon_containerd_exec.go:190), so the only daemon socket in a container's reach through `${DOCKER_SOCKET}` is its own dockerd. It does **not** change the second half: `net-<N>` still contains `containerd-<N>.sock` (private/renet/pkg/runpaths/runpaths.go:79), so a bind of that socket through the API still reaches containerd under any dockerd-only gate, and a privileged container still reaches runc/host-root.
An authz plugin also runs as a separate daemon process dockerd dials over `/run/docker/plugins` (private/renet/pkg/daemon/daemon.go:16); renet already ships `go-plugins-helpers` handlers for IPAM and network drivers (private/renet/cmd/renet/main.go:20-21, :638-639), so the mechanism is familiar, but it adds a dockerd config dependency (`--authorization-plugin`) and a round-trip per API call while leaving the containerd-socket and runc paths open.
**Rejected as the primary gate.**

**Option B — an in-renet socket proxy in front of each repo's dockerd (recommended).** dockerd listens on a private internal socket inside `net-<N>`; a small renet-owned proxy listens on the public `runpaths.DockerSocket(N)` path that `${DOCKER_SOCKET}`, the CLI and renet itself already target (private/renet/cmd/renet/docker_command.go:13-26, private/renet/pkg/ps/ps.go:175-176). The proxy forwards transparently and, for the container-affecting endpoints only (`POST /containers/create`, `POST /containers/{id}/update`, `POST /exec/{id}/start` via the create body, `POST /build`), decodes `HostConfig` and refuses a request whose fields fall outside the policy. This closes the API path the breach used *and* the containerd-socket bypass Option A leaves open, because the policy's bind check refuses a container that binds `containerd-<N>.sock` or any cross-repo/host path the same way the compose validator does (private/renet/pkg/compose/validate.go:331-357). It is portable (pure Go over a unix socket, no AppArmor/SELinux profile), unlike the daemon-native options, which `private/renet/docs/DOCKERD_SANDBOX.md:38-42` rejects for portability. It shares one policy source with the compose validator (D3).

**Option C — dockerd daemon options.** `no-new-privileges`, the default seccomp and AppArmor profiles, and `userns-remap` are all *overridden* by `Privileged:true`, so none of them stops the breach; they are kept only as defence in depth. `userns-remap` and rootless dockerd both break renet's model directly: CRIU sets `userns_mode: host` (private/renet/pkg/compose/wrapper.go:408) and the daemon pins `default-cgroupns-mode: host` (private/renet/pkg/daemon/systemd.go:570), and `private/renet/docs/DOCKERD_SANDBOX.md:210-212` already records that user-namespace isolation "breaks several assumptions in the current renet architecture." **Rejected.** The one daemon-side change this plan does make is to move dockerd's listening socket to an internal path so the proxy can own the public one (D4).

**Legitimate workloads that need elevated-but-bounded privilege (surveyed, so the policy is an envelope, not a blanket deny).** renet's own model already runs every service with host networking (`network_mode: host`, private/renet/pkg/compose/wrapper.go:181), host cgroupns (private/renet/pkg/daemon/systemd.go:570) and a per-service `cgroup_parent` (private/renet/pkg/compose/wrapper.go:192) — these are the isolation mechanism (eBPF at `rediacc.slice`, private/renet/pkg/ebpf/socket_isolation.c:85-240), not a privilege to deny. Opt-in elevated needs are narrow and already enumerated by the compose wrapper: CRIU checkpoint/restore adds exactly `CHECKPOINT_RESTORE`, `SYS_PTRACE`, `NET_ADMIN`, `security_opt: apparmor=unconfined` and `userns_mode: host` (private/renet/pkg/compose/wrapper.go:380, :398, :408); WireGuard adds `NET_ADMIN` and the device `/dev/net/tun` (private/renet/pkg/compose/wrapper.go:439-449); docker-mailserver asks for `NET_ADMIN` (packages/json/templates/messaging/docker-mailserver/docker-compose.yaml:17-18). The Session Hub explicitly advertises "no privileged containers or Docker-in-Docker" (packages/www/src/content/docs/en/hub.md:163). No tutorial, solution template or `.ci` drill under `.ci/tutorials` or `packages/json/templates` uses `privileged: true`, `pid: host`, k3s/kube-in-repo or buildx-in-container (grep of `--include=*.yml --include=*.yaml --include=Rediaccfile` returned only the socket bind and `NET_ADMIN` above; buildx runs as a compose `--build` with `BUILDX_CONFIG` under the repo mount, private/renet/pkg/compose/exec.go:331, not a privileged container). So the policy allows exactly the set the compose wrapper injects and denies everything beyond it — which is why D3 makes both read one source.

**How renet and the CLI keep working.** renet drives dockerd two ways: the `docker` CLI with `DOCKER_HOST` set to `runpaths.DockerHost(N)` (private/renet/cmd/renet/docker_command.go:19-26) and the Go client dialing the unix socket (private/renet/pkg/ps/ps.go:175-176, private/renet/pkg/daemon/ips.go:95-96, private/renet/pkg/hub/containers.go:119-120). Both point at the public socket the proxy will own. renet never sends `Privileged:true`; its only elevated creates are the compose path's CRIU/WireGuard sets, which the policy allows. The proxy must pass through connection hijacking (exec, attach, logs -f, build stream) byte-for-byte; a plain HTTP reverse proxy would break hijack, so the proxy inspects only the request line, headers and body of the gated POSTs and otherwise splices the two connections (D5).

### D2. The policy: one envelope, two tiers, shared with the compose validator

A new leaf package `private/renet/pkg/dockerpolicy` (standard library plus the `docker/api/types/container` structs renet already vendors, private/renet/go.mod:8) exposes `Decision Evaluate(hc *container.HostConfig, cfg *container.Config, netID int, opt OperatorOpt)`. Two tiers, matching the compose validator's existing split between soft (`--unsafe`-overridable) and hard (never-overridable) errors (private/renet/pkg/compose/validate.go:450-486):

**Hard-deny (never overridable, mirrors `hardErrors`/`hostErrors`):**
- any `Binds`/`Mounts` source that resolves into another network's `net-<M>`, the legacy shared tree, a host daemon socket (`docker.sock`, `containerd.sock`, including this network's `containerd-<N>.sock`), or `/proc`, `/sys`, `/dev` outside the allowed device set, reusing the exact canonicalisation and refusal of `validateHostRuntimeBinds`/`checkVolumeHostPath` (private/renet/pkg/compose/validate.go:331-395);
- `CapAdd` containing `SYS_ADMIN`, `ALL`, or any capability outside the allow-set `{CHECKPOINT_RESTORE, SYS_PTRACE, NET_ADMIN}`;
- `SecurityOpt` containing `seccomp=unconfined` or `apparmor=unconfined` **except** the single value `apparmor=unconfined` which CRIU requires (private/renet/pkg/compose/wrapper.go:392, :398) — matched exactly, no `label=...:unconfined` smuggling;
- `Devices` outside `{/dev/net/tun}` (private/renet/pkg/compose/wrapper.go:444).

**Soft-deny (denied unless the per-repo operator opt-in is set; the API analog of `--unsafe`):**
- `Privileged:true`;
- `PidMode == "host"`, `IpcMode == "host"`, `UTSMode == "host"`.

**Explicitly allowed (the renet model):** `NetworkMode == "host"`, `UsernsMode == "host"`, `CgroupnsMode == "host"`, `CgroupParent` under `/rediacc.slice/rediacc-<N>/`. These are allowed unconditionally because they are how renet isolates, not how a container escapes (private/renet/pkg/daemon/systemd.go:569-570, private/renet/pkg/compose/wrapper.go:181, :192). A deny of `NetworkMode:host` would break every repo; this is why the prompt's "filter NetworkMode=host" item is resolved as *allow*, with the reason recorded here.

`OperatorOpt` carries whether the repo has an operator-granted privileged opt-in (D6). The hard-deny tier ignores it; the soft-deny tier is relaxed by it. This keeps the operator-vs-operator threat model the compose validator already states (private/renet/pkg/compose/validate.go:401-405): a compose author (or a container) cannot grant itself cross-repo reach by any flag, but a true privileged workload is possible with an explicit, auditable operator grant.

### D3. One policy source for both the API path and the compose file path

The compose validator's three per-service checks (`collectServiceErrors` for privileged/pid/ipc at private/renet/pkg/compose/validate.go:157-181, `validateHostRuntimeBinds` at :331-357, `checkVolumeHostPath` at :366-395) are re-expressed as calls into `dockerpolicy`: the validator maps a parsed `ServiceConfig` into the same `container.HostConfig`/`Config` fields and calls `Evaluate`, so a rule exists once. The compose wrapper's injected sets (private/renet/pkg/compose/wrapper.go:380, :398, :408, :444) become references to `dockerpolicy`'s allow-set constants, so the gate and the injector cannot drift: if a future cap is added to CRIU's needs, it is added in one place and both the wrapper and the proxy accept it. T3 pins this with a test that the wrapper's injected caps are a subset of `dockerpolicy.AllowedCaps`.

### D4. Where the gate lives and how dockerd is reconfigured

- dockerd's `hosts` moves from the public socket to a private internal socket inside the same directory, `runpaths.DockerInternalSocket(N)` = `net-<N>/docker-<N>-internal.sock` (new helper in private/renet/pkg/runpaths/runpaths.go beside `DockerSocket`, :61). The daemon.json template and generator change their `hosts` entry (private/renet/daemon-setup/daemon.json.template:5, private/renet/pkg/daemon/systemd.go:554). The public `runpaths.DockerSocket(N)` is now the proxy's listen path, unchanged for every consumer.
- the proxy is a new hidden subcommand `renet daemon dockerproxy-exec --network-id=N`, spawned as a **third supervised sibling** by `StartForeground` after dockerd's internal socket is ready (private/renet/pkg/daemon/start_foreground.go:183-219), supervised and torn down by `superviseChildren` the same way (private/renet/pkg/daemon/start_foreground.go:228-290). It runs in the host mount namespace (not the sandbox), creates the public socket with the same `0660 root:docker` ownership the socket unit used (private/renet/pkg/daemon/systemd.go:198-205) so the CLI and `${DOCKER_SOCKET}` consumers reach it, and dials the internal socket.
- `removeStaleRuntimeFiles` also removes the internal socket on restart (private/renet/pkg/daemon/start_foreground.go:321-327).

**Failure mode:** if the proxy dies, the public socket is gone and both renet and containers lose the daemon — so it is `Restart=always` by virtue of being a `StartForeground` child under the existing systemd unit (private/renet/pkg/daemon/systemd.go:168-176); dockerd keeps running on the internal socket and reconnects when the proxy restarts. The proxy is stateless, so a bounce loses only in-flight requests.

### D5. The proxy mechanics (the load-bearing implementation detail)

For every connection: read the HTTP request line and headers. If the method+path is not one of the gated POSTs, splice both directions and return (this covers hijacked exec/attach/logs/build streams unchanged). If it is a gated POST, buffer the body up to a cap, decode into `container.HostConfig`/`Config`, call `dockerpolicy.Evaluate`. On deny, write `403 Forbidden` with a JSON `{"message": "..."}` body naming the refused field and the `${DOCKER_SOCKET}`/opt-in remedy (so `docker run` prints a clear reason, not a hang), and close. On allow, replay the buffered head+body to the internal socket and splice the rest. `POST /build` is gated because a build's `RUN --security=insecure`/privileged stages flow through it; the policy rejects a build request carrying a privileged security mode while allowing the normal `network host` build renet injects (private/renet/pkg/compose/wrapper.go:92, :101). Chunked and `Content-Length` bodies are both handled; a body over the cap with a gated path is refused closed rather than streamed ungated.

### D6. Per-repo operator opt-in

The soft-deny tier is relaxed only by an explicit operator grant stored in the repo's own config (read by renet at daemon start, threaded into `ForegroundConfig` and on to the proxy), surfaced as a repo-level setting — never by anything the container or the compose file can set, and never by `renet compose --unsafe` (which stays a compose-file-only, soft-error override, private/renet/cmd/renet/main.go:234, :1191-1193). A repo with the grant set logs one line at daemon start ("privileged container API enabled for network N by operator grant") so the posture is visible in `journalctl -u rediacc-docker-<N>`. The hard-deny tier (cross-repo reach) is never relaxed, by anyone — this is the operator-vs-operator boundary D2 preserves.

### D7. Errors surface to users as a Docker 403

Because the gate is a real Docker API response, `docker run --privileged` prints `docker: Error response from daemon: privileged mode is refused on this repository's Docker daemon; ask the operator to grant it, or drop --privileged` and exits non-zero, identical in shape to any daemon rejection. The compose path keeps its existing validator messages (private/renet/pkg/compose/validate.go:160-181), now sourced from the same strings.

## Migration and compatibility

- **One policy source** (D3): the compose validator and the proxy both call `dockerpolicy.Evaluate`; the compose wrapper's injected privileges reference the same allow-set constants. No dual list.
- **No dual socket paths for consumers.** Every existing consumer keeps using `runpaths.DockerSocket(N)`; only dockerd's own `hosts` moves to the internal path. Clean break, no fallback (CLAUDE.md session rule: no compatibility theater).
- **First restart** picks up the change exactly as the dependency plan's D5 does: `start-foreground` rewrites daemon.json on every start (private/renet/pkg/daemon/start_foreground.go:378-383 region) and the socket/service unit text changes, so a running daemon restarts once and the proxy appears. Containers reconnect through the public socket at the same path.

## Revision after review 031d303c (2026-10-23, supersedes D2's soft tier and D6)

Per-commit review of private/renet 031d303 raised two highs. `Privileged` with the D6 operator grant hands the container every host device, no seccomp or AppArmor, no masked paths and host root through `/proc/1/root`, so the grant voids the hard tier and the "cross-repo reach is never relaxed" promise; `PidMode=host` with the allowed `SYS_PTRACE` cap reaches `/proc/1/root` the same way. And `Resources.DeviceRequests` (GPU/CDI) was never inspected. The lead's decision: `Privileged` and host `pid`/`ipc`/`uts` join the HARD tier, the D6 grant no longer relaxes them, and any non-empty `DeviceRequests` is a hard denial. No surveyed workload needs them (D1). The soft tier keeps only the compose validator's `--unsafe` bind paths after an audit for cross-repo reach (worklist #500debc0). T4's "opt-in flips Privileged from 403 to pass" is therefore void: T4 delivers only what still sits in the soft tier, plus the Session Hub delegation of Finding 1.

## Findings from T1 (2026-10-23, private/renet 031d303)

These bind T2-T4; each box's writer reads this section with its box.

1. The Session Hub binds a per-user Docker socket into its own container (`private/renet/pkg/hub/containers.go:797`, socket from `provisionUserDaemon` at `private/renet/pkg/hub/containers.go:251`). That socket belongs to another network id, so the hard tier refuses it as a cross-network bind and the proxy would 403 the hub's own create. T2/T4 need an explicit delegation (an operator-granted list of networks a repo may bind), never a relaxation of the hard tier.
2. Named volumes bypass a create-only gate: `POST /volumes/create` with the local driver and `o=bind,device=/` makes a named volume aimed at a host path, and a later create that uses it by name passes. T2 also gates `POST /volumes/create`, running `dockerpolicy.ClassifyBindSource` on the `device` option.
3. `Evaluate` is pure, so a symlink inside the repo mount aimed into `/run/...` is invisible to it; the per-network sandbox narrowing of PLAN-renet-cross-repo-isolation stays the backstop for that case.
4. T1 already narrowed `runpaths.DockerSocketGlob` to `net-*/docker-*[0-9].sock` so discovery never picks up `DockerInternalSocket` once T3 moves dockerd.
5. Own-mount rule (review fix private/renet 5546219): `Evaluate` does not know the requesting repo's own mount, so a bind of another repo's `/mnt/rediacc/mounts/<guid>/...` (per-repo Docker data, `private/renet/pkg/repository/repository.go:101`) still passes, and so do host paths outside the protected lists (`/srv`, `/home/*/.ssh` read-only). T2/T4 pass the repo mount and datastore into the policy and the bind rule becomes: own mount, named volumes, own socket and secrets, and safe mounts only.

## Risks

- The proxy is on the hot path for every Docker API call a repo makes; a splice bug would break exec/attach/logs/build streaming. T2's hijack test and T6's live build/exec on ops-worker are the gate.
- A future Docker API field that grants host reach (a new `HostConfig` member) would pass an allow-set the gate did not anticipate. The bind/cap/device checks are allow-lists (deny by default) precisely to limit this; the namespace fields are an explicit allow-list too. A new field defaults to pass-through only if it is not in `HostConfig`'s security-relevant set — T1's test enumerates the set, and a Docker bump that adds one is a finding to re-run T1 against.
- If dockerd ever needs its public socket for a feature that bypasses the proxy, the internal-socket move would hide it; none found in the current consumers (all dial `runpaths.DockerSocket(N)`), but T6's matrix is the check.
