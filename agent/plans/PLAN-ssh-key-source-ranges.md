## Problem

- Hosted executor containers cannot reach hostinger (72.61.137.225) over IPv4. The CLI's IPv6 retry (fafbb7b60, `infra.publicIPv6`) does reach sshd, from 2a09:bac1:5540:28::3e4:28 and 2a09:bac5:4e3e:270f::3e4:28.
- sshd refuses them: line 15 of /home/muhammed/.ssh/authorized_keys carries the probe key `rediacc-live-console-probe-2026-10-26` with `from="104.28.0.0/16",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty,no-user-rc`. The line was written by hand; PLAN-console-executor-multi-org round 4 (agent/plans/PLAN-console-executor-multi-org.md:355) records the hand install and a `sed` revoke.

**How a key reaches authorized_keys today.**
- The hosted executor authenticates with the config's own key, `credentials.ssh.privateKey` (packages/shared/src/config-schema/schemas.ts:505-513), through `machineConnections.acquire` (packages/cli/src/services/machine/machine-connection.ts:137-147; packages/cli/src/services/executor/local-executor.ts:437-439). The probe orgs' configs hold the probe key there.
- No rdc verb installs a config's key on a machine: `machine add` writes config and pins host keys only (packages/cli/src/commands/machine/register.ts:120-164); `machine setup` runs `renet setup` then `postSetupMachineTasks`, which re-deploys repo keys only (register.ts:21-33, :269-350); `machine provision` hands the public key to the cloud provider for new VMs only (packages/cli/src/services/tofu/cluster-tf-generator.ts:80-95).
- renet's `ConnectionManager.DeployPublicKey` (private/renet/pkg/ssh/keys.go:25-30, :177-183) has no callers.
- Today an executor or probe key reaches a machine only by hand.

**Option writers today.** The only code that writes authorized_keys options is the per-repo key path, `command="<renet> sandbox-gateway ..." <key>` (packages/cli/src/services/repo/repo-key-deployment.ts:56), replacing by the key's first 50 characters (:57, :66) and removing by marker (:136-141); `machine setup` re-runs it (register.ts:24). Nothing writes `from=` or `restrict`.

**Where settings live.** Per machine, `resources.machines.<name>` (schemas.ts:338-347, `infra` at :319-331); config-wide, `account`, `defaults`, `credentials`, top-level `infra` and `policy` (:485-537, :590). The v3 root is `.loose()`, nested objects are plain `z.object` and drop unknown keys (:562-566, :592).

**The ranges.** Cloudflare publishes no container egress range (research 2026-10-28: the Containers docs name none; the Workers TCP-sockets page says outbound TCP is "sourced from a prefix that is not part of list of IP ranges"). 104.28.0.0/16 lies in ARIN CLOUDFLARENET 104.16.0.0/12, outside https://www.cloudflare.com/ips-v4. 2a09:bac0::/29 is the RIPE parent of the CLOUDFLAREWARP /32 nets; both observed IPv6 sources fall inside it. Observed in use: 104.28.154.80, 104.28.163.155, 104.28.163.183, 104.28.156.1, 2a09:bac1:5540:28::3e4:28, 2a09:bac5:4e3e:270f::3e4:28. The ranges are shared Cloudflare egress, so `from=` narrows a key to Cloudflare's network; the key stays the authentication.

## Design

1. **Config shape: one top-level `access` bucket (packages/shared).**
   ```jsonc
   "access": {
     "sourceRanges": { "ipv4": ["104.28.0.0/16"], "ipv6": ["2a09:bac0::/29"] },
     "keys": {
       "console-probe": {
         "publicKey": "ssh-ed25519 AAAA... rediacc-live-console-probe-2026-10-26",
         "restrict": true,
         "sourceRanges": { "ipv4": [...], "ipv6": [...] },
         "machines": {
           "hostinger": true,
           "edge-box": { "sourceRanges": { "ipv6": ["2a09:bac0::/29"] } }
         }
       }
     }
   }
   ```
   - Top-level, because the root is `.loose()`: an older CLI that rewrites the config keeps `access` whole, while a field under `resources.machines.*` would be stripped.
   - Resolution for a (key, machine) pair: `keys[k].machines[m].sourceRanges` ?? `keys[k].sourceRanges` ?? `access.sourceRanges`; each level replaces the one below whole. An empty resolution is refused by the schema: an access key with no range is unrestricted, and an unrestricted key belongs in `credentials.ssh`.
   - `SourceRangesSchema` is `{ ipv4?: Cidr4[], ipv6?: Cidr6[] }`, at least one entry across both, at most 32 per list. Each entry: `z.cidrv4()`/`z.cidrv6()` format; the right family for its list; prefix length above 0; host bits zero (sshd matches nothing on a CIDR with host bits set; the error names the canonical form, e.g. `104.28.1.0/16 is not a network address; use 104.28.0.0/16`); no duplicates after canonicalisation.
   - `AccessKeySchema.publicKey` is one OpenSSH public key line of type ssh-ed25519, ssh-rsa, ecdsa-sha2-nistp256/384/521, sk-ssh-ed25519@openssh.com or sk-ecdsa-sha2-nistp256@openssh.com; the base64 blob decodes (with `atob`, keeping the module portable, schemas.ts:28-41) and its inner type equals the stated type; the optional comment must not contain the marker token. Two keys with the same blob are refused; key and machine names use `resourceName` (schemas.ts:85-92).
   - Sensitivity: `'/access': { kind: 'identifier' }` for the whole subtree, as `'/policy'` (packages/shared/src/config-schema/sensitivity.ts:91), so a push that rewrites who may log in is field-committed. `npm run check:ci-schema-coverage` stays green.
   - `'access'` joins `CONFIG_KEY_ORDER_V3` after `'resources'` (schemas.ts:710-723).
   - `HOSTED_EXECUTOR_SOURCE_RANGES = { ipv4: ['104.28.0.0/16'], ipv6: ['2a09:bac0::/29'] }` in packages/shared/src/config/network.ts, its comment naming the RDAP owners and saying the ranges are observed, not published. It is only a seed: `--hosted-executor` copies the values into the config; no code reads it while resolving.
   - packages/shared/src/validation/cidr.ts: `parseCidr`, `canonicalCidr`, `cidrContains(cidr, address)`, BigInt for IPv6, never `node:net`; exported through validation/index.ts.

2. **Rendering and rewriting: a pure module (packages/cli/src/services/machine/authorized-keys.ts).**
   - `parseAuthorizedKeys(text)` returns one entry per physical line: raw bytes, line ending, kind (`blank` | `comment` | `key` | `unparsed`), options, type, blob, comment, marker. Options are tokenised quote-aware, so `command="... x y"` and `from="a,b"` stay single tokens.
   - `renderAccessLine({ configId, name, key, ranges, restrict })` gives `from="<ipv4...>,<ipv6...>"[,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty,no-user-rc] <type> <blob>[ <comment>] rdc-access:<configId[0:8]>:<name>`. IPv4 first, then IPv6, each in declared order. The restriction set is the one that passed live in round 4 (the CLI's ssh2 client uses no pty and no forwarding). `restrict: false` keeps `from=` alone, for a team key `rdc term` also uses.
   - The marker is the last token of the comment field; its config-id prefix scopes management, so two configs managing one machine never touch each other's lines.
   - `planAccessRewrite(parsed, desired[], configId)` returns `{ text, changes[] }`: a marked line still desired is rewritten in place (`update`) or recorded `unchanged`; a desired key with no marked line adopts the first unmarked line with the same blob in place (`adopt`) and removes every further line with that blob (`drop-duplicate`), since sshd tries each matching line and an unrestricted duplicate would bypass `from=`; a same-blob line carrying `command=` refuses with `ACCESS_KEY_CONFLICT`; a desired key with no line is appended (`append`); a marked line no longer desired is removed (`remove`). Every other line keeps its bytes and line ending; a file without a final newline gets one only when a line is appended. Planning its own output gives the same bytes and only `unchanged`.

3. **Applying over SSH (packages/cli/src/services/machine/access-push.ts).**
   - `pushAccess(machineName, { dryRun })` resolves the desired lines, opens a lease with `machineConnections.acquire` (machine-connection.ts:137; the IPv6 retry comes with it), resolves `$HOME`, reads `$HOME/.ssh/authorized_keys` over SFTP (missing means empty) and records its SHA-256.
   - Lockout guard: read the client address from `$SSH_CONNECTION`; refuse with `ACCESS_LOCKOUT`, writing nothing, when the session's own public key has the same blob as a desired access key and `cidrContains` puts the address outside that key's ranges for this machine.
   - Write: an unchanged plan writes nothing (`written: false`). Otherwise the new text goes to `$HOME/.ssh/.authorized_keys.rdc-<random>` over SFTP; one exec compares the live file's sha256 with the recorded one and on a match runs `chmod 600` and `mv -f` over authorized_keys (with `mkdir -p` and `chmod 700` on `.ssh`); on a mismatch it deletes the temp file and exits 3, surfacing `ACCESS_FILE_CHANGED` (retryable). File contents never pass through a shell.
   - Report: `{ machine, path, written, changes: [{ key, action, line }] }`. The path is `~/.ssh/authorized_keys` of `machine.user`, as repo-key-deployment.ts:62 assumes.

4. **Verbs.**
   - Config side, through `updateSyncedConfig` (packages/cli/src/services/config/synced-write.ts:50-60): `rdc config access add <key> --public-key <line|path> [--hosted-executor] [--ipv4 <cidr,...>] [--ipv6 <cidr,...>] [--no-restrict]`; `rdc config access remove <key>`; `rdc config access ranges [--ipv4 ...] [--ipv6 ...] [--hosted-executor] [--clear]`; `rdc config access list`.
   - Machine side, mirroring `machine infra set|show|push` (packages/cli/src/commands/machine/infra.ts:46-60): `rdc machine access set <machine> --key <key> [--ipv4 ...] [--ipv6 ...] [--clear-ranges]`; `rdc machine access remove <machine> --key <key>`; `rdc machine access show <machine>`; `rdc machine access push <machine> [--dry-run]`.
   - `machine setup` re-applies access: `postSetupMachineTasks` (register.ts:21-46) calls `pushAccess(name)` after the repo keys, non-fatal with a visible warning. `machine remove` drops that machine from every key's `machines`.
   - `machine access push` joins `PROXY_EXCLUSIONS` (packages/cli/scripts/generate-cli-contract.ts:79): an executor never rewrites its own access. The contract is regenerated.
   - `ACCESS_LOCKOUT` and `ACCESS_KEY_CONFLICT` exit 2, not retryable; `ACCESS_FILE_CHANGED` exits 1, retryable; all three join `normalizeError`'s table (packages/cli/src/utils/errors.ts).

5. **Moving the hostinger probe key under management.** The operator's config that manages hostinger declares `console-probe` with `--hosted-executor` and binds it to hostinger. The first push adopts line 15 by blob and rewrites it in place with both ranges and the marker, appending nothing. Revoking becomes `machine access remove hostinger --key console-probe` then a push, replacing the `sed` revoke in PLAN-console-executor-multi-org:355.

6. **Clean break.** Unmarked lines are adopted once; the old trailing-comment revoke stops being documented; no setting is read from anywhere but `access`.

## Alternatives rejected

- A `from=` list on `credentials.ssh`: the team key is also the laptop's key, so restricting it to Cloudflare locks the laptop out. Restricting the team key stays possible as an access key whose `publicKey` is the team key, behind the lockout guard.
- Fields under `resources.machines.<m>`: an older CLI strips them (schemas.ts:338).
- Ranges resolved at runtime from the constant: the operator asked for both families written in the config, and a CLI upgrade would otherwise change a customer's access silently.
- D1 `organizations` or an account-server setting: not portable, and no account-server path reaches machines.
- renet `DeployPublicKey` extended with options: needs a renet release before the first push; the planner belongs where the TypeScript tests run.
- A shell-side rewrite (grep/sed): cannot adopt by blob with quote-aware option parsing, and puts key material through a shell.
- The OpenSSH `restrict` keyword: needs OpenSSH 7.2+ and differs from the explicit list that passed live.

## Risks

- The ranges are observed, not published; Cloudflare may egress from another range. A refusal names the address in sshd's log, and the fix is a config edit and a push, no release.
- The ranges are shared Cloudflare egress: `from=` narrows a key to Cloudflare, not to one tenant; the key stays the authentication.
- A custom `AuthorizedKeysFile` or root-managed keys are not covered; `machine access show` reports the path it read.
- The lockout guard reads `$SSH_CONNECTION`, the address sshd saw, which is the one `from=` checks.
- config-resources.ts is a busy file: A1 is its only writer here, and no other plan's writer may hold it at the same time.
- A remote config pushes a field-committed change; a stale local view is refused and the edit replayed on the fresh copy (synced-write.ts:43-60).
