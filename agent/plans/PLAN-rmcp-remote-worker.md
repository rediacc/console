## Ask

`https://mcp.<region>.rediacc.cloud/g/<grantId>` is an MCP server an agent adds with no install (D1). OAuth clients sign in through the account UI; headless clients send `Authorization: Bearer rmcp_...` (D11). It answers within the client time budgets (D15), tells the agent plainly when the grant expired and where to re-authorize, and behaves exactly like the local stdio server (D18) because both are built from one tool registry and one decide().

## Context (read 2026-11-20 against the tree and the 2026-11-20 research; a writer re-reads each citation before relying on it)

1. **The SDK in the tree is v1.** `packages/cli/package.json:30` pins `@modelcontextprotocol/sdk ^1.31.0`. v1.x will not implement spec 2026-07-28; the v2 packages (`@modelcontextprotocol/server`, `createMcpHandler`) do and run on Workers (agent/programs/remote-mcp/03-external-research.md). PLAN-rmcp-local-mcp.md moves the shared registry to v2 first.
2. **Spec 2026-07-28 is stateless.** No `Mcp-Session-Id`, no GET stream, no `initialize` handshake; each POST carries `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`; servers implement `server/discover` and validate `Origin` (403 on an invalid one). Elicitation runs through MRTR: an `input_required` result with an opaque `requestState` the server must integrity-protect, bind to the user, time-limit and accept once.
3. **Auth profile the clients need.** ChatGPT has no static-key path and claude.ai's static header is a limited beta, so OAuth is required for them: PKCE S256, RFC 9728 metadata with `resource` equal to the URL, a 401 carrying `WWW-Authenticate: Bearer resource_metadata=...`, Client ID Metadata Documents advertised with `client_id_metadata_document_supported: true` and `none` in `token_endpoint_auth_methods_supported`, DCR as fallback, `iss` in authorization responses, rotating refresh tokens, a token endpoint answering in under 10 s, redirects `https://claude.ai/api/mcp/auth_callback` and loopback on any port. Claude Code, Cursor, VS Code, Windsurf, Gemini/Antigravity and both vendor APIs accept a static `Authorization` header.
4. **Client time and size limits.** ChatGPT and the Cursor CLI time out near 60 s, claude.ai at 240 s, the Cursor IDE near 300 s; no client documents MCP tasks, and progress does not extend a timeout. claude.ai caps a result near 150k characters, Claude Code at 25k tokens unless `_meta["anthropic/maxResultSizeChars"]` raises it. VS Code allows 128 tools per request, Windsurf 100 in total.
5. **workers-oauth-provider** (1.2.4) supports CIMD, DCR, PKCE, RFC 9728, RFC 8707 and token exchange, and stores grants and hashed tokens in KV. Its props encryption only protects KV at rest: any Worker that validates tokens sees the raw token. So the provider, its KV and validation must live in this Worker for D13 to hold. It does not enforce scopes.
6. **Logging.** Logpush `ClientRequestURI` and OTel `url.full` record the full path and query unredacted; headers are logged only through configured custom fields; Tail Workers redact header names containing auth or token by heuristic, and `getUnredacted()` exposes everything (D14).
7. **Proxy tier today.** The proxy Worker resolves a tenant with `env.ISSUER.route(token)` (workers/proxy/src/index.ts:127-135; `ExecutorIssuer.route` at private/account/src/services/executor-issuer.service.ts:118), with no cache in the Worker. Containers are capped at `HARD_CAP = 25` per target (workers/proxy/src/capacity.ts:12) and sleep after `sleepAfter = '2m'` (workers/proxy/src/org-executor.ts:96). The proxy Worker binds `ACCOUNT` and `ISSUER` services (workers/proxy/wrangler.template.toml:26-36) and is routed per region as a custom domain (workers/proxy/wrangler.eu.toml:10-11).
8. **Deploy tooling.** `deploy_proxy` deploys the proxy Worker per target and region with record and rollback (.ci/rediacc_ci/deploy/deploy_proxy.py:4-6); `cd-deploy-worker.yml` and `cd-deploy-account.yml` carry the CD legs; regions live in `regions.json` (keys include `workerName`, `proxyWorkerName`, `domain`).
9. **Durable Object and rate-limit facts.** About 1,000 requests per second per object; the Workers rate-limit binding is per location and eventually consistent, so it is an approximate throttle only.

## Design

### 1. Shape of the Worker (workers/mcp)

- One Worker per region, `mcp.<region>.rediacc.cloud`, custom domain like the proxy. Bindings: `OAUTH_KV` (KV), `GRANTS` (service binding to the account Worker's `resolveGrant` RPC), `EXECUTOR` (service binding to the proxy Worker), `RATE` (a Durable Object namespace), `RATE_APPROX` (the rate-limit binding).
- Transport: `createMcpHandler(factory)` from the v2 SDK, stateless, JSON responses, `legacy: 'stateless'` so 2025-revision clients still connect, GET and DELETE answered 405, `Origin` validated with `originValidationResponse` against an allowlist (claude.ai, chatgpt.com, the region's own origin; requests with no `Origin` from native clients pass).
- `initialize`, `tools/list` and `server/discover` are served from the shared registry (`packages/shared/src/mcp/registry.ts`, PLAN-rmcp-local-mcp.md LM1), filtered to `surface === 'proxy'` and then by the grant's scope, with a deterministic order and `ttlMs`. None of them wakes a container.
- `tools/call` resolves the grant, runs the per-grant rate limit, and forwards to the proxy Worker's org DO over the `EXECUTOR` binding with `{grantId, S, tool, args, requestId}` in the body, never in the URL. The proxy Worker hands it to the container's grant session (PLAN-rmcp-agent-grants.md Design 4), which runs decide() and the command.

### 2. Authorization server in this Worker (RW-A)

- `workers-oauth-provider` with `OAUTH_KV`; endpoints `/.well-known/oauth-protected-resource/g/<grantId>`, `/.well-known/oauth-authorization-server`, `/authorize`, `/token`, `/register` (DCR fallback), `/revoke`.
- Metadata: `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported` including `none`, `code_challenge_methods_supported: ["S256"]`, `authorization_response_iss_parameter_supported: true`.
- CIMD fetches go through an SSRF guard: https only, a public host (no private, loopback, link-local or metadata ranges after DNS resolution), a size cap, a timeout, and a per-host cache.
- `/authorize` validates the client, `redirect_uri` (exact match; claude.ai callback and loopback on any port allowed) and PKCE, then redirects to the account UI's `McpAuthorize` page with an opaque, HMAC-signed, single-use `authRequest` handle (no secret in the URL).
- The account page (RW-U) runs the grant creation of PLAN-rmcp-agent-grants.md Design 3 (2FA and elevation, unlock, draw `S`, wrap, post the wrapped CEK and tag hash to the account Worker) and then form-POSTs `{authRequest, grantId, S}` to this Worker's `/authorize/complete`. Only this Worker ever receives `S` (D13).
- `/authorize/complete` calls `completeAuthorization` with props `{grantId, S, userId, orgId}`; access tokens live 1 hour, refresh tokens rotate with reuse detection and live until the grant's expiry. Every request checks the token's audience equals the canonical resource URL for that grant.
- Scopes are enforced here: the grant's scope (read-only, tool list, machines, repos) filters `tools/list` and refuses `tools/call` outside it.

### 3. Bearer fallback

`Authorization: Bearer rmcp_<grantId>.<S>` (and `x-api-key` with the same value) skips OAuth: the Worker parses it with the shared module, derives the tag and resolves the grant the same way. A token in a query string is refused with 400.

### 4. Grant resolution (one RPC per call)

`resolveGrant(grantId, authTag)` on the account Worker (an RPC method next to `ExecutorIssuer.route`) does one joined read: grant, org and placement, membership and role, entitlement, `cek_generation`. It answers `{active, orgId, placement, userId, teamId, configId, region, scope, overrides, expiresAt, reason}`. The grant names exactly one config (D55): every `tools/call` runs against that config only, and a tool argument naming another config is refused with `REDIACC_GRANT_SCOPE`. Token and grant lifetimes follow D54: OAuth access tokens never outlive the grant, refresh tokens stop at the grant's `expiresAt` (7 days by default, 30 days at most), and `resolveGrant` refuses an expired grant whatever the cache holds. The MCP Worker caches an active answer per `(grantId, authTagHash)` for `min(30 s, expiresAt - now)`; a pushed revocation (PLAN-rmcp-agent-grants.md AG-S5) also purges this cache through a `/internal/revoke` call on the MCP Worker.

### 5. Expiry, revocation, re-authorization

- An unknown grant or a wrong tag gets a bare 401, with no detail.
- A known grant with a valid tag that is expired, revoked or key-rotated: `initialize`, `tools/list` and `server/discover` still answer; each `tools/call` returns `isError: true` with `structuredContent {code: "REDIACC_GRANT_EXPIRED" | "REDIACC_GRANT_REVOKED" | "REDIACC_KEY_ROTATED", reauthUrl, expiredAt}` and a text line telling the model to give the user `reauthUrl`. `reauthUrl` carries only the grant id.
- For an OAuth access token that expired, the answer is HTTP 401 with `WWW-Authenticate: Bearer resource_metadata=...`, so the client refreshes or re-runs OAuth itself.

### 6. Confirmation (D21)

When decide() answers `needs_confirmation`, a client that declared elicitation gets an MRTR `input_required` result with a form request and a `requestState` sealed with AES-GCM under a Worker secret, carrying `{grantId, userId, tool, argsHash, nonce, exp}` (2-minute TTL). The retry must carry the same grant, user, tool and argument hash, and the nonce is burned in the grant's rate-limit DO, so a state is accepted once. A client without elicitation gets an `isError` result naming the `confirm` argument; the retry with `confirm: true` passes decide().

### 7. Time and size budgets (D15)

- The forward to the executor uses a 50-second attach window; a longer job returns `{jobId, next: "job_status"}`, and the registry's `job_wait` tool (PLAN-rmcp-local-mcp.md LM6) blocks for at most 50 s per call.
- Paging is the registry's (LM6): the Worker passes the `cursor` through unchanged and sets `_meta["anthropic/maxResultSizeChars"]` on the large-output tools the registry marks.

### 8. Rate limits

One `RATE` DO per grant enforces a strict budget (60 calls per minute, 5 concurrent `tools/call`), and the `RATE_APPROX` binding throttles per grant per location before the DO is reached. Over-budget calls get `isError` with `code: "REDIACC_RATE_LIMITED"` and a retry hint; that code joins the enum in `packages/shared/src/mcp/errors.ts` after LM1 lands.

### 9. Logging guards (D14)

`mcp_logging_guard.py` fails CI when any wrangler file under `workers/` enables a Logpush custom field that captures a request header, when any source under `workers/mcp` calls `getUnredacted()`, or when a route pattern or handler reads a credential from the URL. A planted violation in its test proves each rule fires.

### 10. Deploy and operations

- `deploy_mcp.py` mirrors `deploy_proxy.py`: per target and region, a record, rollback by version id, a smoke check (`server/discover` answers, the metadata documents parse, an unauthenticated `tools/call` gets 401).
- `cd-deploy-worker.yml` gains the MCP leg after the proxy leg; `regions.json` gains `mcpWorkerName` per region; DNS is the custom domain in each region's wrangler file.
- Monitoring: per-grant call, error and latency counters through Workers Analytics Engine, an ops alert on a burst of `REDIACC_GRANT_*` refusals or destructive calls from one grant, and a weekly report of grants by client.

### 11. On-premise host (D48-D50)

- **One portable handler.** The MCP request handling (Design 1, 3-8) moves into `packages/shared/src/mcp-host/` as a Hono app factory that takes four adapters: `OAuthStore` (grants, clients, codes, refresh tokens), `RateLimiter`, `GrantResolver` and `ExecutorTransport`. The Cloudflare MCP Worker becomes a thin host that binds KV, the rate-limit Durable Object, the issuer service binding and the proxy route. The Node on-premise account entry (private/account/src/entry/on-premise.ts, routes from `createOnPremiseRoutes` in private/account/src/routes/on-premise-index.ts) mounts the same app at `/mcp` with account-database adapters: new tables in `private/account/src/db/mcp-schema.ts`, a database rate limiter with the same per-grant ceilings, a resolver that reads `config_agent_grants` in-process, and an executor transport that calls `rdc serve --mode daemon` through `EXECUTOR_URL` (private/account/src/types/env.ts:379-381).
- **The OAuth library on Node (D53).** workers-oauth-provider runs on both hosts. On Cloudflare it reads `OAUTH_KV`; on the Node entry it reads a KV-shaped adapter (`get`, `put` with TTL, `delete`, `list` by prefix) over a SQLite table in the account database. RW-OP0 is a spike that must prove two things before RW-A1 starts: the library runs unmodified on Node over that adapter, and it rotates refresh tokens for public clients with reuse detection. If either fails, the fallback is a minimal authorization server of our own in `mcp-host` over `OAuthStore` (PKCE S256, CIMD with DCR fallback, RFC 8414 and RFC 9728 metadata, RFC 8707 audience, `iss`, refresh rotation, revocation), used on both hosts so the code stays single; the outcome is recorded in this plan.
- **What differs on-premise.** No Cloudflare: the Worker secrets become environment variables or config on the host, the edge logging guards of Design 9 become a check on the Node request logger, and the CIMD fetch obeys the host's egress rules; with no internet, OAuth clients that need CIMD cannot register, and the bearer path stays available.


### 12. Per region (D58)

- One MCP Worker per region at `mcp.<region>.rediacc.cloud` (eu, us, asia, and each bench region), each with its own `OAUTH_KV`, its own rate-limit Durable Object namespace, and service bindings only to its own region's account Worker (`GRANTS`) and proxy Worker (`EXECUTOR`). No binding crosses regions.
- The region is part of every public identifier: the MCP URL host, the RFC 9728 `resource` value and authorization-server metadata, and the bearer's grant row (stored in the D1 of the org's region by PLAN-rmcp-agent-grants.md).
- A grant presented to the wrong region is refused, never proxied: `resolveGrant` in that region finds no row, and the Worker answers with a structured error `REDIACC_WRONG_REGION` naming the right region's MCP URL when the grant id carries a region prefix, or a bare 401 when it does not. Config data, keys and grants therefore never leave their region.
- Deploy, CD and DNS run per region (Design 10), the bench regions mirroring production; the on-premise host is a single region and omits the prefix check.
