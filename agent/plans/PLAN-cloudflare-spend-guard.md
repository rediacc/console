### Cloudflare documentation (read 2026-10-23)

- Observability pricing (https://developers.cloudflare.com/observability/pricing/): from 2026-12-01, "50 GB per billing cycle" ingestion and "10 GB-month per billing cycle" storage, then "$0.25 per GB" and "$0.10 per GB-month". "Paid usage continues automatically after an allowance is exhausted." "Sampling data before storage reduces both ingestion and storage usage." The Workers OTLP export page adds that "persisted data contributes to Cloudflare Observability ingestion and storage usage".
- Notifications (https://developers.cloudflare.com/notifications/notification-available/): the alert "Usage Based Billing" is for "Customers who want to receive a notification when the usage of a product goes above a set level"; each policy picks one product and one threshold, and "Thresholds depend on the product chosen"; "Usage-based billing notifications are available to Pay-as-you-go accounts only. Most Enterprise contract accounts are not supported."
- The policy API is token-drivable (https://developers.cloudflare.com/api/resources/alerting/subresources/policies/methods/create/): `POST /accounts/{account_id}/alerting/v3/policies`, accepted permissions "Notifications Write" or "Account Settings Write"; body `alert_type`, `name`, `enabled`, `mechanisms` ("IDs for email type will be the email address"), optional `filters`; the `alert_type` enum includes `billing_usage_alert`, and the filters `limit` and `product` are "Used for configuring billing_usage_alert".
- The product values and limit ranges are listed by `GET /accounts/{account_id}/alerting/v3/available_alerts` (https://developers.cloudflare.com/api/resources/alerting/subresources/available_alerts/methods/list/), whose `filter_options` are the "Format of additional configuration options (filters) for the alert type"; it accepts "Notifications Read" among others. The docs page names no complete product list, so T1 reads it live and records it.
- Usage datasets:
  - GraphQL Analytics, token permission "Account Analytics" Read (https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/api-token-auth/).
  - R2: `r2StorageAdaptiveGroups` (`bucketName`, `payloadSize`, `metadataSize`, `objectCount`, `uploadCount`) and `r2OperationsAdaptiveGroups` (`bucketName`, `actionType`, `actionStatus`), each with an `accountTag` filter (https://developers.cloudflare.com/r2/platform/metrics-analytics/).
  - Workers: `workersInvocationsAdaptive` with sums `requests`, `errors`, `subrequests`, quantiles `cpuTimeP50` and `cpuTimeP99`, dimension `scriptName` (https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-workers-metrics/).
  - D1: `d1AnalyticsAdaptiveGroups`, `d1StorageAdaptiveGroups` (`databaseSizeBytes`) and `d1QueriesAdaptiveGroups` (https://developers.cloudflare.com/d1/observability/metrics-analytics/).
- Observability volume per Worker: no GraphQL dataset for observability ingestion is documented. The Workers Observability telemetry API is: `POST /accounts/{account_id}/workers/observability/telemetry/query`, permission "Workers Observability Write", with `view: "calculations"`, a `count` calculation and `groupBys` that "produce per-group aggregate values" (https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/). It counts events, not bytes; T4 converts counts to bytes with the measured mean event size from Loki and cross-checks the dashboard's Billable Usage page once.
- R2 lifecycle (https://developers.cloudflare.com/r2/buckets/object-lifecycles/): `npx wrangler r2 bucket lifecycle add <BUCKET_NAME> [OPTIONS]` and `lifecycle list`; "object lifecycles currently has a 1000 rule maximum"; "Buckets have a default lifecycle rule to expire multipart uploads seven days after initiation"; objects go within about 24 hours of expiry. The local wrangler (`workers/www/node_modules/.bin/wrangler r2 bucket lifecycle add --help`) takes positional `bucket`, `name`, `prefix` and options `--expire-days`, `--abort-multipart-days`, `-y`. A prefix is a literal string prefix, so one rule per format directory is needed.

## Design

1. **Notifications as code.** `.ci/config/cf-spend-guard.json` is the one source of thresholds: per product, the `billing_usage_alert` limit, the weekly-report ceiling, and the sampling ceiling the gate reads. `.ci/rediacc_ci/ops/cf_notifications.py` upserts one policy per product by name (`spend-guard:<product>`): `GET .../alerting/v3/policies`, then `PUT .../policies/{id}` or `POST`, email mechanism to `muhammed@rediacc.com` (the operator address the SES alarm docs already use, `private/account/docs/email/observability.md:85`). A product the `available_alerts` listing does not offer is reported as `UNAVAILABLE <product>` and named in the dashboard fallback section of the T8 doc, never silently skipped.
2. **Initial thresholds**, about twice the included Workers Paid allowance so a doubling alerts before the bill does, subject to the live `filter_options` ranges: Workers requests 20 million a month and CPU 60 million ms; R2 storage 200 GB (operator /ask 2026-10-23 "Keep 20, raise the alert to 200 GB": the 20 kept release folders already hold about 85 GB of the measured 151 GB, so a doubling of the 10 GB allowance would alert from day one), Class A 2 million and Class B 20 million operations; Observability ingestion 40 GB and storage 8 GB-month (80 percent of the included 50 GB and 10 GB-month); Containers at the cost guard's 2-instance budget, about $15 a month, expressed in whatever unit the product filter takes.
3. **Tokens.** `cf_auth` gains a scoped mint that takes the groups a caller needs (Notifications Write for T1, Account Analytics Read and Workers Observability Write for T4 and T6, Workers R2 Storage Write for T3), resolved by name from `/user/tokens/permission_groups` rather than hard-coded ids, so the long-lived `auto-rotation-management` policy does not grow. Every minted token self-destructs at the end of the run, as today.
4. **Sampling after measurement.** Target values, confirmed or changed by T4's numbers: stable account traces and logs at 0.1; edge and bench as measured (kept at 1 while their daily volume stays under 1 percent of the included ingestion), which makes them the named exemptions: they are public Workers too, so the ceiling applies to them unless `.ci/config/cf-spend-guard.json` lists the config in an explicit `sampling_exempt` map with its reason, and T5 never infers an exemption; www traces at 0.1; `persist = false` where the Cloudflare explorer is not needed, which means every config whose data already reaches Tempo and Loki through an OTLP destination takes `persist = false` and only bench keeps `persist = true` for the explorer. The ceiling the gate enforces on public Workers is 0.1.
5. **R2 lifecycle as a backstop, not the primary.** The application keeps deciding first; lifecycle windows sit beyond the app's: `<fmt>/pr-` at 14 days (app: 3), `<fmt>/dryrun-` at 21 days (app: 7), and `--abort-multipart-days 1` on `rediacc-releases`. A bucket matching `rediacc-backups*`, `*-backups-*` or `rediacc-configs*` is refused by the script before any call.
6. **Weekly report.** A read-only GraphQL and Observability read with thresholds from the same JSON; red on breach, red on the nightly-maintenance log line, and green only with a nonzero count of buckets, databases and Workers read.

## Risks

- **A lifecycle rule deletes something the application still needs.** An open PR whose channel was uploaded more than 14 days ago loses its oldest objects. The windows are set well past the app's own (3 and 7 days), and a PR channel older than 3 days has already been deleted by Phase 8b, so the rule only catches what the app missed. Backup and config buckets never get a rule: a chunk the GC still references would be lost with no signal, and T3's refusal list plus its planted-rule test hold that line.
- **Sampling hides a rare error.** At 0.1, nine in ten error traces of a rare failure are not stored. Logs carrying `console.error` lines are the signal for those; if T4 shows logs are small, logs stay at 1 and only traces drop, recorded as T2's decision.
- **`persist = false` loses the Cloudflare explorer** for the stable Workers. Tempo and Loki on hostinger carry the same data through the OTLP destinations, so the explorer is redundant there; bench keeps it.
- **The account is not Pay-as-you-go.** The notifications doc says usage-based billing alerts are for Pay-as-you-go accounts only. T1's `available_alerts` read settles it; if `billing_usage_alert` is absent, T1 records that, the weekly report becomes the primary guard, and the dashboard fallback is named in the T8 doc.
- **Event counts are not bytes.** T4's byte figure is an estimate from a mean event size. The one-time Billable Usage cross-check bounds the error; a gap above 2x is recorded and the ceiling in the JSON follows the billed figure.
- **A token with Notifications Write or Analytics Read leaks.** Each script mints a scoped token for its run and self-destructs it, and no value reaches argv or a log; the tests assert the latter.
