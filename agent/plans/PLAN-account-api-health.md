## Incident (2026-11-28)

At 07:13Z an edge Workers release (`release:local --channel edge --workers-only --branch-release`) shipped account code whose `forensicsStoreFromEnv` counted the plain `ACCOUNT_FORENSICS_S3_BUCKET` var (workers/account/wrangler.eu.toml:18, the same line in wrangler.us.toml and wrangler.asia.toml) beside the three FSL1 secrets production does not carry. With the secrets absent and the bucket present it threw "forensics store is half configured" (private/account/src/services/forensics-store.ts:191). It runs inside the per-request service middleware (private/account/src/app.ts:673, under the `app.use('/account/api/*')` at private/account/src/app.ts:346), so every `/account/api/v1/*` request in eu, us and asia answered 500. Account commit 19e01bd2 fixed it (private/account/src/services/forensics-store.ts:168-176 records the reason).

Why nothing caught it:

- Every release smoke probes only server-info: `verify_edge_endpoints._region_health` (.ci/rediacc_ci/deploy/verify_edge_endpoints.py:401-409), `verify_stable_endpoints._region_health` (.ci/rediacc_ci/deploy/verify_stable_endpoints.py:186-189) and the bench smoke (`SMOKE_PATH`, .ci/rediacc_ci/ops/deploy_bench.py:964, `smoke` at :1074). `/health` (private/account/src/app.ts:286) and server-info (private/account/src/app.ts:299) are registered before the service middleware (private/account/src/app.ts:346), so both answered 200 on a Worker whose every API route answered 500.
- release:local has no preview stage, and its plan expands per-region rows in table order (.ci/rediacc_ci/release/local.py:1231-1249), so all three account deploys (.ci/rediacc_ci/release/local.py:936-942) run before the single `verify-endpoints` smoke (.ci/rediacc_ci/release/local.py:1027-1031). CD deploys the regions as a parallel matrix with `fail-fast: false` (.github/workflows/cd-deploy-account.yml:254-256). PLAN-preprod-simulation.md fixes both.
- The PR preview would NOT have caught it: ci.yml deploy-preview (.github/workflows/ci.yml:1507) deploys the www Worker, which wraps `createApp` directly (workers/www/src/index.ts:2) rather than the production entry (workers/account/src/index.ts:2), and its generated [vars] (.ci/rediacc_ci/deploy/deploy_www.py:167-182) carry no `ACCOUNT_FORENSICS_S3_BUCKET`, so the store returned null there and smoke-test-preview (.github/workflows/ci.yml:1760, .ci/scripts/test/smoke-test-preview.ts:77) would have passed. Besides, Console CI created no runs for PRs #602, #603 and #605, and #607's runs were cancelled before the preview job.
- Config drift: wrangler.bench-eu.toml, wrangler.bench-us.toml and wrangler.bench-asia.toml carry no `ACCOUNT_FORENSICS_*` var (grep finds only the FORENSICS_COMPACT_QUEUE binding), so bench could not reproduce the production shape either.

## Design

**D-smoke (S1).** `.ci/rediacc_ci/deploy/account_api_smoke.py` is the one API smoke every stage calls: `/account/api/v1/health` 200, server-info 200, `/account/api/v1/portal/me` 401 without a session (`sessionAuth`, private/account/src/routes/portal.ts:170 and :196, throwing 401 at private/account/src/middleware/session.ts:12), and `/account/api/v1/telemetry/config` 200 (private/account/src/routes/telemetry.ts:35). A 5xx anywhere is red. Each probe retries while a new version propagates (bounded, attempt count printed), prints the status and the first 2 KB of the body on failure, and exits 0 green, 1 red, 2 a bad argument. A boot-matrix (B1) finding that portal/me answers another code changes the expected code here, never the test.

**D-edge (S2).** `.ci/rediacc_ci/deploy/edge_region_smoke.py --region R` runs D-smoke against one region's production origin after its account deploy. Red: it calls R1's sender, prints the rollback commands deploy_record already builds (`rollback_commands`, .ci/rediacc_ci/deploy/deploy_record.py:838, printed at :928-929), and exits 1, which stops the run before the next region once PLAN-preprod-simulation.md makes the order region-major. It never rolls back. The existing `rollback` row (.ci/rediacc_ci/release/local.py:1009-1023, "close the executor, return the proxy, print the rest" at .ci/rediacc_ci/deploy/deploy_record.py:1351) returns only the proxy and touches no account Worker or D1, so it stays; ruling 3's reasons concern rows the new code wrote and customer writes. That default is recorded for the operator to veto. verify_edge_endpoints.py and verify_stable_endpoints.py call D-smoke per region in place of the server-info probe, so the post-release checks of cd-release-edge.yml (:597-601) and cd-release-stable.yml (:294) gain it with no workflow edit.

**D-mail (A1, R1).** Two classes in .ci/config/ops-health.json: `emergency` (customer-facing 5xx targets: account API, account health, proxy, www, and the ingest sources `release-smoke` and `local-ci-presence`) and `routine` (machines, drift, root grants, telemetry, dmarc, cf-usage). An emergency transition mails at the first red pair (`to_red` 2, .ci/config/ops-health.json:14) from emergency@rediacc.com, subject prefixed `[EMERGENCY]`, one mail per red and one recovery mail, de-dup kept (`DueReason`, workers/ops-health/src/state.ts:79). Routine transitions move to a daily digest beside the weekly one (`digestSubject`, workers/ops-health/src/mail.ts:59; `worker.digest`, .ci/config/ops-health.json:50). The sender is a plain [vars] value `OPS_MAIL_FROM_EMERGENCY`, like `OPS_MAIL_FROM` (workers/ops-health/wrangler.toml:18), since an address is not a secret; the recipients stay the bws key OPS_ALERT_EMAILS. R1 decision: a release-smoke red sends DIRECTLY through a Python SES sender (`.ci/rediacc_ci/release/emergency_mail.py`, the SES keys of the ops-health profile, .ci/config/secret-supply.json:931-940) and ALSO posts `red` to the ingest through ops_health_post (.ci/rediacc_ci/release/ops_health_post.py). Reason: an ingest entry turns into a mail only on the next cron run (up to 10 minutes) and then waits on the transition rule, while the release red is already confirmed by D-smoke's retries and the operator must read it before choosing a rollback. No Python SES sender exists in .ci/rediacc_ci today (a grep for SendEmail finds only enterprise/secrets.py). R1's signature is fixed here so PLAN-preprod-simulation.md can call it: `send(region, route, status, excerpt, rollback) -> message_id`.

**Gate wiring.** B1, B2 and P1 are three-point gates (gate-author: package.json, scripts/ci-runner/manifest.ts, a workflow step). This plan owns the package.json script and the ci.yml step; manifest.ts and gates.lock.json belong to PLAN-ciquick-gate-contract.md, so each writer reports its manifest entry text and the lead applies it once no gate-contract writer holds those files, then runs `npm run gen:gates -- --check`. A gate box is ticked only after that check passes.
