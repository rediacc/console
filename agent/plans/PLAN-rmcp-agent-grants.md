## Ask

A hosted executor must open a user's config for an agent with no browser present, for as long as the user allowed and no longer (D8, D9). The grant the user creates in the account UI carries the user's identity, one config, an expiry, the per-URL overrides (D16, D23) and a scope. Every way the user can lose access (removal, team change, subscription lapse, store deletion, CEK rotation, a 2FA reset) ends the grant.

## Context (read 2026-11-20 against the tree; a writer re-reads each citation before relying on it)

1. **Key slots cannot hold agent grants.**
   - `config_key_slots` is at private/account/src/db/config-schema.ts:100, unique on (store, user, method) at :123. A second grant of the same user would collide.
   - The executor-token mint treats "has a key slot" as active membership (private/account/src/services/config.service.ts, the check near :2314 with the comment "Active membership, not merely org membership: a user with no key slot"). An agent grant must never count as a slot there.
2. **The CEK wrap has no AAD.** `cekWrap(cek, wrappingKey)` is at packages/shared/src/config-crypto/cek.ts:60, and slots feed `deriveWrappingKey(slotSecret, serverSecret)` into it (packages/shared/src/config-crypto/slots.ts:5, :179). Binding a grant to its context must live in the HKDF info, or the server can swap one wrapped CEK for another.
3. **The executor grant today is a 30-minute row.** `config_executor_grants` is at private/account/src/db/config-schema.ts:328; its TTL is `EXECUTOR_GRANT_TTL_MS = 30 * 60 * 1000` (private/account/src/services/config.service.ts:396), recorded by `POST /configs/executor-grant` (private/account/src/routes/configs.ts:986) and consumed by `POST /configs/executor-token` (:1069).

## Design

### 1. The secret and the keys (packages/shared/src/config-crypto/agent-grant.ts)

- The browser draws `S`, 32 random bytes. The bearer form is `rmcp_<grantId>.<base64url(S)>`.
- `authTag = HMAC-SHA256(S, "rediacc-agent-grant-auth-v1")`. The account server stores `SHA-256(authTag)` only.
- `K = HKDF-SHA256(S, salt = grantId, info = "rediacc-agent-grant-wrap-v1")`.
- The slot key is `HKDF-SHA256(K || serverSecret, salt = grantId, info = "rediacc-agent-grant-slot-v1|" + grantId + "|" + storeId + "|" + cekGeneration)`. What is wrapped under it is the config's own subkey (D56, PLAN-rmcp-policy-record.md Design for per-config subkeys), never the org CEK, with the existing AES-GCM wrap; the slot-key info also carries `configId`, so a wrap moved to another config does not open.
- Exports: `newAgentGrantSecret()`, `formatAgentBearer()`, `parseAgentBearer()`, `deriveAuthTag()`, `hashAuthTag()`, `wrapConfigKeyForAgentGrant()`, `unwrapConfigKeyForAgentGrant()`. The account server imports only `parseAgentBearer` and `hashAuthTag`; it never calls the wrap or the unwrap.

### 2. The row (`config_agent_grants`)

Columns: `id`, `config_store_id`, `user_id`, `org_id`, `team_id` (nullable for an org-level config), `config_id` (NOT NULL: exactly one config per grant, D55), `cek_generation`, `config_key_version`, `wrapped_config_key` (nullable after hard delete), `auth_tag_hash`, `label`, `client_kind` (`oauth` or `bearer`), `client_id` (OAuth client id or CIMD URL, nullable), `scope_json` (read-only flag, tool allowlist, machine globs, repo globs), `overrides_json` (`allowGrandRepos: boolean | string[]`, `allowClusterOps: boolean`), `expires_at`, `soft_expired_at`, `revoked_at`, `revoked_reason`, `created_at`, `last_used_at`, `call_count`. Indexes on (store, user) and (org, revoked_at), and a unique index on `auth_tag_hash`.

The executor-token "active member" check keeps reading `config_key_slots` only; a test pins that an agent grant does not satisfy it.

### 3. Creating a grant (account web, AG-W)

A new page `AgentGrants.tsx` under the console tree. Creating a grant requires a session with 2FA and elevation (D28; TOTP counts, and a `requirePasskey` store requires a passkey as it already does). The browser unlocks the CEK with `SharedConfigUnlock`, draws `S`, derives the tag and the slot key with `serverSecret` from the config session, unwraps the chosen config's subkey (the page picks exactly one config, D55), wraps that subkey and posts `{configId, teamId, label, expiresAt, scope, overrides, wrappedConfigKey, configKeyVersion, authTagHash, cekGeneration}` to `POST /agent-grants`. `S` leaves the browser only as the bearer shown once on screen (D13); the OAuth path in PLAN-rmcp-remote-worker.md hands `S` to the MCP Worker by form POST instead.

Expiry choices: 1 hour, 8 hours, 24 hours, 7 days, 30 days, default 7 days (D54). The server validates it: an absent `expiresAt` becomes 7 days, one beyond 30 days or in the past is refused with `grant_expiry_invalid`, and a renewal is a new grant, never an extension.

### 4. Opening a grant (account route and executor)

`POST /account/api/v1/configs/agent-session`, authenticated by the executor's issued bearer (as `/configs/executor-token` is), body `{grantId, authTag}`:

- refuses unless the grant is live (not revoked, not soft-expired, `expires_at` in the future), the tag hashes to `auth_tag_hash`, the grant's org is the executor's pinned org, the user is still an org member with a key slot in the store, the team membership still passes the team-access table, the org is not console-blocked, and the store's `cek_generation` equals the grant's. Every refusal carries one indistinguishable code;
- answers `{wrappedConfigKey, configKeyVersion, serverSecret, cekGeneration, storeId, configId, teamId, configToken, expiresAt, overrides, scope}`. `configToken` is a writable chain (PLAN-rmcp-writeback.md) with `scope_team_id` set to the grant's team and `agent_grant_id` set to the grant, so revocation deletes it;
- updates `last_used_at` and `call_count` off the answer's critical path.

The device-token routes refuse any chain carrying `agent_grant_id`.

In the container, `agent-grant-session.ts` keeps one session per `grantId`, not per user. It derives `K` from `S` (passed per request by the MCP Worker through the DO, never stored), calls `agent-session`, unwraps the config subkey into a non-extractable key (the container never holds the org CEK for an agent principal), and caches the decrypted config under `(grantId, configVersion)`. After a sleep the next call rebuilds it. `container-config.ts` routes an agent principal to this session instead of the user-keyed one.

### 5. Revocation and expiry

- **Soft expiry**: at `expires_at` the grant stops being served; `wrapped_config_key` is deleted 24 hours later, or at once on revoke.
- **Cascades** (each sets `revoked_at` and `revoked_reason`, deletes `wrapped_config_key` and the agent's config chain): member removal (`removeMember`), team leave and team archive (`archiveTeam` and the team-membership removal path), console block or subscription lapse (the entitlement service), store and org deletion (`deleteStore`), CEK rotation commit (every grant of the store, reason `key_rotated`), and `disable2fa` of the grant's user.
- **Push**: on any revocation the account Worker calls the proxy Worker's org DO (`revokeGrant(grantId)` on `OrgExecutor`, workers/proxy/src/org-executor.ts), which tells the container to drop the session and its cached config. The 60-second introspect cache is then only a backstop.
- **Kill switch**: an org owner or admin revokes every grant of the org at once (`POST /agent-grants/revoke-all`).

### 6. Management UI and audit

- The page lists the user's grants (label, config, client, scope, overrides, created, last used, call count, expiry) with revoke. Owners and admins see every grant of the org and the kill switch.
- An email on creation, reusing the API-token email shape (`sendAgentGrantCreated`).
- Audit events: `agent_grant.created`, `agent_grant.used` (sampled to one per grant per hour), `agent_grant.expired`, `agent_grant.revoked` (with reason), `agent_grant.overrides_changed`. Overrides change only by creating a new grant (D23 narrows; widening a live URL means a new URL), so `overrides_changed` records the replacement pair.

### 7. Entitlement

The hosted tier needs `server_recoverable_org_passphrase` (Context 5). Creating a grant on a store without it is refused with the same reason code and a portal message naming the setting, rather than producing a grant no executor can open.

### 8. On-premise

The account side is the same code on the Node entry: the `config_agent_grants` migration applies to the on-premise database, `POST /configs/agent-session` is served by the Node account server, and grant creation runs in the same portal pages. The daemon executor opens a grant session exactly as the container does (split secret, slot key derived in the executor, CEK in RAM), so `agent-grant-session.ts` is mode-independent; the daemon's enrolled config is not used for grant principals. Pushed revocation (AG-S5) has an on-premise transport: instead of the Durable Object RPC, the account server calls the daemon's revoke route through the per-org executor resolver (PLAN-rmcp-executor-hardening.md Design 19), authenticated with the daemon's pinned CA and the account server's own token. Rehydration after a daemon restart replaces the container-sleep case.


### 9. Per region (D58)

A grant row lives in the D1 of its org's region, created through that region's portal, and only that region's MCP Worker and executor can resolve it. The grant id carries the region as a prefix (`eu_`, `us_`, `asia_`, and the bench regions), so a Worker in another region can name the right one in its refusal (PLAN-rmcp-remote-worker.md Design 12) without any lookup across regions. On-premise is a single region with no prefix check.
