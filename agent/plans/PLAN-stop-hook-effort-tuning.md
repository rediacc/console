## Why

The session that a check blocks is the worst judge of whether that check should exist: tuning by annoyance turns `smart` into `quiet`. Tuning by outcome keeps the checks that cause real work and drops the ones that only cause paperwork. The data is half there already (reggate, claim-check and the advisory queue record pieces of it) and is thrown away today.

## Design

1. OUTCOME LEDGER. Every block and every advisory the Stop hook emits gets an id. At later stops the hook classifies what followed: `work` when a commit, worklist tick, lease or plan tick touching what the check named follows within 3 stops (operator ruling); `paperwork` when only a status reply or a STATE.md rewrite followed; `overruled` when the operator overrode it or the check's claim was refuted by evidence, such as a ticked item it called open; `expired` otherwise. Rows go to agent/ledgers/effort-outcomes.jsonl (key, level, verdict, outcome, session, time). Operator actions (an effort or switch change, a /ask answer that overrules a check) are recorded as strong signals.
2. PROPOSALS. `worklist.py --effort-propose <me> <key> <block|advise|off>@<level> '<evidence>'` appends to agent/ledgers/effort-proposals.jsonl; the evidence must cite ledger rows (counts and ids), and a proposal without them is refused. Sessions never edit effort.json directly for tuning.
3. TUNER, at the end of each context (operator ruling). When the context hooks see the session at about 85% of its auto-compact threshold (the existing context-band machinery in .claude/hooks/context/), the Stop hook asks the session to spawn an `effort-tuner` sub-agent, once per context. The session hands it what it lived through: the outcome rows of this context, the checks it found useful or useless and why, and any judge errors it saw. The sub-agent computes per-key precision over the ledger window, writes a candidate effort.json diff with its evidence table, tests it (the effort-table gate, the effort tests, and a replay of this context's recorded stops at the new thresholds showing which blocks would change), and delivers it as a patch. A context that compacts before the tuner finishes leaves the patch and its evidence on disk for the next session.
4. TRUST, asymmetric. Promotions (stricter) apply automatically and are reported (operator ruling); demotions are batched into one /ask with the table diff in a preview, and each answer is recorded so it is not re-asked (operator ruling); the FLOOR is untouchable by the tuner (the existing gate refuses a demoted FLOOR key). Every tuned key carries `tuned_at` and `review_after`; a demoted key whose absence later correlates with a miss (CI red, or a review finding the check would have named) is promoted back.
5. JUDGE LEARNING. Confirmed judge errors (re-raised finished work, rule-breaking advice, status-table demands) become rules in the judge's input or its advice filter, as the release-age rule did; the tuner lists recurring error shapes and proposes the rule with a test.
