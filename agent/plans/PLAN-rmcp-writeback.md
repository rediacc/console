## Ask

A command dispatched by the hosted executor (container tier) must either persist every config change it makes to the config store, or fail before any host side effect. Today it does neither: writes stay in request memory and the command reports success with a stderr warning. The operator ruled the class dangerous (D6) and placed a stop-gap first (D5).

## Context (read 2026-11-20 against the tree; a writer re-reads each citation before relying on it)

## Decisions

D49 and D50 (the on-premise daemon gets the same write-back scenarios as the hosted executor), D5 (stop-gap first, inside this plan), D6 (memory is not the only copy of a record; an unsaved record fails before any host side effect), D10 (the executor pushes through a writable chain minted under a live grant, reusing compare-and-swap replay), D3 (every sibling found is fixed here), and the clean-break rule: no flag keeps the old in-memory behaviour.

## Design

1. **WB0 stop-gap.** In `writeScoped`, a version-bumping write under a container request scope throws `ConfigWriteUnavailableError` (error code `CONFIG_WRITE_UNAVAILABLE`, i18n message naming the command and "run locally until write-back ships"). State writes (`bumpVersion: false`) still apply in memory for the request. The `packages/cli/src/services/serve/server.ts:381-382` warning and the `specWrites` counter are deleted. Because the write precedes the host job (Context 5), no volume, fork or VM is created.
2. **Writable executor chain.** `POST /configs/executor-token` gains `write: true`, honoured only when the request carries a live `config_executor_grants` row for (session, executor principal, user) and the grantor's token is live. The minted chain is `readOnly: false`, `scope_team_id` = the grant's team, bound to the user; the team access table applies per push as for any member. A writable executor chain is refused for device-token minting. The grant TTL slides on each mint (PLAN-rmcp-executor-hardening.md EH6 owns the TTL rule; this plan owns the mint-path code).
3. **Egress.** `POST /account/api/v1/configs/session` and `PUT /account/api/v1/configs/<id>` (optional `teamId` query, body cap equal to the account route's) join the token routes beside `CONFIG_PULL_RE`.
4. **Request-scoped remote state.** The scope holds a `RemoteResourceState` built from the session CEK and the writable chain; `writeScoped` is replaced by `pushWithReplay`; `isRemoteConfigFile` reads the scope instead of returning false. After a push the cached document and version are replaced.
5. **Concurrency.** One async mutex per (session, configId) around pull, `/session` and PUT; one chain per container instance per (user, team); on 401 or an exhausted chain, re-mint once. Cross-device and cross-placement races are handled by compare-and-swap replay.
6. **Rollback only on a definitive failure.** `repo create` and `repo fork` roll back the registration only when the job is known failed or cancelled; a timeout, lost stream or unknown state leaves the entry, and the settle step (`rollbackCreate`) decides when the job settles. Siblings are swept: every command whose `catch` removes a config entry it registered.
7. **Job polls write-capable.** The job routes run under the same request scope as dispatch, so settle steps that write config (rollback, identity refresh) push; after a container sleep the scope rehydrates from the grant.
8. **Audit fail-closed for mutating commands.** A mutating command whose audit event cannot be delivered after the retry fails with `AUDIT_UNAVAILABLE` before dispatch where the event is pre-dispatch, and reports `audit_failed` in the result where it is post-dispatch; reads keep the warning.
9. **Terminal events idempotent server-side.** The terminal event's idempotency key becomes `job:<jobId>:terminal`, so a lost ledger produces a duplicate the account route drops; the in-memory ledger stays only as a cache.
10. **On-premise daemon write-back.** The `writeback` suite of the shared scenario runner (`rediacc_ci.testrun.onprem_scenarios`, PLAN-rmcp-executor-hardening.md Design 16) drives the daemon of an on-premise stack: a served `repo create`, `repo delete` and `repo fork` each produce exactly one pushed version that a second device's `rdc repo list` reads; a push racing a laptop push replays and keeps both edits; an account server stopped mid-command fails the command with no host job started; the same scenarios run against the hosted executor under `--compare bench` once WB1 has landed.
