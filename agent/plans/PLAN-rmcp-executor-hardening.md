## Design

1. **Introspect.** `active: true` requires a current org role for the creator; a creator with none answers `active: false`. The response adds `expiresAt` (ISO) in `proxy.dto.ts`.
2. **Verifier cache.** Entry lifetime is `min(CACHE_TTL_MS, expiresAt - now)`; the map is an LRU capped at 1,024 entries with expired entries evicted on read.
3. **teamSlug.** The principal's team slug is resolved once per request and passed to `authorize`.
4. **Cache key.** The container config cache is keyed by (session id, team id); a principal of another team gets its own pull.
5. **Revalidation.** Each request compares the cached version with the store's current version (one `HEAD`-equivalent read the account route answers from D1, no blob) and re-pulls on mismatch.
6. **Grants per (org, user, team).** `grantsByUser` becomes keyed by (org, user, team) and holds a set of session ids; the newest live session wins for lookup, none is dropped silently. The executor grant TTL slides on each mint and each executor-token request.
7. **CLI re-grant and reuse.** On `EXECUTOR_SESSION_UNKNOWN` the client opens a new session and re-grants once, then retries the command with the same `requestId`. The session id and the executor's public key are cached in the CLI's token directory for the session TTL, so consecutive `rdc --proxy` runs skip server-info, session and CEK.
8. **Ready (D52).** Public `GET /v1/ready` answers only `ready`, `reason` and `workerVersion`, for every caller. Occupancy moves to `GET /v1/internal/occupancy`, which the proxy answers only to the account Worker: the request must carry an internal credential the account Worker attaches over its `EXECUTOR` service binding (an issuer-signed, short-lived internal token verified through the `ISSUER` binding, never a Worker secret shared with clients), and any other caller gets 404. The account server gains the one consumer: `GET /admin/executor-occupancy` (root auth, `rootAuth()`) reads it per region, and the bench drill reads occupancy through that admin route with the root API token instead of polling the proxy. The ready.ts comment drops the review 900c1e14.2 trade and states the new contract.
9. **Daemon bind.** `--host` defaults to `127.0.0.1`. A non-loopback `--host` requires `--tls-cert` and `--tls-key` and serves HTTPS; without them the command refuses with an i18n error.
10. **Login token expiry.** A CLI login token gets a 90-day idle expiry that slides on use, capped at 365 days absolute; a refresh past the cap requires the device-code flow again.
11. **Device-code token at rest.** The minted token is stored sealed under a key derived from the poll secret (the verifier already stored is its hash), so the row holds ciphertext; the claim decrypts and deletes it atomically.
12. **Global strict limits.** Introspect, `proxy/cli-token` and device-code creation move to the D1 `rate_limits` table; the in-memory limiter stays only for coarse per-isolate shedding.
13. **Store refusal message.** `ISSUER_STORE_UNSUPPORTED` reaches the caller as a structured error naming the missing setting and the portal page that enables it.
14. **Stale comments** at Context 14 corrected.
15. **On-premise stack.** `rediacc_ci.testrun.onprem_stack up|down|status [--machines vm|container]` starts, in order: RustFS, the on-premise account server (the `rediacc-server-onprem:dev` image by default, or the on-premise entry from source with `--from-source` for fast iteration) with TEST_MODE seams (reusing `start_account.py`'s seeding and token mint), a config store set up through the same seams, `rdc serve --mode daemon` enrolled against it with its own `proxy:exec` token, and the machines (ops VMs through `./rdc.sh ops up --basic`, or a container machine for runners without KVM). It writes one env file (`.onprem/stack.env`) naming every URL, token path and config name; `down` stops every process group it started and refuses a port that already answers, as `start_account.py` does. Enrollment uses the headless path available at the time and switches to the generated machine secret once PLAN-rmcp-policy-record.md lands it (D46).
16. **Scenario runner (the name sibling plans call).** `PYTHONPATH=.ci python3 -m rediacc_ci.testrun.onprem_scenarios --suite <name> [--env .onprem/stack.env] [--compare bench]`. A suite is a module under `.ci/rediacc_ci/testrun/onprem_suites/` registering named scenarios; each scenario drives the real CLI, the daemon and, where relevant, the stdio or remote MCP server, and writes one JSON verdict line. `--compare bench` runs the same scenarios against `./rdc.sh --config eu-bench` and fails on any differing verdict or code (the D49 parity tier). Suites added by sibling plans: `writeback`, `grants`, `local-mcp`, `config-edit`, `orphan`, `policy`, `decide-parity`, `remote-mcp`. This plan ships the runner, the `smoke` suite and the `daemon` suite.
17. **CI lane.** `npm run test:onprem` (the runner over every registered suite against a container-machine stack) is wired at the three points the gate estate requires: the `package.json` key, a lane entry in `scripts/ci-runner/manifest.ts` (with `gates.lock.json` regenerated by its generator), and a step in `.github/workflows/ci-ops-test.yml`, the workflow that already has KVM; `npm run check:ci-parity` holds the three equal.
18. **Air-gapped image test.** `rediacc_ci.testrun.onprem_image --airgapped` builds the shipped on-premise image (`rediacc_ci.ops.build_server onprem`, tag `rediacc-server-onprem:dev`, the root `Dockerfile` `--target onprem`; never `private/account/Dockerfile`), runs it on an internal Docker network with no route out, starts the daemon and a container machine on the same network, runs the `smoke`, `daemon` and (once present) `remote-mcp` suites, and fails if any container attempted an outbound connection (a deny-all egress proxy logs every attempt).
19. **Daemon reachability on-premise.** The account server resolves an executor per org: a new on-premise setting maps an org to its daemon URL and pinned CA (`executor_url`, `executor_ca_pem`, D1/SQLite migration), falling back to `EXECUTOR_URL` for a single-org install; the console relay and the Node-hosted MCP server (D48, PLAN-rmcp-remote-worker.md) use the same resolver. The daemon side is Design 9 (loopback default, TLS required off loopback); the account server verifies the daemon's certificate against the pinned CA and refuses plain HTTP to a non-loopback daemon.
