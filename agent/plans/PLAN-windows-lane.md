## Design

D1. Windows is a client role in the fleet, never a worker. A Windows VM runs rdc and reaches the Linux workers; renet never orchestrates it as a target. It is declared by id, `VM_WINDOWS='31'` (address 192.168.111.31, domain `rediacc31`), empty by default, so a plain `ops up` changes nothing. `ops up` creates Windows clients after the cluster orchestration and does not block it; `ops down` and `ops status` include them.
The trade-off: a separate role keeps `VM_IMAGE`, `--os` and the worker orchestration untouched, at the cost of a second creation path in the driver. Folding Windows into `GetKVMImages` was rejected, because every consumer of that list assumes a cloud image, cloud-init and a renet worker.

D2. Image source and licensing. The base is the Windows 11 Enterprise Evaluation ISO, as in the spike (Context 1). Each host supplies its own ISO at `WINDOWS_ISO` (default `$RENET_DATA_DIR/images/win11-eval.iso`), checked against a sha256 pinned in `opsconfig/windows.go`, and the virtio ISO the same way. No baked Windows image is published to ghcr or R2.
UNVERIFIED, to be quoted by WL0 before anyone relies on it: that the evaluation EULA forbids redistributing an installed image, that the evaluation period is 90 days, and that the Evaluation Center download can be scripted without an interactive form.
The alternatives: Windows Server 2025 evaluation (longer period, OpenSSH built in, but not the desktop platform rdc users run, and VS Code desktop behaves differently), or a purchased or subscription licence (removes the expiry, costs money, operator-only). The default is the Windows 11 evaluation with a re-bake before expiry; the bake records its install date and `renet ops windows status` warns 14 days before the period ends.

D3. Bake and reuse. A bake is the measured 36 min (Context 5), so it runs once per host and ISO: `renet ops windows bake` installs to a golden qcow2 (`rediacc-custom-win11-<isohash8>.qcow2`) and shuts it down; `ops up` then creates each Windows VM as a qcow2 overlay on the golden image, the way Linux VMs overlay their base, so a re-create costs a boot (minutes), not a bake.
(corrected 2026-11-27, tester batch 20) The bake also stops Windows Update from rebooting the guest: it stops and disables the wuauserv and UsoSvc services and sets the AU policies NoAutoUpdate=1 and NoAutoRebootWithLoggedOnUsers=1, because an automatic update rebooted the tester VM in the middle of `ops up` at 2026-11-27T01:55Z. The same batch is the first definitive pass of the target this plan automates: `rdc ops up --basic --backend hyperv` on Windows 11 from zero, no hand steps, exit 0 in 461 s, both VMs with fixed memory (the O3-O13 chain of renet and CLI fixes landed on 1121-1).
One client needs no sysprep; more than one Windows client per fleet would share a SID and computer name and needs `sysprep /generalize` in the bake, which stays out of scope until a second client is wanted.
The openssh phase (835 s) stays the long pole; the bake ports setup.ps1 v2 and adds what the suites need: MSYS2 with rsync (winget id `MSYS2.MSYS2` then `pacman -S --noconfirm rsync`, both UNVERIFIED), a hosts entry `fleet-guard-probe` for the guard suite (Context 7), and a VS Code install that fails the bake when `code --version` prints nothing (the v2 failure in Context 5).
The administrator password is generated per bake and stored 0600 under `RENET_DATA_DIR`, as cloud-init passwords already are (`private/renet/pkg/infra/vm/kvm/driver.go:25`), and the authorized key is the renet-staged `id_rsa.pub` the fleet already authorizes (`.claude/agents/ops-vms.md:38-40`); neither is a literal in the repository.

D4. One NIC on `renet11`. `renet11` already NATs to the internet (Context 11), so the Windows VM gets exactly one virtio NIC on it, with the deterministic MAC and a static 192.168.111.31 set in the unattend file's TCPIP component. The two-NIC OVMF hang (Context 6) then cannot occur, and no hot-plug step exists.
UNVERIFIED until WL5: that Windows Setup and winget work through `renet11`'s NAT. The fallback, if they do not, is the spike's arrangement (install on `default`, hot-plug `renet11` after first boot), carried as a driver option rather than a second code path.

D5. Nested Hyper-V. The host has nested KVM and host-passthrough CPU (Context 18), so Hyper-V inside the Windows VM is possible in principle, which would let `rdc ops` itself be tested with the Hyper-V backend on a Windows host. It costs a reboot, RAM (a nested Linux guest inside an 8 GB Windows VM) and an unmeasured slowdown. The Windows client role does not need it; it is a separate probe box (WL14) whose result decides whether a follow-up plan adds a Hyper-V leg.

D6. How the harness talks to the VM: SSH for every test step, the guest agent for bootstrap and diagnosis. SSH is the path a user's terminal takes, runs as the user with their profile, and is what `run-all.sh` already uses.
The guest agent (`guest-exec`, `guest-file-read`) runs as SYSTEM in session 0, so a test through it would not exercise the user's DPAPI keys or PATH; it serves the bake's readiness probe (`C:\rediacc-setup.done`) and log collection when SSH is down. Steps that need the interactive session (VS Code desktop, and DPAPI if SSH key logons cannot reach the user's master key, see Risks) run through a `/IT` scheduled task, as the spike does (Context 6).

D7. The harness: `npm run win:check`, a `vm:check` analogue in `.ci/rediacc_ci/drills/win_check.py`. It takes the fleet lock, builds the CLI bundle and renet once, stages the bundle, `renet.exe`, `renet-linux-amd64` and the fleet key over scp, runs the PowerShell suites over SSH, and judges. Every suite step prints one line `RDC-STEP {"id":..., "rc":..., "expect":..., "ok":...}`; the driver judges those lines, never prose.
Verdicts follow vm:check: VERIFIED 0, FAILED 1, NOT_VERIFIED 77 (`win-vm-unavailable`, `win-bake-missing`, `no-assertions`, `phase-not-run`). The receipt lands in `.ci/cache/win-check/receipt.json` with the shared envelope of `rediacc_ci.proof.receipt`.
Targets: fleet worker 11 by default (ops VMs are development-only, `.claude/agents/ops-vms.md:110`); `--target hostinger` adds the term and sync suites against a hostinger fork with `REDIACC_NO_PROVISION=1` and writes only under the fork's `winspike-test/`, removed afterwards (README:32).

D8. Which suites run first. Wave 1 on Windows, in order: keys (config init, machine add, scan-keys positive, the three negatives each expecting a non-zero exit, and host-key equality against Linux `ssh-keyscan`), guard (refused without override, allowed with override on the boundary, refused with the override injected below the boundary, plus `renet process-ancestry` direct), term (fleet machine 11), sync (MSYS2 rsync round trip with space and non-ASCII names, byte-identical by hash).
Wave 2: DPAPI through an rdc verb that writes secure storage (the verb is UNVERIFIED; WL7 names it from `secure-storage.ts` callers) and vscode connect (desktop session, screenshot kept as evidence, verdict from the `exit=` line). The Linux regression half of `run-all.sh` is dropped: `vm:check` V1.x and the CLI unit suite already own Linux.

D9. Local CI. `win:check` is a local runner (`win-check` in `tiers.live.local_runners`, `RUNNER_NEEDS` value `none`), so a box can carry `Local-route: win-check`. It is NOT a push gate at first: the push guard keeps reading only the vm:check receipt.
Making a Windows receipt required for pushes that touch the win32 paths of Context 14 is an operator decision (Operator-only 3), because it puts a 36 min bake and an 8 GB VM in front of every such push on a fresh host.

D10. The ci.yml lane: a reusable `ci-windows.yml` on windows-latest, called from ci.yml and aggregated by `CI Complete`. It runs (a) the CLI unit suite under `vitest.windows.config.ts`, (b) the guard suite's refusal cases and `renet process-ancestry` with the `renet-windows-amd64.exe` artifact `ci-build-renet.yml` already produces (Context 15), and (c) a bundle smoke: `config init`, `machine add`, and `machine scan-keys` against the runner's own sshd when one is present.
The suite list of (a) is decided by measurement: WL10 runs the whole CLI unit suite on the fleet Windows VM first, and the config either runs everything or excludes the measured failures by name, each with a `BLOCKER:` reason. Remote suites (term, sync, vscode) stay local, because a hosted Windows runner has no Linux worker to reach.
Runner choice, with cost: GitHub windows-latest costs no minutes on a public repository and needs no host (UNVERIFIED billing rule, quoted by WL0), but cannot reach a worker and, UNVERIFIED, offers no nested virtualization.
A Windows VM under KVM on ubuntu-latest (the way ct-tests already boots Linux VMs) would reach a worker, but each run would bake for about 36 min unless a golden image were cached, and a cached image is the redistribution question of D2; the 14848 MB budget (Context 18) also leaves room for a 4 GB Windows VM at most beside bridge and worker.
A self-hosted runner on this KVM host would run the full harness at no minute cost, but on a public repository it lets pull-request code run on the operator's machine; UNVERIFIED that GitHub's hardening guide advises self-hosted runners only for private repositories. Default: windows-latest for (a)-(c), the remote suites through `win:check` locally, no self-hosted runner (Operator-only 2).

## Operator-only

1. Windows licence for the lane. Default: the Windows 11 Enterprise evaluation ISO, supplied per host and re-baked before it expires, nothing published. Alternative: a purchased or subscription licence, which removes the expiry and could permit a cached golden image.
2. A self-hosted runner on the local KVM host for the remote suites in GitHub. Default: none; the remote suites run through `win:check` locally and GitHub runs the windows-latest lane only. Alternative: a self-hosted runner restricted to push-to-main and dispatch, never pull requests.
3. Whether a pushed range touching the win32 paths of Context 14 needs a VERIFIED `win:check` receipt, as VM-facing ranges need vm:check. Default: no, `win:check` stays a local runner with a receipt, and the decision is revisited after WL8 has run for two weeks.
4. Supplying the ISO. Default: each host operator places the ISO at `WINDOWS_ISO` once; if WL0 shows the download can be scripted, `renet ops windows bake` fetches it itself.

## Risks

- DPAPI over SSH (UNVERIFIED): OpenSSH for Windows logs a key-based session on without the user's password, and DPAPI CurrentUser operations can then fail to reach the user's master key. If WL7 sees that, `dpapi.ps1` runs through the desktop-session task, and the finding that SSH-only users cannot store secrets on Windows becomes a CLI defect of its own.
- The evaluation period: a bake past its end fails every Windows step at once; `ops windows status` warns ahead (D2), and the receipt records the bake date.
- Bake time and flakiness: 36 min per bake, with Windows Update speed driving the openssh phase; winget already failed once (Context 5). A golden image per ISO keeps it to one bake per host.
- Host RAM: an 8 GB Windows VM beside the full six-VM fleet (21504 MB) needs about 30 GB; the host had 27 GB available with all seven running (Context 18). `win:check` refuses to start below a stated free-RAM floor rather than swapping.
- Single NIC on `renet11` is unproven for Windows Setup (D4); the hot-plug fallback stays available.
- A full CLI unit suite on Windows can fail widely on POSIX assumptions; the exclusion list in WL10 makes the gap visible by name instead of hiding it.
- Collision with the peer session: win11-spike belongs to console-6c (README:3); WL6 and WL7 use it only after a heads-up message, and from WL5 on the fleet's own `rediacc31` replaces it.
