## Design

D1. Windows is a client role in the fleet, never a worker. A Windows VM runs rdc and reaches the Linux workers; renet never orchestrates it as a target. It is declared by id, `VM_WINDOWS='31'` (address 192.168.111.31, domain `rediacc31`), empty by default, so a plain `ops up` changes nothing. `ops up` creates Windows clients after the cluster orchestration and does not block it; `ops down` and `ops status` include them.
The trade-off: a separate role keeps `VM_IMAGE`, `--os` and the worker orchestration untouched, at the cost of a second creation path in the driver. Folding Windows into `GetKVMImages` was rejected, because every consumer of that list assumes a cloud image, cloud-init and a renet worker.

`rediacc_ci.ops.windows_image` has seven verbs:
- `upload-inputs <iso> <virtio-iso>` hashes both, uploads them and writes `inputs` in the record. It refuses an ISO whose volume label is not an evaluation edition.
- `pack` puts the golden qcow2, OVMF VARS and swtpm state into one zstd tar with its sha256.
- `publish` uploads the image, then writes `image` in the record.
- `fetch` downloads the image, verifies its sha256 and unpacks it into `$RENET_DATA_DIR/images/`.
- `fetch --inputs` downloads both ISOs to `$RENET_DATA_DIR/images/win11-eval.iso` and `virtio-win.iso`, the defaults renet reads, and verifies their sha256. `WINDOWS_ISO` or `VIRTIO_ISO`, when set, wins and skips that download.
- `rebake` runs `fetch --inputs`, then `renet ops windows bake`, `pack` and `publish`.
- `probe` checks that the token reaches its bucket and not `rediacc-public-data`.
`--dry-run` touches neither the network nor the bucket, and the module refuses `rediacc-public-data` as a target by name. An earlier image is deleted only after a newer one has been fetched and verified (WL29).
The record is `.ci/config/windows-image.json`: `{"schema": 1, "bucket": ..., "warn_days": 14, "rebake": "PYTHONPATH=.ci python3 -m rediacc_ci.ops.windows_image rebake", "inputs": null | {"iso": {"key", "sha256", "bytes", "file", "edition", "build"}, "virtio": {"key", "sha256", "bytes", "source"}}, "image": null | {"key", "sha256", "bytes", "edition", "build", "iso_sha256", "virtio_iso_sha256", "installed_at", "expires_at", "expiry_source"}}`. `inputs` and `image` are `null` until their first upload. The image's `iso_sha256` and `virtio_iso_sha256` must equal the `inputs` entries, so an image always names the inputs it was baked from.
The sha256 values `opsconfig/windows.go` pins (WL3) are the same two. WL21's test reads the record and the Go constants and fails when they differ.
The gate `check:ci-windows-image-expiry` (`.ci/rediacc_ci/quality/windows_image_expiry.py`) reads only that file and the clock. A `null` image prints `NO WINDOWS IMAGE RECORDED` and exits 0. A missing or unparseable file is red, and so is an image with `warn_days` or fewer days left (expired included). So is an image whose input hashes differ from `inputs`. The red line names the days left, `expires_at` and the `rebake` command, which needs no human because the ISO comes from the bucket.
The gate's id is in `CLOCK_GATE_IDS`, so the daily drift run goes red and the ops-health post mails, and in `LOCAL_WARN`, so `ci:quick` warns with the re-bake remedy instead of failing the local receipt. Like the other clock gates it blocks PR CI inside the window, and the remedy is one command plus the commit of the new record.
`ops up` with `VM_WINDOWS` uses a golden image found under `$RENET_DATA_DIR/images/`, and bakes from `WINDOWS_ISO` (default `$RENET_DATA_DIR/images/win11-eval.iso`) when there is none. With neither present it refuses, naming `fetch` (and `fetch --inputs` for a bake).

## Risks

- DPAPI over SSH (UNVERIFIED): OpenSSH for Windows logs a key-based session on without the user's password, and DPAPI CurrentUser operations can then fail to reach the user's master key. If WL7 sees that, `dpapi.ps1` runs through the desktop-session task, and the finding that SSH-only users cannot store secrets on Windows becomes a CLI defect of its own. The tester's local run of the dpapi leg passed 34 tests over SSH (findings dpapi), which makes this less likely but does not close it.
- The evaluation period: a bake past its end fails every Windows step at once; `ops windows status` warns ahead (D2), and the receipt records the bake date. The expiry gate (D12) turns PR CI red for the last 14 days until the re-bake commit lands; that is intended, and the remedy is printed.
- Bake time and flakiness: 36 min per bake, with Windows Update speed driving the openssh phase; winget already failed once (Context 5). A golden image per ISO keeps it to one bake per host, and the shared image keeps it to one bake per expiry window.
- Host RAM: an 8 GB Windows VM beside the full six-VM fleet (21504 MB) needs about 30 GB; the host had 27 GB available with all seven running (Context 18). `win:check` refuses to start below a stated free-RAM floor rather than swapping.
- Single NIC on `renet11` is unproven for Windows Setup (D4); the hot-plug fallback stays available.
- A full CLI unit suite on Windows can fail widely on POSIX assumptions; the exclusion list in WL10 makes the gap visible by name instead of hiding it.
- Collision with the peer session: win11-spike belongs to console-6c (handbook `:5`); WL6 and WL7 use it only after a heads-up message, and from WL5 on the fleet's own `rediacc31` replaces it.
- The shared image carries the autologon password in clear text in its registry; a bucket made public by mistake leaks it. `probe` (WL20) refuses an anonymous GET, and the password is rotated by the next re-bake.
- Clients 32-39 cloned from one image share a SID. That is harmless without a domain and is accepted until a domain join is wanted (D3).
- Win32 ssh.exe regressions: a new ops path that execs `ssh.exe` on Windows brings back O11. Every ops call goes through the `sshexec` seam (d8e2b44e), and the `gotest` suite (WL27) runs its tests on Windows.
- The bucket holds an 8.2 GB evaluation ISO, a 0.9 GB virtio ISO and one or two golden images. A private store of Microsoft media depends on WL0's quote, and `upload-inputs` refuses a non-evaluation ISO, since this host also holds one (Context 31).
- An unattended re-bake that publishes a broken image would leave every host without a client. `rebake` keeps the earlier image until the new one has been fetched and verified (WL29), and the record names which inputs built it.
