## Why

The repo shell, the transfer sandbox, repo-key deployment and the VS Code bootstrap have changed several times this wave (renet 21d1e22, 3100a4c, 0033236, bcb9351, and the CLI under packages/cli/src/remote/). Only Go unit tests and CLI unit tests judge those changes. ci:quick starts no VM. The bridge e2e suites run in CI, but none of them drives `rdc` against a VM for repo sync, SFTP, a repo-key shell or VS Code. The one live check for that surface is box V1 of agent/plans/PLAN-shell-sandbox-readonly-view.md, and it is a list of commands for someone to run by hand.

Measured during the investigation: the targeted sequence takes 46-76 s on a warm fleet and 32 s right after a cold start. `ops up --basic` takes 146 s cold (about 97 s of in-VM package setup), `ops down` takes 3-5 s, and the VMs hold 5120 MB. Four flakes turned up, and each one becomes a scripted step here: the SSH host key pinned before a VM rebuild goes stale; minting an account token the investigation's way reset the dev user's password; a deleted fork left its config entry behind (fixed in d105deb15); and the pre-bash scp guard blocks a hand-run upload.

How often it fires. From 2026-09-30 to 2026-10-14 the console had 1911 commits. Of its 57 `private/renet` pointer moves, 10 changed a renet trigger path: dc89a2d97, e3684d061, f56153c61, c42bdbf4c, 38651561c, e5469e1f0, 38ecb987e, 61ca09889, 814f23f77 and 4f0063f11. Every one of those 10 still includes a non-test file. Another 10 commits touched the CLI trigger paths (9 outside `__tests__/`), and two commits appear in both lists, so 18 commits fired in all. Most of them landed on 2026-10-14, in this sandbox wave, so the rate comes in bursts. In renet history alone, 29 commits touched the trigger directories and 20 of them changed test files only. That is the reason for the test exclusion below.

## Design

### 1. The trigger

One Python module, `.ci/rediacc_ci/drills/vm_check_trigger.py`, is the only definition. The script imports it, and so does the guard, through a scoped sys.path insert (`block_unverified_push._policy_rel` at .claude/rediacc_hooks/guards/block_unverified_push.py:922-931; `block_prose_style_commit` imports `rediacc_ci.quality.prose_style` the same way). It follows the shape of `renet_pkg_matrix`: path tuples plus `watched()` (.ci/rediacc_ci/infra/renet_pkg_matrix.py:99-118, :735-736).

- `CONSOLE_PATHS`: `packages/cli/src/remote/` (directory), `packages/cli/src/services/repo/repo-key-deployment.ts`, and `.ci/rediacc_ci/drills/vm_check.py`. The script covers itself, as renet_pkg_matrix's CONSOLE_PATHS lists its own file.
- `RENET_PATHS`, relative to private/renet: the prefix `cmd/renet/sandbox_` (a filename prefix, unlike watched()'s directory-or-exact rule, so the module adds a third form: an entry ending in `_` matches by prefix), plus the directories `pkg/sandbox/`, `pkg/orchestration/` and `pkg/reporuntime/`.
- `EXCLUDE`: `*_test.go` and any path containing `/__tests__/`. Tests change neither the deployed renet nor the CLI bundle (decision D2).
- `changed_paths(root, base, mode)`: console paths from `git diff --name-only <base> <tip>` (mode `push`) or `<base>` against the worktree plus untracked files (mode `worktree`, the rule scripts/ci-runner/run.ts:676-680 uses for ci:quick). When the `private/renet` gitlink differs between base and tip, the module diffs the renet range in the submodule: `git -C private/renet diff --name-only <old gitlink> <new gitlink>`, or `<old gitlink>` against the submodule worktree in mode `worktree`. This is cmd_scope's diff (.ci/rediacc_ci/infra/renet_pkg_matrix.py:760-778) without the network fetch.
- A renet range that cannot be computed (the old gitlink object is missing locally) returns `unknown` with the sha. The guard counts `unknown` as touched and says why, following the turbo guard's rule that a claim it cannot read is not a checked claim (.claude/rediacc_hooks/guards/block_turbo_early_push.py:28).
- `push_base(git, branch)`: a Python port of quick-select.ts `resolvePushBase` (scripts/ci-runner/quick-select.ts:262-294). It tries `@{push}`, then `origin/<branch>`, then `@{upstream}`, then `origin/main`, and skips any tracking ref named for another branch. The script's `--changed` uses it. The guard uses the push's own destination: `refs/remotes/<remote>/<dst>` when it exists, otherwise the merge-base with origin/main.
- `inputs(root, tree)`: the digest the receipt is keyed on. It is sha256 of the sorted `git ls-tree -r <tree> -- <CONSOLE_PATHS>` lines (exclusions applied) plus the tree's `private/renet` gitlink. The script computes the same digest from worktree blobs (`git hash-object` per file plus the submodule HEAD), so what ran and what is pushed compare on equal terms.
- Tests (`.ci/rediacc_ci/tests/test_drills_vm_check_trigger.py`): path cases for each form, including tests-only, sibling-prefix and `msys2/`; fixture repositories with a real gitlink (`git update-index --cacheinfo 160000`), where a pointer move over a `cmd/renet/sandbox_exec.go` change hits, a move over `*_test.go` only does not, a missing old object gives `unknown`, and an unmoved pointer does no submodule work; the six resolvePushBase cases of scripts/ci-runner/quick-select.ts:445-490 replayed against `push_base` with the same expectations; and an `inputs()` digest that is equal across a docs-only commit and different after a trigger-blob or pointer change.

### 2. The script: `npm run vm:check [-- --changed] [--os <image>] [--parent <grand>] [--selftest]`

`.ci/rediacc_ci/drills/vm_check.py` runs as `PYTHONPATH=.ci python3 -m rediacc_ci.drills.vm_check` and is also listed in the drill table (.ci/rediacc_ci/core/run_verbs.py:39-42) as `./run.sh drill vmcheck`. It is built on `rediacc_ci.drills.lib.Drill`, so it inherits the assertion ledger and a summary that never prints the word PASSED over zero assertions (.ci/rediacc_ci/drills/lib.py:430-437). It also inherits the `--selftest` planted-failure convention (:415-429) and the dev-gateway helpers (:445, :635-689).

`--changed` evaluates the trigger with `push_base` in mode `worktree`. With no hit it prints `vm:check: no trigger path changed since <ref> (via <how>); nothing to verify`, writes no receipt and exits 0. It says so out loud, and the guard would not ask for a receipt anyway. Without `--changed` the check always runs.

Rules: every VM action goes through `./rdc.sh`. The script never sets or clears `REDIACC_AGENT`, `CLAUDECODE` or `REDIACC_ALLOW_*`. When the CLI's agent-mode guard refuses a verb (packages/cli/src/utils/agent-guard.ts:74-106, packages/cli/src/utils/command-policy.ts:228-255), the run ends NOT_VERIFIED with class `agent-policy-refused` and the refusal text. The script never uploads with scp. Its only raw `ssh`/`sftp` calls are the read-only probes and the SFTP confinement leg named below, each built from a constant in the module.

Steps, in order. P = preflight and fleet, V = V1's steps, T = teardown.

- P0 lock: an exclusive flock on `rediacc-vm-check.lock` in the directory core_lease uses (.ci/rediacc_ci/core_lease.py docstring: `$XDG_RUNTIME_DIR`, then `/run/user/<uid>`, then `/tmp/rediacc-...-<uid>`). It waits up to `--wait` (default 600 s). If the lock is still held, the result is NOT_VERIFIED `fleet-busy`, naming the holder's pid and session.
- P1 renet provenance: `go version -m private/renet/bin/renet` must show `vcs.revision` equal to `git -C private/renet rev-parse HEAD` and `vcs.modified=false`. When it does not, the script runs `./rdc.sh --version`, which triggers rdc.sh's auto-build, and checks again. A mismatch that survives the rebuild is NOT_VERIFIED `renet-build-mismatch`. Measured today: bin/renet carries vcs.revision a7b5112 with modified=true, while the submodule HEAD and the gitlink are a4c8c613.
- P2 fleet: `/dev/kvm` and `virsh` must be present, or the result is NOT_VERIFIED `no-kvm`. `rdc ops status -o json` gives the running IPs (`running_ips`, lifted into drills/lib.py from its two copies at .ci/rediacc_ci/drills/license.py:115 and .ci/rediacc_ci/drills/backup.py:1482). Reuse mode applies when .1 and .11 are running; teardown then removes only this run's forks. Cold mode applies when neither is running: `./rdc.sh ops up --basic [--os $VM_IMAGE|--os <image>]` (packages/cli/src/commands/ops/up.ts:15,19), and teardown runs `./rdc.sh ops down`. A partial fleet, or an `ops up` with a non-zero exit, is NOT_VERIFIED `fleet-unavailable`, quoting the exit code, the wall time and the last stderr lines. Under `--os`, a reused fleet's image must match, or the result is NOT_VERIFIED `fleet-os-mismatch`. The script never tears down a fleet it did not start.
- P3 host keys: `./rdc.sh machine scan-keys <worker>` (packages/cli/src/commands/machine/register.ts:245-260) runs on every run, before any other SSH, so a rebuilt VM never fails on a stale pinned key. In cold mode, `machine setup <worker>` follows only if VC0 shows that `ops up`'s orchestration leaves it needed.
- P4 account: `./rdc.sh subscription status -o json` with the config's stored token. When that is valid, nothing is minted. Otherwise the dev gateway's port is read with `Drill.gateway_port()`; never hardcode 4800 (.claude/agents/account-dev.md:15). With no healthy gateway the result is NOT_VERIFIED `account-unavailable`, naming `./run.sh account dev`. The script never starts the gateway, because each start re-randomizes the dev passwords (.ci/rediacc_ci/core/account_lifecycle.py:507-531). With a healthy gateway it mints a token for a dedicated login (constant `vm-check@rediacc.dev`) whose password is generated per run and held in memory: `account_ensure_login`, `account_ensure_subscription`, `account_session`, `account_mint_token` (.ci/rediacc_ci/drills/lib.py:635-689; the scopes are those of .ci/rediacc_ci/drills/license.py:510-515). The dev user's password is never reset. The token reaches `rdc` only as `REDIACC_TOKEN` in the child environment, which the CLI ranks above the stored token (packages/cli/src/services/account/subscription-auth.ts:8, :58-66, :121). It never appears on argv, is never written to the config (no `subscription login`), and is never printed. A test asserts that the token's bytes are absent from stdout, stderr, the receipt and the work directory. Decision D3 covers whether a fork may be licensed under a different subscription from its grand; VC0 measures it.
- P5 parent: `--parent` (default `vmcheck-base`) must be a grand repo on the worker in the active config. The script never runs `repo create`; in agent mode the CLI refuses it unless the operator authorized that name before the session started (packages/cli/src/utils/agent-guard.ts:95-106). A missing parent is NOT_VERIFIED `parent-grand-missing`, listing the grands present and the operator's one-time command. P5 also sweeps stale forks: any fork of the parent whose tag matches `vmc-<stamp>-<hex>-[ab]` and whose stamp is more than 1 h old is deleted, and nothing else is touched.
- V1.1 forks: tags `vmc-<MMDDHHMM>-<6 hex>-a` and `-b`, unique per run and within the label grammar (lowercase letters, digits and hyphens, at most 63 characters; packages/shared/src/ref/index.ts:32, :92). `./rdc.sh repo fork <parent> --tag <t> --up` (packages/cli/src/commands/repo-fork.ts:554-562) brings each up and deploys the branch's renet. Assert: a deployed `renet version` read through a read-only ssh probe equals P1's revision. The guid of B comes from `repo list -o json`.
- V1.2 cross-repo: from A's repo shell (`./rdc.sh term connect <parent>:<a> -c '...'`, packages/cli/src/commands/term.ts:462-467), `chmod 0777` and `touch -m -d @0` on `/mnt/rediacc/mounts/<guidB>/.rediacc.json` each fail with `Read-only file system`. B's own shell runs `stat -c '%a %Y'` on the file before and after, and the values match. That replaces V1's machine-level stat, which a machine shell would need; agent mode refuses machine shells (packages/cli/src/utils/agent-guard.ts:74-86).
- V1.3 positive set inside A, each rc 0: write to `~`, `/tmp`, `/dev/shm` and the mount; `chmod 600` in the mount; `docker ps`; `renet compose -- ps`; a git commit in the mount; `vi -c wq ~/v`.
- V1.4 isolation: B's `ls /dev/shm` does not show A's marker. A's `cat /proc/self/cgroup` names `renet-exec-<networkId of A>`. `renet sandbox-exec --detect` runs inside the shell, and its Status and ABI lines go into the receipt (E1's measurement on this image).
- V1.5 sync: `repo sync upload <a> --local <fixture dir> --verify`, then `download` into a second directory, then a byte comparison. The fixture is generated per run with a nested directory, a 0600 file, a symlink and a 1 MiB file.
- V1.6 VS Code: `./rdc.sh vscode connect <parent>:<a> --url-only` (packages/cli/src/commands/vscode.ts:431-442) runs the env setup and prints the URI without starting VS Code. Assert the URI and `<mount>/.vscode-server` through A's shell. On a host where `detectVSCode` refuses (packages/cli/src/commands/vscode.ts:79-86), the step is not run, and the result is NOT_VERIFIED `vscode-absent`, never silently skipped.
- V1.7 SFTP confinement: `sftp -b` through the per-repo SSH alias and identity file that V1.6 wrote (packages/cli/src/commands/vscode.ts:413-418). `put` into A's mount succeeds; `put` into, and `chmod` on, `/mnt/rediacc/mounts/<guidB>/` are refused; B's stat is unchanged. The repo-key deployment that sync performs is itself an SFTP write (packages/cli/src/commands/repo-sync.ts:201-202), so V1.5 covers that half.
- T teardown, in `finally`, which also runs on SIGINT and SIGTERM through a handler that raises: `./rdc.sh vscode cleanup -c <connection>`, then `repo delete` of each fork this run created. Assert that neither tag remains in `repo list -o json` (the d105deb15 behaviour). Then `ops down` in cold mode only, and finally release the lock. A teardown failure turns the result into NOT_VERIFIED `teardown-failed` and lists every leftover: teardown is part of the step.

Verdicts and exit codes: VERIFIED (every assertion passed, teardown clean, exit 0); FAILED (a V-step assertion failed, exit 1); NOT_VERIFIED (the check could not judge, exit 77, the could-not-run code of .claude/rediacc_hooks/guards/block_unverified_push.py:1052). An interrupted run is NOT_VERIFIED `interrupted`. What NOT_VERIFIED looks like:

    === vm:check summary ===

      P0   ok      lock acquired (waited 0 s)
      P1   ok      renet a4c8c613 built clean
      P2   FAIL    fleet: ./rdc.sh ops up --basic rc=1 after 41 s
      --   skip    V1.1-V1.7 not run: no fleet
      T    ok      nothing to tear down (no fork created; the fleet was never up)
      vm:check NOT VERIFIED (fleet-unavailable): ops up --basic exited 1: "<last stderr line>"
      Nothing on the VMs was judged. The push guard treats this tree as NOT verified.
      receipt: .ci/cache/vm-check/receipt.json (status NOT_VERIFIED, tree 3f2a..., renet a4c8c613)

### 3. The receipt

`.ci/rediacc_ci/drills/vm_check_receipt.py` writes and reads it, and the guard imports it the same scoped way. It is written on every run, including a crash past P0. The latest receipt is `.ci/cache/vm-check/receipt.json`, archived as `.ci/cache/vm-check/<tree>.json`. `.ci/cache/` is already gitignored (.gitignore:149). Fields:

`schema` (1); `status` (VERIFIED | FAILED | NOT_VERIFIED); `reason` (`{class, detail}`, null on VERIFIED); `tree` (HEAD^{tree} at the start); `head`; `inputs` (the trigger digest of section 1, computed from the worktree); `renet` (`{pointer: HEAD:private/renet, checkout, built, modified, deployed}`); `trigger` (`{base, via, hits[]}`); `fleet` (`{mode: reused|cold, os, ips[], landlock: {status, abi}}`); `forks` (`[{tag, guid, created, deleted}]`); `steps` (`[{id, desc, rc, verdict, ms, evidence}]`, where evidence is at most 200 bytes and secret-free); `teardown` (`{ok, leftovers[]}`); `runId`, `startedAt`, `finishedAt`, `wallMs`.

Keying: the guard admits a receipt whose `tree` equals the pushed tree, or whose `inputs` equals `inputs(root, pushed tree)`. Either way `status` must be VERIFIED, `renet.built == renet.pointer`, and `renet.modified` must be false. The `inputs` route is the receipt-advance idea of .claude/rediacc_hooks/guards/block_unverified_push.py:14-16: a later commit outside the trigger paths does not cost another VM run, while any trigger blob or a pointer move voids the receipt.

### 4. The push guard: a new `block_vm_unverified_push.py`, not an arm of block_unverified_push

Why a new guard: block_unverified_push is golden-backed (no OWN_SUITE; its golden is .claude/rediacc_hooks/tests/goldens/block_unverified_push.jsonl). An arm there would move frozen golden rows on every refusal. Its `dropped_verdict` (.claude/rediacc_hooks/guards/block_unverified_push.py:1198-1250, called at :1724) is the precedent for "touched, so prove it", but its receipt is another runner's. A new guard declares `CHAIN = "pre-bash"`, `OWN_SUITE = True` and `ORDER = 62`, the slot after block_user_only_command_shell_write at 61. Registration is the guard existing in the directory (.claude/rediacc_hooks/guards/__init__.py, `modules()` scan). It imports block_unverified_push for `every_push_deletes_only`, `pushes_only_origin_main` and `pushed_tree`, as block_push_with_unrecorded_reviews already does (:29, :196).

Scope, the same as .claude/rediacc_hooks/guards/block_unverified_push.py:1621-1676: a command-position `git push` in this checkout. Not judged: a dry run, a delete-only push, a push of what origin/main already is, a submodule push (the console pointer push carries the range), or another repository. A broken environment (no git, no root) lets the push through and warns, like the siblings.

Verdict: `hits = trigger.changed_paths(root, base, "push")` for the pushed tip. No hit: allow, silently, with no git cost beyond the diff. Otherwise read `.ci/cache/vm-check/<pushed tree>.json`, then `receipt.json`:

- no receipt: refuse, naming the hits (up to 10), `npm run vm:check -- --changed` and its cost (about 1 min warm, about 2.5 min cold);
- NOT_VERIFIED: refuse, quoting `reason.class` and `reason.detail`;
- FAILED: refuse, naming the failed step and its evidence;
- VERIFIED but with other inputs, or with a renet build that does not match: refuse, saying which;
- VERIFIED and matching: allow.

The escape: `VM_CHECK_PUSH_REASON='<kind>: <why, 40+ chars> ASKED:<YYYY-MM-DDTHH:MM>Z'`. It is read from the push's own environment assignment through the shared lexer (`run.env`), exactly as TURBO_PUSH_REASON is (.claude/rediacc_hooks/guards/block_turbo_early_push.py:79), so a prefix, an earlier `export` or `env NAME=` all count, and prose does not.

- Kinds:
  - `vm-unavailable`: a NOT_VERIFIED receipt for these inputs must exist, so the attempt was made; the ledger copies its class.
  - `not-runtime`: the touched change cannot alter what runs on a VM; the why names the files.
  - `deadline`: production or CD state that cannot wait; the why names it.
- Every kind needs the `ASKED:` minute, and that minute must match an AskUserQuestion answer in the session transcript within 300 s. The check is `wl_checks._asked_in_transcript` (.claude/hooks/stop/wl_checks.py:292-293, :354-368), the evidence rule of the review waiver (.claude/hooks/stop/wl_review.py:2860-2880). The transcript comes from the payload's `transcript_path`, the way block_plan_without_depends reads it (:257-270). The check proves an operator answer exists at that minute, not that the answer was to this question, so it narrows the escape to the operator's own turn rather than closing it. The operator's own `!` command never reaches PreToolUse (.claude/rediacc_hooks/guards/block_turbo_early_push.py:24).
- `MIN_WHY = 40`, twice turbo's 20 (.claude/rediacc_hooks/guards/block_turbo_early_push.py:63), because the field has to name files or a deadline, not just a kind.
- Ledger: one JSON line per admitted act in `agent/ledgers/vm-check-push-reasons.jsonl` with `ts`, `branch`, `head`, `tree`, `renet`, `kind`, `why`, `asked`, `hits[:10]`, `receipt` (`{status, class}` or null), written only once every act in the command is admitted (`_row`/`_record` shape, .claude/rediacc_hooks/guards/block_turbo_early_push.py:357-381). Written at ORDER 62, it is the last guard, so the line is a true admission record. Turbo's docstring says turbo runs "LAST in the chain" (:22). That has been untrue since guards 58-61, and this guard can refuse a push turbo has already logged. VC4 rewrites that sentence to say so.
- `DEFECT = ("if not hits:", "if True:")` makes every push look untouched. The own suite also plants `inputs-always-equal` and `asked-always-true` and requires each to flip a refusal.
- Differential: `FIXTURES` are console-shaped worlds with a real `private/renet` gitlink: docs-only push; CLI touched with no receipt; CLI touched and VERIFIED; NOT_VERIFIED; FAILED; renet range touching `sandbox_exec.go`; renet range with tests only; a receipt for another pointer; a receipt advanced by a docs commit; a missing old renet object. `ENVS` hold one per world plus a transcript fixture with one AskUserQuestion answer. `EDGE_CASES` cover each kind valid, an unknown kind, a short why, no ASKED, an ASKED that matches no answer, `vm-unavailable` with no NOT_VERIFIED receipt, a dry run, a delete push, the mirror push of main, `git -C private/renet push`, prose naming a push, and a scratch repo. `test_guards_differential.py` cross-feeds these (:766-780 require the `test-<stem>.py` suite for an OWN_SUITE guard). The own suite `test-block_vm_unverified_push.py` follows test-block_turbo_early_push.py: both directions through `dispatch.py` and the ledger read back.
- Registration points: the guard file (scan); ORDER 62 contiguous (.claude/rediacc_hooks/tests/test_dispatch.py:118-165); the suite beside it; `scripts/data/hook-inventory-baseline.json` (read by check:ci-hook-integrity through `rediacc_ci.quality.hook_integrity`); `.ci/config/python-env-registry.json` for the suite's `PATH` and the script's env reads (`VM_IMAGE`, `VM_CHECK_PARENT`, `DRILL_KEEP_WORK`), checked by check:ci-python-env-registry; CLAUDE.md's push bullet (outside the `pr.turbo-batch-end` scope block, so scope-mirrors.json does not move); the hook section of docs/agent-reference/ci-gates.md.

## Decisions taken with defaults (veto any)

1. D1 (parent grand): default `vmcheck-base`, which the operator creates once per fleet outside agent mode, or authorizes by name before the session starts. A cold fleet therefore ends `parent-grand-missing` unless that was done. The alternative, forking any grand already on the worker, is rejected: it ties the check to whichever repo happens to exist.
2. D2 (test exclusion): `*_test.go` and `__tests__/` do not fire the trigger. They leave the deployed binary and the bundle unchanged; 20 of 29 renet commits on these paths were test-only.
3. D3 (subscription): mint under a dedicated `vm-check@rediacc.dev` login so the dev user's password never resets. If VC0 shows that a fork cannot be licensed across subscriptions, the fallback is the stored config token only, with no minting: `account-unavailable` names `rdc subscription login` for the operator.
4. D4 (msys2): `packages/cli/src/remote/msys2/` stays in the trigger because it is in the operator's list, although a Linux VM cannot exercise it.
5. D5 (ledger tracking): the new ledger follows turbo's: untracked and not ignored (today `git ls-files agent/ledgers` lists no turbo-push-reasons.jsonl). Whether guard-written ledgers are committed is left to whoever settles turbo's.

## Risks

- A reused fleet is shared. V1.1 deploys this branch's renet onto vm11 under any other session's e2e run. The lock covers only vm:check runs, and the receipt records `fleet.mode` so a reviewer can see it.
- SIGKILL skips `finally`. P5's sweep of stale `vmc-` forks is the backstop, so a leftover lives at most until the next run plus 1 h.
- Push clones: the receipt lives in `.ci/cache` of the checkout that ran the check. A push from a separate clone finds none and is refused, the same limitation block_unverified_push has.
- The Python `push_base` mirrors resolvePushBase by a replayed case table, not by live parity, so a later change to the TS can drift unnoticed. VC1's test names the TS lines it mirrors.
- An account token binds to the client IP on first use (.claude/agents/account-dev.md:42). Every use here is from one host, but a run through a VPN switch fails P4 as `account-unavailable`.
- `vscode connect --url-only` writes an SSH alias and VS Code settings into the real home. Teardown's `vscode cleanup` removes them, and a cleanup failure is a `teardown-failed` leftover.
