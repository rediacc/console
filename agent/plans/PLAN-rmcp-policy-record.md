## Ask

The authorization policy (which commands each user and team may run, on which machines and repos, with grand-repo and cluster-op switches) must be writable only by the people D29 names, readable by every member and every executor that serves them, and still unreadable by the server (D25, D27).

- **Its own record.** The policy leaves the config document for a separate record encrypted under the store CEK, with its own endpoint and its own version.
- **Roles at write.** Org policy: owner or admin. Team policy: that team's team_admin, or an org owner or admin. Every write needs 2FA and an elevated session; a passkey is optional unless the store sets `requirePasskey` (D28).
- **Ceiling at evaluation.** The effective policy is the org policy intersected with the team policy, deny wins, and a key the org locks is ignored in the team policy and flagged (D29, D30).
- **Grand repos by glob.** `allowGrandRepos: boolean | string[]` with the existing matcher (D26).
- **History is an audit event**, with no stored versions (D31).

## Design

### 1. The record

- One row per (store, config entry) in a new table `config_policies`: `config_store_id`, `config_id`, `team_id` (nullable for the org-level config), `version` (integer, starts at 1), an inline `ciphertext` column (the document is small; a size test confirms it stays under the D1 statement limit), `cek_generation`, `updated_by_user_id`, `updated_at`.
- The blob is `configEncrypt` under the CEK with AAD `'rediacc-policy-aad-v1' NUL canonical({v:1, storeId, configId, teamId|null, version, cekGeneration})`. The server applies the org-passphrase layer as for configs. A swapped, replayed or cross-team blob fails the GCM tag.
- **Rollback guard.** The CLI records the highest policy version per config in its token file beside the config high-water mark and refuses a lower one; the web client keeps it per session.
- **CEK rotation** re-encrypts every policy record in the same rotation commit as the configs (the rotating admin already re-encrypts every team's config).

### 2. The schema

- `allowGrandRepos: z.union([z.boolean(), z.array(z.string().min(1))]).optional()`; a list matches the repo name through `matchesGlob`; `true` equals `['*']`.
- Org policy only: `locked: z.array(<PolicyRule key enum>).optional()`. A team policy that sets a locked key keeps the key in storage (so the UI can show it) and evaluation ignores it.
- For a REMOTE config, `RdcConfigSchema` refuses a `policy` field, `/policy` leaves sensitivity.ts, and no reader consults `config.policy` any more. The server cannot see a policy inside a pushed blob (finding 1), so the guard is that a forged `config.policy` is inert: every reader takes the effective policy from the record only, and the CLI and web refuse to build a push that carries the field.
- A LOCAL-file config (no `remote` block) keeps an optional `policy` field as a ceiling (D24).

### 3. Wire contract (fixed here so S1, A1 and W1 run in parallel)

| Route | Auth | Body / answer |
|---|---|---|
| `GET /configs/:id` (existing pull) | unchanged | adds `policy: {version, cekGeneration, blob} \| null` beside the config blob, so the executor and CLI get both in one request and egress needs no new route |
| `GET /configs/:id/policy` | session or config token, read rule of config-team-access | `{version, cekGeneration, blob} \| 404` |
| `PUT /configs/:id/policy` | session + `requireTwoFactor()` + `requireElevated()` + role (org config: owner/admin; team config: that team's team_admin or owner/admin) + `requirePasskey` honoured | `{baseVersion, cekGeneration, blob}` -> `{version}`; 409 on version conflict; 403 `policy_role` |

Each successful PUT logs `config.policy.updated` with store, config, team, actor and new version, never content (D31).

### 4. Evaluation

- New `mergePolicies(org, team)` in packages/shared/src/policy/merge.ts: for each key, the team value applies only if the org does not lock it and the result is no wider than the org's (allow lists intersect, deny lists union, booleans AND, `allowGrandRepos` globs combine as "org allows AND team allows"). Locked keys the team set come back as `ignoredLocked: string[]` for the UI.
- `evaluatePolicy` keeps its tier walk inside one document; the effective document is the merge. The decision function of PLAN-rmcp-decide.md consumes the merged document.

### 5. Read path

- `packages/cli/src/services/config/policy-record.ts` (new): fetch with the pull, decrypt with the session CEK, check the high-water mark, return the merged effective policy for (config, team). A local-file config reads its own `policy` field as the ceiling.
- The executor's container loader calls the same module once PLAN-rmcp-writeback.md has landed its loader changes (box C2).

### 6. UI

- Permissions page: a selector for the org policy or one team's policy; role-aware save through `PUT /configs/:id/policy`; locks editable on the org policy only; a team policy shows ignored locked keys and attempted widenings as flagged rows; the preview uses `mergePolicies` plus `evaluatePolicy`.
- ConfigEditor: the policy is no longer part of a remote document, so the omission comment and its config-leaves special case are removed.

### 7. Key slots (D36, D39, D43-D46)

- **Methods.** The slot enum becomes `passkey | recovery`. `password` leaves `SlotMethod`, `SlotKdfParams`, the account column enum, the DTOs, every web builder and page, the CLI commands and the i18n keys. Migration 0093 deletes password rows (only the 9 test stores of D32 can hold any; K-M1 re-enrolls them first) and narrows the enum. `PUT /slots/password` and `POST /configs/password-enroll` are deleted, not deprecated.
- **Recovery kit, mandatory.** Every enrollment (store setup, member acceptance, and adding a slot on a new device when the user has no kit yet) generates a recovery code in the client (`RC1-`, 160 random bits, HKDF as today) and blocks completion until the kit is saved. `packages/shared/src/config-crypto/recovery-kit.ts` renders the kit content: store name, user email, creation date, the code in groups, a QR of the code, and recovery instructions. The web offers download (a PDF generated client-side) and print (a dedicated print stylesheet); the CLI writes a text kit to a path the user names and prints the QR in the terminal. A save check follows: the user types the last 4 characters of the code or scans its QR back; a wrong answer re-shows the kit. There is no decline path and no org-level switch. The code never leaves the client unwrapped; the server stores only the recovery slot as today. Regenerating a kit replaces the recovery slot and invalidates the old printout. Keeping the printout is the user's responsibility, and the UI says so at the save step.
- **Safety net (D44).** Every member holds a kit by construction. The server still refuses a deletion that would leave the store with fewer than two key holders and no recovery slot (`deleteSlot`, `removeMember`, and member self-leave), with error code `CONFIG_SAFETY_NET` and a message naming the rule. A key holder is a distinct user with a passkey or recovery slot at the current `cekGeneration`; machine secrets and agent grants do not count. Because a lost printout is invisible to the server, the key-slot page advises store owners to add a second key holder whenever the store has only one.
- **Machine secrets (D46).** New table `config_machine_secrets` (store, owning user, label, scope team or config, HKDF kdfParams, wrappedCek, createdAt, lastUsedAt, revokedAt), separate from `config_key_slots` so the (store, user, method) unique index and the "any slot = member" check (config.service.ts near :2314) never count it. The portal mints one in the browser session that holds the CEK: a generated secret (`RM1-`, 160 random bits), shown once, wrapped like a recovery slot. `POST /configs/machine-enroll` (`config:enroll` api token, body `{ machineSecretId }`) returns kdfParams, wrappedCek and a fresh config token scoped to the secret's team; the CLI derives the slot secret from the secret it was given out of band. Revocation deletes the row and the config tokens minted from it. `rdc config remote enable --machine-secret <id>` reads the secret from stdin or `REDIACC_MACHINE_SECRET`, never from argv.
- **Phone over QR (D45).** Passkey registration and assertion pass WebAuthn hybrid hints so a desktop without a local PRF authenticator can use a phone. The passkey slot records `credentialId` and the transport it was enrolled with in its kdfParams; unlock requests that credential with that transport, and a PRF result that fails to unwrap prompts re-enrollment instead of a generic decryption error. Real-device repeatability is proved in K-L1 before release.


### 8. Per-config subkeys (D56)

- **Envelope v4.** Each config gets its own random 256-bit content key. The config blob is encrypted under that key instead of the org CEK; the content key is wrapped under the CEK (AES-GCM) with AAD `rediacc-config-key-v1 NUL canonical({storeId, configId, teamId, configKeyVersion, cekGeneration})`, and the wrap travels in the envelope as `wrappedConfigKey` next to the commitments. The blob AAD of envelope v3 (`packages/shared/src/config-crypto/selective.ts:15`, `:58`) gains `configKeyVersion`. `ENVELOPE_VERSION` (`packages/shared/src/config-crypto/constants.ts:39`) becomes 4; the server refuses a v3 push and answers 426 `CONFIG_ENVELOPE_UNSUPPORTED` to a v3 reader (`private/account/src/routes/configs.ts:157-184`), a clean break.
- **Who holds what.** A member with a key slot unwraps the CEK and then any config's content key it may read. The executor for a user session derives the content key of the one config it loaded; an agent grant receives only its config's wrapped content key (PLAN-rmcp-agent-grants.md Design 1). The policy record (Design 1) stays under the CEK, because it is org- or team-wide.
- **Rotation.** A CEK rotation re-wraps every content key, which is cheap; a content-key rotation (`configKeyVersion` + 1) re-encrypts one config and kills that config's agent grants.
- **Read and write paths.** Shared crypto (`packages/shared/src/config-crypto/config-key.ts`, new), the CLI client (`packages/cli/src/services/config/config-server-client.ts:97` sends the envelope version), the executor loader (`packages/cli/src/services/serve/container-config.ts:164`), and the web session (`private/account/web/src/api/config-session.ts`).
- **Migration.** The 9 stores of D32 are re-encrypted by hand: each operator or test owner pulls under v3 and pushes under v4 with the new client before the server refuses v3.
