10. **Security guide (D37).** A new page `security-model.md` (category Guides, subcategory account, tags security and account) in 13 locales, linked from config-storage, account-security and architecture. Sections:
    - **Who can see what.** The three config layers in one paragraph, then a table by attacker capability: a database copy only (no config content: blobs live in object storage), database plus object storage (still nothing: layer 3 needs the Worker secret and layer 2 needs a slot secret), a full server compromise (layers 1 and 3 fall; the CEK stays behind passkey PRF output and the 160-bit recovery kit, neither guessable), a removed member (keeps what was already pulled until a CEK rotation), a leaked agent URL (acts as that user on its one config until expiry, at most 30 days and 7 by default, or revocation; it carries only that config's subkey, so no other config of the org is exposed; the URL alone opens nothing outside the hosted executor of its region). Account login passwords are hashed with PBKDF2 at 100,000 iterations, the Workers Web Crypto ceiling, so the guide states that a database copy enables offline guessing of login passwords and that 2FA is the control (D35).
    - **Key scope (D47).** One config store per org, enforced by the setup route's existence check (private/account/src/routes/configs.ts:498-504, 409); `config_stores` itself carries only a plain index on `org_id` (private/account/src/db/config-schema.ts:16-22, :48), so the guarantee is a check-then-insert, not a unique constraint. One CEK per store. Key slots are unique per (store, user, method) (private/account/src/db/config-schema.ts:122-123), so a recovery kit is one per user per org: a user in two orgs holds two kits, and no team kit exists. Teams are server-side access control, not cryptographic isolation (DESIGN-CONFIG-STORAGE.md, "Team scoping", ruling E1), so a kit opens the whole org's CEK. Machine secrets are one per machine per org; agent grants are one per URL and reach exactly one config (D55). Each config has its own subkey under the CEK (D56): a kit or key slot still opens every config of the org, while an agent grant opens only its config, which is the blast-radius difference the page explains with the key-scope diagram.
    - **Agent URLs and regions (D54, D55, D58).** An MCP URL lives 7 days by default and 30 days at most, reaches one config, and belongs to one region (eu, us or asia): its grant, the config, the keys and the executor stay in that region, and a URL presented to another region is refused with the right region named, never forwarded. On-premise is a single region. Executor occupancy is not published (D52) and needs no user-facing text.
    - **What is recoverable.** A lost passkey (recover with the kit, then enroll a new passkey), a lost kit (regenerate it from a working passkey; the old printout stops working), losing both (an owner or admin re-adds the member through the member handoff), the last key holder losing both (unrecoverable; why the key-slot page advises a second key holder), member removal, CEK rotation, a lost repository LUKS credential, and backups. Every member receives a mandatory recovery kit at enrollment and keeping it is the member's responsibility (D43 as changed by the operator).
    - **Agents and remote MCP.** Agent grants, expiry and re-authorization, per-URL opt-ins, the rule that an agent acts only where a human opt-in and the policy ceiling both allow it, and what an agent can never do (edit policy, read secret values, widen its own grant). An on-premise subsection states the differences: no Cloudflare in the path, the Worker secrets of the cloud become environment variables or config on the customer host (so host access replaces the Worker-secret boundary in the attacker table), and tool calls run on the customer's own daemon executor.
11. **Unlock methods (D38, D39, D43-D46).** DESIGN-CONFIG-STORAGE.md drops the "Passkey with PRF (Required)" claim and every master-password slot passage: unlock is a PRF passkey (locally or a phone over QR) or the mandatory recovery kit; headless machines enroll with a generated machine secret; the safety-net rule is stated. config-storage.md (en and 12 locales) loses the master-password method and its PRF-compatibility advice to fall back on a password, and gains the kit step, phone over QR and machine secrets.
12. **Diagrams (D47).** Six SVGs in packages/www/public/img/, named like the existing `account-*.svg` set, embedded as markdown images (`![Key hierarchy](/img/security-key-hierarchy.svg)`, the form account-management.md uses for `/img/account-role-hierarchy.svg`):
    - `security-key-hierarchy.svg`: the three encryption layers and who holds each key (SDK layer and org passphrase: the server; CEK: slot holders only).
    - `security-who-can-see.svg`: the attacker-capability matrix of Design 10 (database only, database plus object storage, full server compromise, removed member, leaked agent URL).
    - `security-key-scope.svg`: org, its one store, the CEK, the configs; teams drawn as access control around configs; one kit per user per org.
    - `security-unlock-recovery.svg`: passkey on the device, phone over QR, the mandatory recovery kit, machine secrets, agent grants, each arrow ending at the CEK.
    - `security-remote-mcp-flow.svg`: client, MCP Worker (OAuth or bearer, split secret), org executor with the CEK in RAM, machines; the expiry and re-authorization branch.
    - `security-policy-ceiling.svg`: org ceiling intersected with team policy, locked keys, and agent = opt-in AND ceiling.
    Colours are literal hex values only: scripts/gates/check-svg-theme-reach.ts forbids `var(--` in SVGs loaded through `<img>`. Each diagram is checked legible on the light and the dark theme. Labels are short English words; the 12 locale pages reuse the same files and translate only the alt text and the caption below each image, which keeps one SVG per diagram. DESIGN-CONFIG-STORAGE.md may embed the first four by relative path.
