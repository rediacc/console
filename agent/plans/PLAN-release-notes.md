## Design

D1. The trailer. `Release-Note: <customer text>` or `Release-Note: none -- <reason>` (reason at least 12 characters), one per commit, read by `git interpret-trailers --parse` like `PR-TASK:`. The text is one line, at most 200 characters, in customer language: it names what a customer sees or can now do, never a file, module, hook, plan, worklist id or internal codename, and it follows the prose style (no second or first person, `docs/agent-reference/prose-style.md` R1/R2), checked through `.ci/scripts/quality/check_prose_style.py`'s rule set so the hook and the gate agree.

D2. Who must carry it. Required when the Conventional Commits type is `feat`, `fix` or `perf` (with or without scope or `!`) AND at least one changed path is a customer path. A customer path is any path outside the internal list in `.ci/config/release-notes.json` (`.claude/**`, `.ci/**`, `agent/**`, `scripts/**`, `.github/**`, `docs/agent-reference/**`, test globs, and the per-submodule equivalents). Every other type (`chore`, `ci`, `test`, `docs`, `style`, `refactor`, `build`, `revert`), every gitlink-only commit, every record or review commit (paths inside `.ci/policy/record-paths.json`) and every commit whose paths are all internal is exempt; an exempt commit that carries the trailer anyway is accepted and its note is collected. One module, `.ci/rediacc_ci/release/release_notes.py`, owns the grammar, the requirement rule and the collector, and the hook, the land check, the CI gate, the Release body and the page data all import it.

D3. Collection without duplication. For a range `<start tag>..<end ref>` the collector reads the console commits in the range, then for each submodule the gitlink delta (`git ls-tree <start tag> private/<sm>` against `git ls-tree <end ref> private/<sm>`) and the submodule commits `old..new` in that submodule. The console gitlink bump is exempt (D2), so a submodule note is counted once, from the submodule commit. Notes are keyed by `(repo, sha)` and then deduplicated by normalized text, so a fix that lands as a console commit and a submodule commit with the same note appears once. `none` notes are counted, never shown.

D4. Grouping. `feat` -> Added, `fix` -> Fixed, `perf` -> Improved; a `!` or a `BREAKING CHANGE:` footer prefixes the note with "Breaking:" inside its group. The same grouping is used in the Release body and on the page, newest version first, notes in commit order inside a group.

D5. The start tag. The notes start at the newest `v*` tag older than the new one that HAS a GitHub Release, read through the GitHub API (`gh release list`), never from local tags and never from the `production` ref. An orphan tag (a tag with no Release) is skipped as a start, and its changes fall into the next Release's range. The body names any skipped orphan ("v4.0.0 was tagged but not published; its changes are listed here").

D6. The Release body. `create_github_release` drops `--generate-notes` and passes `--notes-file <rendered body> --notes-start-tag <start tag>`; the body holds the three groups, a "No customer-facing changes recorded in this range." line when all three are empty, the orphan line of D5, one line naming the current stable version ("Stable: vX, marked Latest; this is an edge release"), and `**Full Changelog**: <repo>/compare/<start tag>...v<V>`. `--latest=false` stays. A `--dry-run` flag prints the body and the `gh` argv and writes nothing. The existing v4.0.1 body is left as is, and no Release body is rewritten.

D7. Orphan tags. An orphan tag is never deleted: the submodule tags and pinned artifacts of that run may already reference it. The retry path of `.github/workflows/cd-release-edge.yml:663-678` keeps completing the Release of its own version, now with the trailer body. A new patch run whose previous tag is an orphan prints a `::warning::` naming it and folds its range in per D5. `create_github_release` refuses when the tag already exists at a commit other than `GITHUB_SHA`, the v2.4.0 shape.

D8. One computation, two consumers. `publish` (full history and submodules) renders the notes once as JSON (`version`, `start_tag`, `orphans`, `groups`, `stable`) and uploads it to the immutable `cli/v<V>/release-notes.json` on the releases origin; `tag-and-release` and the local entry render the Release body from that file, and the www build reads it over HTTP. The local entry computes and uploads it in the same order. Load-bearing, verified in RN5 before relying on it: that `publish` uploads to `cli/v<V>/` before `deploy-marketing-edge` starts, and that the local entry has an equivalent step.

D9. The stable record. The stable promote appends `{version, promoted_at}` to `cli/stable/history.json` on the releases origin, kept out of the edge-to-stable copy (`promote_r2_to_stable.META_EXCLUDES`), in both the soak promote and the `publish_stable` hotfix lane. The history is backfilled once from the successful `cd-release-stable.yml` runs (`gh run list --workflow cd-release-stable.yml --status success`, each run's promoted version), cross-checked against the version the `production` tag names through the API. An edge version E is "in stable since S" for the oldest S in the history with S >= E.

D10. The page data. `.ci/rediacc_ci/release/changelog_data.py` runs before `astro build` (chained in the www `build` script, since `ignore-scripts=true` also skips npm pre-scripts) and writes a gitignored JSON beside the page: every version with a GitHub Release, newest first, plus `APP_VERSION` as the top entry when it is a real version not yet published, each with its groups from `cli/v<V>/release-notes.json` and its stable marker from D9. It fails the build when a fetch fails (the same rule `downloads.astro` follows), and with no `APP_VERSION` (CI www build) it renders the published versions only. The page renders the groups in English, the chrome through `pages.changelog.*` (new keys for the group titles, "In stable since", "No customer notes recorded for this version", "Earlier history"), and keeps the existing dated entries below as "Earlier history".

D11. Backfill. History before the trailer is not reconstructed: versions older than `since` in `.ci/config/release-notes.json` (the first version cut after RN4 lands) show "No customer notes recorded for this version" and a link to their GitHub Release, with the stable marker still computed. No curated summary is written by an agent; one can be added to the "Earlier history" block later as ordinary page content.

D12. Docs. `docs/agent-reference/release-process.md` states that Latest is stable and only `mark_production` moves it, the body format, the start-tag rule, the orphan rule, the notes file and the stable history; `docs/agent-reference/versioning.md` states that local tags are not authoritative (`production` is read through the API, and `git fetch origin '+refs/tags/*:refs/tags/*'` refreshes a stale one); `docs/agent-reference/ci-gates.md` *Commit policy* lists the `Release-Note:` trailer beside `PR-TASK:` and `Plan-Box:`.

## Risks

- A requirement that fires on internal work trains authors to write `none -- n/a`. The internal path list (D2) keeps the trailer off tooling commits, and the 12-character reason refuses a bare `none`.
- An internal name leaking into a customer note. D1's name check catches file paths and plan or item ids; a codename list in `.ci/config/release-notes.json` covers the rest.
- A www build that reaches the network can fail a deploy. D10 fails loudly by design rather than shipping an empty page, the same trade `downloads.astro` already makes.
- The stable backfill depends on GitHub's run history; runs older than its retention are lost, so the backfill records what it found and the page marks versions with no evidence as unknown, not as never-stable.
