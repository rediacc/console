## Design

- **Nothing to delete for elite/bridge.** The plan records the survey as the answer to that line of #606 and keeps the probe reproducible (G1), so the next session does not repeat it against the list endpoint that hides private packages.
- **Protect before resuming.** Phase 3 gains a keep set computed before any delete: every version carrying a channel tag (`stable`, `edge`, `latest`), every strict-semver tag the retention contract keeps (`retention_contract.tag_retention_plan`, the rule Phases 1 and 2 already share), and every child digest named by the manifest list of a kept version (read with `docker buildx imagetools inspect --raw` or the registry manifest API, fails closed: a kept index whose children cannot be read keeps the whole package this run and latches the run failed). The keep set wins over `should_retain`. Package enumeration stays the explicit `GHCR_PACKAGES` tuple, never the list endpoint (Context 1).
- **Then fix the secret.** The preflight failure is a wrong CI secret value, not code: the local profile passes against the same check. The fix rewrites the CI-shared `CLOUDFLARE_R2_*` values through `bws_env store-from-env` from the working profile, which the session does itself (no operator step for a bws value). The order matters: G2 lands before H2, or the first green run deletes `server:stable`.
- **The leftover goes with retention.** `staging-w7p4w-canary-985906` is two months old and outside every keep rule, so the restored Phase 3 deletes it. The first non-dry deletion after a 53-day gap removes thousands of versions, so the operator approves the dry-run list before it runs (G4). If retention cannot be restored, the fallback is the operator's own `delete:packages` grant and the guarded `cleanup_staging` call (G4 names both).
- **Out of scope:** the `server:stable` 1.4.1 lag (Context 8, release pipeline), the other housekeeping jobs failing in the same run ("CI time budget check", "Cloudflare leftovers report"; `PLAN-nightly-green.md` Context 12 covers the budget check), and package visibility changes.

## Risks

- A wrong keep set deletes a live channel image; nothing restores a deleted GHCR version. G3's dry run against the real registry and G4's operator approval sit between G2 and the first delete.
- Reading manifest lists for every kept version adds API calls; Phase 3 already paginates 200 pages per package. The keep set reads only kept indexes, a few dozen per package.
- H2 changes a shared secret that other workflows read (`cd-stage.yml` uses the same three names). The local preflight with the new value must pass before the store, and the fingerprint comparison names which value moves, so a working value is not overwritten by a guess.
