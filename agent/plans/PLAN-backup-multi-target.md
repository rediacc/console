## Context

The operator asked on 2026-11-07 for customers to be able to keep backups in several places, so a lost or damaged store still leaves a recovery point elsewhere. Of the options laid out, the operator chose option 1: several destinations within ONE account, so one config, one licence and one bill cover every copy, with a small renet-side account-server check landing first.

The hostinger incident is why the check comes first. The hostinger machine sits in two configs, eu-remote and eu-bench. A `backup snapshot ...@hostinger --config eu-bench` landed in the eu production store while `backup usage` through eu-bench read bench's store. renet never asks which account a session belongs to: every session verb mints at the URL derived from the installed repository licence's `renewalUrl` (private/renet/cmd/renet/backup_endpoints.go:26-38, called at private/renet/cmd/renet/backup_snapshot.go:1108 and likewise at backup_restore.go:353, backup_browse_at.go:240, backup_repair.go:149 and backup_report.go:252). The licence is picked by signer, the build's baked key first, then the first candidate carrying a delegation cert (private/renet/pkg/license/preferred.go:38-45 and 58-75).

The CLI now refuses such a run before it starts: packages/cli/src/services/backup/backup-store-universe.ts reads every licence installed for the repository and refuses when any names an account server other than the config's, failing closed since ecb3adb7e when the listing cannot be read. It runs from packages/cli/src/services/executor/local-executor.ts:404. A scheduled unit, though, runs `renet backup snapshot` straight from a systemd timer (packages/cli/src/services/backup/backup-schedule-unit-generator.ts:192), so nothing on that path makes the same check. R1 closes that path inside renet itself.

What exists today for several destinations, each checked against the tree at fbefc39f0:

- **The schema already holds several destinations.** `BackupDestinationSchema` (packages/shared/src/config-schema/schemas.ts:273-278) is `kind: 'hosted-service'` with a name, an optional `enabled` and `bandwidthLimit`, an optional `endpoint` and an optional `vaultContent` bag, described as the "customer S3 / self-hosted elite plane" (schemas.ts:264-271).
- **The CLI drops the endpoint.** `buildDestination` (packages/cli/src/commands/backup-strategy-options.ts:54-67) builds a destination from kind, name, enabled and bwlimit only; an existing `endpoint` survives only through the config merge.
- **The validator refuses more than one endpoint.** `destinationsReason` (packages/cli/src/services/backup/backup-strategy-validate.ts:205-216) refuses enabled destinations on more than one distinct endpoint with "One run takes one snapshot to one endpoint".
- **The generator emits one snapshot per run.** `buildChunkStoreCommand` (backup-schedule-unit-generator.ts:182-200) builds ONE `backup snapshot` command, and the caller at backup-schedule-unit-generator.ts:251 says one run is one snapshot whatever the number of destinations.
- **The account server has one object store per deployment.** The presign minter reads `ACCOUNT_BACKUP_S3_ENDPOINT`, `_BUCKET`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY`, `_REGION` and `_PUBLIC_ENDPOINT` (private/account/src/services/backup-chunk-store.ts:996-1010, private/account/src/types/env.ts:214-241), and the Worker logs a misconfiguration when the bucket is bound without them (private/account/src/entry/cloudflare.ts:221-227). Keys are `t/<subscriptionId>/l/<lineageGuid>/c/<sha256>` and `.../m/<snapshotId>` (backup-chunk-store.ts:11-12 and 46-57).
- **The session already returns a data-plane URL.** `Session.DataPlaneURL` (private/renet/pkg/chunkstore/session.go:56-60) is where chunk bytes go and is distinct from the API root; `MintSessionOptions` (session.go:317-334) carries URL, blob, machine id, repository GUID, stream id and intent, and nothing that names a store.
- **A conformance probe exists on both sides.** The account server already probes a plane through its own presigned path before granting writes (private/account/src/services/backup-store-conformance.ts:1-27, cached per data-plane URL at line 185), and private/elite/scripts/s3-conformance-probe.sh probes a candidate endpoint from outside.
- **The D1 rows carry no store.** `backup_manifests`, `backup_streams` and `backup_stream_status` (private/account/src/db/schema.ts:1576, 1721 and 1805) are keyed by subscription, lineage and stream, so two stores of one lineage cannot be told apart today.

## Decisions

- **Variant A now: a per-subscription store registry on the account server.** Each destination names a registered store by id. renet carries the id into the session mint, the server presigns only for that store, and the scheduler takes one snapshot per enabled destination, each committed separately. Every destination is therefore an independent recovery point, and a failure at one store cannot spoil another.
- **Variant B later: `mode: replicate`.** The server copies committed snapshots from a primary store to a secondary one, so the machine uploads once. It is an add-on (P1 to P3) and starts only after variant A has a live proof, because it rests on the same registry and per-store rows.
- **The cross-account refusal stays.** A machine in two configs, such as hostinger in eu-remote and eu-bench, keeps the CLI refusal in backup-store-universe.ts, and R1 adds the same refusal inside renet. Several destinations means several stores inside one account, never several accounts behind one machine.
- **Credentials of customer stores live on the server only.** A machine never holds a customer bucket's keys; it receives presigned URLs for the store its session names, exactly as it does for the hosted store today. The config's `endpoint` and `vaultContent` fields are replaced by `target`, so no bucket credential sits in a config file.
- **Clean break.** The config fields `endpoint` and `vaultContent` are removed rather than kept beside `target`, and the validator's single-endpoint refusal is replaced rather than kept as a fallback. There are no external consumers to migrate.

## Design

**1. Data model (A1).** A new D1 table `backup_stores` holds one row per store: `id` (a short slug unique per subscription, such as `home`, `eu-west` or `office-rustfs`), `subscription_id`, `kind` (`hosted-r2` or `customer-s3`), `region` for a hosted store, the endpoint, bucket, region and public endpoint for a customer store, the sealed credential blob, `conformance` (the last probe verdict and time), `cleanup` (`enabled` or `disabled -- <reason>`), `status` (`active`, `suspended` or `retired`) and timestamps. Every subscription gets an implicit `home` row for the deployment's existing `ACCOUNT_BACKUP_S3_*` store, written by the migration, so every committed manifest has a store from the first day. `backup_manifests`, `backup_streams`, `backup_stream_status`, `backup_sessions` and `backup_lineage_usage` each gain `store_id NOT NULL DEFAULT 'home'`, and every unique index that names a lineage or a stream gains the store id. The object key layout inside a store stays `t/<sub>/l/<lineage>/...`; the store, not the key, says where the bytes are.

**2. Store registration (A2).** `POST /backups/stores` registers a store for the caller's subscription; `GET` lists them and `DELETE` retires one (refused while an enabled destination of any synced config still names it, and refused for `home`). A hosted second region is a choice from the deployment's configured R2 regions and needs no credentials. A customer store (S3, RustFS, an Elite plane) is registered with endpoint, bucket, region and an access key pair. Registration runs the existing conformance preflight (backup-store-conformance.ts) through a plane built for that store, and stores the verdict; a store whose checksum check is not enforced is refused at registration rather than discovered at the first grant. The probe also tries a DELETE: when it is refused, the store is registered with `cleanup: disabled -- delete refused by the store`. Registration is an owner or admin action and is audited.

**3. Session and store id flow (A3, R2).** `backupSessionRequest` (private/account/src/dto/backup.dto.ts:38) gains an optional `storeId`, absent meaning `home`. `mintSession` resolves the store row for the licence's subscription, refuses an unknown, suspended or retired id with a named error, and records the id on the session row. `backupSessionResponse` (backup.dto.ts:367) echoes `storeId`, and `dataPlaneUrl` and `grantKind` become that store's. Every later call on the session (exists, grant, read grant, commit, lease, report) builds its plane from the session's store through one `planeForStore(storeId)` in backup-chunk-store.ts beside `createBackupPlane`, so no call can reach a store other than the session's. In renet, `MintSessionOptions` gains `StoreID`, and every session verb gains `--store <id>`; `backup snapshot` refuses a session whose echoed `storeId` differs from the one it asked for.

**4. Scheduler (C1, C2).** A destination becomes `{ kind: 'hosted-service', name, enabled?, bandwidthLimit?, target? }` with `target` naming a store id, absent meaning `home`. The validator replaces the single-endpoint refusal with two checks: two enabled destinations naming the same target are refused as a duplicate, and a target not in the account's registered stores is refused with the list of registered ids (read through the subscription API at bind time). The unit generator emits one `backup snapshot --store <target>` command per enabled destination, in declaration order, each with its own bandwidth cap. Each command is wrapped so its failure is recorded and the next destination still runs; the unit exits non-zero when any destination failed, so systemd and the dead-man check both see it. The local staged reflink is taken once per destination run, so each snapshot is a consistent point in time of its own.

**5. Restore (R3, C3).** `backup restore`, `restore-path`, `browse --at` and `download --store` take `--from <storeId>`. Without it, the CLI asks the account server for the lineage's stores ranked by newest snapshot whose last verify passed, picks the first, and on a session, grant or chunk failure that is not the snapshot's own fault falls back to the next store that holds a snapshot at or before the requested point, saying which store served the restore. `--at <snapshot>` names a snapshot inside one store; a snapshot id given without `--from` is looked up across the lineage's stores.

**6. Per-target status and failure isolation (A5, S1).** `backup_stream_status` is per store, so `rdc backup status` prints one row per destination: store id, last run, last outcome and reason, newest snapshot, last verify. The dead-man check (`nextExpectedAt`) runs per store stream, so a store that stopped receiving backups alarms on its own while the others stay green. A store that answers 5xx or refuses grants never blocks another store's run, because every run has its own session, lease and commit.

**7. Billing and metering (A4).** Hosted stores, `home` and any second R2 region, are metered exactly as today through `backup_usage` and `backup_lineage_usage`, now per store, and the second region's bytes count toward the same plan quota. A customer bucket's bytes are not stored by Rediacc, so they are not metered by size; a customer store is an entitlement (a plan flag and a store count limit) or a flat monthly fee per registered store, and its manifest metadata (rows, verify runs, index objects) is metered like a hosted store's. The plan limit on the number of stores is enforced at registration.

**8. Clean-up (A6).** Retention sweeps and garbage collection in backup-gc.service.ts run per store with that store's plane. A store marked `cleanup: disabled` keeps its manifests and chunks: the sweep marks expired manifests as expired in D1, stops offering them for restore, and reports the store as clean-up-disabled in `backup status` and in the backup health digest, so the customer knows the bucket grows until delete credentials are added.

**9. Security of held credentials (A1, A2).** A customer store's access key pair is sealed with AES-GCM under a key held as a Worker secret (`ACCOUNT_BACKUP_STORE_KEK`), with the store id and subscription id as additional data, so a row copied to another subscription does not open. The plaintext lives only in the request that builds the plane, never in a log, an error, an audit entry or an API response; `GET /backups/stores` returns the endpoint, bucket and a key-id hint only. Rotation is a re-registration of the same id with new keys, which re-runs the probe. A store whose credentials stop working is marked `suspended` by the first refused grant and named in the health digest.

**10. Replicate mode, later (P1 to P3).** A destination with `mode: replicate` and `from: <storeId>` takes no machine upload. After a commit on the source store, a Queue message names the manifest; a consumer copies the snapshot's chunks first, each hash-checked against its key, then the index object, then the manifest last, and commits a manifest row on the target store only after every object is present. A Durable Object per lineage and target serializes copies, so a slow copy never overlaps the next. A copy that fails retries with backoff and surfaces in per-target status like a failed run.
