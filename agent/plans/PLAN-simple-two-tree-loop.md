## Rulings (ASKED 2026-11-21)

1. One always-on loop, no mode switches. The tree a session runs in is its job.
2. LANDING tree (`/home/developer/console-landing`): babysit the one PR, fix CI, reviews clean, merge (rebase), watch CD, hotfix main-only failures (a `[hotfix]` commit, the operator pushes main), and when the release is fully green promote the development branch as the next PR. With no development work it idles quietly.
3. DEVELOPMENT tree (the main checkout): always builds. Writers drain the Promoted plans, commit, run local ci:quick and vm:check, and push as backup only. It never waits on landing.
4. A plan rides exactly ONE PR, the landing PR (hard rule). Handover happens only when every plan on the development branch is code-complete. Live-run boxes (bench, hostinger, VM) are finished by the landing tree before merge, and the merge gate requires every box ticked.
5. The next PR is taken only after the release is fully green.
6. No draft PR for the development branch. GitHub CI runs once, on the landing PR. LT10 of PLAN-two-track-merge-dev (the draft-PR live proof) is superseded by B0 here.
7. CI lesson feedback: a small CI-only failure in the landing PR makes the landing session ping the development session to extend the local quick checks to catch that class, where that is possible and cheap.
8. Long red: an outside outage (GitHub, a registry 429, no runner) is retried with growing gaps, and the operator is asked after 24 h. The overall limit is a plain 72 h wall clock (an ask whose DEFAULT is "keep fixing"). A check that survives 3 fixes aimed at it is handed to the development session with evidence. When landing fixes break previously green checks (2 in 4 rounds), the landing session pauses and consults the development session (keep, change or undo). The operator is asked only when the two sides cannot resolve it, or at 72 h. Every push or round writes one ledger row.
9. Fix flow for a handed-over failure (Fable-reviewed, option A): the development session supervises a writer in a lease cut on the landing branch tip (`./run.sh worktree lease --tree landing`); the landing session lands it once (`./run.sh worktree land <id>`, submodule first, then the gitlink) and pushes. The development branch catches up only when it needs the fix (`/branch-rebase` onto the landing branch at a batch boundary) or at promote. Development commits are never copied up (block_landing_one_way already refuses that).
10. The landing tree may sit on main (detached origin/main, or main) for a hotfix after the merge. pr-merge.md steps 4 and 6 are reworded. landing.py `_reuse` refusing while on main is acceptable: the exit is `--promote`.

## Design

### D1 The landing state machine

The landing Stop hook reads one state from the world on every stop (the PR, its checks, the merge, main's runs) and names the one next step. No event stores the state, so a restart resumes where the world is.

| State | Entered when | The step it names | Leaves to |
|---|---|---|---|
| L-CI | the landing PR is open and its checks are pending | watch through the ci-watch skill | L-FIX on a red, L-REVIEW on CI Complete SUCCESS |
| L-FIX | a required check is red | diagnose, fix in the landing tree (fix-only freeze), push; the long-red rules (D4) run here | L-CI |
| L-REVIEW | CI Complete SUCCESS on the head | per-commit reviews clean, the PR review answered with wl_prreview.py, threads resolved; open live boxes run here | L-MERGE |
| L-MERGE | every box ticked, CI Complete SUCCESS, reviews clean | `gh pr merge --rebase --auto`, submodules first | L-RELEASE |
| L-RELEASE | the PR merged | watch Console CI on main and the CD edge deploy at the merged sha | L-HOTFIX on a main-only red; on green, notify the development session (`cd-done`) and go to L-IDLE |
| L-HOTFIX | a main-only failure | the tree on detached origin/main, a `[hotfix]` commit with `Hotfix-Evidence:`, the operator pushes main | L-RELEASE |
| L-IDLE | no open landing PR | a quiet stop; nothing blocks | L-CI when promote opens the next PR |

### D2 The development tree

The development hook never reads the landing PR's checks. It orders writers over the Promoted plans (the writers-now survey as its default), local ci:quick and vm:check receipts, and backup pushes. It blocks on the landing tree only for the handover contract (D5) and on a `cd-done` notice when every plan on its branch is code-complete (then promote is its next step).

### D3 Promote

Promote runs from the development session at a commit boundary, never from the landing session, so the development tree is never switched under a running writer. Its premises are three: the landing PR is MERGED, the release at the merged sha is fully green (Console CI on main and the edge deploy both SUCCESS at that sha), and every plan on the development branch is code-complete (every `[writer]` box ticked; lead and live boxes may stay open for the landing tree to finish). With no commits ahead of main the landing tree goes to L-IDLE and promote is not offered.

### D4 Long red

Every push or round on the landing PR appends one row to agent/ledgers/landing-rounds.jsonl: `round, utc, kind (push|rerun|watchdog-retry), run_id, heads, fix_target, reds (each with its category), greens, delta (newly_green, newly_red, regressed, repeat), open_hours, trigger`. The rules read the ledger:

- outage (category infra-likely with an outside signature: GitHub 5xx, registry 429, no runner): rerun with gaps of 10, 20, 40 and 80 minutes, then every 2 h; ask the operator once 24 h of outage rounds have passed.
- operator-only (a new ci_diagnose category: HTTP 401, an expired secret, a billing refusal): ask at once; no retry fixes it.
- stuck (one check red after 3 rounds whose fix_target named it): hand it to the development session with the ledger rows as evidence (D5).
- churn (fixes regress previously green checks in 2 of the last 4 rounds): pause and consult the development session: keep, change or undo.
- wall (72 h since the PR opened): ask the operator, DEFAULT "keep fixing".

### D5 Handover contract

One verb pair, one event kind in the worklist store, addressed by tree role rather than session id (both trees share the main checkout's store, LT14): `worklist.py --handover <me> stuck|churn|lesson <check> <evidence...>` from the landing session, and `--handover-answer <me> <id> lease:<lease-id>|keep|change|undo|done` from the development session. The development hook blocks on an unanswered `stuck` or `churn` handover; a `lesson` one advises. A `stuck` answer names a lease cut with `--tree landing`; the landing hook then blocks on landing it. The lease record names the development session as owner and the landing session as lander, and wl_worktrees counts it unlanded for the lander only.

- Deleted: turbo, turbo_push, batch_size, plan_concurrency, backup_push_h; TURBO_PUSH_REASON and block_turbo_early_push; `--phase babysit|merge|build`, wl_standdown's phase arm, block_focus_spawn; the `ultra` level; the scope regions `pr.turbo-batch-end` and `pr.turbo-kinds`, and `pr.one-plan-per-pr` rewritten.

3. B2, B4, B5, B10 and B7 share wl_checks.py, and B2, B4 share wl_prscope.py, so they run one after another. A parallel start corrupts the lease landings with conflicts; block_plan_concurrency refuses it.
