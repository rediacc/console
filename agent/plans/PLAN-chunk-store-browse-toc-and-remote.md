# PLAN: chunk-store browse, Stage 2 (encrypted TOC writer) and Stage 3 (remote `--at` browse)

Status: proposed
Owner: d778be9d
Updated: 2026-09-23

## Finding

The operator wants Stage 2 (write an encrypted table-of-contents at snapshot time) and Stage 3 (`--at`-style browse of a snapshot that exists only in chunk storage) built now, following the local-first architecture Stage 1 already shipped and the DECISION doc already locked in. Three things ground this plan, verified by reading the actual files rather than trusting the compacted plan summaries:

1. Stage 1's own renet help text names the exact gap this plan closes, verbatim, in `private/renet/cmd/renet/backup_browse.go:29-46`: "What it CANNOT do is browse a snapshot that exists only in chunk storage. A manifest maps grid cells to the hash of their ciphertext, so it carries no filesystem information and no listing can be derived from it. To inspect a historical snapshot, restore it and browse the result." That restore-first workaround is precisely what Stage 3 removes.
2. `agent/plans/PLAN-chunk-store-browse-DECISION.md` (read in full) confirms Stage 1 shipped, and that both the engine-first and server-first commissioned plans converged independently on "encrypted TOC produced at snapshot time, client-side decryption, opaque server storage" for Stage 2/3, while explicitly deferring the build. That convergence is worth taking seriously as a starting point, not re-litigating from scratch.
3. `agent/plans/PLAN-chunk-store-browse-server.md` (read in full) was REJECTED specifically for proposing a `POST /backups/index`/`/manifests/:id/index` route, `indexKey`/`index_bytes` **columns holding index bytes**, and a server-side `backup-index.ts` **decrypt module** -- i.e., content (or content-shaped data) flowing through the account server's own database and a bespoke route, with decrypt capability living in account-server code. Verified still true today: `grep -rn "backups/index\|index_bytes\|backup-index" private/account/src` and `find private/renet/pkg/backupindex` both come back empty, and `private/account/src/routes/backups.ts` / `private/account/src/db/schema.ts` carry no such route or columns.

This plan is designed to stay on the accepted side of that line: server involvement is real (Stage 2/3 cannot avoid it entirely -- see Design 1) but is scoped to be exactly as invasive as what the manifest object already gets today, no more.

**The manifest object itself is plaintext, and that's *why it's safe*, not an oversight:** `private/renet/pkg/chunkstore/manifest.go:38-59` -- `Manifest{Version, SnapshotID, RepositoryGUID, Lineage, CellBytes, ImageBytes, Cells []string, ChangedCells map[string]string}` is uploaded as plain JSON. It's fine for the server to hold this in the clear because every `Cells`/`ChangedCells` value is `ZeroCell` or the SHA-256 of a chunk of LUKS *ciphertext* -- no filename, no path, no directory structure. A TOC is categorically different: it necessarily contains real paths and must never be plaintext at rest server-side. This is exactly the "zero-knowledge" property both prior plans converged on and the rejected server-first plan violated.

**CLI/renet verb-split precedent this plan should reuse, not reinvent** (`private/renet/cmd/renet/backup_restore.go`, `packages/cli/src/commands/backup.ts`):

- `backup_restore.go:24-38` gives the explicit reasoning for making restore a **new verb** rather than a flag on `backup pull`: (1) different license **tier** requirements, (2) a completely different **body** (200 lines of rsync/SSH/CoW machinery share nothing with a chunk download -- "an early return above all of it is exactly the shape that makes a later reader believe those flags apply"), (3) it matches what the e2e test already expected.
- `backup_restore.go:92-95,185-195` -- the machine-level verb takes **only** a snapshot id; a time-shaped `--at` is refused by name with a message pointing at the CLI-level verb, because resolving a time needs `GET /backups/manifests`, which is api-token authenticated and a machine holds no API token.
- `packages/cli/src/commands/backup.ts:114-183` (`registerBackupRestore`) -- the CLI-level `rdc backup restore <artifact-ref> --at <time>` is a **single verb that branches internally** on whether `--at` was given, dispatching to `runRestorePull` (-> `backup_pull`) or `runChunkRestore` (-> `backup_restore`) -- two different renet-level functions behind one CLI command.
- `backup.ts:289-320` (`resolveSnapshotAt`, exported) -- turns a time into a snapshot id by reading `GET /backups/manifests`, taking the newest snapshot at-or-before the time. Already exported and reusable as-is.
- `backup.ts:150-157` -- `deployRepoKeyIfNeeded(targetName, targetMachine)` is called before dispatching a chunk restore, and the surrounding comment names the DR problem directly: "a restore into a config with no config-storage enrollment cannot recover the repo credential (the LUKS passphrase) on a fresh host." This confirms the CLI's local config record already carries `credential` (the LUKS passphrase) per repository, config-storage-replicated so it travels to a fresh machine -- exactly the property Stage 3 needs.

**Credential/key material, verified there is no raw-key-extraction path today:**
- `private/renet/pkg/credentials/keyfile.go` -- `KeyfileStore` generates a random 256-byte **autostart keyfile** per repo GUID (`crypto/rand`, `keyfileSize=256`), stored locally at `{datastore}/.credentials/keys/{guid}.key`, added to LUKS key slot 1. This is **per-machine**, not config-storage-replicated, and rotates independently of the passphrase.
- `private/renet/pkg/luks/luks.go` -- every device operation (`Open`, `OpenWithKeyFile`, `AddKeyFile`, `KillSlot`, `RefreshWithKeyFile`) takes a **password or keyfile path**; grepped for `dump`/`MasterKey` and found nothing -- this codebase never extracts a LUKS volume's raw master key. Introducing that (`cryptsetup luksDump --dump-master-key`) purely to source a TOC-wrapping key would be a new, meaningfully more dangerous capability, not a reuse of what exists.

**Snapshot upload today needs no LUKS key at all -- a real regression risk for Stage 2:**
- `private/renet/pkg/chunkstore/pipeline_linux.go:685-707` (`snapshotSyncPaths`) branches explicitly on whether the repo is currently **mounted or not**, and still proceeds either way -- FIEMAP hole-detection reads the raw backing file, which needs no open/decrypted LUKS device. This is consistent with the manifest hashing ciphertext (grid.go): the whole write pipeline operates below the LUKS layer. **`backup snapshot` is credential-free today.** Any Stage 2 design that makes producing a TOC a hard precondition for a successful snapshot would silently regress that property for keyless/unmounted fleets.

## Design

### 1. Reconciling with the local-first architecture -- the one explicit yes/no ask

Stage 1 was 100% local and server-free. Stage 2 (write) and Stage 3 (remote read) genuinely cannot stay that way, for two narrow, nameable reasons:

- **(a) Discovering/addressing an object that lives only in chunk storage.** This is not new in kind -- it's exactly the mechanism `backup restore` already uses (`MintSession` + `/read-grants` -> `ManifestKeys`). Stage 3's TOC fetch is a sibling read through the *same* mint call, not a new server capability.
- **(b) The server needs to know, per snapshot, whether a TOC object exists and at what key**, purely so it can (i) tell `GET /backups/manifests` callers "this snapshot is browsable" and (ii) include the TOC's key in a read-grant's key map. This is the **only** new server-side state this plan proposes: a nullable pointer column on `backup_manifests`, filled at commit time by the same call that already writes `manifestKey` (`schema.ts:1431`). The server never reads, decrypts, or stores TOC *content* -- only an address, exactly like it already does for the manifest object.

This is deliberately **not** a reintroduction of `PLAN-chunk-store-browse-server.md`'s rejected shape: that plan's `index_bytes` column stored (or was shaped to store) actual index data in SQL, alongside a bespoke `/backups/index` route and a server-side decrypt module -- a standing zero-knowledge liability even if unused. Nothing here adds decrypt capability to the account server, adds a route outside the existing opaque-object/grant path, or stores TOC bytes anywhere but the chunk store object itself.

**The operator decision this plan asks for, framed as plainly as possible:** *Is a nullable `indexKey` (or `hasIndex` boolean) pointer column on the existing `backup_manifests` table -- filled by the same commit call that already writes `manifestKey`, surfaced only as an opaque key string through the existing `/read-grants` and `/manifests` routes, never TOC content, never a decrypt route -- an acceptable, narrow reintroduction of server involvement for Stage 2/3?* If the answer is no, an alternative discovery mechanism (e.g., probing the chunk store for the TOC object's existence directly, with no server-side bookkeeping at all) needs to be worked out before Stage 2 can start, and it would cost every `GET /backups/manifests` caller an extra round trip per snapshot to learn browsability.

### 2. The engine, grounded in what these packages actually look like today

- **Reuse verbatim:** `chunkstore.ReadGrant`/`objectGetter`/`readGrantSource` (`download.go`), `buildGetter`/`s3Getter`/`presignedGetter`/`httpsGetter` (`grants.go`). Add a `GetIndex(ctx, snapshotID) ([]byte, error)` method to `objectGetter`, implemented identically to `GetManifest` on each getter, keyed off a new `IndexKeys map[string]string` field on `ReadGrant`/`S3ReadGrant`/`PresignedReadGrant`, mirroring `ManifestKeys` exactly.
- **Write side:** mirror `session.go`'s `manifestKey`/`PutManifest`/`ManifestKey`/`ManifestKeys` with `indexKey`/`PutIndex`/`IndexKey`/`IndexKeys`. `uploader.go`'s `ManifestPutter` interface gets a sibling `IndexPutter` (or the same interface grows one optional method -- implementer's call, but it must be a no-op-safe addition so existing manifest-only callers aren't forced to implement it).
- **Server mint flow to extend, not replace:** `backup-storage.service.ts:682` `mintReadGrant` already loops `manifestChain` building `manifestKeys`; add one more lookup per chain member (or just the requested snapshot, since a listing only needs the *current* snapshot's TOC, not its ancestors -- see 4) into a new `indexKeys` map, sourced from a `SELECT indexKey FROM backup_manifests WHERE ...` against the same rows already being read for `resolveManifestChain`. `routes/backups.ts:101`'s route and DTOs (`backupReadGrantResponse`) need the new field; no new route.
- **Discovery reuse:** `listManifests` (`backup-storage.service.ts:1094`) already returns everything `resolveSnapshotAt` (`backup.ts:289`) needs to turn a time into a snapshot id. Add `hasIndex: boolean` to `BackupManifestSummary` / the CLI's `BackupManifestEntry` (`backup-storage.ts:45-64`) so a `--at` browse can fail fast, before dispatching to any machine, with an honest "this snapshot has no index" instead of a confusing downstream 404.
- **Local walk machinery to reuse for the writer:** `repodiff/browse.go`'s `Browse` function does open+mount+`filepath.WalkDir`+skip-managed+depth/limit+sort+close in one function. Factor the `WalkDir` body (from `result := &BrowseResult{...}` through the sort, excluding the open/mount/close bracket) into a new exported `repodiff.ListEntries(root string, opts BrowseOptions) (*BrowseResult, error)`, called by both the existing interactive `Browse` (which still owns open/mount/close) and a new snapshot-time writer. This guarantees Stage 3's remote-browse output is **byte-identical in shape** to Stage 1's local output -- the same `BrowseResult`/`BrowseEntry` JSON -- so `packages/cli/src/commands/backup-storage-parser.ts`'s `parseBrowseResult` and every rendering line in `backup-storage.ts:207-274` need zero changes regardless of which stage produced the listing.

### 3. Encryption: reuse the existing repo credential, don't invent a new one

- **Rejected:** deriving from the LUKS volume's raw master key. Nothing in this codebase extracts it today (verified -- see Finding), and building that machinery purely for this feature would be a materially riskier new capability, the opposite of "reuse what exists."
- **Recommended:** HKDF over the repository's existing **LUKS passphrase** -- the `credential` field already carried in the CLI's local repo record (`configService`, referenced at `backup.ts:152,157`), config-storage-replicated so it travels to a machine that has never held the repo before (exactly the property `deployRepoKeyIfNeeded` already provides for chunk restores). Use a fixed info string, e.g. `rediacc-backup-toc-v1` -- the same string the rejected `-server.md` plan had already picked, so a later reader recognizes it as the same idea, now built the local-first way -- to derive an AES-256-GCM key that seals/opens the `repodiff.ListEntries` JSON.
- **Explicit call-out for the operator:** this is not a new secret. It's precisely the credential Stage 1's own help text already requires ("An ENCRYPTED repository still needs its LUKS key... the keyfile must be deployed") to produce *any* listing. Nothing new needs to be provisioned, distributed, or rotated for Stage 2/3 to work everywhere Stage 1 already works.
- **Passphrase over autostart keyfile, and why it matters specifically for Stage 3:** the per-machine autostart keyfile (`KeyfileStore`, `crypto/rand`, slot 1) is *not* config-storage-replicated and is meaningless off the machine that generated it. Stage 3's entire point is browsing from a machine (or a fresh one) that may hold **neither** a local mount **nor** a deployed keyfile for the target GUID. Only the config-storage-replicated passphrase reliably reaches such a machine -- mirroring exactly how `backup restore` already solves the identical DR problem for the image bytes themselves.

### 4. Where the TOC lives

- Its own object, `t/<subscriptionId>/l/<lineageGuid>/i/<snapshotId>`, a new `i/` prefix sibling to the existing `c/` (chunks) and `m/` (manifests) in `backupKeys` (`backup-chunk-store.ts:45-53`) -- **not** embedded inside the manifest object. The manifest's `Validate()` (`manifest.go`) is a hot, structural contract shared by every restore chain-walk; folding a variable-length, separately-encrypted blob into it would force every manifest decode on the restore path to carry (and skip) bytes it never needs, and would blur the manifest's own content-addressing story (which is about grid *cells*, not an unrelated ciphertext blob riding along).
- **No delta-TOC chain for the first cut.** Emit a **full** TOC at every snapshot, not a delta chain mirroring the segmented-manifest work (`journal.go`'s `SegmentRecord{RootSnapshotID, Depth}`, `PLAN-backup-quota-delta-gc.md`). TOC entries are tiny relative to image bytes (path + type + size + mtime, no chunk data); the walk producing them is a brand-new step regardless of whether the underlying manifest is full or delta, and a delta-TOC merge algorithm is real, unbuilt complexity (a second `MaterializeChain`-shaped decision) for little payoff at this scale. This is a deliberate, named deferral -- revisit against the segmented-chain precedent only if TOC object size becomes material.
- **The regression this plan must design against:** `backup snapshot` runs today with **no** LUKS-key precondition (`pipeline_linux.go:685-707` -- FIEMAP reads the raw backing file whether or not the repo is mounted). Stage 2's TOC step (mount + walk) is a **new** requirement that does not exist on the write path today. It must be strictly best-effort and non-blocking: reuse Stage 1's own live-mount-reuse / temporary-open logic; when neither a live mount nor a deployable key is available, **skip** writing a TOC, record that plainly (`hasIndex: false` server-side), and let the snapshot upload succeed exactly as it does today. A keyless or unmounted fleet must keep backing up exactly as reliably as it does now -- browsability is a bonus a credential unlocks, never a gate on the backup itself.

### 5. CLI/renet surface

- **Renet level -- a new FunctionDef, not new params on `backup_browse`.** `backup_browse`'s FunctionDef (`backup.go:154-165`) requires only `machine/team/repository` and is documented, in both Go and the cobra help, as local/credential-free/server-free. Silently widening it with `lineage`/`at` params and adding `storage` to its `Requirements` (as `backup_restore` needs, `backup.go:201`) is exactly the "flag implies features it doesn't have" mistake `backup_restore.go`'s own header comment names as the reason restore is a separate verb from pull. Add `backup_browse_at` (`BackupBrowseAtCommand`, `backup.go`, beside `BackupRestoreCommand`): `Params: lineage (required), at (required, snapshot id only -- a time is refused by name exactly like backup_restore.go:190-195), path, depth, limit`; `Requirements: []string{"machine", "team", "repository", "storage"}`. Implementation (new `cmd/renet/backup_browse_at.go`, or a clearly separated function beside `runBackupBrowse`) reuses `resolveRestoreLicense` + `chunkstore.MintSession` (restore-intent) exactly as `backup_restore.go` does, mints a read grant carrying `IndexKeys`, fetches + decrypts the TOC (3), and prints the **same** `BrowseResult` JSON (2's `ListEntries` reuse).
- **CLI level -- one flag on the existing verb, not a new command.** Mirror `registerBackupRestore`'s shape exactly: `--at <time>` on the existing `rdc backup browse <repo-ref>` (`registerBackupBrowse`, `backup-storage.ts:207`), branching internally like `runRestorePull` vs `runChunkRestore` (`backup.ts:238-336`). When `--at` is present: resolve it via the already-exported `resolveSnapshotAt` (`backup.ts:289`, reused verbatim), call `deployRepoKeyIfNeeded` (same precondition `runChunkRestore` already applies) so the target machine has the passphrase before dispatch, then `executeRepoFunction('backup_browse_at', ...)` instead of `backup_browse`. When `--at` is absent, the code path is **byte-for-byte unchanged** -- this doubles as the regression control (7).

### 6. Scope and sequencing

Stage 3 depends on Stage 2's TOC object existing, so Stage 2 must land, be tested end to end, and be confirmed non-regressing before Stage 3 work starts.

### 7. Test coverage plan

- **Round-trip proof (the strongest available):** write a TOC at snapshot time for a fixture repo with a handful of files, fetch it via the new `backup_browse_at` path, and assert its entries match a Stage-1 local `Browse` of the *same materialized snapshot* byte-for-byte (path/type/size/modtime) -- cross-checking the new remote path against the already-trusted local one on identical content, not just against itself.
- **Fail-closed negative:** tampered TOC ciphertext or wrong key must error loudly, never return a partial or empty listing indistinguishable from "no files" -- directly closing the gap the engine plan's own Outcome flagged as dormant ("no fail-closed negative test for it").
- **`hasIndex:false` path:** a snapshot taken with no LUKS key available must surface a clear, distinct refusal from `backup browse --at`, never a crash or a misleadingly-empty success.
- **Mandatory regression controls, per this repo's own convention (every new feature carries an "the old path still works" case):**
  - A `backup snapshot` run with no keyfile/mount available must still succeed and still be listed by `GET /backups/manifests` (with `hasIndex:false`) -- proving Stage 2 never became a gate on backups.
  - `rdc backup browse <repo-ref>` with **no** `--at` against a locally mounted repo must be asserted to take the exact same code path with zero new server calls -- extend `packages/e2e-tests/tests/25-backup-chunk-store.test.ts`'s existing `backup_browse` leg with a sibling assertion in the same file, so a future change that regresses Stage 1 trips the test file Stage 1 already lives in.
- **CI plumbing to touch:** `.e2e-coverage-allowlist`; suite 25 and/or 26 (`26-backup-storage-cli.test.ts`, per `backup_restore.go`'s own comment naming that file's sketch as its precedent); `check:ci-command-planes` / `check:ci-command-tree` for the new FunctionDef and CLI flag; `check:i18n` / `check:ci-i18n-cli-key-usage` for every new user-facing string, matching Stage 1's convention of wrapping every message in `i18n.T(...)`.
