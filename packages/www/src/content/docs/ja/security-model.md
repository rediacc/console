# セキュリティモデル

このページでは、設定ストレージが何を守るのか、どのキーが何を開くのか、呼び出し元の種類ごとに何に到達できるのかを説明します。セットアップ手順は[設定ストレージ](/ja/docs/config-storage)、セッションとトークンは[アカウントセキュリティとAPI](/ja/docs/account-security)をご覧ください。

## 誰が何を見られるか

保存された設定は3層で暗号化されます。SDK層と組織パスフレーズ層はサーバーがキーを管理します。中間の層がコンテンツ暗号化キー(CEK)で、キースロットの保持者だけがアンロックできます。デバイスに保管されたスロットシークレットとサーバーが保持するシークレットを組み合わせて初めて開くため、どちらか片方だけでは開きません。

| 攻撃者が持つもの | 設定の内容が見えるか | 理由 |
|---|---|---|
| データベースのコピーのみ | 見えない | 設定のブロブはデータベースではなくオブジェクトストレージにある |
| データベースとオブジェクトストレージ | 見えない | 組織パスフレーズ層にはWorkerシークレットが、CEK層にはスロットシークレットが必要 |
| サーバーの完全な侵害 | スロットシークレットなしでは見えない | サーバー側の層は破られるが、CEKはパスキーのPRF出力か160ビットのリカバリーキットの背後に残り、どちらも推測できない |
| 削除されたメンバーのデバイス | すでに取得済みの内容 | CEKローテーション後の新しいバージョンは閉じたまま |
| 漏えいしたエージェントURL | 1つの設定を、そのユーザーとして | [エージェントとリモートMCP](#agents-and-remote-mcp)を参照 |

サーバーはメタデータ(設定ID、チーム、バージョン、タイムスタンプ、ブロブのサイズ)を引き続き見ることができ、リクエストを拒否、遅延、削除することもできます。悪意あるポータルコードを配信するオペレーターは、ブラウザ内のキーを読み取れます。すべてのブロブはストア、設定、チーム、バージョンに紐づいているため、サーバーが気づかれずに差し替えたり編集したりすることはできません。CLIは、すでに確認したものより古いバージョンを拒否します。

## キーのスコープ

- 組織ごとに設定ストアが1つ、ストアごとにCEKが1つあります。チームはサーバー側のアクセス制御であり、暗号による分離ではありません。リカバリーキットやキースロットは組織全体のCEKを開きます。
- キースロットはストア、ユーザー、方式ごとに一意なので、リカバリーキットはユーザーと組織ごとに1つです。2つの組織に属するユーザーは2つのキットを持ち、チーム用のキットはありません。
- マシンシークレットはマシンと組織ごとに1つで、ヘッドレスマシンをエンロールします。
- 各設定には、CEKの下に専用のコンテンツキーがあります。エージェントグラントが持つのは1つの設定のコンテンツキーだけなので、それで組織の他の設定を開くことはできません。
- 各設定の認可ポリシーは、CEKとレコードのポインタから導出されるキーの下にある独立したレコードです。ポリシーキーを1つ持っていても、開けるのはそのポインタのレコードだけです。

## エージェントとリモートMCP

エージェントグラントは、リモートMCPのURLの背後にあるキー保持者の種類です。1つの設定のコンテンツキーに加えて、グラント自身のチーム設定と組織レベル設定のポリシーキーを持ちますが、CEKは持ちません。そのためエージェントは、本人が読めるものとまったく同じものを読みます。

- **有効期間。** URLの有効期間はデフォルトで7日、最長で30日です。その後は失効するか取り消されます。失効したグラントは拒否され、クライアントは再認可します。
- **スコープ。** グラントが届くのは1つの設定で、1つのリージョン(eu、us、asia)に属します。別のリージョンに提示されたURLは、正しいリージョンを示して拒否され、転送されることはありません。オンプレミス環境は単一リージョンです。
- **ポリシー。** エージェントが動作できるのは、人による明示的なオプトインとポリシーの上限の両方が許可する範囲だけです。上限は、チームポリシーで絞り込まれた組織ポリシーです。エージェントはポリシーの編集、シークレット値の読み取り、自身のグラントの拡大ができません。
- **影響範囲。** 漏えいしたURLは、失効または取り消されるまで、その1つの設定に対してそのユーザーとして動作します。そのリージョンのホスト型エグゼキュータの外では何も開きません。

ツールの出力は、ユーザーが接続したモデルプロバイダーに届きます。このプロバイダーをRediaccが選ぶことはありません。

### オンプレミス

経路にCloudflareは存在しません。クラウドのWorkerシークレットは、顧客ホスト上の環境変数または設定になります。そのため、上の表のWorkerシークレットという境界はホストへのアクセスに置き換わり、ツール呼び出しは顧客自身のデーモンエグゼキュータで実行されます。

## ポリシー

ポリシーは独立したレコードで、設定エントリごとに封印されます。認証付きデータがストア、設定、チーム、バージョン、キー世代を結び付けます。サーバーはこれを読めず、再送されたレコードや差し替えられたレコードは整合性タグの検証に失敗します。バージョン1のポリシーレコードは拒否されます。

組織ポリシーを書き込めるのは組織のオーナーまたは管理者だけで、チームのポリシーを書き込めるのはチーム管理者(またはオーナーか管理者)だけです。書き込みには2FAと昇格セッションが必要で、ストアがパスキーを必須としている場合は紐づけ済みのパスキーも必要です。すべてのメンバーと、それを担当するすべてのエグゼキュータがポリシーを読み取ります。組織がロックしたキーは、チームポリシーでは無視されます。

## 復旧できるもの

| 状況 | 復旧方法 |
|---|---|
| パスキーを紛失 | リカバリーキットでアンロックし、新しいパスキーを登録する |
| キットを紛失 | 使えるパスキーから再生成する。古い印刷物は使えなくなる |
| 両方を紛失 | オーナーまたは管理者が、メンバーのハンドオフでメンバーを再追加する |
| 最後のキー保持者が両方を失う | 復旧不可。このため2人目のキー保持者を推奨します |
| メンバーを削除 | そのスロットとトークンは即座に失効する。CEKローテーションで、本人が保持していたキーに対して以降のバージョンが閉じられる |
| CEKローテーション | CEKを新しい世代で包み直し、すべてのリカバリーキットを無効にする |

サーバーは、キー保持者が2人未満になり、かつリカバリースロットが残らなくなるような、スロットの削除、メンバーの削除、メンバーの退出を拒否します。すべてのメンバーはエンロール時に必須のリカバリーキットを受け取り、その保管はメンバー自身の責任です。
