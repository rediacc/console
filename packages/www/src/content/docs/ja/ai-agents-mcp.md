## 概要

2つのMCP（Model Context Protocol）サーバーは1つのレジストリからツールを取得し、リモートサーバーはその一部を提供します。

| サーバー | トランスポート | 実行方法 | ツール |
|---|---|---|---|
| ローカル | stdio | `rdc mcp serve`。エージェントが起動 | すべてのツール |
| リモート | Streamable HTTP | `https://mcp.<region>.rediacc.cloud/g/<grantId>` | リモート用ツール（ローカル専用の表にあるものを除くすべて） |

**前提条件:** ローカルサーバーには、`rdc` がインストールされ、少なくとも1台のマシンが設定されていることが必要です。リモートサーバーには、設定に対するグラントが必要です。

## ローカルサーバー

`rdc mcp serve` は、stdio経由でMCPサーバーを起動します。エージェントがサブプロセスとして起動し、JSON-RPCで通信します。

### Claude Code

プロジェクトの `.mcp.json` に次のエントリを追加します。

```json
{
  "mcpServers": {
    "rdc": {
      "command": "rdc",
      "args": ["mcp", "serve"]
    }
  }
}
```

名前付き設定を使う場合は次のとおりです。

```json
{
  "mcpServers": {
    "rdc": {
      "command": "rdc",
      "args": ["mcp", "serve", "--config", "production"]
    }
  }
}
```

### Cursor

Settings → MCP Servers → Add Server を開き、次のように入力します。

- **Name**: `rdc`
- **Command**: `rdc mcp serve`
- **Transport**: stdio

### オプション

| オプション | デフォルト | 説明 |
|------------|------------|------|
| `--config <name>` | （デフォルト設定） | すべてのコマンドで使う名前付き設定 |
| `--timeout <ms>` | `120000` | コマンドのデフォルトタイムアウト（ミリ秒） |

## リモートサーバー

リージョンごとにMCP Workerが1つ、`mcp.<region>.rediacc.cloud` で動作します。各エージェントは、1つのグラントのURL `https://mcp.<region>.rediacc.cloud/g/<grantId>` に接続します。グラントは、1つの設定、有効期限、スコープを指定します。スコープは、読み取り専用フラグ、許可するツールのリスト、マシン名とリポジトリ名のglobパターンで構成されます。ツール呼び出しは、グラントが属する組織のエグゼキューターで実行されます。

### 認証情報

どちらの形式もグラントを識別します。URLのグラントIDは名前を示すだけです。

| 形式 | 用途 | 送信方法 |
|---|---|---|
| OAuthアクセストークン | claude.aiなどの対話型クライアント | `Authorization: Bearer <token>` |
| エージェントベアラー `rmcp_<grantId>.<secret>` | ヘッドレスエージェント | `Authorization: Bearer` または `x-api-key` |

クエリ文字列に含まれた認証情報は400で拒否されます。OAuthトークンがない、期限切れ、または別のグラントのものである場合は、401と `WWW-Authenticate: Bearer resource_metadata=...` ヘッダーが返ります。このヘッダーはグラントの保護リソースドキュメントを指すため、OAuthクライアントはトークンを更新するか、サインインします。未知のグラント、誤ったシークレット、別のグラントのエージェントベアラーには、いずれも同じ簡素な401が返ります。

### OAuth

Workerは、PKCE（S256のみ）に対応したOAuth 2.1認可サーバーです。クライアントは、Client ID Metadata Documentまたは `/register` での動的クライアント登録で登録します。

| エンドポイント | 目的 |
|---|---|
| `/.well-known/oauth-authorization-server` | サーバーメタデータ |
| `/.well-known/oauth-protected-resource/g/<grantId>` | 1つのグラントの保護リソースドキュメント |
| `/authorize` | 認可を開始し、アカウントページ `/account/mcp/authorize` にリダイレクト |
| `/oauth/token` | コード交換、更新、取り消し |
| `/register` | 動的クライアント登録 |

クライアントは `resource=https://mcp.<region>.rediacc.cloud/g/<grantId>` を送信します。認可が完了するのはリソースが指すグラントだけで、トークンは自分のグラントのURLでのみ使えます。`/authorize` のリダイレクトには、署名付きの使い捨てハンドルが含まれ、シークレットは含まれません。

### トークンの有効期間

トークンがグラントより長く有効になることはありません。

| トークン | 有効期間 |
|---|---|
| アクセストークン | 1時間とグラントの残り時間のうち短いほう |
| リフレッシュトークン | 30日とグラントの残り時間のうち短いほう |

コード交換や更新のたびに、グラントを再度確認します。期限切れ、取り消し済み、またはキーがローテーションされたグラントは `invalid_grant` を返し、OAuthグラントを取り消します。リフレッシュトークンはローテーションされ、同じトークンを2回提示するとグラントが取り消されます。

### グラントごとに1つの設定

グラントが扱うのは、指定された1つの設定だけです。別の設定を指す引数（`config` またはその表記違い）を含む `tools/call` は、何かが実行される前に `REDIACC_GRANT_SCOPE` で拒否されます。複数の設定を持つユーザーは、設定ごとに1つずつグラントを承認します。グラントの許可リストにないツールや、読み取り専用グラントでの書き込みツールは、`tools/list` に表示されず、呼び出しても拒否されます。

### リージョン

グラントIDは `eu_` のようにリージョンで始まります。別のリージョンのWorkerで `/g/<grantId>` にリクエストすると、正しいURLとともに421が返ります。

```json
{
  "code": "REDIACC_WRONG_REGION",
  "message": "This grant lives in the us region. Use https://mcp.us.rediacc.cloud/g/us_...",
  "region": "us",
  "mcpUrl": "https://mcp.us.rediacc.cloud/g/us_..."
}
```

グラントは、自分のリージョン以外では、OAuthリソース、トークンのオーディエンス、認可の対象のいずれとしても受け付けられません。

### グラントの状態と制限

期限切れ、取り消し済み、または設定ストアのキーローテーションでキーを失ったグラントも、`initialize` と `tools/list` には応答します。その後の `tools/call` は、`REDIACC_GRANT_EXPIRED`、`REDIACC_GRANT_REVOKED`、`REDIACC_KEY_ROTATED` のいずれかを `reauthUrl` とともに返します。ユーザーはこのURLを開いて再度承認します。

各グラントでは、1分あたり60回の呼び出しと、同時進行5件の呼び出しが可能です。どちらかの上限を超えた呼び出しには、`retryAfterSeconds` とともに `REDIACC_RATE_LIMITED` が返ります。

## ワークフロー例

**マシンの状態を確認する:**
> 「本番マシンの状態は？」

エージェントが `machine_status` を呼び出し、接続の詳細、システム情報、コンテナ、サービス、リポジトリ、リソース使用状況を取得します。

**アプリケーションをデプロイする:**
> 「ステージングマシンにgitlabをデプロイして」

エージェントが `name: "gitlab"`、`machine: "staging"` を指定して `repo_up` を呼び出すと、リポジトリがデプロイされ、成功または失敗が返ります。

**長時間のジョブを追跡する:**
> 「nextcloudの昨夜のバックアップを復元して」

エージェントが `backup_restore` を呼び出します。待ち時間を超えるコマンドはジョブハンドルを返し、エージェントはジョブが終わるまで `job_wait`（1回あたり最大50秒）と `job_logs` を呼び出します。

**不調なサービスをデバッグする:**
> 「nextcloudが遅い。原因を調べて」

エージェントが `machine_health` を呼び出し、続いて `machine_containers` と `repo_logs` を呼び出して、対処法を提案します。

## セキュリティ

ローカルMCPサーバーは、2層の保護を適用します。リモートサーバーの制限は[リモートサーバー](#リモートサーバー)で説明しています。

### フォーク限定モード（デフォルト）

サーバーはデフォルトで**フォーク限定モード**で動作します。書き込みツール（`repo_up`、`repo_down`、`repo_delete`、`repo_exec`、`repo_push`、`repo_pull`）が操作できるのはフォークのリポジトリだけです。エージェントはグランド（元）のリポジトリに触れられません。これは意図した設計です。

> **リポジトリごとのシークレットは設計上CLIのみで管理します。** `repo_secret_set` と `repo_secret_unset` は意図的にMCPツールとして公開していません。書き込みには `--current <前回の値>` という事前条件（または未検証ローテーションを承認する `--rotate-secret`）が必要であり、この手順は人間が確認する必要があります。シークレットのローテーションを提案するエージェントは、`repo_secret_get` でダイジェストを確認したうえで、JSONエラーエンベロープの `next.options[].run` フィールドを通じてオペレーター向けのCLIコマンドをユーザーに伝えてください。完全なパターンについては [AIエージェントの安全性](/en/docs/ai-agents-safety#structured-next-action-hints)、ユーザー向けの手順については [リポジトリ § シークレット](/en/docs/repositories#secrets) を参照してください。

エージェントがグランドリポジトリを変更できるようにするには、MCPサーバーをホストするエージェント起動前にターミナルで `REDIACC_ALLOW_GRAND_REPO` をエクスポートします:

```bash
export REDIACC_ALLOW_GRAND_REPO='gitlab'   # 単一のリポジトリ
# または 'repo1,repo2,repo3'（エントリ周辺の空白は無視される）、またはすべてのリポジトリに対する '*'
claude   # または cursor、gemini など
```

オーバーライドはプロセス祖先に対して検証されます。つまり、オーバーライドはエージェント起動時にすでにそのプロセスの環境に存在している必要があります。あなたがエージェント（およびそれがスポーンしたMCPサーバー）起動前にエクスポートしたことを意味します。エージェントがセッション途中に変数を設定することで自分自身にアクセス権を付与することはできません。意図的にMCPサーバーの引数にフラグがないのはこのためです。MCPサーバー引数のフラグはそれをそこに配置した人を証明しませんが、祖先チェックはそれを証明します。マシンレベルのアクセス（リポジトリなしの `term connect <machine>` など）には引き続き `*` が必要です。リポジトリ名のリストはマシンレベルのアクセスを解除しません。

### リポジトリごとのSSH鍵とサーバーサイドサンドボックス

各リポジトリは独自のSSH鍵ペアを持ちます。公開鍵は `command=` プレフィックス付きで `authorized_keys` にデプロイされ、すべてのSSHセッションを `renet sandbox-gateway <repo-name>` 経由に強制します。これはサーバーサイドのForceCommandであり、VS Codeを含むいかなるクライアントも回避できません。

**動作の仕組み:**
1. `rdc repo create` または `rdc repo fork` がリポジトリごとに一意のed25519鍵ペアを生成
2. 公開鍵が `command="renet sandbox-gateway <name>"` 付きでリモートにデプロイ
3. その鍵を使用するすべてのSSH接続がゲートウェイを経由し、以下が適用される:
   - **Landlock LSM**: リポジトリのマウントパスへのカーネルレベルのファイルシステム制限
   - **OverlayFS ホームオーバーレイ**: `$HOME` への書き込みはリポジトリごとにキャプチャされ、読み取りは実際のホームにフォールスルー
   - **リポジトリごとのTMPDIR**: `<datastore>/.interim/sandbox/<name>/tmp/`
   - **Dockerアクセス**: リポジトリの隔離されたDockerソケット経由
   - **権限の降格**: 共通ユーザー（`rediacc`）への移行
4. リポジトリの `.envrc` がDockerと環境セットアップのために自動的に読み込まれる

**RW許可**: リポジトリのマウントパス、リポジトリごとのサンドボックスワークスペース、ホームディレクトリ（オーバーレイ経由）、Dockerソケット
**RO許可**: システムパス（`/usr`、`/bin`、`/etc`、`/proc`、`/sys`）
**ブロック**: 他のリポジトリのマウントパス、許可リスト外のシステムファイル

**VS Code統合**: 各リポジトリは `<datastore>/.interim/sandbox/<name>/.vscode-server/` に独自のVS Codeサーバーインストールを持ちます。複数のリポジトリを独立したサンドボックス環境で同時に開くことができ、リポジトリ間でサーバーは共有されません。

ラテラルムーブメントを防止します。エージェントがフォークへのシェルアクセスを取得した場合でも、同じマシン上の他のリポジトリを読み取ったり変更したりすることはできません。マシンレベルのSSH（リポジトリなし）はチーム鍵を使用し、サンドボックス化されません。

## アーキテクチャ

ローカルMCPサーバーはステートレスです。ツールを呼び出すたびに、`rdc` が `--output json --yes --quiet` フラグ付きの独立した子プロセスとして起動されます。これには次の意味があります。

- ツール呼び出し間で状態が漏洩しない
- 既存の `rdc` 設定とSSH鍵を使用
- 1つのコマンドのエラーが他に影響しない
