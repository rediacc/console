# 프록시 & 실행기

일반적으로 `rdc`는 사용자의 머신에서 사용자의 설정과 SSH 키를 사용해 실행되며, 서버에 직접 연결합니다. 프록시 모델은 이 흐름을 둘로 나눕니다. 어떠한 시크릿도 보유하지 않는 씬 클라이언트와, 시크릿을 보유하고 실제 작업을 수행하는 **실행기(executor)**입니다. [웹 콘솔](/ko/docs/web-console)의 실행 버튼과 CLI의 `--proxy` 플래그는 모두 씬 클라이언트이며, 동일한 프로토콜을 사용합니다.

## 명령이 아니라 명령의 의도

씬 클라이언트는 SSH 키, 머신 주소, 복호화된 설정을 전혀 보유하지 않습니다. 무언가를 실행하려 할 때는 명령의 의도만 전송합니다. 즉 명령 식별자(CLI 계약 내 경로, 예를 들어 `repo up`)와 매개변수뿐입니다. 실행기는 동일한 계약에서 해당 명령을 조회해 서버 측 함수로 해석하고, 복호화된 설정에서 대상 머신을 확인한 뒤 자체 SSH 연결로 명령을 실행합니다. 출력은 클라이언트로 스트리밍되어 돌아옵니다.

실행기는 `rdc serve`로 서버로서 시작된 CLI 그 자체입니다. 노트북에서 운영자가 실행하는 것과 동일한 바이너리가 이들을 대신해 명령을 실행하는 존재가 됩니다. 배치 방식은 두 가지입니다.

- **`--mode daemon`**: 사용자가 관리하는 호스트에서 실행되며, 일반 CLI와 마찬가지로 헤드리스로 등록됩니다([설정 저장소](/ko/docs/config-storage) 참조). 스스로 설정 키를 파생시킬 수 있으므로 세션별 권한 부여가 필요 없습니다. SSH가 사용자 네트워크를 벗어나지 않는 엄격한 등급입니다.
- **`--mode container`**: 사용자를 위해 호스팅되는 조직 전용 컨테이너에서 실행됩니다. 처음에는 키를 전혀 가지지 않으며, 클라이언트가 세션에 키를 부여하기 전까지는 아무 작업도 할 수 없습니다. 편의성을 우선한 등급입니다.

## CEK 권한 부여

설정 저장소는 영지식입니다. 서버는 언제나 암호화된 블롭만 저장하며, 콘텐츠 암호화 키(CEK)는 이를 잠금 해제한 클라이언트에서만 평문으로 존재합니다. 따라서 컨테이너 모드 실행기는 키를 *부여*받아야 하며, 이 부여 과정에서 서버에 키가 노출되어서는 안 됩니다.

흐름은 다음과 같습니다. 잠금이 해제된 브라우저가 실행기와 세션을 열어 세션의 공개 키를 받고, X25519를 이용해 CEK를 해당 세션에 봉인합니다. 봉인된 블롭은 계정 서버를 거쳐 전달되지만, 서버는 이를 열어볼 수 없으므로 영지식 속성은 끝까지 유지됩니다. 실행기는 CEK를 메모리에만 복호화하며, 30분 유휴 만료가 적용되고 디스크에는 절대 기록되지 않습니다. 이후의 명령 요청은 `X-Config-Session` 헤더를 통해 부여된 세션을 참조합니다.

감사 측면에서 한 가지가 중요합니다. 세 단계(세션 열기, 키 부여, 명령 실행) 모두 동일한 사용자 신원을 사용합니다. 계정 서버는 자신의 자격 증명을 실행기에 전달하지 않습니다. 각 단계마다 실제 사용자에게 귀속된 단기 토큰을 발급하고, 매번 해당 사용자의 소속을 다시 확인합니다. 실행기는 제시된 토큰을 검증한 뒤에만 동작합니다. 한 사용자가 부여한 권한을 다른 사용자가 사용할 수는 없습니다.

설정의 `state` 부분(호스트 로컬 런타임 데이터)은 애초에 설정 블롭에 담겨 전송되지 않으므로, 이 경로를 통해서도 실행기에 도달하지 않습니다.

## 프록시로 실행할 수 있는 것

모든 명령이 원격으로 실행하기에 적합한 것은 아닙니다. 계약에 포함된 각 명령은 `proxyCapable` 플래그를 가지며, 실행기는 어떤 정책 설정과도 무관하게 서버 측에서 이를 강제합니다.

- **머신 플레인의 비대화형 명령**(배포, 백업, 상태 확인, 로그 등)은 프록시 가능합니다.
- **설정 플레인 명령**은 그렇지 않습니다. 이는 설정을 편집하는 작업이며, 이 경로에서는 브라우저의 몫입니다(웹 콘솔은 대신 자체 설정 편집기로 라우팅합니다).
- **대화형 명령**(터미널, VS Code 세션)은 그렇지 않습니다. 이 회선에는 TTY가 없습니다.
- **클라이언트 측 전송 명령**(`rdc repo sync`)은 그렇지 않습니다. *클라이언트*의 파일 시스템과 머신 사이에서 데이터를 이동시키는 작업인데, 실행기는 클라이언트의 파일에 접근할 수 없습니다.

웹 콘솔은 동일한 플래그를 읽어 명령에 실행 버튼을 표시할지 결정하지만, 실행기는 클라이언트가 무엇을 보내든 프록시 불가능한 명령은 거부합니다.

## 목 실행기

개발 환경에서 실제 실행기가 구성되어 있지 않을 때, 계정 서버는 명령 요청에 목(mock) 스트림과 명확히 가짜임을 알 수 있는 데이터(`mock-` 접두사가 붙은 리소스 이름)로 직접 응답합니다. 덕분에 머신이나 잠금 해제 없이도 폼, 스트리밍, 결과 렌더링을 포함한 콘솔 전체를 실제로 동작시켜볼 수 있습니다. 실제 실행에는 실제 실행기가 필요합니다.

## 실행기의 접속 위치 제한

설정의 `access` 버킷에는 SSH 키에 허용되는 IPv4 및 IPv6 소스 범위가 저장됩니다. 범위는 설정 전체, 키별, 머신별로 지정할 수 있으며, 머신은 해당 실행기가 접속하는 주소에서 온 키만 받아들입니다.

- `rdc config access add <key> --public-key ... --hosted-executor`는 키를 등록하고 호스팅 실행기의 두 범위 `104.28.0.0/16`과 `2a09:bac0::/29`를 연결합니다. 둘 다 관측된 Cloudflare 송신 범위이며 Cloudflare가 공개하는 목록이 아니므로 바뀔 수 있습니다.
- `rdc machine access set <machine> --key <key>`는 머신에 키를 할당합니다. `--ipv4`, `--ipv6`, `--clear-ranges`로 해당 머신의 범위를 조정합니다.
- `rdc machine access push <machine>`은 접근 행을 머신에 기록하며, `--dry-run`은 아무것도 바꾸지 않고 결과만 보여 줍니다.
- `rdc machine access show <machine>`은 현재 적용 중인 접근 행을 출력합니다.

`machine setup`은 접근 행을 다시 적용하므로, 다시 구성한 머신도 제한을 되찾습니다.

현재 SSH 세션의 주소가 사용 중인 키의 범위 밖이라 접속이 차단될 push는 `ACCESS_LOCKOUT`으로 거부되며 아무것도 기록되지 않습니다. 그 사이 머신의 파일이 바뀌었다면 push는 `ACCESS_FILE_CHANGED`로 거부됩니다. 아무것도 적용되지 않았으므로 안전하게 다시 시도할 수 있습니다.

## 작업, 티켓, 폴링

머신 계층의 모든 명령은 머신에서 작업(job)으로 실행됩니다. 작업은 renet이 관리하는 systemd 유닛이며, 상태와 이벤트 로그는 머신의 스풀에 보관됩니다. 그래서 연결이 끊겨도 작업은 멈추지 않고, 어떤 클라이언트든 작업 ID로 이어받을 수 있습니다.

- **연결 창.** 실행기는 작업의 이벤트를 최대 20초 동안 스트리밍하고, 스트림이 조용한 동안에는 10초마다 하트비트 줄을 보냅니다. 창 안에서 끝난 작업은 같은 요청에서 결과를 돌려줍니다. 더 오래 걸리는 작업은 머신과 겹치는 작업을 담은 `job` 줄 뒤에 `state: running`과 작업 ID가 든 결과를 돌려줍니다.
- **폴링.** 이후 클라이언트는 `GET /v1/jobs/<id>/poll`로 마지막으로 본 줄 이후의 이벤트를 작업 상태와 함께 가져오고, 빈 응답이 이어지는 동안에는 간격을 늘립니다. `POST /v1/jobs/<id>/cancel`은 작업을 취소합니다. 두 경로 모두 작업을 시작한 명령과 같은 정책을 적용하며, 종료 상태를 가장 먼저 확인한 폴링이 감사 이벤트를 한 번만 기록합니다.
- **티켓.** 호출마다 CLI 설정 디렉터리(`jobs/<config>.jsonl`)에 티켓도 기록됩니다. `rdc job wait <id>`는 작업을 기다렸다가 그 작업의 종료 코드로 끝나고, `rdc job list`, `status`, `logs`, `cancel`, `gc`는 나머지를 관리합니다. 따라가는 중 Ctrl-C는 취소하지 않고 분리되어 130으로 종료합니다. 연결을 다시 맺지 못한 따라가기는 16으로 종료하고 티켓을 유지합니다.
- **단계.** 설정에 결과를 기록하거나 목록을 출력하는 것처럼 작업 뒤에 이어지는 일은 티켓과 스풀에 기록되는 단계입니다. 단계는 작업의 종료를 가장 먼저 확인한 곳에서 한 번만 실행됩니다. 그곳은 명령 자체, `rdc job wait`, 다음 명령이 출력하는 알림, 실행기의 폴링 중 하나입니다. 소유권 요청은 머신에서 이루어지므로 두 관찰자가 같은 단계를 실행하는 일은 없습니다.
- **겹침.** 같은 저장소나 같은 머신에서 실행 중인 작업과 겹치는 시작은 실행 중인 작업에 연결하는 명령이 담긴 경고를 출력합니다. 겹침 정책이 시작을 거부하면 명령은 15(`BUSY`)로 종료하고, 거부 응답에는 겹치는 작업이 `overlaps`에 담깁니다.
- **클라이언트가 없는 동안의 단계.** 성공 단계는 작업이 `succeeded`일 때만, 롤백 같은 실패 단계는 `failed`이거나 취소됐을 때만 실행됩니다. 작업이 연결 창 안에서 끝나면 실행기는 클라이언트가 연결을 끊어도 연결을 유지하며 단계를 실행하므로, 응답을 놓친 짧은 명령도 단계를 끝까지 마칩니다. 단계는 작업을 시작한 설정과 일치하는 설정의 관찰자에서만 실행되고(연결을 유지하는 실행기가 그 설정으로 단계를 실행하므로 조건이 맞음), 다른 설정은 `N steps pending for config <name>`을 표시합니다. 다음 명령이 출력하는 알림은 그 명령 자체의 출력 뒤 최대 20초 동안 대기 중인 단계를 실행하며, 대화형 텍스트 실행에서만 그렇습니다. `-o json`, `-q`, MCP에서는 아무것도 실행하지 않고 stderr에 `steps pending: rdc job wait <id>`를 출력합니다. 작업의 종료를 본 관찰자가 없는 동안에도 서비스는 계속 실행되지만 단계는 기다립니다. `repo up` 뒤의 DNS 이름, 인증서 동기화, URL 목록, 포크·마이그레이션·복원 뒤의 백업 일정, 다음 푸시를 델타로 만드는 기준 기록이 그 대상입니다. `rdc job list`는 단계가 실행될 때까지 `steps pending`을 표시합니다.
- **예외.** 대화형 명령(`term connect`, `repo tunnel`, `vscode connect`, `repo exec -i`, `repo logs -f`), 클라이언트 측 전송(`repo sync upload`, `download`, `status`와 `backup upload`, `download`), `job` 명령, `serve`, `vscode serve status`와 `stop`, 그리고 `cluster kubeconfig`나 `machine access push`처럼 renet을 호출하지 않는 명령은 작업으로 실행되지 않습니다. `machine provision`과 `deprovision`의 로컬 OpenTofu 구간은 예전처럼 클라이언트에서 실행됩니다. 그 밖의 머신 플레인 명령은 모두 작업입니다.
- **보존.** 끝난 읽기 전용 작업은 1시간, 그 밖의 끝난 작업은 7일 동안 보관합니다. 아무도 가져가지 않은 단계가 있는 작업은 종류와 관계없이 7일 동안 보관하고, 실행 중인 작업은 삭제하지 않습니다. 스풀에는 끝난 작업을 최대 2000개, 256MiB까지 두며 오래된 끝난 작업부터 지우되, 아직 처리되지 않은 단계가 있는 작업은 7일이 지날 때까지 한도 정리에서 건너뜁니다. 정리는 작업을 시작할 때 한 시간에 한 번까지 실행됩니다. 작업의 systemd 유닛은 작업이 끝난 것을 처음 확인한 상태 읽기나 정리 과정에서 중지됩니다.
