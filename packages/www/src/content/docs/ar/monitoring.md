# المراقبة

يوفر Rediacc أوامر مراقبة مدمجة لفحص صحة الأجهزة والحاويات قيد التشغيل والخدمات وحالة المستودعات وتشخيصات النظام.

## صحة الجهاز

الحصول على تقرير صحي كامل لجهاز:

```bash
rdc machine health server-1
```

يُبلغ هذا عن:
- **النظام**: وقت التشغيل، الذاكرة (تحذير فوق 80%، خطأ فوق 90%)، استخدام القرص ومخزن البيانات (تحذير فوق 85%، خطأ فوق 95%)
- **الحاويات**: عدد الحاويات قيد التشغيل والسليمة وغير السليمة؛ الحاوية العالقة في حلقة `Restarting` حرجة
- **الخدمات**: وحدات systemd الفاشلة (خطأ) والوحدات التي تعيد التشغيل باستمرار (حرج)
- **التخزين**: حالة صحة SMART (القرص المعطوب حرج) ودرجة حرارة القرص
- **المستودعات**: مستودعات التشغيل التلقائي غير المحمّلة، واستخدام نظام ملفات كل مستودع (تحذير فوق 85%، خطأ فوق 95%)
- **النسخ الاحتياطية**: المستودعات التي لم تُنسخ احتياطيًا منذ أكثر من 10 أيام، أو المتأخرة عن جدولها أو وجهتها، أو التي فشل آخر تحقق لها
- **التراخيص**: تراخيص المستودعات المنتهية أو المفقودة أو غير المطابقة أو غير الصالحة، والتراخيص التي حان تجديدها
- **عمليات renet**: الخدمات الخلفية التي ما زالت تشغّل ملف renet تنفيذيًا تم استبداله
- **صحة المستودعات**: نتيجة `health()` الخاصة بكل مستودع محمّل (انظر أدناه)
- **الشهادات**: شهادات الوكيل القريبة من الانتهاء، وسجلات CNAME المشتركة لتحدي ACME
- **المشكلات**: المشكلات المكتشفة

رمز الخروج هو الحكم: `0` سليم، `1` تحذير، `2` خطأ، `3` حرج (قرص معطوب، أو حاوية أو خدمة في حلقة إعادة تشغيل). استخدم `--output json` للحصول على مخرجات قابلة للقراءة آليًا؛ وهي تتضمن `repo_health` (تقرير لكل مستودع) و`findings`، ولكل نتيجة رمز ودرجة خطورة (`info` أو `warning` أو `error` أو `critical`) وموضوع وتفصيل، وعند وجود إصلاح تتضمن `fix` (انظر [الإصلاح](#repair)).

## صحة المستودع

يمكن أن يعرّف Rediaccfile دالة `health()` تفحص خدمات المستودع نفسه ([الخدمات](/ar/docs/services)): رمز الخروج `0` سليم، `1` تحذير، `2` خطأ. شغّلها لمستودع واحد:

```bash
rdc repo health my-app@server-1
```

ينتهي الأمر بأسوأ مستوى بين ملفات Rediaccfile في المستودع. المستودع الذي لا يعرّف أي Rediaccfile فيه `health()` يطبع **لا يوجد فحص** وينتهي بالرمز `0`؛ ولا يُبلَّغ عنه سليمًا أبدًا. وتُعدّ `health()` التي انتهت مهلتها أو أُنهيت أو خرجت برمز آخر خطأً، وكذلك تعذّر الوصول إلى الجهاز (رمز الخروج `2`).

يشغّل `rdc machine health` دالة `health()` لكل مستودع محمّل في استدعاء واحد ويدمج أسوأ مستوى في رمز خروجه، مع نتيجة واحدة لكل مستودع كتحذير (`repo.health.warning`) أو خطأ (`repo.health.error`). تُسرد المستودعات التي لا فحص لها ولا يُبلَّغ عنها. وعندما يكون renet على الجهاز أقدم من فحوصات صحة المستودعات، تكون النتيجة تحذيرًا واحدًا هو `renet.repo-health.unsupported` إلى أن يحدّثه `rdc machine setup`.

## انتهاء الشهادات وتحديات ACME

يقرأ `rdc machine health` شهادات ACME الخاصة بالوكيل ويُبلغ عن `cert.expiry.near` لكل شهادة يقل ما تبقى على انتهائها عن 21 يومًا (تحذير) أو عن 7 أيام (خطأ). يجدّد الوكيل قبل 30 يومًا، ولذلك فإن شهادة تقل عن 21 يومًا تعني أن تجديدها يفشل منذ تسعة أيام على الأقل.

كما يُبلغ عن `acme.challenge.cname-shared` عندما يتبع سجل `_acme-challenge.<name>` لاسم شهادة سجل CNAME إلى اسم ليس هو نفسه اسم `_acme-challenge.`، أو عندما ينتهي اسمان عند الاسم نفسه. السجل البديل (wildcard) الذي هو CNAME ينتج هذا الشكل: تصل كل التحديات إلى اسم واحد وتتصادم التجديدات. لا يُبلَّغ عن التفويض المقصود (مثل `_acme-challenge.mail.example.com` الذي يشير إلى `_acme-challenge.mail.example.io`)؛ أدرج أي تفويض مقصود آخر في `ACME_DELEGATED_NAMES` (قائمة أسماء شهادات مفصولة بفواصل) في `config.env` الخاص بالوكيل. أما الاسم الذي تعذّر حلّ سلسلة تحديه (خطأ DNS أو انتهاء مهلة) فيُبلَّغ عنه كـ `acme.challenge.unknown`، وهو تحذير، لأن الفحص لم يُنفَّذ له.

## الإصلاح

تحمل كل نتيجة رمزًا، وحيث يوجد إصلاح آمن تحمل `fix` يتضمن `action` و`class` للأمان و`window_only`. يبقى `rdc machine health` للقراءة فقط؛ والأمر الذي يتصرف هو `rdc machine repair`:

```bash
rdc machine repair server-1 --dry-run     # list what would run
rdc machine repair server-1               # run the auto-safe fixes, then re-check
rdc machine repair server-1 --code cert.expiry.near
```

| الصنف | المعنى |
|---|---|
| `auto-safe` | يعمل افتراضيًا: إعادة تشغيل حاوية أو Traefik، وtrim والتنظيف، وكتابة مرساة ACME |
| `auto-with-backup` | يعمل فقط مع `--with-backup`، بعد لقطة ناجحة للمستودع؛ وفشل اللقطة يلغي الإصلاح |
| `operator-only` | لا يعمل أبدًا. يطبع الأمر الأمر الدقيق الذي يجب تشغيله يدويًا. كل ما يحذف بيانات مسمّاة أو ينفق مالًا يقع هنا |

`window_only` شرط إضافي فوق الصنف: يعمل الإصلاح فقط داخل نافذة الصيانة الخاصة بالجهاز، بصيغة `HH:MM-HH:MM` بتوقيت UTC (ويمكن أن تعبر منتصف الليل). الجهاز بلا نافذة لا ينفّذ هذه الإصلاحات من تلقاء نفسه أبدًا؛ ويشغّلها `--window-override` يدويًا. اضبط النافذة أو امسحها بما يلي:

```bash
rdc machine repair server-1 --set-window 00:00-03:00
rdc machine repair server-1 --set-window off
```

يتحقق كل إصلاح أولًا من أن نتيجته ما زالت قائمة، ولذلك يُبلغ التشغيل الثاني بألا شيء يستدعي العمل. الإصلاحات التي تعمل على الشيء نفسه تُنفَّذ مرة واحدة (إعادة تشغيل واحدة لـ Traefik تغطي كل الشهادات). يُسجَّل كل إصلاح في سجل الجهاز بالوسم `rediacc-repair` وفي حقل JSON المسمى `actions` (`code` و`subject` و`action` و`class` و`result` و`before` و`after`)، وينتهي التشغيل بإعادة فحص كاملة. رمز الخروج `0` عندما لا يتبقى شيء، و`1` عندما تتبقى تحذيرات أو عناصر operator-only، و`2` عندما يتبقى خطأ أو يفشل إصلاح.

| النتيجة | الإصلاح | الصنف |
|---|---|---|
| `datastore.usage.high`, `repo.disk.high` | trim، ثم تنظيف الحاويات المتوقفة والأقراص المجهولة اليتيمة والصور غير المستخدمة | auto-safe |
| `container.unhealthy`, `container.restart-loop` | إعادة تشغيل الحاوية | auto-safe |
| `renet.binary.replaced` | إعادة تشغيل مشرفي المستودعات المتأثرة (`rdc machine restart-services --include-docker`، مقصورًا عليها) | auto-safe، داخل النافذة فقط |
| `cert.expiry.near` | إعادة تشغيل Traefik ليعيد محاولة التجديد | auto-safe |
| `acme.challenge.cname-shared` | كتابة مرساة ACME (أدناه) | auto-safe |
| `repo.health.warning`, `repo.health.error` | تشغيل `repair()` الخاصة بالمستودع ([الخدمات](/ar/docs/services)) | الصنف الذي يعلنه Rediaccfile |
| `repo.unmounted`, `service.failed`, `service.restart-loop`, `backup.*`, `license.*`, `renet.repo-health.unsupported` | يُطبع كأمر يجب تشغيله | operator-only |

النتائج التي لا إصلاح لها (أعطال SMART ودرجة الحرارة والذاكرة وقرص النظام وفشل التحقق) يُبلَّغ عنها وتُترك للمشغّل.

لا يمس التنظيف المحور (hub) أبدًا: الحاويات الموسومة بـ `rediacc.hub.*` والأقراص الموسومة بـ `rediacc.hub.user` أو المسماة `rediacc-hub-home-*` مستثناة، فيبقى المجلد الرئيسي لمستخدم المحور سليمًا عبر كل عملية استرداد للمساحة. أما البقية التي لا يستطيع trim والتنظيف تحريرها (الأقراص المسماة وبيانات التطبيقات الكبيرة) فتبقى قرار المشغّل.

### إصلاح المستودع

```bash
rdc repo repair my-app@server-1 --dry-run
rdc repo repair my-app@server-1
```

ينفّذ `rdc repo repair` دوال `repair()` الخاصة بالمستودع بالأصناف نفسها: يعمل `auto-safe`، ويحتاج `auto-with-backup` إلى `--with-backup`، ولا يعمل `repair()` غير المعلن (`operator-only`) إلا بعد الإجابة عن سؤاله أو مع `--yes`. بعد ذلك تعمل `health()` مرة أخرى، ويتبع رمز الخروج المستوى الذي تنتهي عنده: `0` سليم أو لا يوجد فحص، `1` تحذير، `2` خطأ أو فشل `repair()`.

### مرساة ACME

السجل البديل (wildcard) في DNS الذي هو CNAME يجعل كل اسم `_acme-challenge.<host>` يتبعه، فتصل كل التحديات إلى اسم واحد وتتصادم التجديدات (`acme.challenge.cname-shared`). يكتب الإصلاح سجل TXT بالقيمة `rediacc-acme-anchor` عند كل `_acme-challenge.<name>` متصادم عبر رمز Cloudflare الخاص بالوكيل، ثم يعيد تشغيل Traefik. السجل الصريح يُخرج الاسم من نطاق السجل البديل، فيصل التحدي إلى حيث ينبغي. يضيف الإصلاح سجلات فقط، وتُترك المرساة الموجودة كما هي.

الأسماء المدرجة في `ACME_DELEGATED_NAMES` (قائمة أسماء شهادات مفصولة بفواصل في `config.env` الخاص بالوكيل) تفويضات مقصودة: لا تُرسَّخ بمرساة ولا يُبلَّغ عنها أبدًا. وعندما لا يملك الوكيل رمز Cloudflare صالحًا للاستخدام، يلجأ الإصلاح إلى `LEGO_DISABLE_CNAME_SUPPORT=true` في `config.env`، ولكن فقط عندما لا يكون أي اسم مفوَّض معلنًا، لأن هذا المتغير يوقف تتبع CNAME لكل الأسماء؛ ومع إعلان تفويض تبقى النتيجة operator-only. يعمل الإصلاح نفسه عند كل تثبيت للوكيل (`rdc machine infra push`) ومنفردًا عبر `renet proxy acme-fix` على الجهاز.

## عرض الحاويات

عرض جميع الحاويات قيد التشغيل عبر جميع المستودعات على جهاز:

```bash
rdc machine status server-1 --containers
```

| العمود | الوصف |
|--------|-------|
| Name | اسم الحاوية |
| Status | وقت التشغيل أو سبب الإيقاف |
| State | قيد التشغيل، متوقف، إلخ. |
| Health | سليم، غير سليم، بدون |
| CPU | نسبة استخدام المعالج |
| Memory | استخدام الذاكرة / الحد الأقصى |
| Repository | المستودع الذي يمتلك الحاوية |

الخيارات:
- `--health-check`, إجراء فحوصات صحية نشطة على الحاويات
- `--output json`, مخرجات JSON قابلة للقراءة آليًا

تتضمن مخرجات JSON تفاصيل الحاويات الكاملة (`labels` و`port_mappings` و`image` و`id`) بالإضافة إلى `repository` (الاسم المحلول) و`repository_guid` (المعرّف GUID الأصلي) و`domain` و`autoRoute`.

## عرض الخدمات

عرض خدمات systemd المتعلقة بـ Rediacc على جهاز:

```bash
rdc machine status server-1 --services
```

| العمود | الوصف |
|--------|-------|
| Name | اسم الخدمة |
| State | نشط، غير نشط، فاشل |
| Sub-state | قيد التشغيل، متوقف، إلخ. |
| Restarts | عدد مرات إعادة التشغيل |
| Memory | استخدام ذاكرة الخدمة |
| Repository | المستودع المرتبط |

الخيارات:
- `--stability-check`, تمييز الخدمات غير المستقرة (فاشلة، أكثر من 3 إعادات تشغيل، إعادة تشغيل تلقائية)
- `--output json`, مخرجات JSON قابلة للقراءة آليًا

تتضمن مخرجات JSON تفاصيل الخدمات الكاملة مع `repository` (الاسم المحلول) و`repository_guid` (المعرّف GUID الأصلي).

## عرض المستودعات

عرض المستودعات على جهاز مع إحصائيات مفصلة:

```bash
rdc machine status server-1 --repositories
```

| العمود | الوصف |
|--------|-------|
| Name | اسم المستودع |
| Size | حجم صورة القرص |
| Mount | مثبّت أو غير مثبّت |
| Docker | Docker daemon قيد التشغيل أو متوقف |
| Containers | عدد الحاويات |
| Disk Usage | الاستخدام الفعلي للقرص داخل المستودع |
| Modified | وقت آخر تعديل |

الخيارات:
- `--search <text>`, التصفية حسب الاسم أو مسار التثبيت
- `--output json`, مخرجات JSON قابلة للقراءة آليًا

تتضمن مخرجات JSON الحقلين `name` (الاسم المحلول) و`guid` (المعرّف GUID الأصلي)، كما تدرج لكل مستودع مصفوفتَي `containers` (بما فيها `domain` و`autoRoute` و`repository`/`repository_guid`) و`services`.

## صحة التخزين

فحص تجزئة BTRFS ومشاركة reflink عبر جميع المستودعات على جهاز:

```bash
rdc machine status server-1 --storage-health
```

| العمود | الوصف |
|--------|-------|
| Quota | الحجم الأقصى للمستودع (حد نموه، يُضبط عند الإنشاء أو بتغيير الحجم / auto-grow) |
| Allocated | ما تشغله الصورة المتفرقة فعلياً في التجمع الآن |
| Unique | البيانات الفعلية الفريدة التي يمتلكها هذا المستودع فقط |
| Shared | كتل البيانات المُعاد استخدامها عبر المستودعات بواسطة روابط BTRFS المرجعية (نسخ مجانية) |
| Reclaimable | الفجوة بين Allocated والمستخدم فعلياً التي يستطيع [`repo trim`](/ar/docs/repositories#reclaim-space-trim) إعادتها إلى التجمع. يُعرض `-` للمستودعات غير المحمّلة |
| Discards | ما إذا كان الحجم المشفر يُمرّر طلبات discard (`on` لأي مستودع حُمِّل بإصدار حالي) |
| Divergence | النسبة المئوية من الصورة الفريدة لهذا المستودع بدلاً من المشتركة (القيمة الأعلى تعني قدراً أكبر قابلاً للاسترداد عند الحذف) |
| Frag | عدد امتدادات الغيغابايت في صورة copy-on-write (معلوماتي فقط) |

Quota والتخصيص رقمان مختلفان بالتصميم: مستودع بحصة 20 جيجابايت يخزن 6 جيجابايت من البيانات لا يُكلّف التجمع إلا ما خصّصه فعلاً. يستطيع التجمع إذن أن يَعِد بحصة إجمالية تفوق حجمه الفعلي، ويُظهر عمود Reclaimable مقدار ما لم يُستخدم من تخصيص كل مستودع وبإمكان trim استرداده.

يُبلّغ ملخص التجمع أسفل الجدول عن مستوى امتلاء مخزن البيانات والمساحة التي تحجزها لقطات النسخ الاحتياطي:

```
Pool: 265.4 GB used, 95.2 GB free (73.6% full)
Backup snapshots pin 2.1 GB (1 active, 0 stale; stale ones are removed by 'rdc machine prune')
```

ما دامت نسخة احتياطية جارية، تبقى لقطتها تُشير إلى كل كتلة مشتركة مع المستودعات الحية، فتُحرّر عمليات الحذف وtrim مساحة أقل حتى تنتهي دورة النسخ الاحتياطي وتُحذف اللقطة. تُزال اللقطات القديمة المتبقية من عمليات نسخ احتياطي مقطوعة تلقائياً بواسطة مُدير التخزين في غضون دقائق.

يعرض الملخص إجمالي المدخرات من روابط BTRFS المرجعية:

```
14 repos, 224.3 GB virtual size
Unique data: 323.7 MB | Shared: 224.0 GB | Efficiency: 99.9%
```

- **الحجم الافتراضي** هو مجموع أحجام صور المستودعات. هذا ما تبدو عليه المستودعات، غير أنه يحسب مزدوجًا الكتل المشتركة عبر الروابط المرجعية.
- **البيانات الفريدة** هي التخزين الفعلي الذي تستهلكه بيانات المستودع الموجودة في مستودع واحد فقط. وهذا ما ستحرره عند حذف مستودع.
- **المشترك** هو البيانات المُعاد استخدامها عبر المستودعات بواسطة روابط BTRFS المرجعية. يؤدي تفريع مستودع إلى إنشاء نسخ مرجعية تشترك في الكتل حتى يكتب أحد الطرفين بيانات جديدة، عندها تتباعد الكتل.
- **الكفاءة** هي نسبة البيانات المُعاد استخدامها عبر الروابط المرجعية. القيمة الأعلى أفضل. الجهاز الذي يحتوي على كثير من تفريعات الأصل ذاته سيُظهر كفاءة قريبة من 100%.

عمود Frag معلوماتي. يحسب امتدادات ملف الصورة copy-on-write، لا الملفات التي يقرأها تطبيقك من داخلها، لذا يُسجّل قيماً مرتفعة في ظل أحمال الكتابة العشوائية الاعتيادية (قواعد البيانات، طبقات الحاويات) ولا يتنبأ بأداء القراءة على التخزين المدعوم بـ SSD. لا يوفر Rediacc عمداً أمر defragment: فـ `btrfs filesystem defragment` يلغي مشاركة التفريعات والقطع الأثرية المرتبطة بـ reflink، مما قد يُضاعف الاستخدام بشكل كبير على تجمّع قريب من الامتلاء بينما تُظهر الاختبارات أنه لا فائدة ملحوظة في سرعة القراءة. للقياسات الكاملة والمنطق التفصيلي، راجع [رقم التجزئة لديك يبدو مخيفاً. قِستُ ما يكلّفه فعلاً.](/ar/blog/i-benchmarked-btrfs-fragmentation).

يعمل الفحص بشكل متوازٍ ويستغرق 5-15 ثانية حسب عدد المستودعات وحجمها. عند عدم تحديد `--storage-health`، يظهر تلميح من سطر واحد بعد مخرجات الاستعلام كتذكير.

## فحص BTRFS

يجدول Rediacc تلقائيًا فحص BTRFS أسبوعيًا على كل جهاز. يقرأ الفحص كل كتلة بيانات في مخزن البيانات، ويتحقق من المجاميع الاختبارية، ويُبلغ عن أي تلف. يكتشف هذا تلف البيانات الصامت (تعفن البت) قبل انتشاره في النسخ الاحتياطية والتفريعات.

يعمل الفحص كل يوم أحد الساعة 02:00 بالتوقيت المحلي للجهاز مع تأخير عشوائي يصل إلى ساعة واحدة. يعمل بأدنى أولوية I/O (`ionice idle` و`nice 19`) حتى لا يتعارض مع الخدمات قيد التشغيل. على الأجهزة المدعومة بـ SSD، توقع نحو 8 دقائق لكل 100 غيغابايت من مخزن البيانات.

يُثبَّت مؤقت الفحص تلقائيًا عند أول بدء تشغيل للخدمة بعد ترقية renet. عند تغيير سياسة الفحص في إصدار renet مستقبلي، تُحدِّث نفسها عند بدء التشغيل التالي دون الحاجة إلى أي إجراء من المستخدم.

### حالة الفحص

يُحفظ نتيجة آخر فحص خارج حجم BTRFS (في `/var/lib/rediacc/scrub-last-result.json`) حتى يظل قابلًا للقراءة حتى في حالة وجود مشكلات في الحجم. تتضمن مخرجات `rdc machine status --system` حقل `scrub_status`:

```json
"scrub_status": {
  "last_run_human": "3 days ago",
  "status": "ok",
  "total_errors": 0,
  "uncorrectable": 0,
  "duration_seconds": 312
}
```

| الحالة | المعنى |
|--------|--------|
| `ok` | اكتمل الفحص الأخير دون أخطاء |
| `never_run` | لم يعمل الفحص بعد (تم تثبيت المؤقت للتو) |
| `overdue` | مضى على آخر فحص أكثر من 14 يومًا |
| `errors_found` | عثر الفحص على عدم تطابق في المجاميع الاختبارية (تحقق من عددَي `total_errors` و`uncorrectable`) |
| `failed` | خرجت عملية الفحص برمز غير صفري |

إذا كانت قيمة `uncorrectable` أكبر من صفر، فلا يمكن إصلاح الكتل المتأثرة تلقائيًا (BTRFS ذو قرص واحد لا يحتوي على نسخة احتياطية زائدة). استعد المستودع المتأثر من أحدث نسخة احتياطية.

### الفحص اليدوي

لتشغيل فحص فوري (مثلًا بعد انقطاع التيار الكهربائي أو ترحيل القرص):

```bash
rdc term connect server-1 -c "sudo renet maintenance scrub --datastore /mnt/rediacc"
```

تُحفظ النتيجة في ملف JSON ذاته وتظهر فورًا في `rdc machine status --system` التالي.

## نظرة عامة على الجهاز

الحصول على نظرة عامة كاملة على جهاز بما في ذلك معلومات النشر:

```bash
rdc machine status server-1
```

يوفر هذا:
- اسم المضيف ووقت التشغيل
- استخدام الذاكرة والقرص وDatastore
- إجمالي المستودعات، وعدد المثبّتة، وعدد المستودعات التي يستجيب فيها Docker daemon
- معلومات تفصيلية لكل مستودع

استخدم `--output json` للحصول على مخرجات قابلة للقراءة آليًا.

## اختبار الاتصال

التحقق من اتصال SSH بجهاز:

```bash
rdc term connect server-1 -c "hostname"
```

يطبع هذا الأمر اسم المضيف البعيد عند النجاح أو خطأ اتصال في حال الفشل، مما
يتحقق من DNS ومنفذ SSH والمصادقة بالمفتاح في خطوة واحدة.

## التشخيصات (doctor)

تشغيل فحص تشخيصي كامل لبيئة Rediacc الخاصة بك:

```bash
rdc doctor
```

| الفئة | الفحوصات |
|-------|----------|
| **البيئة** | إصدار Node.js، إصدار CLI، وضع SEA، تثبيت Go، توفر Docker |
| **Renet** | موقع الملف الثنائي، الإصدار، CRIU، rsync، أصول SEA المضمنة |
| **التكوين** | الإعداد النشط، المحوّل، الأجهزة، مفتاح SSH |
| **المحاكاة الافتراضية** | التحقق من إمكانية تشغيل أجهزة افتراضية محلية (`rdc ops`) |

يُبلغ كل فحص عن **OK** أو **تحذير** أو **خطأ**. استخدم هذا كخطوة أولى عند استكشاف أي مشكلة وإصلاحها.

رموز الخروج: `0` = نجاح الكل، `1` = تحذيرات، `2` = أخطاء.

## فحوصات جاهزية الخدمات

أثناء `repo up`، ينتظر renet حتى تقبل خدمات HTTP الاتصالات قبل إعلانها جاهزة. يراعي هذا الانتظار فحوصات صحة Docker على النحو التالي:

- الحاويات التي يُبلّغ عنها Docker بأنها **سليمة** تُقبَل فوراً دون أي فحص TCP.
- الحاويات التي لا تزال ضمن `start_period` الخاص بفحص صحتها تُسجَّل كملاحظة إعلامية لا تحذيراً؛ يواصل الوكيل إعادة المحاولة حتى ترتبط بمنفذها.
- خدمات Compose التي لا تملك حاوية قيد التشغيل (مثل تلك الموجودة خلف ملف تعريف غير نشط) تُتخطى.
- كل ما عدا ذلك يُفحص عبر TCP لمدة أقصاها 15 ثانية (عيّن `REDIACC_READINESS_TIMEOUT`، بالثواني، لتغيير هذه القيمة).

تعريف [فحص صحة Docker](https://docs.docker.com/reference/dockerfile/#healthcheck) على الخدمات بطيئة الإقلاع يمنح renet إشارة جاهزية موثوقة ويُقلّل من الضجيج في مخرجات النشر.
