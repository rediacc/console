أنت توجّه مساعد برمجة بالذكاء الاصطناعي نحو بنيتك التحتية. عندما يتحكم Claude Code أو Cursor أو Gemini CLI أو Copilot CLI أو أي مساعد مماثل في تشغيل `rdc`، تتعامل معه واجهة سطر الأوامر بشكل مختلف عن الإنسان الجالس أمام لوحة المفاتيح. تشرح هذه الصفحة ما يمكن للوكيل فعله، وما لا يمكنه فعله، وكيف تصمد الضمانات حتى عندما يحاول الوكيل التحايل عليها.

## مرجع سريع: ما يمكن للوكلاء فعله وما لا يمكنهم فعله

| العملية | الإعداد الافتراضي للوكيل | كيفية الفتح لحالة استخدام محددة |
|---|---|---|
| `rdc config show` (معتَّم) | ✅ allowed |  |
| `rdc config field get --pointer <pointer>` (نموذج معتَّم أو ملخص) | ✅ allowed |  |
| `rdc config field get --pointer <pointer> --digest` | ✅ allowed |  |
| `rdc config field set --pointer <pointer>` (حقل عام) | ✅ allowed |  |
| `rdc config field set --pointer <pointer>` (حقل حساس، **مع `--current` صحيح**) | ✅ allowed |  |
| `rdc config edit --dump --redacted` (JSONC معتَّم) | ✅ allowed |  |
| `rdc config audit {log, tail, verify}` | ✅ allowed |  |
| `rdc config field set --pointer <pointer>` (حقل حساس، بدون `--current`) | 🔴 refused | تزويد `--current "<القيمة القديمة>"` |
| `rdc repo secret set <repo> --rotate-secret` (تدوير بدون `--current`) | 🔴 refused | تزويد `--current`، أو يُجري إنسان التدوير من طرفية |
| `rdc config field get --pointer <pointer> --reveal` | 🔴 refused | استخدام `--digest` بدلاً من ذلك |
| `rdc config show --reveal` | 🔴 refused | استخدام `rdc config show` العادي |
| `rdc config edit` (المحرر التفاعلي) | 🔴 refused، بلا تجاوز | الاطلاع عبر `--dump --redacted`، وتغيير حقل واحد عبر `config field set --current` |
| `rdc config edit --apply <file>` | 🔴 refused، بلا تجاوز | الأمر نفسه؛ يطبّق إنسان من طرفية التعديلات على المستند كاملاً |
| `rdc config edit --reveal` | 🔴 refused، بلا تجاوز | الأمر نفسه |
| `rdc config field rotate --pointer <pointer>` | 🔴 refused | يشغّله إنسان من طرفية تفاعلية |
| تغيير مستودع grand (الإنتاج) | 🔴 refused | موافقة صريحة من إنسان لهذا المستودع، ضمن سياسة تسمح بتغيير مستودعات grand ([أدناه](#one-decision-opt-in-and-policy-ceiling)) |
| عمليات دورة حياة العنقود أو مخزن البيانات | 🔴 refused | موافقة صريحة من إنسان لهذا العنقود، ضمن سياسة تسمح بعمليات العناقيد |
| `rdc term connect <machine>` (SSH مباشر إلى الجهاز) | 🔴 refused | تفريع مستودع أولاً والاتصال بالنسخة المفرعة |

كل ما يُرفض للوكيل يُكتب في سجل التدقيق مع `outcome: refused` وسبب الرفض. وتعديل المستند الكامل للإعدادات لا مسار له أمام الوكيل إطلاقاً: فالإعدادات تحمل بيانات اعتماد LUKS لكل مستودع، والوكيل الذي يستطيع إعادة كتابتها يستطيع أيضاً حذف بيانات اعتماد لا يمكن فتح الحجم المشفر بدونها.

## كيف يتم اكتشاف الوكلاء

تتعامل واجهة سطر الأوامر مع العملية على أنها وكيل عند تحقق أي من الشروط التالية:

- أي من المتغيرات `REDIACC_AGENT` أو `CLAUDECODE` أو `GEMINI_CLI` أو `COPILOT_CLI` مضبوط على `"1"`، أو `CURSOR_TRACE_ID` مضبوط بأي قيمة.
- على Linux: أي عملية أصل في سلسلة السلف تحتوي على إحدى هذه المتغيرات في بيئتها (عبر `/proc/<pid>/environ`). حتى لو قام الوكيل بحذف متغيراته الخاصة باستخدام `env -i` أو سكريبت مغلف، تظل سلسلة الأصل تخبر واجهة سطر الأوامر بمن بدأ التشغيل.

يعمل الاكتشاف مرة واحدة لكل عملية ويُخزَّن مؤقتاً. ولا يمكن تعطيله. ويُعلِّم تفويض MCP البعيد استدعاءاته على المنفِّذ بأنها استدعاءات وكيل، دون حاجة إلى اكتشاف.

## قرار واحد: الموافقة الصريحة وسقف السياسة معاً

كل واجهة تشغّل أمر `rdc` (واجهة CLI وخادم MCP المحلي وخادم MCP البعيد و`rdc --proxy` ووحدة تحكم الويب) تسأل دالة القرار نفسها، فترفض وتسمح بالأشياء ذاتها. وتطبّق الدالة شرطين، ولا يتصرف الوكيل إلا حيث يتحقق الاثنان:

1. **سقف السياسة.** سياسة المؤسسة، مقيَّدة بسياسة الفريق، تحدد الأوامر والأجهزة والمستودعات التي يجوز للمستدعي استخدامها، وهل يُسمح أصلاً بتغيير مستودعات grand (`allowGrandRepos`) وبعمليات العناقيد (`allowClusterOps`). وإذا لم يكن للإعدادات سجل سياسة فتُطبَّق قيمة افتراضية بحسب الدور: يستطيع المالكون والمسؤولون التصرف، ولا يستطيع الأعضاء. السياسة سجل مختوم منفصل لا يكتبه إلا المالكون والمسؤولون ([النموذج الأمني](/ar/docs/security-model#policy))؛ ولا يستطيع أي وكيل ولا أي أمر في CLI تعديلها.
2. **الموافقة الصريحة من الإنسان.** داخل السقف، يحتاج الوكيل مع ذلك إلى إنسان يسمّي مستودع grand أو العنقود الذي يجوز له تغييره:
   - **الوكلاء المحليون** (CLI وMCP المحلي): يصدّر الإنسان `REDIACC_ALLOW_GRAND_REPO` (أسماء المستودعات، أو `*`) أو `REDIACC_ALLOW_CLUSTER_OPS` (أسماء العناقيد، أو `*`) في الطرفية قبل تشغيل الوكيل. تفحص CLI سلسلة العمليات الأصلية، فلا يُعتدّ بمتغير يضبطه الوكيل في منتصف الجلسة ([كيف يُفحص ذلك على كل نظام تشغيل](#how-a-local-opt-in-is-verified-on-each-os)).
   - **الوكلاء البعيدون** (MCP البعيد): تكون الموافقات جزءاً من التفويض الذي ينشئه الإنسان في واجهة الحساب ([الخادم البعيد](/ar/docs/ai-agents-mcp#remote-server)).

لا توسّع الموافقة الصريحة السقف أبداً: فالمستودع الذي تغلقه السياسة يبقى مغلقاً مهما قالت البيئة أو التفويض. ولا تحتاج النسخ المفرعة (forks) إلى موافقة. والمستودع الذي لا تستطيع CLI تحديد هويته يُعدّ grand.

**التغييرات المدمِّرة تسأل أولاً.** عندما يُصرَّح للوكيل بتغيير مدمِّر في مستودع grand (مثل `repo delete`)، تكون الإجابة `needs_confirmation`. يعرض عميل MCP على المستخدم نافذة تأكيد؛ أما العميل الذي لا يملك ذلك فيحصل على وسيط `confirm` يعيده بعد سؤال المستخدم. وفي CLI يعيد الإنسان تشغيل الأمر مع `--confirm-grand <repo>`.

تحمل كل إجابة رمزاً ثابتاً (`POLICY_DENIED` و`GRAND_REPO_DENIED` و`CLUSTER_OPS_DENIED` و`AGENT_OPT_IN_MISSING` و`FORK_BLOCKED` و`AGENT_BLOCKED` و`CONFIRMATION_REQUIRED`)، فيتفرّع النص البرمجي أو الوكيل بحسب الرمز لا بحسب الرسالة ([مخرجات JSON](/ar/docs/ai-agents-json-output)).

## نموذج بوابة المعرفة

التعديلات الحساسة تتبع اتفاقية `passwd(1)`: لتغيير سر، أثبت أنك كنت تعرفه بالفعل. **متماثل للبشر والوكلاء**. كلاهما يمر بنفس البوابة. لا يوجد تجاوز بحجة "أنا أمام لوحة المفاتيح".

- تريد تدوير رمز API مخزَّن في `/credentials/cfDnsApiToken`؟
- تسأل واجهة سطر الأوامر: "ما هي القيمة الحالية؟"
- يزوّد الوكيل (أو الإنسان) النص الصريح عبر `--current "$OLD"`. تُجزِّئ واجهة سطر الأوامر `$OLD` بـ SHA-256 وتقارنه بملخص القيمة المخزَّنة حالياً. تطابق → تنفيذ الكتابة. عدم تطابق → رفض، تسجيل.
- للتدوير دون التحقق من القيمة السابقة، مرّر `--rotate-secret` (يستبعد `--current` ويستبعده). يُسجَّل ذلك في التدقيق بوضوح بوصفه تدويراً، ولا يُعتدّ به إلا لإنسان على طرفية تفاعلية: أما الوكيل، أو نص برمجي بلا طرفية على stdin، فيحتاج دائماً إلى `--current`.

النموذج يغلق ثلاث أسطح هجومية:

1. **التدوير الصامت**: الوكيل الذي لم يكن له وصول سابق إلى `$OLD` لا يستطيع استبداله بقيمة من اختياره.
2. **التسرب عبر الاستطلاع**: استجابة الملخص لا تحتوي أبداً على نص صريح؛ حتى سجل التدقيق المخترق يُظهر `expected abc12345…, got deadbeef…`، وليس القيم الأساسية.
3. **الكتابة العرضية فوق إعدادات الإنتاج**: يتطلب `--current` متعمداً في كل مرة، حتى على TTY. يلتقط خطأ "قصدت ضبط STRIPE_TEST لكنني في shell الإنتاج".

### تلميحات الإجراء التالي المنظمة

عند فشل الشرط المسبق، يحمل غلاف JSON (مع `--output json`) حقلاً منظماً `errors[].next` يخبر الوكلاء بالضبط بما يقترحونه على الإنسان:

```json
{
  "errors": [{
    "code": "PRECONDITION_MISMATCH",
    "message": "...",
    "next": {
      "summary": "Provide the current value or acknowledge rotation.",
      "options": [
        { "description": "Re-read current digest, then retry with --current",
          "run": "rdc repo secret get mail --key STRIPE_KEY" },
        { "description": "Skip the precondition (rotation, audited)",
          "run": "rdc repo secret set mail --key STRIPE_KEY --value <new> --mode file --rotate-secret" }
      ]
    }
  }]
}
```

**ينبغي للوكلاء أن ينقلوا `next.options[].run` حرفياً إلى الإنسان بدلاً من اختراع أوامر من عندهم.** هذا يتجنب حالة الفشل التي يخترع فيها الوكيل أمراً غير موجود، ويُبقي المشغّل متحكماً في الإجراء الفعلي. أما خيار التدوير فيشغّله الإنسان من طرفية؛ ويُرفض للوكيل نفسه.

### مثال توضيحي

```bash
# الحصول على الملخص القصير لنموذج التعتيم (آمن للوكلاء).
$ rdc config field get --pointer /credentials/cfDnsApiToken
{"pointer": "/credentials/cfDnsApiToken", "value": "<redacted:secret>:abc12345"}

# محاولة الكتابة فوق بلا إثبات: مرفوض.
$ rdc config field set --pointer /credentials/cfDnsApiToken --new '"agent-picked-value"'
✗ Precondition failed: sensitive path requires --current

# تزويد النص الصريح الحالي: مسموح.
$ rdc config field set --pointer /credentials/cfDnsApiToken \
    --current "$OLD_CF_TOKEN" \
    --new   "$NEW_CF_TOKEN"
Set /credentials/cfDnsApiToken
```

إذا لم يكن لدى الوكيل `$OLD_CF_TOKEN` قط، فلا يستطيع استيفاء الشرط المسبق ويُرفض التدوير. ومن يملك القيمة يستطيع إجراءه مع ذلك: بتمرير `--current` من صدفته، أو بـ `rdc config field rotate` على طرفية تفاعلية.

## التعتيم افتراضياً

كل أمر `rdc` يقرأ الحالة الحساسة: `config show`، `config field get`، `config machine list`، `config edit --dump --redacted`: يُرجع **نماذج تعتيم** لحقول الأسرار، وليس نصاً صريحاً:

```
"sshKey":       "<redacted:credential>:9f3a2c1b"
"cfDnsApiToken":"<redacted:secret>:abc12345"
"storages.s3-prod.vaultContent": "<redacted:secret>:1f2e3d4c"
```

اللاحقة السداسية عشرية المكونة من 8 أحرف في النموذج هي أول 8 أحرف من `sha256(canonicalize(value))`: كافية للتمييز بين قيمتين مختلفتين بنظرة واحدة، غير كافية للعكس. يمكن للوكيل استخدام النموذج لتتبع ما إذا كانت القيمة قد تغيرت دون رؤيتها قط.

`--reveal` يرفع التعتيم للبشر على TTY تفاعلي. يُرفض الوكلاء بغض النظر عن حالة TTY. كل منح يكتب قيداً في سجل التدقيق بـ `reveal_granted`؛ كل رفض يكتب قيداً `refused` مع إشارات الوكيل للجهة الفاعلة مرفقة.

## كيفية التحقق من الموافقة الصريحة المحلية على كل نظام تشغيل

يعتمد كل من `REDIACC_ALLOW_GRAND_REPO` و `REDIACC_ALLOW_CLUSTER_OPS` على التحقق من سلسلة السلف لإثبات أن الموافقة الصريحة ضبطها الإنسان ولم يحقنها الوكيل. يعمل التحقق على Linux وmacOS وWindows، لكن الشاهد الذي يقرؤه يختلف من منصة لأخرى، وتختلف قوة الضمان أيضاً:

| المنصة | الشاهد | قوة الضمان |
|---|---|---|
| Linux | `/proc/<pid>/environ` لكل عملية في السلسلة | صورة وقت التنفيذ من النواة. لا تستطيع العملية تعديل بيئتها بأثر رجعي. |
| macOS | مكالمة نظام `kern.procargs2` يقرأها مساعد صغير مضمّن في `rdc` | نفس خاصية صورة وقت التنفيذ كما في Linux. قابلة للقراءة لعملياتك بدون حقوق المسؤول. |
| Windows | كتلة البيئة المباشرة لكل عملية سلف (PEB)، يقرأها نفس المساعد، مع حماية ضد إعادة استخدام PID | أضعف: Windows لا تحتفظ بصورة وقت التنفيذ، لذا يقرأ التحقق الذاكرة الحالية. العمليات الأب لا تزال لا تستطيع إعادة الكتابة من قِبَل شيء يشغله وكيل عادي، لكن الشاهد غير مجمّد في النواة مثلما هو على Linux و macOS. |

على macOS وWindows تشغّل CLI الملف التنفيذي `renet` المضمَّن لإجراء القراءة؛ ويبلغ المساعد عن المتغيرات المراقَبة التي تحملها كل عملية سلف، ويبقى منطق القرار كله داخل CLI. وإذا كان المساعد مفقوداً أو قديماً أو فشل لأي سبب، فلا تستطيع CLI التحقق من الموافقة الصريحة و**تفشل بإغلاق آمن**: تُرفض الموافقة وتذكر رسالة الخطأ أن التحقق لم يكن متاحاً، لا أن خطأً قد وقع. لا يُظهر التثبيت السليم هذه الرسالة أبداً؛ وإعادة تثبيت `rdc` تستعيد المساعد.

ما يبقى صحيحاً على كل منصة: يجب أن تكون الموافقة الصريحة موجودة أصلاً في بيئة عملية الوكيل عند بدئها. تُصدَّر في الطرفية ثم يُشغَّل الوكيل. أما الوكيل الذي يضبط المتغير في منتصف الجلسة فيُرفض.

## سجل التدقيق

كل تعديل، كل رفض، كل منح `--reveal` يكتب سطر JSONL في `~/.config/rediacc/audit.log.jsonl` (النمط `0600`، يتدوّر عند 10 ميجابايت). كل سطر مرتبط بتجزئة: حقل `prevHash` الخاص به هو `sha256("<السطر السابق>")`. العبث بأي سطر يكسر السلسلة في كل سطر تالٍ.

```jsonl
{"ts":"2026-04-21T10:02:47.831Z","actor":{"kind":"agent","agentSignals":["CLAUDECODE"]},"command":"config field set","paths":["/credentials/cfDnsApiToken"],"outcome":"ok","configId":"...","configVersion":48,"prevHash":"sha256:9f3a..."}
{"ts":"2026-04-21T10:02:51.114Z","actor":{"kind":"agent","agentSignals":["CLAUDECODE"]},"command":"config edit","paths":[],"outcome":"refused","reason":"agent environment","prevHash":"sha256:abc1..."}
{"ts":"2026-04-21T10:03:05.220Z","actor":{"kind":"human"},"command":"config show --reveal","paths":[],"outcome":"reveal_granted","configId":"...","configVersion":48,"prevHash":"sha256:deac..."}
```

### الفحص

```bash
# سرد القيود الأخيرة
rdc config audit log --since 24h

# التصفية بنمط glob للمؤشر
rdc config audit log --path '/credentials/*'

# القيود الصادرة عن الوكلاء فقط
rdc config audit log --actor agent

# بث القيود الجديدة مباشرةً (Ctrl+C للإيقاف)
rdc config audit tail

# التحقق من سلامة سلسلة التجزئة
rdc config audit verify
# → "Chain integrity verified across 247 entries."
#   أو
# → "Chain broken at line 103: file has been tampered with or corrupted."
```

### ما لا يظهر أبداً في سجل التدقيق

- قيم الأسرار بنص صريح
- كلمات المرور والرموز ومفاتيح SSH
- القيم القديمة/الجديدة في حالة عدم تطابق الشرط المسبق `--current` (بادئة الملخص المكونة من 8 أحرف فقط)

السجل آمن للمشاركة مع مراجع الأمن أو إرفاقه بتقرير خطأ.

## حدود النموذج السلوكي

ضمانات الوكيل **سلوكية، وليست مشفَّرة**. الوكيل المصمم أو الموجَّه الذي يعمل بنفس UID ملف الإعدادات يستطيع دائماً تشغيل `cat ~/.config/rediacc/rediacc.json` وقراءة النص الصريح، لأن الملف قابل للقراءة من قِبَل العملية.

للتطبيق المشفَّر الحقيقي، استخدم [مخزن الإعدادات المشفَّر](/ar/docs/config-storage): تعيش الأسرار على الجانب الخادم، كل حقل حساس يحمل التزام HMAC خاصاً به، وعامل الحساب يرفض الكتابات التي لا يتطابق شرطها المسبق `--current` مع ما هو مُخزَّن بالتجزئة. الخادم لا يرى النص الصريح أبداً (معرفة صفرية)، لكنه يُطبِّق البوابة.

مسار الملف المحلي: الطريق السهل آمن. مسار المخزن البعيد: الطريق الصعب صعب أيضاً.

## ما لا يعزله Rediacc

تحمي ضمانات الوكيل في هذه الصفحة البنية التحتية الخاصة بـ Rediacc نفسها: ملف الإعدادات وعملية Docker لكل مستودع وبيانات المستودع المشفَّرة بـ LUKS وصندوق رمل SSH المقصور النطاق. لكنها لا تحمي الخدمات الخارجية التي يحتفظ مستودعك ببيانات اعتمادها.

النسخة المتفرعة من المستودع هي BTRFS reflink لحجم الأصل. كل ما هو موجود على القرص في الأصل يكون متطابقاً بايتاً ببايت في النسخة المتفرعة: الكود والبيانات وملفات `.env` على حد سواء. إذا احتوى مستودعك على `STRIPE_LIVE_KEY` أو `AWS_ACCESS_KEY_ID` أو رمز API لـ Railway أو أي بيانات اعتماد طويلة الأمد لخدمة طرف ثالث، فإن النسخة المتفرعة ترثها. يمكن لوكيل يعمل في صندوق رمل النسخة المتفرعة قراءة ذلك الملف أو تسريب القيمة أو استخدامها لاستدعاء واجهة برمجة التطبيقات لطرف ثالث. ولا تملك خدمة الطرف الثالث أي وسيلة لمعرفة أن الاستدعاء جاء من نسخة متفرعة بدلاً من الإنتاج.

هذا هو خط المسؤولية المشتركة:

| الحدود | المالك |
|---|---|
| بيانات المستودع، فضاء أسماء التحميل، نطاق Docker، ضمانات الوكيل، سجل التدقيق، حقن الأسرار وقت النشر | Rediacc |
| كود التطبيق الذي يستخدم تلك الأسرار، وأي بيانات اعتماد مُضمَّنة في الصورة وقت البناء | مطوّر المستودع |

الحد الأساسي مدمج في النظام: **[أسرار المستودع الخاصة](/ar/docs/repositories#secrets)** مخزَّنة في مستوى منفصل عن صورة المستودع المشفَّرة ولا تُنسخ عبر حدود التفريع. تبدأ حاويات النسخة المتفرعة بخريطة أسرار فارغة وتعرّف نفسها بوصفها جهة فاعلة خارجية مختلفة عن الأصل. اضبطها باستخدام `rdc repo secret set` (وضع env لاستبدال compose، ووضع file لكتل `secrets:` من tmpfs). بوابة الطفرة متماثلة. يجب على البشر والوكلاء على حد سواء تزويد `--current` (الشرط المسبق بأسلوب passwd) للكتابة فوق قيمة قائمة أو حذفها؛ أما `--rotate-secret` (تدوير مُسجَّل) فهو البديل لإنسان على طرفية.

**عزل المستودعات المتبادل مُطبَّق.** لا يستطيع ملف compose الخبيث أو المهمل في المستودع B الإشارة إلى دليل أسرار المستودع A. يرفض مدقق compose في renet رفضاً قاطعاً أي مسار `secrets: file:` أو `configs: file:` أو `env_file:` يشير خارج دليل `${REDIACC_NETWORK_ID}` للمستودع الحالي، والرفض غير قابل للتجاوز بـ `--unsafe`. دفاع متعمق: صندوق رمل Landlock حول العملية الفرعية bash في Rediaccfile يقصر قراءات نظام الملفات على دليل أسرار الشبكة الحالية فقط، لذا يفشل `cat /var/run/rediacc/net-<other>/secrets/X` من Rediaccfile خبيث بخطأ EACCES على مستوى النواة. والأمر نفسه ينطبق على واجهة Docker البرمجية: يخدم مقبس Docker لكل مستودع وكيل سياسات في renet يرفض `--privileged` وقيم `pid` و`ipc` و`uts` الخاصة بالمضيف وطلبات الأجهزة وعمليات الربط (binds) التي تصل إلى بيئة تشغيل مستودع آخر أو بياناته، ويرد بالرمز `403`. لذا لا تستطيع حاوية تحمل `${DOCKER_SOCKET}` استخدام الواجهة للوصول إلى مستودع آخر، ولا يقتصر الفحص على ملف compose. وحده المشغّل يستطيع توسيع قاعدة الربط، لمجلدات مضيف محددة بالاسم، عبر تصريح مملوك للجذر لا تستطيع أي حاوية الكتابة إليه.

نمطان إضافيان يسدّان الحالات الحدية:

1. **لا تُضمِّن بيانات اعتماد الإنتاج في نظام ملفات المستودع نفسه.** ملف `.env` مُدمَج في الصورة، أو بيانات اعتماد محفوظة في حجم خلال `up()`، ينتقل عبر reflink إلى النسخة المتفرعة. تحمي ميزة أسرار المستودع فقط القيم التي تحتفظ بها في مستوى الأسرار. لا تستطيع حماية البايتات التي تعيش بالفعل داخل صورة LUKS بأثر رجعي. للمستودعات الحالية التي تحتوي على ملفات `.env` مُضمَّنة، انقلها يدوياً إلى أسرار المستودع.
2. **قيّد الشبكة الصادرة للنسخة المتفرعة بترشيح eBPF للخروج** بحيث لا تستطيع النسخة المتفرعة الوصول إلا إلى localhost ونقاط نهاية صندوق الرمل المحددة بوضوح. عزل شبكة Rediacc لكل مستودع هو الأساس؛ قوائم السماح للخروج لكل نسخة متفرعة غير مبنية اليوم، لكن المسار مفتوح.

يتولى Rediacc حقن الأسرار وقت النشر وعزل النسخ المتفرعة وعزل المستودعات المتبادل. أما النصف الخاص بـ"لا تُضمِّنه في الصورة" فيقع على عاتقك.

## وصفات سريعة

### السماح لوكيل بالعمل على مستودع grand واحد

```bash
# بوصفك الإنسان، قبل بدء الوكيل:
export REDIACC_ALLOW_GRAND_REPO='gitlab'
claude              # أو cursor أو gemini وغيرها.
```

يستطيع الوكيل الآن تغيير `gitlab`، حيث تسمح السياسة بتغيير مستودعات grand، ولا يستطيع تغيير أي مستودع grand آخر. أما التغيير المدمِّر، مثل `repo delete gitlab`، فيظل يطلب التأكيد.

### تدوير رمز سحابي دون معرفة القيمة القديمة

```bash
# بوصفك الإنسان، من طرفية تفاعلية:
rdc config field rotate --pointer /credentials/cfDnsApiToken --new "$NEW_CF_TOKEN"
```

يبقى التدوير بلا `--current` من شأن الإنسان. أما الوكيل الذي يعرف القيمة الحالية فيستخدم `rdc config field set --current` بدلاً منه.

### اكتشاف الحقول التي يُسمح للوكيل بلمسها

```bash
rdc config field list --sensitive --output json
```

يُرجع كل قالب مؤشر ونوعه (`secret` / `credential` / `pii` / `identifier`) وما إذا كان ملتزماً بغلاف HMAC من جانب الخادم.
