# 事件报告

已声明的事件（[事件响应](/zh/docs/incident-response)）会生成三份分阶段报告，供客户向监管机构提交。Rediacc 根据证据生成这些文档。事件是否重大或是否需要报告，仍由客户判断，每份报告都会这样说明。

## 阶段

每个阶段只列出它所要求的部分，不多也不少，因此某阶段不需要的部分会被省略，而不是留空。

| 阶段 | 截止时间 | 新增内容 |
|---|---|---|
| 预警 | 得知后 24 小时 | 头部信息、时间线、入侵指标、疑似恶意行为和跨境影响 |
| 通知 | 得知后 72 小时 | 初步评估、数据影响（类别、大致数量、成员国）和 ATT&CK 技术 |
| 最终 | 通知后一个日历月 | 根本原因和缓解措施 |

最终报告在通知之后，因此要先生成通知。每个阶段都包含前一阶段的各部分。

报告中的每个事实都会说明它是如何得知的：在证据中观察到、由客户录入，或推断得出。推断出的事实带有置信度和检测器给出的理由。评估、数据类别、成员国、疑似原因、已采取的行动、联系人和技术，都是客户在生成之前于事件页面录入的内容。

## 格式

| 格式 | 用途 |
|---|---|
| JSON | 规范且可验证的形式 |
| STIX 2.1 | 供威胁情报工具使用的指标包 |
| PDF | 可阅读的文档，支持非拉丁文字，每页页脚都带有免责声明、二维码和报告哈希 |

在事件页面上，每个阶段的每种格式都有一个下载按钮。在命令行中：

```bash
rdc incident export <id> --stage early-warning
rdc incident export <id> --stage notification --format stix
rdc incident export <id> --stage final --format pdf --out ./reports
```

格式默认为 JSON。`--format` 仅在与 `--stage` 一起使用时有效。文件以其报告 ID 命名写出。

## 签名与验证

每份报告都用 Ed25519 报告密钥签名，报告 ID、阶段和哈希记录在公开记录中。签名覆盖报告的规范内容，因此签名之后的任何改动都会被发现。

报告可以在三个地方检查：

- 位于 `/account/verify/report/<id>` 的验证页面，PDF 上的二维码会打开它。检查在浏览器中针对已发布的报告密钥运行，不会上传任何内容。JSON 文件可以完整检查。PDF 无法在浏览器中重新计算哈希，因此页面会确认 PDF 带有该报告的哈希，并指向 JSON 文件以便完整检查。
- 命令行，针对 JSON 报告：

```bash
rdc forensics verify --report ./reports/<report-id>.json
```

内容或签名不匹配时，命令以退出码 1 结束。PDF 通过生成它的 JSON 报告来验证。

- 报告内部的证据印章，记录该窗口的 Verify evidence 结果：谁验证的、使用哪个版本以及何时验证。

## 字段映射

每个报告字段都映射到客户所适用的各项监管制度，因此内容可以直接沿用而无需重新录入。映射涵盖三种制度：NIS2 第 23(4) 条、实施条例 (EU) 2025/302 的事件通知格式，以及 GDPR 第 33(3) 条。示例：

| 报告字段 | NIS2 | GDPR |
|---|---|---|
| 得知时间 | 第 23(4)(a) 条 | 第 33(1) 条 |
| 时间顺序 | 第 23(4)(d) 条 | 第 33(3)(a) 条 |
| 联系人 | 第 23(4) 条 | 第 33(3)(b) 条 |

在某项制度中没有对应项的字段会说明原因，而不是被省去。例如，GDPR 第 33(3) 条的通知没有参考编号或结案时间。

## 报告不声称的内容

每个阶段都会印出两条声明：

- 流记录证明的是流量和目的地，而不是内容。
- 事件是否重大或是否需要报告，由客户判断。

Rediacc 不会代表客户向监管机构提交任何内容。
