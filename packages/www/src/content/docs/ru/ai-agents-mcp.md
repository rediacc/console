## Обзор

Два MCP-сервера (Model Context Protocol) предоставляют один и тот же реестр инструментов:

| Сервер | Транспорт | Как работает | Инструменты |
|---|---|---|---|
| Локальный | stdio | `rdc mcp serve`, запускается агентом | Все инструменты |
| Удалённый | Streamable HTTP | `https://mcp.<region>.rediacc.cloud/g/<grantId>` | Удалённые инструменты, то есть все, кроме перечисленных в таблице только локальных |

**Требования:** для локального сервера нужен установленный `rdc`, настроенный хотя бы с одной машиной. Для удалённого сервера нужен грант на конфигурацию.

## Локальный сервер

`rdc mcp serve` запускает MCP-сервер через stdio. Агент запускает его как подпроцесс и общается с ним по JSON-RPC.

### Claude Code

В `.mcp.json` проекта добавьте запись:

```json
{
  "mcpServers": {
    "rdc": {
      "command": "rdc",
      "args": ["mcp", "serve"]
    }
  }
}
```

Или с именованной конфигурацией:

```json
{
  "mcpServers": {
    "rdc": {
      "command": "rdc",
      "args": ["mcp", "serve", "--config", "production"]
    }
  }
}
```

### Cursor

Откройте Settings → MCP Servers → Add Server:

- **Name**: `rdc`
- **Command**: `rdc mcp serve`
- **Transport**: stdio

### Параметры

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `--config <name>` | (конфигурация по умолчанию) | Именованная конфигурация для всех команд |
| `--timeout <ms>` | `120000` | Таймаут команд по умолчанию в миллисекундах |

## Удалённый сервер

В каждом регионе работает один MCP Worker по адресу `mcp.<region>.rediacc.cloud`. Каждый агент подключается к URL одного гранта: `https://mcp.<region>.rediacc.cloud/g/<grantId>`. Грант указывает одну конфигурацию, срок действия и область доступа: флаг «только чтение», список разрешённых инструментов и шаблоны (glob) имён машин и репозиториев. Вызовы инструментов выполняются на исполнителе организации, которой принадлежит грант.

### Учётные данные

Обе формы определяют грант; идентификатор гранта в URL лишь называет его.

| Форма | Применение | Передаётся как |
|---|---|---|
| Токен доступа OAuth | Интерактивные клиенты, например claude.ai | `Authorization: Bearer <token>` |
| Bearer-токен агента `rmcp_<grantId>.<secret>` | Агенты без интерфейса | `Authorization: Bearer` или `x-api-key` |

Учётные данные в строке запроса отклоняются с кодом 400. Отсутствующий, просроченный или чужой токен OAuth получает 401 с заголовком `WWW-Authenticate: Bearer resource_metadata=...`, который указывает на документ защищённого ресурса гранта, так что OAuth-клиент обновляет токен или выполняет вход. Неизвестный грант, неверный секрет и bearer-токен агента от другого гранта получают один и тот же голый 401.

### OAuth

Worker является сервером авторизации OAuth 2.1 с PKCE (только S256). Клиенты регистрируются через Client ID Metadata Document или динамическую регистрацию клиентов по адресу `/register`.

| Эндпоинт | Назначение |
|---|---|
| `/.well-known/oauth-authorization-server` | Метаданные сервера |
| `/.well-known/oauth-protected-resource/g/<grantId>` | Документ защищённого ресурса одного гранта |
| `/authorize` | Начинает авторизацию и перенаправляет на страницу аккаунта `/account/mcp/authorize` |
| `/oauth/token` | Обмен кода, обновление и отзыв |
| `/register` | Динамическая регистрация клиентов |

Клиент передаёт `resource=https://mcp.<region>.rediacc.cloud/g/<grantId>`. Авторизация завершается только для гранта, названного в ресурсе, а токен работает только по URL своего гранта. Перенаправление с `/authorize` несёт подписанный одноразовый идентификатор и не содержит секрета.

### Срок жизни токенов

Токен никогда не живёт дольше своего гранта.

| Токен | Срок жизни |
|---|---|
| Токен доступа | Меньшее из значений: 1 час и оставшееся время гранта |
| Токен обновления | Меньшее из значений: 30 дней и оставшееся время гранта |

Каждый обмен кода и каждое обновление заново проверяют грант. Просроченный, отозванный грант или грант со сменой ключа отвечает `invalid_grant` и отзывает OAuth-грант. Токены обновления ротируются, а повторное предъявление одного и того же токена отзывает грант.

### Одна конфигурация на грант

Грант обслуживает только ту конфигурацию, которую называет. Вызов `tools/call` с аргументом, указывающим другую конфигурацию (`config` или его вариант написания), отклоняется с `REDIACC_GRANT_SCOPE` до выполнения чего-либо. Пользователь с несколькими конфигурациями авторизует по одному гранту на каждую. Инструмент вне списка разрешённых или инструмент записи при гранте только для чтения не попадает в `tools/list` и отклоняется при вызове.

### Регионы

Идентификатор гранта начинается с его региона, например `eu_`. Запрос к `/g/<grantId>` на Worker другого региона получает ответ 421 с правильным URL:

```json
{
  "code": "REDIACC_WRONG_REGION",
  "message": "This grant lives in the us region. Use https://mcp.us.rediacc.cloud/g/us_...",
  "region": "us",
  "mcpUrl": "https://mcp.us.rediacc.cloud/g/us_..."
}
```

Грант никогда не принимается как ресурс OAuth, аудитория токена или цель авторизации за пределами своего региона.

### Состояния гранта и лимиты

Грант, у которого истёк срок, который отозван или потерял ключ из-за ротации ключей хранилища конфигураций, по-прежнему отвечает на `initialize` и `tools/list`. Каждый `tools/call` при этом возвращает `REDIACC_GRANT_EXPIRED`, `REDIACC_GRANT_REVOKED` или `REDIACC_KEY_ROTATED` вместе с `reauthUrl`, который пользователь открывает для повторной авторизации.

Каждый грант допускает 60 вызовов в минуту и 5 одновременно выполняемых вызовов. Вызов сверх любого из лимитов возвращает `REDIACC_RATE_LIMITED` с `retryAfterSeconds`.

## Примеры рабочих процессов

**Проверить состояние машины:**
> «Каково состояние моей продакшн-машины?»

Агент вызывает `machine_status` и получает сведения о подключении, информацию о системе, контейнеры, сервисы, репозитории и использование ресурсов.

**Развернуть приложение:**
> «Разверни gitlab на моей staging-машине»

Агент вызывает `repo_up` с `name: "gitlab"` и `machine: "staging"`: репозиторий разворачивается, и возвращается результат, успех или ошибка.

**Следить за долгой задачей:**
> «Восстанови вчерашнюю ночную резервную копию nextcloud»

Агент вызывает `backup_restore`. Команда, не уложившаяся в отведённое время, возвращает дескриптор задачи, и агент вызывает `job_wait` (до 50 с за вызов) и `job_logs`, пока задача не завершится.

**Отладить неисправный сервис:**
> «Мой nextcloud тормозит, выясни, в чём дело»

Агент вызывает `machine_health`, затем `machine_containers` и `repo_logs` и предлагает исправление.

## Безопасность

Локальный MCP-сервер применяет два уровня защиты. Лимиты удалённого сервера описаны в разделе [Удалённый сервер](#удалённый-сервер).

### Режим только для форков (по умолчанию)

По умолчанию сервер работает в **режиме только для форков**: инструменты записи (`repo_up`, `repo_down`, `repo_delete`, `repo_exec`) могут работать только с репозиториями-форками. Агенты не могут трогать grand-репозитории (оригиналы). Так задумано.

> **Секреты репозитория доступны только через CLI по замыслу.** Инструменты `repo_secret_set` и `repo_secret_unset` намеренно **не** предоставляются как MCP-инструменты. Запись требует предусловия `--current <previous-value>` (или `--rotate-secret` для подтверждения непроверенной ротации), и эта процедура требует участия человека. Агентам, которым нужно предложить ротацию секрета, следует вызвать `repo_secret_get` для подтверждения хеша, а затем передать оператору CLI-команду через поле `next.options[].run` в JSON-конверте ошибки. Подробнее: [Безопасность AI-агентов](/en/docs/ai-agents-safety#structured-next-action-hints) и [Репозитории § Секреты](/en/docs/repositories#secrets).

Чтобы разрешить агенту изменять grand-репозитории, экспортируйте `REDIACC_ALLOW_GRAND_REPO` в своём терминале **перед запуском агента, который хозяйствует MCP-сервер**:

```bash
export REDIACC_ALLOW_GRAND_REPO='gitlab'   # один репозиторий
# или 'repo1,repo2,repo3' (пробелы вокруг записей игнорируются), или '*' для всех репозиториев
claude   # или cursor, gemini и т. д.
```

Переопределение проверяется относительно цепочки предков процесса: оно учитывается только тогда, когда оно уже присутствовало в окружении самого процесса агента, что означает, что вы экспортировали его перед запуском агента (и MCP-сервера, который он породил). Агент не может выдать себе доступ, установив переменную в середине сессии. Намеренно отсутствует флаг сервера для этого: флаг в аргументах MCP-сервера не несёт доказательства, кто его туда поместил, в то время как проверка цепочки предков это несёт. Доступ на уровне машины (например, `term connect <machine>` без репозитория) по-прежнему требует `*`; список имён репозиториев его не открывает.

### Персональные SSH-ключи репозитория и серверная песочница

У каждого репозитория есть собственная пара SSH-ключей. Публичный ключ добавляется в `authorized_keys` с префиксом `command=`, который направляет все SSH-сессии через `renet sandbox-gateway <repo-name>` -- серверный ForceCommand, который не может быть обойдён ни одним клиентом, включая VS Code.

**Как это работает:**
1. `rdc repo create` или `rdc repo fork` генерирует уникальную пару ключей ed25519 для каждого репозитория
2. Публичный ключ устанавливается на удалённом хосте с параметром `command="renet sandbox-gateway <name>"`
3. Каждое SSH-подключение по этому ключу проходит через шлюз, который применяет:
   - **Landlock LSM** -- ограничения файловой системы на уровне ядра для пути монтирования репозитория
   - **OverlayFS home overlay** -- запись в `$HOME` перехватывается на уровне репозитория, чтение проваливается до реального домашнего каталога
   - **Персональный TMPDIR** по пути `<datastore>/.interim/sandbox/<name>/tmp/`
   - **Доступ к Docker** через изолированный Docker-сокет репозитория
   - **Сброс привилегий** до универсального пользователя (`rediacc`)
4. Файл `.envrc` репозитория загружается автоматически для настройки Docker и окружения

**Разрешено RW**: путь монтирования репозитория, рабочее пространство песочницы репозитория, домашний каталог (через overlay), Docker-сокет
**Разрешено RO**: системные пути (`/usr`, `/bin`, `/etc`, `/proc`, `/sys`)
**Заблокировано**: пути монтирования других репозиториев, системные файлы за пределами списка разрешений

**Интеграция с VS Code**: каждый репозиторий получает собственную установку VS Code Server по пути `<datastore>/.interim/sandbox/<name>/.vscode-server/`. Несколько репозиториев могут быть открыты одновременно в независимых изолированных окружениях без общего сервера.

Это предотвращает горизонтальное перемещение: даже если агент получит доступ к оболочке форка, он не сможет прочитать или изменить другие репозитории на той же машине. SSH-подключение на уровне машины (без репозитория) использует командный ключ и не изолируется в песочнице.

## Архитектура

Локальный MCP-сервер не хранит состояния. Каждый вызов инструмента запускает `rdc` как изолированный дочерний процесс с флагами `--output json --yes --quiet`. Это означает:

- Нет утечки состояния между вызовами инструментов
- Используются ваши существующие настройки `rdc` и SSH-ключи
- Ошибки в одной команде не влияют на другие
