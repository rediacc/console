Когда вы указываете AI-ассистент кодирования на вашу инфраструктуру, CLI Rediacc обнаруживает это. Если Claude Code, Cursor, Gemini CLI, Copilot CLI или любой другой AI-ассистент кодирования управляет `rdc`, CLI применяет иной набор правил, чем для человека за клавиатурой. На этой странице объясняется, что агент может делать, что не может, и как защитные ограничения удерживаются даже тогда, когда агент пытается их обойти.

## Краткий справочник: что агенты могут и не могут делать

| Операция | Поведение агента по умолчанию | Как разблокировать для конкретного случая |
|---|---|---|
| `rdc config show` (с редактированием) | ✅ allowed |  |
| `rdc config field get --pointer <pointer>` (заглушка или дайджест) | ✅ allowed |  |
| `rdc config field get --pointer <pointer> --digest` | ✅ allowed |  |
| `rdc config field set --pointer <pointer>` (публичное поле) | ✅ allowed |  |
| `rdc config field set --pointer <pointer>` (чувствительное поле, **с корректным `--current`**) | ✅ allowed |  |
| `rdc config edit --dump --redacted` (JSONC со скрытыми значениями) | ✅ allowed |  |
| `rdc config audit {log, tail, verify}` | ✅ allowed |  |
| `rdc config field set --pointer <pointer>` (чувствительное поле, без `--current`) | 🔴 refused | Указать `--current "<старое значение>"` |
| `rdc repo secret set <repo> --rotate-secret` (ротация без `--current`) | 🔴 refused | Передать `--current`, либо человек выполняет ротацию в терминале |
| `rdc config field get --pointer <pointer> --reveal` | 🔴 refused | Использовать `--digest` вместо этого |
| `rdc config show --reveal` | 🔴 refused | Использовать простой `rdc config show` |
| `rdc config edit` (интерактивный редактор) | 🔴 refused, без переопределения | Просмотреть через `--dump --redacted`, изменить одно поле через `config field set --current` |
| `rdc config edit --apply <file>` | 🔴 refused, без переопределения | То же; изменения всего документа применяет человек в терминале |
| `rdc config edit --reveal` | 🔴 refused, без переопределения | То же |
| `rdc config field rotate --pointer <pointer>` | 🔴 refused | Человек запускает его в интерактивном терминале |
| Изменение grand-репозитория (продакшн) | 🔴 refused | Явное согласие человека для этого репозитория в рамках политики, разрешающей изменения grand-репозиториев ([ниже](#one-decision-opt-in-and-policy-ceiling)) |
| Операции жизненного цикла кластера или датастора | 🔴 refused | Явное согласие человека для этого кластера в рамках политики, разрешающей операции с кластерами |
| `rdc term connect <machine>` (прямой SSH на машину) | 🔴 refused | Сначала сделать форк репозитория и подключиться к форку |

Каждый отказ агенту записывается в журнал аудита с `outcome: refused` и причиной. Для правки конфигурации целиком у агента вообще нет пути: конфигурация хранит учётные данные LUKS каждого репозитория, и агент, способный её переписать, мог бы удалить и такие данные, без которых зашифрованный том не открыть.

## Как агенты обнаруживаются

CLI считает процесс агентом, если выполняется хотя бы одно из условий:

- Одна из переменных `REDIACC_AGENT`, `CLAUDECODE`, `GEMINI_CLI`, `COPILOT_CLI` установлена в `"1"`, или `CURSOR_TRACE_ID` установлена вообще.
- На Linux: любой родительский процесс в цепочке предков имеет одну из этих переменных в своём окружении (через `/proc/<pid>/environ`). Даже если агент удалит свои переменные с помощью `env -i` или скрипта-обёртки, родительская цепочка всё равно сообщит CLI, кто его запустил.

Обнаружение выполняется один раз на процесс и кэшируется. Его нельзя отключить. Разрешение для удалённого MCP помечает свои вызовы как вызовы агента на стороне исполнителя, без всякого обнаружения.

## Одно решение: явное согласие И потолок политики

Каждый интерфейс, запускающий команду `rdc` (CLI, локальный MCP-сервер, удалённый MCP-сервер, `rdc --proxy` и веб-консоль), обращается к одной и той же функции принятия решений, поэтому все они отказывают и разрешают одно и то же. Она применяет два условия, и агент действует только там, где выполнены оба:

1. **Потолок политики.** Политика организации, суженная политикой команды, определяет, какие команды, машины и репозитории вправе использовать вызывающая сторона, и разрешены ли вообще изменения grand-репозиториев (`allowGrandRepos`) и операции с кластерами (`allowClusterOps`). Если у конфигурации нет записи политики, действует значение по умолчанию в зависимости от роли: владельцы и администраторы могут действовать, участники нет. Политика хранится в отдельной запечатанной записи, которую пишут только владельцы и администраторы ([Модель безопасности](/ru/docs/security-model#policy)); ни один агент и ни одна команда CLI не может её изменить.
2. **Явное согласие человека.** Внутри потолка агенту всё равно нужен человек, который назовёт grand-репозиторий или кластер, разрешённый к изменению:
   - **Локальные агенты** (CLI и локальный MCP): человек экспортирует `REDIACC_ALLOW_GRAND_REPO` (имена репозиториев или `*`) или `REDIACC_ALLOW_CLUSTER_OPS` (имена кластеров или `*`) в терминале до запуска агента. CLI проверяет цепочку родительских процессов, поэтому переменная, заданная агентом посреди сессии, не засчитывается ([как это проверяется в каждой ОС](#how-a-local-opt-in-is-verified-on-each-os)).
   - **Удалённые агенты** (удалённый MCP): согласия входят в разрешение, которое человек создаёт в интерфейсе аккаунта ([Удалённый сервер](/ru/docs/ai-agents-mcp#remote-server)).

Согласие никогда не расширяет потолок: репозиторий, закрытый политикой, остаётся закрытым, что бы ни говорили окружение или разрешение. Форкам согласие не нужно. Репозиторий, который CLI не может опознать, считается grand.

**Разрушительные изменения сначала запрашивают подтверждение.** Если агенту разрешено разрушительное изменение grand-репозитория (например, `repo delete`), ответ будет `needs_confirmation`. MCP-клиент показывает пользователю запрос подтверждения; клиент без такой возможности получает аргумент `confirm`, который нужно отправить обратно после вопроса пользователю. В CLI человек повторно запускает команду с `--confirm-grand <repo>`.

Каждый ответ содержит стабильный код (`POLICY_DENIED`, `GRAND_REPO_DENIED`, `CLUSTER_OPS_DENIED`, `AGENT_OPT_IN_MISSING`, `FORK_BLOCKED`, `AGENT_BLOCKED`, `CONFIRMATION_REQUIRED`), так что скрипт или агент ориентируется на код, а не на текст сообщения ([JSON-вывод](/ru/docs/ai-agents-json-output)).

## Модель шлюза знаний

Чувствительные изменения следуют соглашению `passwd(1)`: чтобы изменить секрет, докажите, что вы его уже знали. **Одинаково для людей и агентов**. Оба проходят через один и тот же шлюз. Нет никакого обхода типа «я сижу за клавиатурой».

- Хотите ротировать токен API, хранящийся в `/credentials/cfDnsApiToken`?
- CLI спрашивает: «какое текущее значение?»
- Агент (или человек) предоставляет открытый текст через `--current "$OLD"`. CLI хэширует `$OLD` с помощью SHA-256 и сравнивает с дайджестом хранящегося значения. Совпадение → запись выполняется. Несоответствие → отклонено, зафиксировано в аудите.
- Чтобы выполнить ротацию без проверки прежнего значения, передайте `--rotate-secret` (взаимоисключающе с `--current`). Это явно фиксируется в аудите как ротация и засчитывается только человеку в интерактивном терминале: агенту, как и скрипту без терминала на stdin, по-прежнему нужен `--current`.

Модель закрывает три поверхности атаки:

1. **Скрытая ротация**: вызывающий (агент или человек) без предварительного доступа к `$OLD` не может заменить его своим значением.
2. **Утечка через зондирование**: ответ с дайджестом никогда не содержит открытый текст; даже скомпрометированный журнал аудита показывает `expected abc12345…, got deadbeef…`, не базовые значения.
3. **Случайная перезапись конфигурации пользователя**: требует намеренного `--current` каждый раз, даже в TTY. Ловит ошибку «я хотел установить STRIPE_TEST, но я в shell'е prod».

### Структурированные подсказки следующего действия

Когда предусловие не выполняется, JSON-конверт (`--output json`) содержит структурированное поле `errors[].next`, которое точно говорит агентам, что предложить человеку:

```json
{
  "errors": [{
    "code": "PRECONDITION_MISMATCH",
    "message": "...",
    "next": {
      "summary": "Provide the current value or acknowledge rotation.",
      "options": [
        { "description": "Re-read current digest, then retry with --current",
          "run": "rdc repo secret get mail --key STRIPE_KEY" },
        { "description": "Skip the precondition (rotation, audited)",
          "run": "rdc repo secret set mail --key STRIPE_KEY --value <new> --mode file --rotate-secret" }
      ]
    }
  }]
}
```

**Агентам следует передавать `next.options[].run` человеку дословно, а не придумывать собственные команды.** Так исключается ситуация, когда агент выдумывает несуществующую команду, а оператор сохраняет контроль над самим действием. Вариант с ротацией предназначен для человека в терминале; самому агенту он недоступен.

### Практический пример

```bash
# Получить короткий дайджест заглушки редактирования (безопасно для агентов).
$ rdc config field get --pointer /credentials/cfDnsApiToken
{"pointer": "/credentials/cfDnsApiToken", "value": "<redacted:secret>:abc12345"}

# Попытка перезаписи без доказательства: отклонено.
$ rdc config field set --pointer /credentials/cfDnsApiToken --new '"agent-picked-value"'
✗ Precondition failed: sensitive path requires --current

# Предоставить текущий открытый текст: разрешено.
$ rdc config field set --pointer /credentials/cfDnsApiToken \
    --current "$OLD_CF_TOKEN" \
    --new   "$NEW_CF_TOKEN"
Set /credentials/cfDnsApiToken
```

Если у агента никогда не было `$OLD_CF_TOKEN`, он не может выполнить предусловие, и ротация отклоняется. Тот, кто знает значение, всё равно может её выполнить: передав `--current` из своей оболочки или запустив `rdc config field rotate` в интерактивном терминале.

## Редактирование по умолчанию

Каждая команда `rdc`, которая читает чувствительное состояние: `config show`, `config field get`, `config machine list`, `config edit --dump --redacted`: возвращает **заглушки редактирования** для секретных полей, не открытый текст:

```
"sshKey":       "<redacted:credential>:9f3a2c1b"
"cfDnsApiToken":"<redacted:secret>:abc12345"
"storages.s3-prod.vaultContent": "<redacted:secret>:1f2e3d4c"
```

8-символьный шестнадцатеричный суффикс заглушки: это первые 8 символов `sha256(canonicalize(value))`: достаточно для различения двух разных значений с первого взгляда, недостаточно для обратного вычисления. Агент может использовать заглушку для отслеживания изменения значения, не видя его никогда.

`--reveal` снимает редактирование для людей на интерактивном TTY. Агентам отказывается независимо от состояния TTY. Каждое разрешение записывает запись аудита `reveal_granted`; каждый отказ записывает запись `refused` с прикреплёнными сигналами агента актора.

## Как проверяется локальное явное согласие в каждой ОС

`REDIACC_ALLOW_GRAND_REPO` и `REDIACC_ALLOW_CLUSTER_OPS` оба полагаются на проверку цепочки родительских процессов, чтобы доказать, что согласие задал человек, а не внедрил агент. Проверка работает в Linux, macOS и Windows, но источник, который она читает, на разных платформах разный, как и надёжность гарантии:

| Платформа | Источник данных | Уровень гарантии |
|---|---|---|
| Linux | `/proc/<pid>/environ` для каждого процесса вверх по цепочке | Снимок в момент exec, предоставляемый ядром. Процесс не может ретроактивно отредактировать, с чем он был запущен. |
| macOS | Системный вызов `kern.procargs2`, читаемый небольшим вспомогательным инструментом внутри `rdc` | То же свойство снимка exec как на Linux. Читаемо для собственных процессов без прав администратора. |
| Windows | Блок живого окружения каждого родительского процесса (PEB), читаемый тем же вспомогательным инструментом с защитой от переиспользования PID | Слабее: Windows не хранит снимок exec, поэтому проверка читает текущую память. Родителям по-прежнему невозможно переписать себя чем-либо, что обычно запускает агент, но источник данных не заморожен ядром, как на Linux и macOS. |

В macOS и Windows CLI запускает встроенный бинарный файл `renet` для чтения; вспомогательная программа сообщает, какие из отслеживаемых переменных несёт каждый предок, а вся логика решения остаётся в CLI. Если вспомогательная программа отсутствует, устарела или даёт сбой по любой причине, CLI не может проверить согласие и **отказывает безопасно**: согласие отклоняется, а в ошибке сказано, что проверка была недоступна, а не что что-то сделано неправильно. На исправной установке это сообщение не появляется; переустановка `rdc` восстанавливает вспомогательную программу.

Что верно на любой платформе: согласие должно уже присутствовать в окружении процесса агента к моменту его запуска. Его экспортируют в терминале, а затем запускают агента. Агент, задавший переменную посреди сессии, получает отказ.

## Журнал аудита

Каждое изменение, каждый отказ, каждое разрешение `--reveal` записывает строку JSONL в `~/.config/rediacc/audit.log.jsonl` (режим `0600`, ротация при 10 МБ). Каждая строка связана хэшем: поле `prevHash` равно `sha256("<предыдущая строка>")`. Изменение любой строки разрывает цепочку во всех последующих строках.

```jsonl
{"ts":"2026-04-21T10:02:47.831Z","actor":{"kind":"agent","agentSignals":["CLAUDECODE"]},"command":"config field set","paths":["/credentials/cfDnsApiToken"],"outcome":"ok","configId":"...","configVersion":48,"prevHash":"sha256:9f3a..."}
{"ts":"2026-04-21T10:02:51.114Z","actor":{"kind":"agent","agentSignals":["CLAUDECODE"]},"command":"config edit","paths":[],"outcome":"refused","reason":"agent environment","prevHash":"sha256:abc1..."}
{"ts":"2026-04-21T10:03:05.220Z","actor":{"kind":"human"},"command":"config show --reveal","paths":[],"outcome":"reveal_granted","configId":"...","configVersion":48,"prevHash":"sha256:deac..."}
```

### Просмотр

```bash
# Список последних записей
rdc config audit log --since 24h

# Фильтр по глобу указателя
rdc config audit log --path '/credentials/*'

# Только записи от агентов
rdc config audit log --actor agent

# Потоковая трансляция новых записей в реальном времени (Ctrl+C для остановки)
rdc config audit tail

# Проверка целостности хэш-цепочки
rdc config audit verify
# → "Chain integrity verified across 247 entries."
#   ИЛИ
# → "Chain broken at line 103: file has been tampered with or corrupted."
```

### Что никогда не появляется в журнале аудита

- Открытый текст секретных значений
- Парольные фразы, токены, SSH-ключи
- Старые/новые значения при несоответствии предусловия `--current` (только 8-символьный префикс дайджеста)

Журнал можно безопасно передать проверяющему безопасности или прикрепить к отчёту об ошибке.

## Ограничения поведенческой модели

Ограничения агента являются **поведенческими, а не криптографическими**. Решительный или специально настроенный агент, работающий с тем же UID, что и файл конфигурации, всегда может выполнить `cat ~/.config/rediacc/rediacc.json` и прочитать открытый текст, поскольку файл доступен для чтения процессом.

Для настоящего криптографического контроля используйте [зашифрованное хранилище конфигурации](/en/docs/config-storage): секреты хранятся на стороне сервера, каждое чувствительное поле несёт HMAC-обязательство на уровне поля, и воркер аккаунта отклоняет записи, чьё предусловие `--current` не совпадает по хэшу с хранящимися данными. Сервер никогда не видит открытый текст (нулевое знание), но шлюз применяется принудительно.

Локальный файл: лёгкий путь безопасен. Удалённое хранилище: обходной путь криптографически труден.

## Что Rediacc не изолирует

Защитные ограничения агента на этой странице защищают собственную инфраструктуру Rediacc: файл конфигурации, Docker-демон каждого репозитория, LUKS-зашифрованные данные репозитория, ограниченную SSH-песочницу. Они не защищают внешние сервисы, для которых ваш репозиторий хранит учётные данные.

Форк репозитория это BTRFS reflink тома родителя. Всё, что хранится на диске у родителя, побайтово идентично в форке: код, данные и `.env` файлы одинаково. Если ваш репозиторий содержит `STRIPE_LIVE_KEY`, `AWS_ACCESS_KEY_ID`, токен Railway API или любые другие долгоживущие учётные данные для стороннего сервиса, форк наследует их. Агент, работающий в песочнице форка, может прочитать этот файл, экспортировать значение или использовать его для вызовов стороннего API. У стороннего сервиса нет способа узнать, что вызов пришёл из форка, а не из продакшн.

Это линия разделения ответственности:

| Граница | Владелец |
|---|---|
| Данные репозитория, пространство имён монтирования, область Docker, защитные ограничения агента, журнал аудита, инъекция секрета во время развертывания | Rediacc |
| Код приложения, который использует эти секреты, и любые учётные данные, встроенные в образ во время сборки | Разработчик репозитория |

Основная защита встроена: **[секреты для каждого репозитория](/en/docs/repositories#secrets)** хранятся в отдельной области от зашифрованного образа репозитория и не копируются через границу форка. Контейнеры форка загружаются с пустой картой секретов и идентифицируют себя как другой внешний субъект, чем родитель. Устанавливайте их с помощью `rdc repo secret set` (режим env для интерполяции compose, режим file для блоков tmpfs `secrets:`). Шлюз мутации одинаков. И люди, и агенты должны предоставить `--current` (предусловие passwd-стиля) для перезаписи или удаления существующего значения; `--rotate-secret` (ротация в журнале аудита) подходит для человека в терминале.

**Кроссрепозиторная изоляция применяется принудительно.** Вредоносный или халатный compose-файл в репо B не может ссылаться на каталог секретов репо A. Валидатор compose renet жёстко отклоняет любой путь `secrets: file:`, `configs: file:` или `env_file:`, который указывает за пределы директории `${REDIACC_NETWORK_ID}` текущего репо, и отклонение НЕ переопределяется с помощью `--unsafe`. Оборона в глубину: песочница Landlock вокруг bash-подпроцесса Rediaccfile ограничивает чтение файловой системы только директорией секретов текущей сети, поэтому `cat /var/run/rediacc/net-<other>/secrets/X` из вредоносного Rediaccfile не срабатывает с EACCES на уровне ядра. То же верно для Docker API: сокет Docker каждого репо обслуживает политик-прокси renet, который отклоняет с `403` `--privileged`, `pid`, `ipc` и `uts` хоста, запросы устройств и bind-монтирования, дотягивающиеся до рантайма или данных другого репо. Поэтому контейнер с `${DOCKER_SOCKET}` не может через API добраться до другого репо, и проверяется не только compose-файл. Расширить правило bind-монтирований, для именованных каталогов хоста, может только оператор, выдав разрешение, принадлежащее root, в которое не может писать ни один контейнер.

Два дополнительных шаблона закрывают граничные случаи:

1. **Не встраивайте учётные данные продакшена в саму файловую систему репозитория.** `.env` файл, коммитенный в образ, или учётные данные, сохранённые в томе во время `up()`, рефлинкиются в форк. Функция секретов для каждого репозитория защищает только значения, которые вы храните в плоскости секретов. Она не может постфактум защитить байты, которые уже живут внутри LUKS-образа. Для существующих репо с встроенными `.env` файлами поднимите их в секреты для каждого репозитория вручную.
2. **Ограничьте исходящий сетевой трафик форка с помощью eBPF egress-фильтрации** так, чтобы форк мог достигать только localhost и явных конечных точек песочницы. Сетевая изоляция Rediacc для каждого репозитория является основой; allowlist исходящего трафика для каждого форка не построен сегодня, но путь открыт.

Rediacc обрабатывает инъекцию во время развертывания, кросс-форк изоляцию и кросс-репо изоляцию. Половина «не встраивайте в образ» лежит на вас.

## Быстрые рецепты

### Разрешить агенту работать с одним grand-репозиторием

```bash
# От имени человека, до запуска агента:
export REDIACC_ALLOW_GRAND_REPO='gitlab'
claude              # или cursor, gemini и т. д.
```

Теперь агент может изменять `gitlab`, если политика разрешает изменения grand-репозиториев, и никакой другой grand-репозиторий. Разрушительное изменение, например `repo delete gitlab`, по-прежнему запрашивает подтверждение.

### Выполнить ротацию облачного токена, не зная старого значения

```bash
# От имени человека, в интерактивном терминале:
rdc config field rotate --pointer /credentials/cfDnsApiToken --new "$NEW_CF_TOKEN"
```

Ротация без `--current` остаётся за человеком. Агент, знающий текущее значение, вместо этого использует `rdc config field set --current`.

### Узнать, какие поля агент может трогать

```bash
rdc config field list --sensitive --output json
```

Возвращает каждый шаблон указателя, его тип (`secret` / `credential` / `pii` / `identifier`) и входит ли он в HMAC-конверт на стороне сервера.
