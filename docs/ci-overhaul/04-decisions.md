## D. Merge queue, reconsidered honestly

The first answer was "drop it". After pushback and research the position is softer and the
reasoning changed.

**What is true:**
- Available on `console` (public, org-owned). **Not** available on `renet`/`account`/`elite`
  (private on a free org; Enterprise Cloud required).
- It re-runs CI on the combined result, so each entry costs an extra run.
- **GitHub's server-side merge does not check out submodules**, so it cannot tell that one
  gitlink is a descendant of another and reports a conflict where local git fast-forwards.
- CD writes submodule pointers to main automatically: 10 of the last 40 main commits are CD
  auto-pushes, five of them `chore(release): update homebrew-tap submodule pointer`.

**What I got wrong the first time, and corrected:**
- I led with the submodule-conflict risk. At **queue depth 1** that risk largely dissolves,
  because CD fires *after* a merge and no other merge is landing during your own entry.
- I said queue runs could never be fast-pathed. Wrong. If main has not moved since the PR's
  last green, the queue branch content is **identical** to what already passed, which is
  exactly the content-identity test the baseline engine performs. Extend the engine to
  `merge_group` and a queue entry costs almost nothing in the common case.

**So it is feasible, and the honest objection is different:** at depth 1 it duplicates what
`strict_required_status_checks_policy` gives for one line, while costing a `merge_group`
trigger, a third event for the baseline engine, a ruleset rule, and the documented
"required check must report on `merge_group` or the entry hangs forever" trap.

**The trigger condition that would flip this to "do it": running multiple PRs concurrently**,
which is plausible once a 24/7 agent is landing work. Revisit then, with the design above.

## E. The v2 deferral issue (content to file)

Title: *"v2: deferred items from the ci-overhaul program, with reasons"*

Each entry must carry **why**, so a future session does not relitigate from scratch.

1. **GitHub Projects v2 automation.** GraphQL-only; needs `read:project`/`project` scope.
   Verified live that `admin:org` plus `repo` is insufficient. Requires a long-lived
   org-scoped credential, which is the exact class that injection guidance says can be
   recovered over time, on a public repo. **Replaced by sub-issues**, which work on the plain
   repo-scoped token (100 children, 8 levels, one parent per issue; verified live).
2. **Agent editing `.github/workflows/**`.** Dropped permanently, not deferred. No
   `app-token` preset requests `workflows`, and `rediacc-ci-cd` lacks the permission
   entirely. The autopilot escalates with a proposed patch.
3. **Merge queue.** See section D. Live option, not rejected.
4. **GitHub Discussions as a decision database.** No labels, not greppable, not in the working
   tree, not diff-reviewable. `docs/adr/` wins on every axis for zero cost. **Carry forward
   the operator's prompt-injection concern**: once agents read issue bodies, the untrusted-text
   quarantine pattern applies to issues too.
5. **The idea-database half of ask 11.** ADRs record decisions, not undecided ideas. Cheap
   substitute: an `idea` label or a `docs/ideas/` convention.
6. **E2E matrix reduction.** Wall-neutral; revisit only if concurrency binds.
7. **`#533` compose-stack consolidation.**
8. **Intra-quality serial chain.** Roughly 80 gates run serially in one lane, so a www-only PR
   still pays every cli and renet static gate. Job-level scoping does not touch this. Separate
   project.
