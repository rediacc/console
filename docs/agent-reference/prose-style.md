# Writing style: the work, not the person

The work, the event or the artifact is the subject, or the shared "we" is. The second person and the first person both stay out. Thanks are said in full, and praise is directed at the work rather than at whoever produced it.

That is the whole rule. The eighteen below are what it looks like applied, and they live in one place: [.ci/config/prose-style-rules.json](../../.ci/config/prose-style-rules.json).

Nothing else in this repository restates a rule. The table here is generated from that file, the linter loads it, both hook guards load it, and the test suite builds one case per example in it. A rule changed there changes all four, with no edit anywhere else.

## What a green means, and what it does not

Three limits, stated here rather than discovered later.

**`advisory` means the rule is written down and not mechanically detected.** Nine of the eighteen are. The reason is per-rule and recorded in the rules file, and it is usually that the pattern which would catch the rule also catches its own counter-example.

R12's bad example `The project failed.` and R3's good example `The build failed after the last change.` are the same surface shape; separating them needs to know what kind of noun the subject is. An advisory rule is one for a person to apply, not one the gate enforces.

**The gate is shrink-only.** `.ci/config/prose-style-baseline.json` freezes the debt that existed when this landed, so a green means NO NEW finding rather than a clean tree. The baselined count is printed on every success line for exactly that reason.

Both halves are enforced: a new finding fails, and a baselined finding that no longer fires ALSO fails, with instructions to drain it. A new finding does not belong in the baseline.

The drain verb is `check --drain`. It removes the rows that no longer fire and adds nothing, then runs the ordinary check, so a new finding fails in the same run. `check --write-baseline` freezes the whole current set instead and refuses whenever that set holds a finding the baseline lacks; `--accept-new` overrides that refusal and is a typed decision, never a drain.

**One surface is out of scope, one is read only for width, and one file kind is not read at all.** `private/` holds four git submodules, which are other repositories. `packages/www` IS in the corpus (since 9616fa247), but a translated copy under `packages/www/src/content/<collection>/<locale>/` is held to R18 and R19 only: every other rule matches English words, so on a translation it reports the language rather than the prose (`locale_copy_pattern` in the rules file). The English source under `/en/` keeps every rule; reflowing it re-keys each locale's `sourceHash`, so its debt is baselined, not rewrapped.

`.sh` is absent from the include list because this repository's shell surface is shrinking under a bash-to-Python migration. Each is recorded in the rules file with its reason.

Beyond those, exemptions are by NAME with a `BLOCKER:` reason, and every run PRINTS how many findings each one suppressed. A quiet exemption is how a gate stops meaning what its name says.

## Running it

```
.ci/scripts/quality/check_prose_style.py --selftest       65 controls, both directions
.ci/scripts/quality/check_prose_style.py check            the tree (npm run check:ci-prose-style)
.ci/scripts/quality/check_prose_style.py check <path>...  named files only
.ci/scripts/quality/check_prose_style.py check --json     machine-readable
.ci/scripts/quality/check_prose_style.py check --drain    drop baselined rows that no longer fire
.ci/scripts/quality/check_prose_style.py reflow --check   dry run: what would rejoin
.ci/scripts/quality/check_prose_style.py reflow --write   actually rejoin
.ci/scripts/quality/check_prose_style.py sync             the table above, on stdout
```

`reflow` undoes hard-wrapping: a paragraph broken across several narrow lines is joined into one, then re-wrapped only at a genuine sentence-ending period -- never at a plain word boundary.
A joined paragraph with no such period, however far past the limit it runs, is left on one line: R18's own floor-not-ceiling contract (768 is where a break is ALLOWED, not required, and a line that closes on its own genuine sentence-ending period is never flagged either way) applies to the tool that fixes a line exactly as it applies to the rule that checks one.
It is a DRY RUN by default, and it leaves fences, headings, tables, blockquotes, indented code, link definitions and list items alone.

It has never been run against this tree. As of 2026-09-16 it reports 399 of 447 markdown files and 36,784 lines that would rejoin.

## Where it is enforced

| Surface | What it sees | What it does |
|---|---|---|
| `npm run check:ci-prose-style` | every markdown file, and the comments of every Python, TS/JS and Go file | fails on a new error-severity finding |
| `block_prose_style_edit` (pre-edit hook) | the NEW content of an Edit, Write, MultiEdit or NotebookEdit | refuses the edit; a finding already in the baseline is a warning, so a whole-file rewrite of a legacy document still works |
| `block_prose_style_commit` (pre-bash hook) | `git commit` messages (including `-F` files and heredocs) and `gh pr create/edit/comment/review` bodies | refuses the command |

Both guards fail OPEN when the engine cannot be loaded, and say on stderr that the text went UNEXAMINED. A blocked edit over a missing module would be worse than the thing being guarded, and a silent pass would be worse than both.

## Getting a line past it

A line that genuinely has to carry a violation, because it IS the example or because it quotes somebody, takes an explicit marker on that line: `<!-- style-ok -->` in markdown, `# style-ok` or `// style-ok` in code. The same shape as `<!-- slop-ok -->` next door in the content-quality gate.

Several things are already not prose and need no marker: fenced code, inline code spans, URLs and link targets, blockquotes (somebody else's words), headings, tables, `gen-docs` generated regions, indented blocks in markdown AND inside Python comments and docstrings, and any line beginning `bad:` / `wrong:` / `avoid:`, which exists to hold the violation.

The marker is for a line that is an example. Reaching for it to get past the gate is the thing it is not for.

## A draft that is over the line, in one round trip

The guard reads the tool call's OWN new content, not how that content was produced.
A long, un-reflowed `Edit`/`Write` call is refused by R18 with the recipe printed inline; the fix is not to route the write through `git commit`/`cp`/a script to dodge the guard, since the guard has no bash twin on purpose and a route around it produces an unexamined write rather than a compliant one.

Reflow first, THEN call `Edit`/`Write` directly with the reflowed text -- no indirection needed:

```
.ci/scripts/quality/check_prose_style.py reflow --write <scratch-path>
.ci/scripts/quality/check_prose_style.py check <scratch-path>
```

Once `check` is clean, an `Edit`/`Write` carrying that exact text passes the guard on the first try, because the guard lints the payload's `content`/`new_string`, not the tool that produced it. This was verified directly: the same reflowed paragraph that a raw `Edit` call refused was accepted by `Edit` once reflowed, with no other change.
